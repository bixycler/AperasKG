# Aperas Skill — History <a name='id/BlockNode:00CEA5MHD8001' class='aperas-anchor aperas-id'></a>

## Current Status <a name='id/BlockNode:00CEA5MHD8002' class='aperas-anchor aperas-id'></a>

The restructure has landed and has been revised five times since. `skills/aperas/SKILL.md` (reached by symlink from `.agents/skills/` and `.claude/skills/`) is v2: four levels — Philosophy, Orientation, Discipline, Mechanics — read top-down, with a scope statement and a worked example at each of the first three levels, and only current, verified items in the file at all. v1.1 repaired the vertical thread between the levels, v1.2 grounded the recall machinery in the philosophy that makes it non-optional, v1.3 widened the scope from graph edits to the whole session while replacing the mechanical read-side gate with a remembered consent question, v1.4 re-keyed rules to outcomes rather than to the verb or event that produces them, and v2 retired the inline status vocabulary, raised reading the shadow to the same standing as writing to it, added the upward direction to traversal, and moved the document's own past into the graph. Open Issues is empty; what remains is [trigger accuracy against a held-out split](../planning/aperas-skill.md#id/BlockNode:00CEDFKN3000A), still unmeasured.

All eighteen original items survived, relevelled rather than rewritten — item 18's graph-substance principle promoted to Orientation where it explains the rest, items 1/2/11/12/17 and half of 14 gathered into Discipline around an explicit edit loop, and the syntax and command-level items collected into Mechanics. Item 14's other half (the Freeflow document shape) left the skill entirely for `design/documentation.md`, and item 8's tool gap became a pointer to its tracked issue instead of inline prose. Remaining from [Task Breakdown](../planning/aperas-skill.md#id/BlockNode:00CEA5M6S8005): step 5's example harvest is partially done — the contrast pair, the traversal transcript and the edit loop are in, the Mechanics command-plus-failure-text examples are not yet systematic.

## Milestones <a name='id/BlockNode:00CEA5MHD8004' class='aperas-anchor aperas-id'></a>

- The skill was factored out of `kg-doc-ingest` once a second workflow needed the same practices, and grew from there by accretion — one item per live incident, appended in the order things were learned.
- Its full text was dumped verbatim into this concern's discussion doc as [v0 SKILL.md (verbatim, 2026-09-12)](../discussion/aperas-skill.md#id/BlockNode:00CE95MVP8001), split so that every item is an individually addressable block, making the rewrite discussable by citation rather than by line number.
- The governing philosophy was restated in the graph itself for the first time — the ApeironNgn-era corpus had been operating on it without ever naming it, which is why the skill's most load-bearing statement had ended up last in a flat list. It is not new: `archive/Aperas-design.md` has carried it from the start, as the Apeiron/Aperas/Peras triad, the fluid-core-versus-crystallized-interface split, and deep read/deep write as the Multi-Agent Projection Pattern's defining capabilities. That founding document is itself written as an unbounded tree of nested list items with no headings at all — practising the Freeflow shape the skill only later stated as a rule.
- A gap between documented practice and normative design was found and closed in the same pass: the Freeflow-as-unbounded-tree rule existed only in the skill, never in [`design/documentation.md`'s own Scratchpad section](../design/documentation.md#id/BlockNode:00CE9FTDAR004), which still showed a heading-based example. Folded back into the design doc.

- The first tooling staging step was taken: <a name='id/BlockNode:00CEDP10P8001' class='aperas-anchor aperas-id'></a> `scripts/show_node.py` bundles the raw-node reader that had been hand-rewritten roughly eight times in a single session, covering the five uses that actually recurred — full record with `props`/`tombstonedAt`, exact stored text for round-tripping an edit, children with tombstones marked, full-text search standing in for the absent `aperas search`, and owning-artifact lookup. The skill's instruction to write "a small one-liner" is gone, replaced by a pointer. It is explicitly a staging area rather than a fix: the tracked gaps it stands in for ([`aperas show <ref>`](../issues/treeview.md#id/BlockNode:00CE1GW638006), and [`unfold`'s missing tombstone marker](../issues/treeview.md#id/BlockNode:00CE8T6W7G001)) remain open.

- **The rewrite's own eval set was run for the first time, and it caught a real bug**: <a name='id/BlockNode:00CEFF85V8001' class='aperas-anchor aperas-id'></a> four prompts ([discussion](../discussion/aperas-skill.md#id/BlockNode:00CEDVTB68001)), each graded by direct graph inspection — never the acting subagent's own report — across two arms, v0 (extracted from git history) and the current v1 skill. Three of four prompts passed cleanly on both arms. The fourth, `complete-list-push`, exposed [a real, previously-undocumented reconcile bug](../discussion/aperas-skill.md#id/BlockNode:00CEF7TB2G000): `aperas update <heading-id>` matches piped list content against the stored children array by raw position, tombstones included, not by content/key as both skill versions claim. v0's own prescribed technique (push the complete reconstructed list to the parent heading) triggers it; v1's updated Mechanics guidance (prefer `insert --after` for unordered lists) happens to avoid it. Confirms the restructure is measurably safer in at least one concrete case, not merely better organized.

- **The first gap found in v1 itself was closed — a missing corollary, not a missing item**: <a name='id/BlockNode:00CF2NPBKR001' class='aperas-anchor aperas-id'></a> filing a new concern's Open Issues from findings already recorded across four discussion docs left every origin unlinked, because the skill stated Citation direction's constraint (no down-citations) without the obligation that follows from it — that promotion adds the link at the origin, pointing up. Three separate passages each almost covered it and none did, and the one that names the mechanism, Crystallization's topology axis, existed only in [`design/aperas-skill.md`](../design/aperas-skill.md#id/BlockNode:00CEA5Y5JG00J) and had never been carried into the operational file. Closed by a new `### Promotion links at the origin` section under Discipline, sited directly after Citation direction so the constraint and its corollary are read together. Notable as the first item to enter v1 by the skill's own stated path rather than by restructuring what was already there: incident, captured raw in Freeflow, confirmed by reading both documents, promoted to the level that explains it.

- **v1 was snapshotted into the graph, by copy rather than by projection**: <a name='id/BlockNode:00CF4763DR001' class='aperas-anchor aperas-id'></a> [v1 SKILL.md (verbatim, 2026-09-13)](../discussion/aperas-skill.md#id/BlockNode:00CF46W4Q8001) now sits beside v0's dump, split so every item is individually addressable. Copy, not a live projection, was the deliberate choice: a projection holds only the current version, so what a restructure *drops* would survive nowhere but git archaeology — and that loss is not hypothetical, since v0's presence in the graph is the only reason item 18's third trigger was found missing from v1. Successive snapshots make the skill's evolution the object of study rather than just its latest state. This milestone's link points *down* the gradient, which the citation-direction rule permits for a pointer that is the block's whole referent rather than one of many possible mentions.

- **v1.1 — the vertical thread between levels was repaired, and a structural audit found one of the gaps itself**: <a name='id/BlockNode:00CF4RAGDR001' class='aperas-anchor aperas-id'></a> crystallization is now stated at Philosophy and Orientation rather than existing only as a Discipline rule grounded off-level in the design doc, and dense linking is realized below Orientation rather than only asserted there — including the restoration of a concrete trigger v1 had silently dropped from v0's item 18. Seven additions, recorded verbatim as [a delta on the v1 snapshot](../discussion/aperas-skill.md#id/BlockNode:00CF4QNWZR001) rather than as a fresh snapshot, since a snapshot is taken at a major version and minor versions thread onto it. One addition was not found by reading at all: an audit of [the vertical thread](../discussion/aperas-skill.md#id/BlockNode:00CF4D9XT0001) queried every principle for realizers below it and returned zero for "keep an active view," a gap nobody had named, now closed by its own Discipline section. The same audit missed the crystallization gap from the backward direction and caught it from the forward one — the realizer's grounding link pointed outside the level structure — which is recorded as the sharper lesson: the query inherited the tooling's asymmetry, since `backlinks` is a verb and forward traversal is not.

- **v1.2 — the recall machinery got the principle that makes it non-optional, and the tooling prompted its own recording for the first time**: <a name='id/BlockNode:00CF5ZS9QR001' class='aperas-anchor aperas-id'></a> snapshot, delta, drift check and the `Supersedes` marker had all been built without anything above them explaining why they are required rather than convenient — a forward audit of [the thread](../discussion/aperas-skill.md#id/BlockNode:00CF4D9XT0001) returned zero grounding for each. Closed by a Philosophy statement that *nobody working this graph will remember, so the graph must be what notices*, with its companion explaining why a look-it-up rule is only half a discipline: doing the work and recording it are separate acts, and only a comparison against the world outside the graph can see the second one missing. Recorded as [the v1.2 delta](../discussion/aperas-skill.md#id/BlockNode:00CF5ZE1S0001). Notable for how the recording happened: `scripts/skill_drift.py` reported all three additions the moment they were written, so for the first time the record was prompted by the tooling rather than by a reader noticing an omission — which is the principle demonstrating itself within minutes of being stated.

- **v1.3 — the trigger gap was closed, and closing it revealed that invocation is not governance**: <a name='id/BlockNode:00CFATN6S8001' class='aperas-anchor aperas-id'></a> two earlier sessions had investigated `reconcile.ts`/`node.ts` by plain file reads with no traversal and no skill load at all — the frontmatter description named only graph-editing triggers, so a task framed as source-code work never matched it. A mechanical `PreToolUse` gate built to close that broke three independent ways under live hook tracing and was retired for being personal, machine-specific and invisible to anyone who had not set it up; v1.3 traded it for a one-time consent question the skill asks and remembers, and widened its scope from graph edits to the whole session. Recorded as [the v1.3 delta](../discussion/aperas-skill.md#id/BlockNode:00CF80MKFG001). The description that shipped still did not fire, and what fixed it was pure ordering — the identity sentence demoted beneath an unconditional imperative keyed on session position, amended onto the same commit and [recorded as its own delta entry](../discussion/aperas-skill.md#id/BlockNode:00CF9SRRFG001) once `skill_drift.py` reported it written-but-unrecorded. Notable for what it exposed rather than what it fixed: with the skill loading on turn one, a session still read an entire task out of the projections and edited code before its first `aperas` call, which is what [Batch 2 of Planning](../planning/aperas-skill.md#id/BlockNode:00CFAMC7XR000) now exists to answer.

- **v1.4 — rules re-keyed to outcomes, after the same defect produced three separate failures in one session**: <a name='id/BlockNode:00CGA5Y2P8001' class='aperas-anchor aperas-id'></a> with v1.3's description finally firing on turn one, a session loaded the skill, consented to it, and still read an entire task out of the projections before editing code — so the trigger was never the last problem. Three rules failed in the same shape, each keyed to the operation that first surfaced it rather than to the result it was guarding: orientation keyed to "editing the graph" never fired for a read, identity preservation keyed to `remove` never fired for a parent-heading `update` that tombstoned seventeen nodes, and the provenance obligation keyed to "promotion" never fired for an edit adding evidence to an entry already in place. Recorded as [the v1.4 delta](../discussion/aperas-skill.md#id/BlockNode:00CGA4ZN88001), and nine issues moved to Resolved with their mechanisms named. The load-bearing addition is a Philosophy statement the founding design always implied and the skill had never carried: Aperas is an evidence-based documentation system, a claim and its provenance are one object — `archive/Aperas-design.md` defines deep read as provenance projection, while `SKILL.md` had reduced backward traversal to context and blast radius and used the word "evidence" exactly once, about something else. Notable for how it was caught: not by any check in the file, all of which passed, but by a reader running `aperas backlinks` on a claim and getting nothing back.

- **v2 — the status vocabulary retired, the read side raised to parity, and the document's own past moved into the graph**: <a name='id/BlockNode:00CGF71QX8001' class='aperas-anchor aperas-id'></a> a user read of v1.4 found four defects sharing one cause. The inline `[current]`/`[superseded]`/`[unverified]` markers had been obsoleted by this concern's own snapshot-and-delta thread, which records the same distinction more precisely and without touching the rules; across four versions nothing was ever marked `[unverified]`, so 36 items each paid a tag to flag an exception that never arrived. Philosophy's shadow rule named only the write side — a projection is never where a change is made — leaving reading and searching the shadow to a corrective paragraph four items below it. Orientation's deep-read section named forward/downward and backward but not **upward**, the cheapest direction there is and the one that answers the pull toward opening a whole artifact for context: for a node at `discussion/a.md/h1/freeflow/a/aa/aaa`, unfolding `discussion/a.md/h1/freeflow/a` is usually already enough. And five items narrated the document's own past instead of stating the rule — a disclaimer about a section's former name, an explanation of which half used to be missing, a note on how a rule got generalized. The shared cause is the context skill the document itself teaches for reading, failing in its own writing: those phrases carry context in the plan they were argued in, and lose all of it in `SKILL.md`, where the only context is the block and the blocks above it. The repair in every case was to rewrite the original until it stands alone, never to leave it and append a correction. Provenance was deliberately kept apart from history and stays in the file, since an incident explains why a rule that is true now is true. Recorded as [v2 SKILL.md (verbatim, 2026-09-15)](../discussion/aperas-skill.md#id/BlockNode:00CGF613VR001) — a fresh snapshot rather than a delta, because rewriting 36 items would otherwise have left the drift check reporting the whole document as both added and dropped against the v1 baseline.
