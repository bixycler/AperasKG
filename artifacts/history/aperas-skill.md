The restructure has landed. `skills/aperas/SKILL.md` (reached by symlink from `.agents/skills/` and `.claude/skills/`) is now v1: four levels — Philosophy, Orientation, Discipline, Mechanics — read top-down, each item marked `[current]`, `[superseded]` or `[unverified]`, with a scope statement and a worked example at each of the first three levels.

All eighteen original items survived, relevelled rather than rewritten — item 18's graph-substance principle promoted to Orientation where it explains the rest, items 1/2/11/12/17 and half of 14 gathered into Discipline around an explicit edit loop, and the syntax and command-level items collected into Mechanics. Item 14's other half (the Freeflow document shape) left the skill entirely for `design/documentation.md`, and item 8's tool gap became a pointer to its tracked issue instead of inline prose. Remaining from [Task Breakdown](../planning/aperas-skill.md#id/BlockNode:00CEA5M6S8005): step 5's example harvest is partially done — the contrast pair, the traversal transcript and the edit loop are in, the Mechanics command-plus-failure-text examples are not yet systematic.

## Milestones <a name='id/BlockNode:00CEA5MHD8004' class='aperas-anchor aperas-id'></a>

- The skill was factored out of `kg-doc-ingest` once a second workflow needed the same practices, and grew from there by accretion — one item per live incident, appended in the order things were learned.
- Its full text was dumped verbatim into this concern's discussion doc, split so that every item is an individually addressable block, making the rewrite discussable by citation rather than by line number.
- The governing philosophy was restated in the graph itself for the first time — the ApeironNgn-era corpus had been operating on it without ever naming it, which is why the skill's most load-bearing statement had ended up last in a flat list. It is not new: `archive/Aperas-design.md` has carried it from the start, as the Apeiron/Aperas/Peras triad, the fluid-core-versus-crystallized-interface split, and deep read/deep write as the Multi-Agent Projection Pattern's defining capabilities. That founding document is itself written as an unbounded tree of nested list items with no headings at all — practising the Freeflow shape the skill only later stated as a rule.
- A gap between documented practice and normative design was found and closed in the same pass: the Freeflow-as-unbounded-tree rule existed only in the skill, never in `design/documentation.md`'s own Scratchpad section, which still showed a heading-based example. Folded back into the design doc.

- The first tooling staging step was taken: <a name='id/BlockNode:00CEDP10P8001' class='aperas-anchor aperas-id'></a> `scripts/show_node.py` bundles the raw-node reader that had been hand-rewritten roughly eight times in a single session, covering the five uses that actually recurred — full record with `props`/`tombstonedAt`, exact stored text for round-tripping an edit, children with tombstones marked, full-text search standing in for the absent `aperas search`, and owning-artifact lookup. The skill's instruction to write "a small one-liner" is gone, replaced by a pointer. It is explicitly a staging area rather than a fix: the tracked gaps it stands in for (`aperas show <ref>`, and `unfold`'s missing tombstone marker) remain open.

- **The rewrite's own eval set was run for the first time, and it caught a real bug**: four prompts ([discussion](../discussion/aperas-skill.md#id/BlockNode:00CEDVTB68001)), each graded by direct graph inspection — never the acting subagent's own report — across two arms, v0 (extracted from git history) and the current v1 skill. Three of four prompts passed cleanly on both arms. The fourth, `complete-list-push`, exposed [a real, previously-undocumented reconcile bug](../discussion/aperas-skill.md#id/BlockNode:00CEF7TB2G000): `aperas update <heading-id>` matches piped list content against the stored children array by raw position, tombstones included, not by content/key as both skill versions claim. v0's own prescribed technique (push the complete reconstructed list to the parent heading) triggers it; v1's updated Mechanics guidance (prefer `insert --after` for unordered lists) happens to avoid it. Confirms the restructure is measurably safer in at least one concrete case, not merely better organized.
