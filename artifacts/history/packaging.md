# Packaging — History <a name='id/BlockNode:00CDDVCKCG001' class='aperas-anchor aperas-id'></a>

## Current Status <a name='id/BlockNode:00CDDVCKCG002' class='aperas-anchor aperas-id'></a>

The full packaging effort is done, with no open gaps: the rename to `packaging.md`, the 3-way workspace split, the `aperas` dispatcher, `identity.json`/`aperas.config.json` configuration (including two independent path roots), a real build-to-`bin`, and the explicit-start service redesign are all shipped and verified — see [Configuration](../design/packaging.md#id/BlockNode:00CDHSJQE8001), [Workflow](../design/packaging.md#id/BlockNode:00CDY7PGG0001), and [Distribution](../design/packaging.md#id/BlockNode:00CDW3R42G001). `kg:show <ref>` — a raw single-node inspection command, once tracked here — turned out to be a TreeView/node-rendering gap rather than a packaging one, and moved to `AperasKG/artifacts/archive/Aperas-treeview-design.md`.

## Milestones <a name='id/BlockNode:00CDDVCKCG003' class='aperas-anchor aperas-id'></a>

- Workspace split: <a name='id/BlockNode:00CDH1CNN8002' class='aperas-anchor aperas-id'></a> `packages/core`/`cli`/`web` under `Aperas/monorepo/`, all three type-check clean, full `npm run verify` harness (18 checks) passes end-to-end from the new location.

- `aperas` dispatcher: <a name='id/BlockNode:00CDHAY1P8002' class='aperas-anchor aperas-id'></a> every `kgX.ts` exports its own `main()`, a static verb table in `packages/cli/src/aperas.ts` argv-dispatches to it, `npm run aperas -- <verb> <args>` verified identical to the matching `kg:<verb>` script for several read/write verbs, and the full `verify` harness still passes. Still not an installable global binary — that's [the runtime question](../discussion/packaging.md#id/BlockNode:00CDDVC33G009), deliberately untouched.

- `identity.json` + `aperas identity`, help-text rewrite: <a name='id/BlockNode:00CDY84BJ8002' class='aperas-anchor aperas-id'></a> machine-local `machineNumber` moved out of the env-var-only `APERAS_MACHINE_NUMBER` lookup into `$XDG_CONFIG_HOME/aperas/identity.json` (reader/writer plus `aperas identity show`/`set <n>`); every `kgX.ts`'s own `--help`/missing-arg usage line rewritten from `kg:X --` to `aperas <verb>`. Full `verify` suite still passes.

- Build-to-`bin`: <a name='id/BlockNode:00CDY85ZQG002' class='aperas-anchor aperas-id'></a> `packages/cli/build.mjs` (`esbuild`, `oxigraph` external) produces a self-contained `packages/cli/dist/` — bundle plus a generated minimal `package.json` with a real `bin` entry. Verified running standalone via plain `node`, no `tsx`, against the real graph. Resolves [the runtime question](../discussion/packaging.md#id/BlockNode:00CDDVC33G009).

- Explicit-start service redesign: <a name='id/BlockNode:00CDY87KN8001' class='aperas-anchor aperas-id'></a> `ensureServiceRunning()` no longer auto-spawns — `aperas service start`/`stop`/`restart` (`kgService.ts`) are the only commands touching the service process directly, `start`/`restart` the only place `process.cwd()` is read to resolve+bind a graph. Lock/socket moved to a fixed `$XDG_RUNTIME_DIR`-based location. Verified live in dev and built-bundle modes, full `verify` suite clean. Resolves [the graph-location question](../discussion/packaging.md#id/BlockNode:00CDDVC33G00A).

- `aperas.config.json`: <a name='id/BlockNode:00CDY8A3KG002' class='aperas-anchor aperas-id'></a> created at `AperasKG/aperas.config.json` (`{ "graph": "." }`), marking `AperasKG` as its own graph root; the design doc's [Configuration](../design/packaging.md#id/BlockNode:00CDHSJQE8001) and [Workflow](../design/packaging.md#id/BlockNode:00CDY7PGG0001) sections written up to match. Verified live: stopped the service, cold-started the built bundle from a cwd deep inside `AperasKG/artifacts/`, confirmed it discovered the config by walking up (not the dev fallback) and bound to the real path; an ordinary command run from an unrelated cwd (`monorepo/`) still connected correctly through the fixed-location socket.

- Two-path graph config, gap closed: <a name='id/BlockNode:00CDZQWM0G002' class='aperas-anchor aperas-id'></a> `aperas.config.json`'s `graph` field now takes either a plain path (shorthand) or `{ "apeiron": "...", "artifacts": "..." }` (independent roots). `getArtifactsDir()`'s remaining callers (`runTrack`/`runIngest`/`runProject`, the shared `apeironNgn/artifacts.ts`/`folders.ts`/`node.ts` helpers) now resolve correctly via an env-var-first default (`APERAS_ARTIFACTS_ROOT`, set alongside `APERAS_APEIRON_ROOT` at `aperas service start`/`restart` time), with zero signature changes anywhere. Verified live: cold-started the built bundle from a cwd deep inside `AperasKG/`, confirmed the lock recorded the real discovered paths for both roots (not the coincidental fallback), then ran `aperas project` from an unrelated cwd and confirmed it read/wrote against the correctly-bound `artifacts/`. Closes the one gap flagged in the previous milestone.
