# Linking — History <a name='id/BlockNode:00CDBZ7698001' class='aperas-anchor aperas-id'></a>

## Current Status <a name='id/BlockNode:00CDBZ7698002' class='aperas-anchor aperas-id'></a>

Two internal-reference conventions coexist: node-ID addressing (currently implemented as `[[code]]`-wrapped `Kind:snowflake`, verified in `astParser.ts`/`resolve.ts`; the target design drops the `[[...]]` wrapper in favor of `aperas://id/<ID>` or `#id/<ID>`, see [Architecture](../design/linking.md#id/BlockNode:00CDBYV4T8002) and [Topology](../design/linking.md#id/BlockNode:00CDBYV4T8007)) and slug-anchor addressing (`#fragment` matched against an injected `<a name="...">`, prototyped but not yet adopted corpus-wide — see [Open Issues](../issues/linking.md#id/BlockNode:00CDBYV5A8002)).

## Milestones <a name='id/BlockNode:00CDBZ7698003' class='aperas-anchor aperas-id'></a>

- **TerminusDB era**: <a name='id/BlockNode:00CDBZ7698005' class='aperas-anchor aperas-id'></a> `[title]([[code]])` convention designed and settled — `code` a snowflake/node-id, bare `[[...]]` reserved for a never-built UI auto-expansion, never for hand-typing or parsing on its own (`Aperas-deep-path-resolution-design.md`, `Aperas-markdown-fractal-mapping-design.md` §4, archived under `archive/tdb-era/` — backend superseded, convention carried forward unchanged).
- **ApeironNgn era**: <a name='id/BlockNode:00CDBZ7698006' class='aperas-anchor aperas-id'></a> same convention re-implemented and live-verified (`astParser.ts`'s `collectLinkCodes`/`WIKILINK_PREDICATE`, `resolve.ts`'s deep-path grammar) — used extensively in `Aperas-apeironngn-design.md`'s own self-references, in the verbose full-heading-text form, e.g.:
  
  ```markdown
  [Step 7](<[[/Aperas-apeironngn-design.md/# ApeironNgn: Embedded Substrate Design/4. Rollout sequence/Step 7: `ArtifactNode extends BlockNode`, the root block retired outright, `text` a copied abstract for both — implemented, verified]]>)
  ```
- **2026-09-08: slug-anchor convention prototyped**: <a name='id/BlockNode:00CDBZ7698008' class='aperas-anchor aperas-id'></a> slug-anchor authoring convention (`slugify()`-derived, `/`-joined segment paths as explicit `<a name>` anchors, referenced via plain `#fragment` links) prototyped and validated live in `test-slugifed-path.md`, as a more compact, pre-ingestion-friendly alternative to hand-typing the full-heading-text `[[deep-path]]` form, e.g.:
  
  ```markdown
  <a name='---sub-1/----sub-1-1'></a>
  ### Sub 1.1
    
  [Sub 1.1](#---sub-1/----sub-1-1)
  ```
  
  Recorded as its own design concern (`design/linking.md`, see [Landing on standard links + injected anchors](../discussion/linking.md#id/BlockNode:00CDBZ76TG002)) rather than folded into `documentation`.
- **2026-09-09: `kg:title` removal**: <a name='id/BlockNode:00CDBZ769800B' class='aperas-anchor aperas-id'></a> Slice 1's lead-in-term extraction (`astParser.ts`'s `extractLeadInTitle`) made a pre-existing title mechanism, `kg:title` (an out-of-band, graph-only title override, decoupled from a block's own text), impractical by comparison: `reconcile.ts`'s `carryForwardFields` only ever carried a title forward when the block's *text* matched exactly, so a manually-set title was silently lost on the very next edit to that text — a real, if long-standing, fragility surfaced only once a real alternative (a title derived deterministically from the text itself) existed to compare it against. Removed `kg:title` outright (`kgTitle.ts`, its two service ops, `carryForwardFields`'s title line) in favor of the explicit lead-in term as the one and only title mechanism, for every block type. `kg:update` (`kgUpdate.ts`) gained a compensating capability: a heading target's title, being the one block type actually projected back to disk, is now itself editable by piping a leading heading line whose `#` depth matches the target's own (rejected otherwise) — mirroring exactly how a real document's heading is parsed (anchor-stripped, tree-anchor prop carried through). Fixed one adjacent, pre-existing bug found while wiring that path: `kg:update`'s default (non `--text-only`) reconcile branch never included `props` in its own reconcile shape at all, so any heading update through it — title-changing or not — silently dropped that heading's tree-anchor prop; it now defaults to preserving the target's existing props unless the new heading-rename path explicitly supplies a replacement.
- **2026-09-09: cross-artifact link staleness**: <a name='id/BlockNode:00CDBZ769800C' class='aperas-anchor aperas-id'></a> Live editing of this very concern's own docs surfaced a second gap: `discussion/linking.md` linked to a heading just added to `design/linking.md` in the same pass, and that link resolved against whichever of the two artifacts' graph states happened to be current at ingestion time — an artifact whose own text never changes has nothing to trigger a fresh link-resolution pass, so a dangling reference stayed dangling even after its target came into existence, fixable only by manually corrupting `ingestedHash` to force a re-ingest. `resolveBlockLinks` (`apeironNgn/artifacts.ts`) now stashes every code a block fails to resolve — including a `#fragment` form that's merely routine-unresolved, not warned as dangling — as a `danglingRef` prop on its own referring `ArtifactNode`, rewritten wholesale on every ingestion. `kg:ingest` (`kgIngest.ts`'s `runIngest`) gained a closing sweep, `retryDanglingRefs`: after the requested artifacts and folder tree are settled, every stashed code across every live artifact is retried against the current graph, and any artifact with at least one now-resolvable code is force-reingested via a new `ingestFromDisk`/`ingestArtifact` parameter, `bypassUnchangedCheck` — added deliberately separate from just clearing `ingestedHash`, since that field is also how `ingestFromDisk` decides whether to reconcile against existing content or fresh-mint every block as brand new (see [Discussion](../discussion/linking.md#id/BlockNode:00CDBZ76TR008)).
- **2026-09-10: lead-in colon end-of-run fix**: <a name='id/BlockNode:00CDBZ769G000' class='aperas-anchor aperas-id'></a> Live re-ingestion of this concern's own Slice 2 draft (`planning/linking.md`) surfaced a bug in `findLeadInColonOffset`'s (`astParser.ts`) space-after-colon check: a lead-in colon that's the very last character of its own mdast text node (e.g. `- **Heading**:` immediately followed only by nested list children, no inline "rest" on the same line) always fell through as if genuinely ambiguous, because the check read the next character from that text node's own truncated `.value` rather than the real document — there was nothing left to find, not because anything suspicious followed. Fixed by treating "nothing left in this text run" the same as "a space follows"; the earlier guards (inline-code exclusion, bold/italic exclusion) run first and are unaffected. See [Design](../design/linking.md#id/BlockNode:00CDBYV4TG000) and [Discussion](../discussion/linking.md#id/BlockNode:00CDBZ76TR00E).
- **2026-09-10: Slice 2 landed**: <a name='id/BlockNode:00CDBZ769G001' class='aperas-anchor aperas-id'></a> completing the toolset for working directly on Apeiron, corpus-wide rollout left as its own separate topic. `apeironNgn/node.ts`'s `rejectSlugPathCollisions` now rejects a document at ingestion time if any block's full slug-path — or an embedded anchor name still on it — is already claimed by a different block, live or within the same fresh parse; a writer-facing hard reject only, no lifecycle tracking (see [Design](../design/linking.md#id/BlockNode:00CDBYV4TG006)). The cleanup pass turned out to need no new removal API at all: an `aperas-tree` anchor is derived fresh from source text on every ingestion, so deleting the tag from the file and re-ingesting is the whole mechanism — confirmed live once the actual safety check was corrected to a full-text corpus search rather than `kg:backlinks` (which only sees already-tracked referrers). Slice 1's own scratch-ingest verification, left pending since it landed, is folded into `verify.ts` as steps 13-15 alongside Slice 2's own new coverage. See [Discussion](../discussion/linking.md#id/BlockNode:00CDBZ76TR00C) for a real id-format bug this surfaced while landing.
