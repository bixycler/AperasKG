# Webapp — Issues <a name='id/BlockNode:00CJ6V6370001' class='aperas-anchor aperas-id'></a>

## Open Issues <a name='id/BlockNode:00CJ6V6370002' class='aperas-anchor aperas-id'></a>

- **Whether the tree renderer surfaces every position of a multi-position `Link`**: <a name='id/BlockNode:00CJ6V6370003' class='aperas-anchor aperas-id'></a> the graph carries one `position` prop per occurrence, and the endnote's `^ a b` back-references need one anchor per position. Whether `renderTreeWithView` emits such a link once or once per position is unchecked. A renderer question, not a model one, and it must be answered before the endnote can claim to be faithful.
- **How a deep write is handed to the Agent**: <a name='id/BlockNode:00CJ6V6370004' class='aperas-anchor aperas-id'></a> composing an intent and handing it off — a copied prompt, an MCP endpoint, an embedded chat pane — is unexamined, and deliberately out of Phase 1. It is deferred rather than rejected, and nothing in Phase 1 should foreclose any of the three.
- **Ctrl-click on the fold arrow folds instead of zooming, and swallows the event**: <a name='id/BlockNode:00CMWN0XDG001' class='aperas-anchor aperas-id'></a> `FolderDiv.tsx`'s `Gutter` is the only click site in that file which never checks `ctrlKey`/`metaKey` — the node line, both link-row modes and the backlinks popover all do — and because its handler calls `e.stopPropagation()`, the row's own zoom handler never sees the event either. So ctrl-clicking the arrow silently folds and the zoom is simply lost, which reads as "zoom doesn't work" to anyone who aims at the control rather than at the title; found by a user hitting it on first use of the app. This contradicts the settled design rather than filling a gap in it: [zoom in is a new apex](../discussion/webapp.md#id/BlockNode:00CJ2V1YAR009) specifies the gesture on the arrow itself ("ctrl-clicking a fold arrow re-renders with that node as apex"), so the implementation has never matched what was agreed. Fixing it is also a precondition for [the redesigned gesture set](../discussion/webapp.md#id/BlockNode:00CMWMP6X8001), where ctrl must work uniformly on the row, the arrow and the stem.
- **Every block-structured node renders as one flattened run of literal markup in the UI — tables, fenced code and ASCII diagrams are all unreadable**: <a name='id/BlockNode:00CMX4NCW8001' class='aperas-anchor aperas-id'></a> a `[table]` shows as `| a | b | | --- | --- | | 1 | 2 |` in flowing prose, and a `[code]` block shows its own ``` fences as text with every line rewrapped, destroying column alignment. Three independent causes, confirmed live rather than inferred. **(1) The structure is already gone server-side**: every `RenderNodeItem.abstract` is a one-line preview, and `truncateForPreview` (`astParser.ts`) collapses *all* whitespace — `text.replace(/\s+/g, ' ')` — so newlines die with the spaces; `/api/tree` returns the table's abstract containing no `\n` at all, which is why `.fd-abstract`'s `white-space: pre-wrap` preserves nothing. **(2) There is no block-level renderer**: `Inline.tsx` is deliberately inline-only (`**bold**`, `` `code` ``, `*italic*`, `[text](href)`), so even with newlines restored it would emit literal pipes and fences. **(3) The row's title is a raw snowflake**: `table`/`code` have no extractable lead-in term, so `astParser.ts`'s fallback title (the block's own id) is what the UI prints as the node's name. Presentation-only — the stored text and the projected `.md` are both correct, and `aperas tree`/`unfold` previews collapse identically, so this is not webapp-specific and no data is at risk. It matters now because the [fold/unfold redesign](../discussion/webapp.md#id/BlockNode:00CMWMP6X8001) deliberately carries its state table, gesture matrix and transition diagram as `[table]`/`[code]` blocks: the document most worth reading in the UI is the one the UI renders worst.
- **A checkbox's checked state never reaches any renderer, console or webapp**: <a name='id/BlockNode:00CMXJQX1R001' class='aperas-anchor aperas-id'></a> `astParser.ts:705-706` stores it correctly as a `checked` prop and strips the literal `[ ]`/`[x]` from `.text`/`.title` so it isn't duplicated as text, and `project.ts` re-emits it correctly on the way back to `.md` — but `RenderNodeItem` (`node.ts`) has no `checked` field at all, and `buildNodeItem` never reads the prop, so every reader downstream of the render tree sees a plain listItem with no marker anywhere: not `aperas tree`, not `aperas unfold`'s own preview, not the webapp. The round trip through disk is correct; only the *reading* path drops it, the mirror image of [the table/code gap above](#id/BlockNode:00CMX4NCW8001) — that one loses structure already present in the abstract string, this one never puts the value in the string's carrier (`RenderNodeItem`) to begin with. Fix is additive: a `checked?: boolean` field, read via `getProp` the same way `holder`/`starred` already are, surfaced as a real glyph rather than folded into title text (a `- [ ]`/`- [x]` prefix would collide with `.fd-title`'s own bold styling the way it collides with nothing today).

## Resolved <a name='id/BlockNode:00CJ6V637000F' class='aperas-anchor aperas-id'></a>

- **Resolved: fold/unfold felt like seconds per click**: <a name='id/BlockNode:00CJ840278001' class='aperas-anchor aperas-id'></a> the dev API bridge shelled out a fresh `tsx packages/cli/src/aperas.ts <verb>` subprocess per request — a full Node-plus-TypeScript-transpile startup on every click, on top of the service round trip that was already fast. Fixed by moving the bridge into its own long-lived process (`packages/web/devApiServer.ts`, spawned once by `vite.config.ts`) that talks to the ApeironNgn service directly over its unix socket, the same `request`/`ensureServiceRunning` every `kg*.ts` entrypoint already uses. A second, independent cause compounded it: `flush: true` on the `unfold`/`fold` service calls forced a full ~1600-node content-mirror dehydrate to disk on every click, because `service.ts`'s own 'unfold'/'fold' cases set the content-`dirty` flag unconditionally (a defensive catch-all for the rare case where resolving a bare `--view` mints a first-use `Profile`). `TreeView`'s own fold state is genuinely ephemeral UI state with its own independently-tunable flush cadence (design/webapp.md's Persistence) — it needs no per-click disk write at all. Fixed by dropping `flush` from the dev bridge's `unfold`/`fold` calls. Timed before/after: ~450ms per click down to ~10ms once both fixes landed — nothing here was ever a SolidJS cost.
- **Resolved: Slice 1 — `buildRenderTree` extracted into `@aperas/core`**: <a name='id/BlockNode:00CJ8FJNKR001' class='aperas-anchor aperas-id'></a> verified against the existing suite plus a live before/after byte-diff on a real corpus view, and again exhaustively against the UI — every one of 36 rendered rows' fold counts matched `aperas tree --view`'s own `[+N]` tags in sequence, extracted straight from the live DOM.
- **Resolved: Slice 5 — `FolderDiv` ported to Solid**: <a name='id/BlockNode:00CJ8FJNKR002' class='aperas-anchor aperas-id'></a> fold/unfold writes to the real `TreeView.unfolds` set and refetches; verified exhaustively against the CLI (see Slice 1's own entry, same check covers both).
- **Resolved: Slice 7 — zoom**: <a name='id/BlockNode:00CJ8FJNKR003' class='aperas-anchor aperas-id'></a> ctrl-click and breadcrumbs both change apex via the same code path a deep-linked URL uses; confirmed live via the browser and via URL query-param navigation.
- **Resolved: bare-path corpus links (no `#id/...` fragment) rendered inert in the UI**: <a name='id/BlockNode:00CJAW3BS0001' class='aperas-anchor aperas-id'></a> `design/linking.md`'s Context section links `**Discussion**`/`**Planning**` by plain relative path with no fragment at all — a form the graph's own resolver never even attempted to resolve until the same-day core fix (see [History](../history/linking.md#id/BlockNode:00CJAVGNJG001)). Resolving it in the graph wasn't enough on its own: `Inline.tsx` has no server round trip of its own to learn a link's target, so it still needs a `#id/<Kind>:<id>` fragment sitting in the href text itself. Fixed with `bakeResolvedLinkIds` (`apeironNgn/node.ts`), which bakes each already-resolved bare-path link's target into its href for the render tree only — the stored text and every projected file stay untouched. Verified live in a real browser: clicking both links now navigates to their target `ArtifactNode`, breadcrumbs and content updating correctly.
- **Resolved: the webapp's 1s poll remounted the entire tree**: <a name='id/BlockNode:00CNRB3A90001' class='aperas-anchor aperas-id'></a> `<For>` reconciles by object reference, and a plain `createResource` handed it a fresh object graph on every poll — so it tore down and remounted every row each second, dropping any open inline editor mid-edit. Fixed with `reconcile(data, {key: 'id'})` (`solid-js/store`), merging each poll's response into a persistent store by node id. Unblocked by renaming `RenderLinkItem.linkId` to `id` in `core` — an unmotivated naming split with no functional reason, found while auditing for a uniform reconcile key. Verified live in a browser: 45 tagged DOM nodes and a mid-edit, unsaved textarea both survived 4 poll ticks with no remount. Full investigation: [Freeflow](../discussion/webapp.md#id/BlockNode:00CNR2E3D0001).
