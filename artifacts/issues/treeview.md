- **`List` isn't consumed by a preceding `Heading` the way a single paragraph already is**: <a name='id/BlockNode:00CE1GW638008' class='aperas-anchor aperas-id'></a> resolved by [list-consumption](../design/list-consumption.md#id/BlockNode:00CE32GQM8001) — a heading whose only content is a list (no leading paragraph to consume) now dissolves the list's items as the heading's own flat children (case 3 of the unified law) instead of leaving them wrapped in a separate `list`-typed node. Not literally merged into `.text` the way a lone paragraph is (a list can't collapse into a scalar string), but no longer floats as a separate, opaque child block either — see [History](../history/list-consumption.md#id/BlockNode:00CE32GW3G002). - **GFM task-list items round-trip broken**: <a name='id/BlockNode:00CE1GW638007' class='aperas-anchor aperas-id'></a> originally found here: [archive-migration discussion](../discussion/archive-migration.md#id/BlockNode:00CE0HD0HG007) — `- [ ] text` reportedly stored the literal `[ ] ` marker inside the block's own `.text` alongside a separate `checked: false` prop, so `aperas project` would re-emit `- [ ] ` on top of the leftover `[ ] `, doubling to `- [ ] [ ] text`. Re-tested live during the list-consumption migration (both a direct `parseMarkdownTree`/`serializeBlock` round trip and a real `aperas insert` against the live corpus): does not reproduce, renders correctly. `git log` shows the checkbox-handling code in `astParser.ts` has never changed since it was first written. No corroborating evidence anywhere in the graph that this was ever actually observed broken in a real projected artifact — awaiting a decision on whether to close as not-reproducible or keep open pending further investigation. See [list-consumption discussion](../discussion/list-consumption.md#id/BlockNode:00CE8J339R001) for the re-test note. **Correction: it does reproduce, narrower than either re-test tried.** Confirmed live on this session's own discussion plan checkboxes, then isolated and traced to the exact upstream line — full account in [discussion/treeview.md](../discussion/treeview.md#id/BlockNode:00CGJHDK68001). The real trigger is narrower than "bold" and broader than either re-test tried: `mdast-util-gfm-task-list-item`'s `exitParagraphWithTaskListItem` only trims the checkbox's mandatory leftover space, and re-bases the paragraph's own position past it, when the paragraph's first inline child is a `text` node — `- [x] Plain: rest.` qualifies, `- [x] **Bold**:`/`*Italic*:`/`` `code`: ``/`[link](url):` do not, since CommonMark's inline tokenizer never materializes a lone leading space with nothing before an inline span as its own text node. `astParser.ts` has no checkbox-marker-stripping logic of its own — it only reads `node.checked` into a prop — so it faithfully trusts the un-rebased position for `rawSlice`, including the leftover marker as literal text. Both earlier re-tests happened to use plain-text task items, which is exactly why neither one reproduced it. **Resolved**: the real fix lives upstream (`mdast-util-gfm-task-list-item`), out of reach here, so `astParser.ts` compensates defensively — a listItem already known to be a checkbox (`node.checked` boolean) has a leading `/^\[[ xX]\]\s*/` stripped from both its extracted `text` and `title` after the fact, regardless of what leaked or why. Verified live end-to-end: a bold-lead checkbox item pushed through the real service now stores clean text with `checked` set correctly, and projects to a single, correct `- [x]` marker — confirmed by re-checking this session's own six plan checkboxes, which had actually rendered doubled (`[ ] [x]`) before this fix and render correctly now.

- **Stale `TreeView.unfolds` references have no general cleanup**: <a name='id/BlockNode:00CE1GW638004' class='aperas-anchor aperas-id'></a> `TreeView.unfold(ref)` appended with no existence check, and the only cleanup — a reactive strip-on-hard-delete — only fired at the exact moment a specific id was hard-deleted; nothing revisited an *existing* `unfolds` entry against what's currently live. Confirmed live: `.state/TreeView.jsonld`'s `default` view had named 10 `BlockNode` ids with no corresponding document at all, after unrelated reconciliation churn elsewhere reassigned/removed the blocks those ids used to name. See [Settled](../discussion/treeview.md#id/BlockNode:00CE1FFSR8006) for the chosen fix direction. **Resolved**: `TreeView.unfold(ref)` now refuses (silent no-op) a ref with zero quads at write time, and a new `pruneStaleUnfolds` sweep runs at the same explicit-sweep points as `pruneUnreachableTombstones` to catch a ref going stale later. The corpus's own `default` view was already clean of stale ids by the time the sweep landed (0 pruned on a real run) — see [Settled](../discussion/treeview.md#id/BlockNode:00CE1FFSR8006) for the mechanism and its `verify.ts` coverage.
- **A bare `aperas unfold <ref>` (no `--view` flag at all) mutates the `"default"` view instead of peeking**: <a name='id/BlockNode:00CE1GW638005' class='aperas-anchor aperas-id'></a> should be read-only — resolve and print a preview, touching no `TreeView` state — matching `aperas tree`'s own no-view default. It fell into the same bootstrap-and-mutate path that `aperas unfold <ref> --view` (flag present, no name) is supposed to trigger. `aperas fold`'s own no-`--view` case isn't resolved by this — folding presupposes some view's state to collapse, so a peek-equivalent doesn't obviously apply. **Resolved**: `kgUnfold.ts` now distinguishes the `--view` flag's outright absence (peek — `runUnfold` given `view: null`, no `resolveTreeView`/`ensureDefaultView` call at all) from the flag present with no name following it (unchanged bootstrap-and-mutate default-view behavior). Verified live: a bare `aperas unfold` on an already-unfolded ref left the default view's `unfolds` count unchanged (43 -> 43), while `--view default` on a fresh ref still grew it (43 -> 44).
- **No raw single-node inspection command**: <a name='id/BlockNode:00CE1GW638006' class='aperas-anchor aperas-id'></a> `aperas tree`/`aperas backlinks --text` only ever show a rendered preview (title + truncated, anchor-stripped abstract) — right for browsing, not for verifying a stored field is exactly what's about to be pushed back via `aperas update`/`aperas insert`, or for reading a field no command shows at all (`props`, `tombstonedAt`). `aperas project --dry-run` reconstructs real markdown but only at the whole-artifact level. Before this, the only way to see a node's exact stored state was a direct `BlockNode.jsonld`/`ArtifactNode.jsonld` read outside the CLI entirely. Originally tracked under packaging, relocated here since it's a node-inspection gap, not a packaging one — the same gap the [`aperas` skill's own item 8](../history/aperas-skill.md#id/BlockNode:00CEDP10P8001) independently names — that gap's skill-script stage; `scripts/show_node.py` staged the gap, `aperas show <ref>` below was the still-open toolset-update stage of the same lifecycle. **Resolved**: `aperas show <ref>` (`kgShow.ts`) resolves the normal deep-path way, then prints the node's exact stored fields via `dehydrate.ts`'s own `serializeDoc` — the identical per-kind shape walk that writes the on-disk mirror, reused rather than re-implemented, so "what `show` prints" can't drift from "what's actually on disk." `--text` prints only the raw `text` field, undecorated, meant to be redirected to a file and piped back into `kg:update` for a byte-identical round-trip.

- **`aperas unfold` doesn't mark tombstoned children; both `unfold` and `tree` should hide them by default**: <a name='id/BlockNode:00CE8T6W7G001' class='aperas-anchor aperas-id'></a> `aperas tree --view <name>` appends a `(tombstoned)` suffix to a tombstoned node's line; `aperas unfold` showed the identical node with no marker at all, indistinguishable from a live sibling — confirmed live, see [Discussion](../discussion/treeview.md#id/BlockNode:00CE8T49MR001). Proposed direction: don't just bring `unfold` in line with `tree`'s tag — suppress tombstoned nodes from both commands' default output, and add a `--tombstoned` flag to opt into seeing them. **Resolved exactly as proposed**: `TreeOptions.showTombstoned` (default `false`) gates every renderer — `kg:tree`'s plain and view-based paths, and `kg:unfold`'s own separate preview path — hiding a tombstoned node and its subtree entirely by default, tagged `(tombstoned)` only with `--tombstoned`. `kg:unfold` additionally refuses to unfold a tombstoned node directly without the flag, rather than returning something misleadingly empty. Verified live and in `verify.ts`. See [Discussion](../discussion/treeview.md#id/BlockNode:00CE8T49MR001).

- **`aperas tree` had no way to name where a render actually started, or where a viewcone zoom moved it to** — every line only ever carried an id and a title, so reading a `tree`/`unfold` render meant a separate `aperas path <id>` call to place it in the corpus at all. First attempt over-corrected: a `(path)` tag on *every* line, immediately caught as wrong — repeating the full path on each descendant says the same prefix over and over, since every line under a render's own apex is already relative to it by construction. **Resolved**: exactly two breadcrumb points instead, each printed once, in `aperas://tree/<path>` form (`aperas path`'s own format, directly reusable as a `<ref>`). (1) The apex `aperas tree <ref>` was actually pointed at, as the render's own first line, computed in `kgTree.ts` rather than inside `TreeNode.renderTree()` itself, so `verify.ts`'s own direct `renderTree()` calls keep their existing line-count assumptions untouched. (2) In `--view` mode, wherever a link escapes its owner's viewcone into its own nested one (§13 — the target's own structural position loses canonical placement to the link, an "escaping win"), that position, indented to match — an ordinary in-cone link or a superseded pointer line changes nothing about what "here" means, so neither gets one. Verified live: constructed an actual escaping-link case (unfold a link whose target's own natural position is folded elsewhere) and confirmed the zoom breadcrumb appears exactly there, nowhere else.

- **`kg:unfold` never got the breadcrumb `kg:tree` did**: <a name='id/BlockNode:00CMPNS0B0001' class='aperas-anchor aperas-id'></a> [the fix above](#id/BlockNode:00CJ01QAJ0000) only touched `kgTree.ts` — `kg:unfold`'s own output (`kgUnfold.ts`) kept printing straight from `id  [label]  title`, no `aperas://tree/<path>` anywhere, even though its own target is exactly as reusable a `<ref>` as a tree render's apex is. **Resolved**: same format, same placement — one line before the target's own, computed the same way (`TreeNode.toPath()`), omitted rather than printed broken wherever `toPath()` can't walk it. For the `Link` case, the breadcrumb names the *target*'s path, not the Link's own (a Link has none — same reason the ref resolver can't route one through path-segment matching either), matching the target getting the full/uncapped text treatment right below it.
