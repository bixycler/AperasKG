## Open Issues <a name='id/BlockNode:00CE1GW638002' class='aperas-anchor aperas-id'></a>

- **Stale `TreeView.unfolds` references have no general cleanup**: <a name='id/BlockNode:00CE1GW638004' class='aperas-anchor aperas-id'></a> `TreeView.unfold(ref)` appends with no existence check, and the only cleanup — a reactive strip-on-hard-delete — only fires at the exact moment a specific id is hard-deleted; nothing revisits an *existing* `unfolds` entry against what's currently live. Confirmed live: `.state/TreeView.jsonld`'s `default` view has named 10 `BlockNode` ids with no corresponding document at all, after unrelated reconciliation churn elsewhere reassigned/removed the blocks those ids used to name. See [Settled](../discussion/treeview.md#id/BlockNode:00CE1FFSR8006) for the chosen fix direction.
- **A bare `aperas unfold <ref>` (no `--view` flag at all) mutates the `"default"` view instead of peeking**: <a name='id/BlockNode:00CE1GW638005' class='aperas-anchor aperas-id'></a> should be read-only — resolve and print a preview, touching no `TreeView` state — matching `aperas tree`'s own no-view default. Today it falls into the same bootstrap-and-mutate path that `aperas unfold <ref> --view` (flag present, no name) is supposed to trigger. `aperas fold`'s own no-`--view` case isn't resolved by this — folding presupposes some view's state to collapse, so a peek-equivalent doesn't obviously apply.
- **No raw single-node inspection command**: <a name='id/BlockNode:00CE1GW638006' class='aperas-anchor aperas-id'></a> `aperas tree`/`aperas backlinks --text` only ever show a rendered preview (title + truncated, anchor-stripped abstract) — right for browsing, not for verifying a stored field is exactly what's about to be pushed back via `aperas update`/`aperas insert`, or for reading a field no command shows at all (`props`, `tombstonedAt`). `aperas project --dry-run` reconstructs real markdown but only at the whole-artifact level. Today the only way to see a node's exact stored state is a direct `BlockNode.jsonld`/`ArtifactNode.jsonld` read outside the CLI entirely. Originally tracked under packaging, relocated here since it's a node-inspection gap, not a packaging one — the same gap the [`aperas` skill's own item 8](../history/aperas-skill.md#id/BlockNode:00CEDP10P8001) independently names — that gap's skill-script stage; `aperas show <ref>` below is the still-open toolset-update stage of the same lifecycle.

- **`aperas unfold` doesn't mark tombstoned children; both `unfold` and `tree` should hide them by default**: <a name='id/BlockNode:00CE8T6W7G001' class='aperas-anchor aperas-id'></a> `aperas tree --view <name>` appends a `(tombstoned)` suffix to a tombstoned node's line; `aperas unfold` shows the identical node with no marker at all, indistinguishable from a live sibling — confirmed live, see [Discussion](../discussion/treeview.md#id/BlockNode:00CE8T49MR001). Proposed direction: don't just bring `unfold` in line with `tree`'s tag — suppress tombstoned nodes from both commands' default output, and add a `--tombstoned` flag to opt into seeing them. No fix designed yet.

- **GFM task-list items round-trip broken**: <a name='id/BlockNode:00CE1GW638007' class='aperas-anchor aperas-id'></a> originally found here: [archive-migration discussion](../discussion/archive-migration.md#id/BlockNode:00CE0HD0HG007) — `- [ ] text` reportedly stored the literal `[ ] ` marker inside the block's own `.text` alongside a separate `checked: false` prop, so `aperas project` would re-emit `- [ ] ` on top of the leftover `[ ] `, doubling to `- [ ] [ ] text`. Re-tested live during the list-consumption migration (both a direct `parseMarkdownTree`/`serializeBlock` round trip and a real `aperas insert` against the live corpus): does not reproduce, renders correctly. `git log` shows the checkbox-handling code in `astParser.ts` has never changed since it was first written. No corroborating evidence anywhere in the graph that this was ever actually observed broken in a real projected artifact — awaiting a decision on whether to close as not-reproducible or keep open pending further investigation. See [list-consumption discussion](../discussion/list-consumption.md#id/BlockNode:00CE8J339R001) for the re-test note. **Correction: it does reproduce, narrower than either re-test tried.** Confirmed live on this session's own discussion plan checkboxes, then isolated and traced to the exact upstream line — full account in [discussion/treeview.md](../discussion/treeview.md#id/BlockNode:00CGJHDK68001). The real trigger is narrower than "bold" and broader than either re-test tried: `mdast-util-gfm-task-list-item`'s `exitParagraphWithTaskListItem` only trims the checkbox's mandatory leftover space, and re-bases the paragraph's own position past it, when the paragraph's first inline child is a `text` node — `- [x] Plain: rest.` qualifies, `- [x] **Bold**:`/`*Italic*:`/`` `code`: ``/`[link](url):` do not, since CommonMark's inline tokenizer never materializes a lone leading space with nothing before an inline span as its own text node. `astParser.ts` has no checkbox-marker-stripping logic of its own — it only reads `node.checked` into a prop — so it faithfully trusts the un-rebased position for `rawSlice`, including the leftover marker as literal text. Both earlier re-tests happened to use plain-text task items, which is exactly why neither one reproduced it. **Resolved**: the real fix lives upstream (`mdast-util-gfm-task-list-item`), out of reach here, so `astParser.ts` compensates defensively — a listItem already known to be a checkbox (`node.checked` boolean) has a leading `/^\[[ xX]\]\s*/` stripped from both its extracted `text` and `title` after the fact, regardless of what leaked or why. Verified live end-to-end: a bold-lead checkbox item pushed through the real service now stores clean text with `checked` set correctly, and projects to a single, correct `- [x]` marker — confirmed by re-checking this session's own six plan checkboxes, which had actually rendered doubled (`[ ] [x]`) before this fix and render correctly now.
