## Open Issues <a name='id/BlockNode:00CF1WZ4JG002' class='aperas-anchor aperas-id'></a>

- **A parent-heading list-push reconciles children by array position, tombstones included, not by content/key**: found running `aperas-skill`'s own eval against [issues/treeview.md's Open Issues list](../issues/treeview.md#id/BlockNode:00CE1GW638002) — piping the heading line plus every visible item (skipping tombstoned ones, as any reasonable read would) zips the piped items against storage slots by raw position, silently reassigning live content onto wrong ids once a tombstoned sibling is interleaved. Contradicts what both the skill and the code's own doc comments claim ("exact-key matching"). Root cause not yet read off `reconcile.ts` directly — identified from reproduced symptom, confirmed only in a disposable eval sandbox, not the live corpus. Same defect family as the next two items below — one fix in `reconcile.ts` likely closes all three.
- **`aperas update`'s reconciliation can silently match fresh content onto an already-tombstoned node's id without reviving it**: reproduced twice in `list-consumption`'s eval sandbox — a new bullet's content lands on a stale, already-tombstoned id instead of a fresh one, and `tombstonedAt` is never cleared, so the content stays invisible even though the summary line reports a clean match/add. Root cause not yet investigated in `reconcile.ts`.
- **`matchLeftoverByAbstract` (Gestalt/Ratcliff-Obershelp recursion) is position-sensitive**: <a name='id/BlockNode:00CF1WZ4JG005' class='aperas-anchor aperas-id'></a> works for reconciling siblings that share a rough common order, not for an unordered bag of whole-artifact identities scattered across concern folders — a match's recursive split can discard a whole quadrant of otherwise-valid candidates. Worked around for the rename path specifically (replaced by exact-key matching there), but the same algorithm is used elsewhere in `reconcile.ts` and may still carry the weakness on those other paths.
- **A fully-dead container is never itself tombstoned**: <a name='id/BlockNode:00CF1WZ4JG006' class='aperas-anchor aperas-id'></a> `pruneUnreachableTombstones` only collects nodes that are themselves tombstoned and unreachable; nothing ever tombstones a container once its last live child is gone (children get tombstoned one at a time as they're resolved, but the now-vacuous wrapper is never itself marked dead). Confirmed live against `issues/packaging.md`'s own dead nested-list-wrapper chain. Minor/cosmetic relative to the three above, but the same tombstone-lifecycle gap.
- **A multi-artifact `kg:ingest` isn't transactional either**: <a name='id/BlockNode:00CF1WZ4JG008' class='aperas-anchor aperas-id'></a> `ingestArtifacts`/`ingestAllArtifacts` (`apeironNgn/artifacts.ts`) loop per file with no try/catch, so a later file's failure leaves earlier files' writes already committed to the in-memory store with no rollback across the batch. Same shape as the single-`kg:insert` gap above, one layer up (a batch of artifacts vs. a batch of nodes within one call) — likely the same underlying fix (validate everything before writing anything) closes both.
- **Folder/Artifact-tier holders have no promotion channel at all, and nothing clears `.holder` once real content lands underneath**: found live creating this very doc. `aperas resolve --create-holder` scaffolds a placeholder `ArtifactNode`/`Block` chain, and filling real content into the *Block* children works fine — but `kg:insert`'s promote path is Block-tier only ("kg:insert only positions Block-level nodes"), so there is no verb that ever flips a Folder/Artifact's own `.holder` back off, even once every child underneath it is real. `aperas project` correctly refuses to render such a subtree ("still has a placeholder (holder) node somewhere in its subtree"), but nothing resolves that refusal short of a direct edit or removing and recreating the artifact disk-first. Matches `Aperas-crud-design.md` §4.1/§6 exactly. Until fixed, the graph-first "sketch a structure" path only actually works for adding a subtree *within* an already-real, already-projectable artifact — not for creating a brand-new artifact from nothing.

- **A props-only change reports as `0 changed`, so a write that really happened is invisible in the summary**: `reconcileTree`'s summary categories (matched/moved/changed/added/removed) are computed over text, so a push whose only effect is on a node's `props` — a list item's `checked`, or a run's `orderedList`/`startIndex` — comes back as `N matched, 0 changed` while a real write has occurred. Confirmed live pushing GFM checkboxes onto `planning/aperas-skill.md`'s Task Breakdown: every one of the 17 items gained a fresh `checked` StringProp and the summary reported `17 matched, 0 moved, 0 changed, 0 added, 0 removed`. Not data loss — the write lands and projects back correctly — but the summary cannot be used to confirm it, and reading it as "nothing was written" is the natural mistake. Same family as the skill's own "verify by traversal, not by the summary line", surfacing in a category the line does not cover at all.
