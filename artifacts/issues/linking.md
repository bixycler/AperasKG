# Linking — Issues <a name='id/BlockNode:00CDBYV5A8001' class='aperas-anchor aperas-id'></a>

## Open Issues <a name='id/BlockNode:00CDBYV5A8002' class='aperas-anchor aperas-id'></a>

One open item below — links silently failing to persist or resolve, across three distinct mechanisms found so far, via unrelated causes.

- **Links silently fail to persist or resolve, via at least four distinct mechanisms found so far, with nothing detecting any of them automatically on its own**: <a name='id/BlockNode:00CGMWQ6T0001' class='aperas-anchor aperas-id'></a> a claim's `.links` field can go empty (or never populate) while every other signal — the write's own summary line, the projected markdown, a plain `unfold` preview — looks completely normal, since nothing renders `.links` by default and no command reports "this claim's provenance just went missing." Four confirmed instances below, unrelated call sites at the surface: (1), (3) and (4) turned out to share one root cause (a scope mismatch between `resolveBlockLinks`'s `pending` and `oldWikilinksByBlock` populations), now fixed at each of the three known sites; (2) alone remains open, with no fix direction yet.
  
  - **(1) Historical staleness has no standing safeguard, only a one-time hand sweep**: <a name='id/BlockNode:00CGN6GJV8002' class='aperas-anchor aperas-id'></a> `resolveBlockLinks` used to run only from `kg:ingest`, so any node last touched before that entry point existed (or before a later fix) carries a permanently-empty `.links` no matter what its text cites — a graph-wide sweep found and fixed 9 real cases (see [History](../history/linking.md#id/BlockNode:00CDBZ7698003)), but the sweep was a one-time hand pass, not a standing safeguard. A fresh corpus-wide check today found the same symptom already back on nodes the sweep never touched (e.g. `planning/core.md`'s own Batch 1 item 1, `BlockNode:00CGGTQ620002` — untouched since the sweep, `.links` empty despite an unchanged real citation in its text). The sweep fixed a snapshot; nothing keeps re-checking it, so drift just accumulates again under a different name. Needs a repeatable sweep, not another one-time hand pass.
    
    - **Resolved**: <a name='id/BlockNode:00CJ38WX0G001' class='aperas-anchor aperas-id'></a> the sweep is now standing, and two of its three triggers need nobody to remember them. The service re-checks the written artifact after every `update`/`insert`/`remove` and reports what that write resolved but failed to persist, on the write's own response; it re-checks the whole corpus at startup and on `reload`, carrying any finding on *every* later response until it clears (the same channel `contentConflict` uses, chosen because a lost link is invisible in every ordinary rendering and so has to arrive unasked-for). Only the end-of-batch corpus pass is left to discipline, because it alone catches damage that lands in a *different* artifact from the one edited — folded into the skill's *Stage each verified step* rather than given a step of its own. Verified live end to end: dropping one real link edge on disk and restarting produced the warning at startup, and that warning then surfaced on unrelated `tree` and `path` calls before `--repair` cleared it.
  - **(2) A fresh regression, mechanism unknown**: <a name='id/BlockNode:00CGN6GJV8003' class='aperas-anchor aperas-id'></a> four nodes (`BlockNode:00CF1WZ4JG005`, `BlockNode:00CE1GW638004`, `BlockNode:00CE1GW638006`, `BlockNode:00CE8T6W7G001`) each had a link genuinely resolve — `aperas update --text-only` reported "N resolved" for every one of them — and each still ended up with an empty `.links` afterward, discovered only because a reader manually re-checked one by direct id. Extensive attempts to reproduce it under controlled conditions all failed to trigger the loss: matching move-then-`--text-only`-update sequences (single node and 4-node batches), a sibling heading's plain reconcile in between, a full `aperas service stop`/`start` cycle, and the exact stop → manual `ArtifactNode.jsonld` edit → start sequence used elsewhere in the same session. Re-running each affected node's own unchanged `update --text-only` a second time did resolve and this time verifiably persist the link, so the fix for the *symptom* is cheap once found — the *cause* is not. Needs a reproduction before any fix can be attempted at all.
  - **(3) Promoting a holder node can drop links from unrelated descendants elsewhere in the same artifact**: <a name='id/BlockNode:00CJ38Z8T0001' class='aperas-anchor aperas-id'></a> `aperas update --text-only` calls whose only purpose was clearing a `.holder` flag on an `ArtifactNode`/H1/heading — no text change, no link-bearing block touched directly — left 8 list items several levels below empty of `.links`, none of them the target of any of the three writes and each previously confirmed to hold a real, resolved `Link`. `aperas check-links --repair` restored all 8 in one pass. Distinct from (1)/(2) in blast radius: the damage lands on nodes the write never touched at all, not just on the written node's own subtree.
    
    - **Resolved**: <a name='id/BlockNode:00CJ3Z5DM0001' class='aperas-anchor aperas-id'></a> root cause was a scope mismatch shared with `check-links --repair`'s own bug above — `kg:update --text-only`'s `collectOldWikilinksByBlock(target, ...)` recursed into `target`'s *existing* children by default, while its own `pendingLinks` covers only `target` itself plus the freshly piped `overflow`. `resolveBlockLinks`'s key-union then reprocessed every untouched existing child with zero pending codes, wiping its real `.links`. Fixed the same way: `collectOldWikilinksByBlock` gained a `recursive` flag, and `kg:update` now passes `recursive: false` specifically for `--text-only` (the reconcile branch stays recursive, correctly, since its `pendingLinks` already covers the whole subtree). `verify:slow` gained a dedicated step (20) with a parent-plus-real-child fixture, asserting the child's `Link` id survives a `--text-only` update to the parent untouched — confirmed to fail against the pre-fix code and pass against the fix. Verified live against the actual corpus too: re-running the exact `--text-only` update on [`BlockNode:00CGMWQ6T0001`](../issues/linking.md#id/BlockNode:00CGMWQ6T0001) that triggered this twice during (1)/(3)'s own write-up left both children's `Link` ids completely unchanged, with no integrity warning. Full account in [discussion/linking.md](../discussion/linking.md#id/BlockNode:00CJ2WQ1SR001).
  - **(4) A third scope-mismatch site: `ArtifactNode.ingestFromDisk`'s tombstone-holdback branch, on `aperas ingest --track` (not `kg:update`)**: <a name='id/BlockNode:00CN0MVG2R001' class='aperas-anchor aperas-id'></a> found live while testing the new frontmatter-`description` feature on `design/treeview.md` — adding frontmatter to an already-tracked artifact whose reconcile also happened to find an unrelated, pre-existing pending removal (a stale tombstoned `list` node left over from the list-consumption migration, held back since `--force` wasn't passed) silently wiped `.links` on 6 of that same artifact's own Context-section bullets (`**Discussion**`/`**Issues**`/`**Planning**`/`**History**`), none of them touched by the frontmatter edit at all. Same root-cause class as (3), a different call site: `ingestFromDisk`'s early return (tombstones pending, `!force`) hands back `pendingLinks: descriptionPendingLinks` only — the full-body `extractLinkCodes(finalRoot)` never runs, since that happens after this return point — but `oldWikilinksByBlock`/`oldLinkTargets` were collected recursively over the *whole* artifact before the tombstone gate ran. `resolveBlockLinks`'s key-union then reprocessed every other block with zero pending codes and wiped its real `.links`, exactly the invariant `collectOldWikilinksByBlock`'s own doc comment warns against. Repaired live via `aperas check-links --repair` (6 → 0 discrepancies).
    
    - **Resolved**: <a name='id/BlockNode:00CN0MYWT0001' class='aperas-anchor aperas-id'></a> fixed at the actual early-return site (`node.ts`'s `ArtifactNode.ingestFromDisk`) — `oldLinkTargets`/`oldWikilinksByBlock` are now trimmed down to just the artifact's own key before being returned, instead of handing back the full-artifact maps, matching the same scoping (3)'s fix already established for `kg:update --text-only`/`repairLinkIntegrity`. New regression test: `verifyExtended.ts` step 22 (a citing block with a real resolved link, plus a sibling paragraph removed between two ingests specifically to trip the tombstone-confirmation gate without `--force`) — confirmed to fail against the pre-fix code and pass against the fix. `npm run verify` and `npm run verify:slow` both pass clean end to end against the fixed corpus.

- **`aperas retype`'s automatic title derivation has no slug-path collision guard, unlike every other title-changing write path**: <a name='id/BlockNode:00CN4NZRRR001' class='aperas-anchor aperas-id'></a> confirmed live — `rejectSlugPathCollisions` (`node.ts`, design/linking.md's Full-Path Collisions) is called from `ArtifactNode.ingestFromDisk` (`node.ts`), `kg:insert` (`kgInsert.ts:125`), and `kg:update` for *any* title change, heading retitle or non-heading re-derivation alike (`kgUpdate.ts:207-214`, explicitly scoped to cover exactly this case per its own comment: "relevant whenever `title` actually changed... heading retitle or non-heading re-derivation alike"). `kgRetype.ts` has no such call anywhere in the file — its title assignment at `target.title = toTitle` (line 248) is a bare, unguarded write, even though retype's own defining feature is deriving a *fresh* title (folding a heading's words into a lead-in, or cutting a lead-in back out into a heading) exactly the kind of change the other three sites exist to protect. Reproduced live in a scratch artifact: two sibling blocks under one parent heading, one a heading titled "Existing Sibling", the other a listItem with the identical bold lead-in "**Existing Sibling**" — `aperas retype <listItem> --to h3` succeeded with no error or warning, producing two live sibling headings both titled "### Existing Sibling" under the same parent, indistinguishable in `aperas tree`'s own render. Fix direction: call `rejectSlugPathCollisions(store, target.parent.toPath(), [...])` at `kgRetype.ts`'s title-assignment point, the same shape `kgUpdate.ts:207-214` already uses — not yet implemented, found while auditing every title-extraction path after [the packaging slug-path collision](../discussion/packaging.md#id/BlockNode:00CN4DGBQ0001) raised the question of whether the guard covers every site that mints or changes a title, not just full-document ingest.

## Resolved <a name='id/BlockNode:00CDBYV5A800A' class='aperas-anchor aperas-id'></a>

- **Heading-in-list**: <a name='id/BlockNode:00CDBYV5A800C' class='aperas-anchor aperas-id'></a> resolved — a block's title isn't limited to headings, which cap at H6 and don't fit an unbounded tree. Any block whose text opens with a colon-delimited lead-in term (`Term: rest of the text`) uses that term as its title; bold/`**...**` around the term is a free style choice, not part of the rule, and its `**` characters slugify like any other non-alphanumeric character if present, same as headings' `#` markers. List nesting carries unbounded depth the same way heading nesting carries bounded depth. See [Architecture](../design/linking.md#id/BlockNode:00CDBYV4T8002). The exact rule for which colon counts as the delimiter — outside bold *and* inline code, length-capped, language-dependent — was refined after live corpus ingestion surfaced real corruption from a simpler version of it; see [Lead-In Term Detection](../design/linking.md#id/BlockNode:00CDBYV4TG000).
- **`[[deep-path]]` coexistence**: <a name='id/BlockNode:00CDBYV5A800D' class='aperas-anchor aperas-id'></a> not needed, at least for now — `aperas://` scheme URLs (in-app) and `#fragment`s (compatible/pre-ingestion), including an `id/<ID>` fragment form, already make an internal reference unambiguous without a `[[...]]` wrapper. See [Topology](../design/linking.md#id/BlockNode:00CDBYV4T8007).
- **"No automated rename repair"**: <a name='id/BlockNode:00CDBYV5A800E' class='aperas-anchor aperas-id'></a> misdiagnosed — a rename adds an anchor rather than replacing one, so an old reference doesn't break at rename time; there's nothing to repair, only a later cleanup once it's actually safe. See [Architecture](../design/linking.md#id/BlockNode:00CDBYV4T8002).
- **"Duplicate-slug collisions"**: <a name='id/BlockNode:00CDBYV5A800F' class='aperas-anchor aperas-id'></a> misdiagnosed — a collision only happens when two blocks share an identical *full* slug-path (same heading text at the exact same tree position), a genuine authoring error, correctly a hard reject, not a case needing disambiguation logic. Reusing the same heading title at different tree positions is ordinary and never collides, since the full path includes the distinguishing ancestor segments. See [Topology](../design/linking.md#id/BlockNode:00CDBYV4T8007).
- **Every `<block-slug-path>` written so far omitted its own H1 segment.** `toPath()` (`apeironNgn/node.ts:455-471`) walks every `BlockNode` ancestor — the H1 heading included — contributing a slug segment for each, stopping only at the owning `ArtifactNode`/`FolderNode`. Every anchor and cross-reference in this concern's own docs had been computed without that leading segment (traced back to the very first `test-slugifed-path.md` validation, which never included its own H1 either) and has been corrected corpus-wide. See [Topology](../design/linking.md#id/BlockNode:00CDBYV4T8007).
- **Cross-artifact link staleness on ingestion**: <a name='id/BlockNode:00CDBYV5A800H' class='aperas-anchor aperas-id'></a> resolved — an artifact whose own text doesn't change is never re-ingested on its own, so a link it couldn't resolve stayed stale even after its target came into existence elsewhere in the corpus, with no way to fix it short of hand-editing `ingestedHash` to force a re-ingest. `kg:ingest` now stashes every code a block fails to resolve on its own referring artifact, and retries every stashed code against the current graph after its main work is done, force-reingesting (without discarding reconciliation identity — see [Discussion](../discussion/linking.md#id/BlockNode:00CDBZ76TR008) for the `hadContent`/`bypassUnchangedCheck` distinction) any artifact where at least one now resolves. See [Workflows](../design/linking.md#id/BlockNode:00CDBYV4TG007).
- **A lead-in colon followed only by nested list children got no title**: <a name='id/BlockNode:00CDBYV5A800J' class='aperas-anchor aperas-id'></a> resolved — `findLeadInColonOffset`'s space-after-colon check read the next character from the colon's own mdast text node, which simply ends at the colon when nothing inline follows it on the same line (e.g. `- **Heading**:` before a nested list), and treated that the same as a genuinely ambiguous no-space case. Fixed by accepting "nothing left in this text run" the same as "a space follows" — the inline-code and bold/italic exclusions run first and are unaffected. See [Lead-In Term Detection](../design/linking.md#id/BlockNode:00CDBYV4TG000) and [Discussion](../discussion/linking.md#id/BlockNode:00CDBZ76TR00E).
- **Collision check only covered a block's current slug-path**: <a name='id/BlockNode:00CDBYV5A800K' class='aperas-anchor aperas-id'></a> resolved — Slice 2's collision check (`apeironNgn/node.ts`'s `rejectSlugPathCollisions`) checks every anchor `name` still embedded in a block's `treeAnchor` prop or raw text too, not just its current `toPath()`, since [Anchor-Matching Requirement for Resolution](../design/linking.md#id/BlockNode:00CDBYV4TG005) already treats either as a live resolvable target. See [Planning](../planning/linking.md#id/BlockNode:00CDBZ77F000X).

- **`aperas update` never re-derives a non-heading block's title**: <a name='id/BlockNode:00CGFE4SV0002' class='aperas-anchor aperas-id'></a> replacing a paragraph's `.text` leaves `.title` frozen at whatever ingest originally derived from the lead-in term, even when the new text no longer has that lead-in at all — so the block goes on previewing under a title for content it no longer holds. Root cause confirmed directly in `kgUpdate.ts`: `runUpdate`'s local `title` variable is assigned only in the heading-target/heading-input branch — for a paragraph/listItem target it stays `undefined` for the entire function, so the old title is carried forward unconditionally, every time, not merely left stale by a parsing quirk. Also confirmed worse than a stale-title problem: verifying it by re-pushing a node's own `--text` output (assumed complete) tombstoned that node's 4 real children, since `--text` never shows children and a non-`--text-only` update reconciles the piped (empty) overflow against what's really there. Recovered via the staged `git` checkpoint; see [discussion/linking.md](../discussion/linking.md#id/BlockNode:00CGGA9J68000) for the full incident. Invisible in the rendered projection, since only a heading's title is ever written back to disk (`kg:title`'s removal made the lead-in term the one and only title mechanism, with `update` compensating for heading targets only) — but `tree`, `unfold` and `backlinks --text` all display the stale title in the graph itself, with the summary line's `0 changed` giving no hint either way. No CLI route yet to repair an already-stale title short of tombstoning the block. Found live while rewriting `design/aperas-skill.md`'s Topology paragraph for the `aperas` skill's v2; full account in [discussion/linking.md](../discussion/linking.md#id/BlockNode:00CGF83D4G001). **Resolved**: `runUpdate`'s paragraph branch now reads `title = firstChild.title` too (already computed by the parser for every paragraph, nothing new to derive), skipped only when `target` itself is a heading (where `firstChild` is the adopted leading paragraph, a different piece of text from the heading's own title). Decoupled from `props`, which must stay untouched for a non-heading re-title — a new `retitling` flag (true only for an actual heading retitle) now gates the two prop-replacement sites that used to key off `title !== undefined` alone. Verified live: a scratch paragraph's title updates on content change and a scratch listItem's `orderedList`/`startIndex`/`checked` props survive a title-changing update untouched; a real heading retitle still replaces its own props (tree-anchor) as before.

- **`extractAnchorNames` treats a quoted example anchor as a real claimed name — no code-span awareness**: <a name='id/BlockNode:00CGGHVBF8001' class='aperas-anchor aperas-id'></a> `astParser.ts`'s `extractAnchorNames(text)` is a bare regex over a block's raw text, with no AST/markdown awareness, so an anchor tag written *inside backticks as an illustration* is indistinguishable from one the projector actually spliced in. `rejectSlugPathCollisions` then enforces the illustration as a real claimed name. Confirmed live: the `aperas` skill's own item 2 (SKILL.md) quotes a complete anchor tag to warn readers off pasting projected files back in, and that quoting alone made the block claim the address as its own — `BlockNode:00CE95MVP8008` holds it today. Only one claimant exists so far, so nothing has collided yet, but `design/linking.md` (the canonical anchor-syntax spec) is exactly the kind of document that must quote the same example, and would collide the moment it does. Not a judgement call: a code span is literal display text by definition, so an anchor inside one is never a real claim — the regex needs to skip backtick-delimited spans, mirroring how `findLeadInColonOffset` already excludes `inlineCode`. Full account in [discussion/aperas-skill.md](../discussion/aperas-skill.md#id/BlockNode:00CECCBKNG001). **Resolved**, and widened while fixing it: a shared `anchorMatchesOutsideCode` helper now filters out any `ANCHOR_NAME_RE` match sitting inside a backtick span before either function sees it. Found designing the fix, not by this issue: `stripInlineAnchors` — this session's own new storage-time call included — had the identical gap in the opposite direction, and would *strip* a legitimately-quoted anchor example as if it were real projection markup, corrupting genuine prose. Both functions fixed from the one shared helper. Verified in isolation: a real anchor is still extracted/stripped, a quoted example is preserved untouched in both directions, and a mixed case (one real, one quoted) resolves each correctly.

- **Graph-wide sweep for the pre-fix "wikilink never resolved" residue — 9 real cases found and fixed, not the 20 first estimated**: <a name='id/BlockNode:00CGGG6N5G001' class='aperas-anchor aperas-id'></a> `resolveBlockLinks` used to run only from `kg:ingest`, never `kg:update`/`kg:insest` ([this doc's own account above](#id/BlockNode:00CF1276D0001)) — already fixed in the current code, but every node last touched before that fix kept a permanently-empty `.links` regardless of what its text actually cited. A first pass (any stored `text` containing `](...#...)`with an empty `.links`) found 20 candidates graph-wide; most turned out to be false positives once checked by hand — a fenced code-block example in `design/documentation.md` with placeholder ids (`00C0000000001`, all zeros), and half a dozen copies of `SKILL.md`'s own wikilink-syntax documentation quoting the pattern with a literal `<ID>`/`...` placeholder inside backticks, none of them real citations at all. Re-run comparing each node's *actual* `#id/BlockNode:...` fragments (code fences and inline-code spans excluded from the count) against its resolved `.links` targets found exactly 9 genuine cases, spread across `planning/linking.md`, `issues/packaging.md`, `history/aperas-skill.md` and `discussion/aperas-skill.md` — all resolvable (every target confirmed live, none tombstoned or missing). Fixed by re-touching each with `aperas update <id> --text-only` (piping the node's own unchanged text) — chosen over a plain `update` specifically because a plain reconcile risks tombstoning real children on a node whose full shape isn't known up front (the near-miss recorded just above this entry); `--text-only` never reconciles children at all, so it was safe regardless. Confirmed by re-running the same precise sweep afterward: zero remaining. A companion check for the opposite failure — a resolved `Link` whose *target* is now dead or missing — also came back empty, so this concern's link integrity is otherwise clean as of this pass.

- **Link Integrity Checking built (`aperas check-links`)**: <a name='id/BlockNode:00CGN6GJVG000' class='aperas-anchor aperas-id'></a> resolved — the drift-style check has been built (`checkLinkIntegrity` and `repairLinkIntegrity` in `@aperas/core`), and its first landed version had a real gap, since fixed. It scans for live nodes where internal link codes exist in `node.text` but have no corresponding resolved `Link` in `.links`, and repairs them via the `--repair` flag, catching both historical staleness and transient regressions without needing to know the root cause (see [Open Issues](#id/BlockNode:00CGMWQ6T0001)). **Found on review, fixed**: the original match logic compared each text occurrence against `.links` by raw substring containment against the target's opaque id — reading as thorough (it correctly found and fixed 40 real historical discrepancies across 7 artifacts on its first live run) but actually sound only for codes that textually embed the id (`path#id/<ID>`, `aperas://id/<ID>`), which happens to be every code this corpus currently writes. It could not have verified `[[<deep-path>]]` addressing (`resolve.ts`'s deep-path grammar — a real, currently-live convention, "used extensively" in `Aperas-apeironngn-design.md`'s own self-references per `history/linking.md`) at all: a heading-path string shares no substring with the opaque id it resolves to, so a perfectly-resolved deep-path link would have been reported as missing. The one test meant to catch a genuine drop (deleting a `Link`'s `predicate` quad) also turned out to be vacuous — the match logic never reads `predicate`, and the scratch fixture already carried unrelated discrepancies of its own, so the assertion could never actually fail regardless of whether the deletion did anything (confirmed live: the count was identical before and after). **Actually fixed**: `checkLinkIntegrity` now resolves each occurrence for real via `resolveOneCode` (`artifacts.ts`, the same dispatch `resolveBlockLinks` itself uses, exported and called with `createHolder: false` so a scan can never mutate the graph as a side effect), and only reports a code that resolves to a live target with no matching entry in `.links` — an unresolved code is left alone, since that's routine (a bare `#fragment` anchor) or already `danglingRef`/`retryDanglingRefs`'s own separate concern. `verify.ts`'s step 19 replaced the vacuous predicate-quad deletion with a precise before/after discrepancy-count assertion against a real, freshly-resolved link.

- **`check-links --repair` re-mints every `Link` id in an affected artifact, not just the broken one**: <a name='id/BlockNode:00CHYM4Z1G001' class='aperas-anchor aperas-id'></a> found while verifying the standing sweep end to end — one deliberately-dropped link edge, repaired, produced a 63-insertion/37-deletion diff across `BlockNode.jsonld`, because `repairLinkIntegrity` re-ran `resolveBlockLinks` over *every* block carrying link text in the affected artifact, and that regenerated each `Link` subdocument (and its `position` `StringProp`) under a fresh id even where nothing was wrong. Targets and positions were preserved, so this was churn rather than data loss — but `Link` ids are addressable in their own right: a `TreeView.unfolds` entry can name one (`node.ts`'s `unfold(ref)` accepts a `Link` id), so a repair could silently orphan an unfolded link, which `pruneStaleUnfolds` then cleans up on the next sweep — the viewer's own fold state quietly lost to a repair that touched an unrelated block. Same identity-preservation principle the skill applies to blocks, one tier down.
  
  - **Resolved**: <a name='id/BlockNode:00CJ0XSZ8R001' class='aperas-anchor aperas-id'></a> two compounding causes, not one. First, `repairLinkIntegrity` scoped its re-resolution to every link-bearing block in the affected artifact (`collectAllBlockNodes`) instead of just the blocks the discrepancy report actually names. Second, and more fundamental, it called `resolveBlockLinks` with `oldWikilinksByBlock` left `undefined` — the parameter that lets a freshly-resolved target reuse an existing `Link`'s id rather than minting a new one — so even a single touched block would have reminted every one of its own wikilinks, correct ones included.
