## Settled <a name='id/BlockNode:00CE32GXH0008' class='aperas-anchor aperas-id'></a>

- **The unified law**: <a name='id/BlockNode:00CE32GXH000A' class='aperas-anchor aperas-id'></a> a list attaches to whatever most immediately precedes it, textually — a separate node if one exists (what looks like "consumption": the list nests *inside* that node), or the enclosing container's own merged identity if its leading paragraph was already consumed into it (what looks like "dissolution": the list's items become the container's *own* children, flat). These are the same rule, not two competing models — they only differ in whether "the nearest preceding text" turned out to be a standalone node or the container itself.
- **When no consumer exists at all — dissolve anyway**: <a name='id/BlockNode:00CE32GXH000B' class='aperas-anchor aperas-id'></a> nothing precedes the list (a code block or blockquote sits directly above it, or it's literally the first content with no leading paragraph) — the list still dissolves into flat children of its true structural parent, at the position it occupied. There is no case in this model where a bare, unaddressable `list` wrapper is the *correct* outcome, only cases where today's code hasn't been extended to avoid one yet.
- **Superseded: normalize to "the run's own first item always owns `orderedList`/`startIndex`", universally**: <a name='id/BlockNode:00CE32GXH000C' class='aperas-anchor aperas-id'></a> not just for orphan-dissolution as first proposed. Checked the actual code before deciding: `project.ts`'s `renderChildren` already has the run's first item in scope as its loop cursor at the exact point it reads these props — reading from it unconditionally removes a fallback branch, not adds one. `astParser.ts`'s three adoption branches (consumption, self-dissolution, orphan) currently need three different `setProp` targets — self-dissolution specifically threads a dedicated `parentListProps` field back through `ChildrenResult` solely because the container node doesn't exist yet when the list is seen. Normalizing collapses all three into one `setProp(items[0], ...)` call, run once before any branch, and removes `parentListProps` from the interface entirely. Also uncovered a real, intentional test in `verify.ts` ("Expected the heading itself to carry the adopted list's orderedList/startIndex props") asserting today's anchor-owns-it convention — needs rewriting regardless, since the orphan-dissolution work already breaks its adjacent-lists test. Cost: 48 existing anchors (18 headings, 18 listItems, 12 paragraphs) need their props relocated down to their own first child, beyond the 59 `list` nodes already in scope — same migration operation, just wider. Decided: normalize.
- **Run boundaries at render time are marked by an item's own explicit props, not by type alone**: <a name='id/BlockNode:00CE4757W0005' class='aperas-anchor aperas-id'></a> verified live against the project's own parser — `# H` followed directly by a bullet list then an ordered list (no blank line, no separator) produces two adjacent mdast `list` nodes with nothing between them, exactly the case the original `adoptionAnchor`-reset comment names. Once both dissolve as orphans, their items land back-to-back in the same parent's children, all typed `listItem` — a boundary-scan keyed on type alone (`while (children[j].type === 'listItem') j++`) would merge them into one run and read only the first item's props, silently losing the second list's ordered-ness. Fix: a run ends not just where the type changes, but wherever the *next* item carries its own explicit `orderedList` (`getProp(item, 'orderedList') !== undefined`, distinguishing a real per-item value from an inherited/absent one) — every dissolved run's first item already gets this set at parse time regardless of adjacency, so the render-side scan only needs to consult it, not compute anything new. Specific to orphan-dissolution: consumption and self-dissolution can never produce two runs under one parent, so this case never arises for either.

- **Implemented and migrated**: <a name='id/BlockNode:00CE5E7X88001' class='aperas-anchor aperas-id'></a> all three cases live in `astParser.ts`/`project.ts`, corpus migration verified byte-identical (one approved, understood exception in `issues/packaging.md` — a pre-existing dead nested-list-wrapper chain whose old rendering quirk manufactured spurious blank lines). See [History](../history/list-consumption.md#id/BlockNode:00CE32GW3G002).

## Checkpoints <a name='id/BlockNode:00CE5KSNVR001' class='aperas-anchor aperas-id'></a>

- **A fully-dead container is never automatically cleaned up**: <a name='id/BlockNode:00CE5KSNVR002' class='aperas-anchor aperas-id'></a> found while explaining why a service restart hadn't already collected `issues/packaging.md`'s dead nested-list-wrapper chain. Not a GC/reachability bug — `pruneUnreachableTombstones` only collects nodes that are *themselves* tombstoned and unreachable, and nothing ever tombstones a container once its last live child is gone (individual items get tombstoned one at a time as they're resolved; the now-vacuous wrapper is never itself marked dead). Promoted to [issues/core.md's Open Issues](../issues/core.md#id/BlockNode:00CF1WZ4JG006) — still belongs in a general crud/tombstone-lifecycle concern once one exists in the graph (`crud.md` is still archived, next on `archive-migration`'s own list).
- **`aperas update`'s reconciliation can silently match fresh content onto an already-tombstoned node's id without reviving it**: <a name='id/BlockNode:00CE5KSNVR003' class='aperas-anchor aperas-id'></a> while writing this doc set's own Resolved section, a new bullet's content landed on the id of an unrelated, already-tombstoned test-probe node from earlier live-testing — the reconciler apparently reused that dead slot (likely a positional fallback match, not a content match) but never cleared `tombstonedAt`, so the new content silently rendered as invisible until caught by noticing the Resolved section had one fewer visible item than pushed. Recovered by directly clearing `tombstonedAt` on the specific node once identified. Reproduced a second time, identical shape: pushing the same Resolved heading's full content plus one new item, right after tombstoning an unrelated single-item probe added moments earlier, landed the new item on that exact same tombstoned id again — strongly suggesting the fallback prefers reusing *any* available tombstoned child in the heading's own children array over minting a fresh id for a genuinely new, unmatched entry, regardless of content. Promoted to [issues/core.md's Open Issues](../issues/core.md#id/BlockNode:00CF1WZ4JG004) — the root cause in `reconcile.ts`'s matching logic still needs its own investigation.

- **Three independent sightings of the same `reconcile.ts` identity-matching fragility, never tied together**: <a name='id/BlockNode:00CF12B710001' class='aperas-anchor aperas-id'></a> this doc's own [dead-container](../discussion/list-consumption.md#id/BlockNode:00CE5KSNVR002) and [tombstone-reuse](../discussion/list-consumption.md#id/BlockNode:00CE5KSNVR003) findings above, plus [packaging's `matchLeftoverByAbstract` position-sensitivity](../discussion/packaging.md#id/BlockNode:00CDEM7DVG002) (replaced by exact-key matching for renames, but never checked against `kg:update`'s own reconcile path), are three angles on one underlying defect family — `reconcile.ts`'s matching/lifecycle logic being unreliable around identity, not three unrelated bugs. None of the three write-ups reference either of the others. Worth one shared home once CRUD/reconciliation gets its own dedicated concern, per this doc's own note above.

## Freeflow <a name='id/BlockNode:00CE32GXH000D' class='aperas-anchor aperas-id'></a>

- **Started from two live mistakes**: <a name='id/BlockNode:00CE32GXH000F' class='aperas-anchor aperas-id'></a> while working `archive-migration`'s own [`treeview` sub-task](../discussion/archive-migration.md#id/BlockNode:00CE0HD0HG007), `aperas insert`/`update` targeting a `list` node directly twice produced an accidental nested-list-in-list, once for a Task Breakdown item and once for a History milestone. Both recovered by targeting the parent heading with full corrected content instead — but that workaround doesn't scale once a freeflow tree grows deep, which is what prompted asking whether the `list` container could be eliminated at the root. One of the two gaps logged there ("`List` isn't consumed by a preceding `Heading`") is this design's own direct origin — see [Issues](../issues/treeview.md#id/BlockNode:00CE1GW638008), now resolved by it.
  
  - Corpus survey before proposing anything: <a name='id/BlockNode:00CE32GXH000G' class='aperas-anchor aperas-id'></a> 54 `list` nodes vs. 307 `listItem`s; 159 items (52%) already have no `list` parent — parented directly by a heading, another listItem, a paragraph, or an artifact, and all of it projects correctly. Nothing depends on a list node's identity (zero `Link`s target one, zero `TreeView.unfolds` entries name one). The only payload a container carries is `orderedList`/`startIndex`.
- **First proposal — overbuilt**: <a name='id/BlockNode:00CE32GXH000H' class='aperas-anchor aperas-id'></a> drop `list` entirely, put `ordered`/`startIndex` on every item unconditionally, migrate via a splice-fixpoint. Motivated by a hypothesized "one parent, two lists, one prop slot" collision.
  
  - Corrected on inspection of `astParser.ts`'s actual adoption logic (§8): <a name='id/BlockNode:00CE32GXH000J' class='aperas-anchor aperas-id'></a> `adoptionAnchor` resets to `null` after *every* list, adopted or orphaned — specifically to stop "two lists directly adjacent... incorrectly merg[ing] into a single adoption target, corrupting whichever `orderedList`/`startIndex` was set first" (the code's own comment, verbatim). A second list under the same parent either adopts into a different, later anchor, or becomes its own separate orphaned node — never a bare run merged with the first. The hypothesized collision doesn't occur for consumption/self-dissolution; per-item props would have solved a problem that can't happen there.
- **The consumption/dissolution distinction, surfaced by a concrete counter-example**: <a name='id/BlockNode:00CE32GXH000K' class='aperas-anchor aperas-id'></a> `# H1 / > Blockquote / paragraph text / - item1 / - item2` — traced through `convertChildren`: the paragraph sits at index 1 (blockquote is first), so it's a real emitted node, and the list adopts *into* it (`H1 { Blockquote, paragraph { item1, item2 } }`), not flattened up to be siblings of the paragraph. Confirmed the same shape live in this very conversation: a reply's own "(a)/(b)" list, immediately following a colon-terminated lead-in paragraph two paragraphs below an unrelated one, parses (by the same rule a human reader applies) as children of the *nearest* paragraph, not the more distant one.
  
  - Checked whether this nesting is even visible in projected markdown: <a name='id/BlockNode:00CE32GXH000M' class='aperas-anchor aperas-id'></a> it isn't — `project.ts`'s `paragraph` case adds no indentation for adopted children, so consumption and dissolution render byte-identical. The difference is purely graph shape, invisible in the `.md` file — same as the container question itself.
  - But graph shape isn't cosmetic here: <a name='id/BlockNode:00CE32GXH000N' class='aperas-anchor aperas-id'></a> [design/treeview.md](../design/treeview.md#id/BlockNode:00CE1GW4YG006)'s own fold rule cascades through a node's structural children. Whichever node genuinely owns a list's items is the node whose fold/unfold reaches them — so nesting depth has real behavioral consequences even though it's invisible on disk.
- **Settled**: <a name='id/BlockNode:00CE32GXH000P' class='aperas-anchor aperas-id'></a> consumption is correct as designed — it matches ordinary reading comprehension, not an accident to flatten away. The only remaining gap is the no-anchor-at-all case, and even that should dissolve rather than stay wrapped — see Settled, above.
- **A third live mistake, while writing this very entry**: <a name='id/BlockNode:00CE32GXH000Q' class='aperas-anchor aperas-id'></a> piping plain text with no leading `- ` marker into a list-target `insert` parsed as a bare `paragraph`, not a `listItem` — breaking the run in two instead of extending it (verified via the actual projected output: the new entry rendered with no bullet, no indentation, as a stray paragraph between two list runs). Recovered the same two-step way as a wrongly-created nested list: create, promote the real item out via `insert <item-id> --after <sibling>`, tombstone the wrapper.

- **Migration debugging, three real bugs found and fixed along the way**: <a name='id/BlockNode:00CE5EHVXR001' class='aperas-anchor aperas-id'></a> none of the three were design errors — each surfaced only once the migration script actually ran against the real corpus, not a synthetic sample.
  
  - Ordering bug: <a name='id/BlockNode:00CE5EHVXR002' class='aperas-anchor aperas-id'></a> relocating the 48 legacy anchors' props (Part B) after fixpoint-splicing the 59 orphaned lists (Part A) let Part A write a *fresh* `orderedList` onto a listItem that also happened to be one of the 48 — Part B then misread that fresh value as stale legacy data and tried to relocate it a second time, onto a nonexistent child. Fixed by running Part B first, snapshotting all 48 values upfront before any writes (a listItem anchor's own first child can itself be another one of the 48 — a nested adoption — so reads and writes had to be fully decoupled, not just reordered).
  - Stale-tombstone-as-items[0] bug: <a name='id/BlockNode:00CE5EHVXR003' class='aperas-anchor aperas-id'></a> a list nested inside another live list (a pre-existing wart from an earlier `aperas insert <list-id>` mistake) can, once *its own* nested list resolves in an earlier fixpoint pass, be left holding an already-tombstoned marker among its own `children`. Left unfiltered, that dead marker could land at `items[0]` and silently take the run-leader prop meant for a real item — found live via `issues/packaging.md`'s "Resolved" list, a genuine 3-deep chain of exactly this wart. Fixed by filtering tombstoned entries out of `items` before processing.
  - Contaminated-baseline bug (methodology, not code): <a name='id/BlockNode:00CE5EHVXR004' class='aperas-anchor aperas-id'></a> the migration script's own "before" snapshot was computed by re-projecting the *not-yet-migrated* graph through the *already-updated* `project.ts` — which reads props from each run's own first item, a place not-yet-migrated data doesn't have them yet. That's not a valid baseline; it's exactly the inconsistency the migration exists to fix. Corrected to read the real checked-in files off disk as "before," `project.ts`'s new code only ever applied to the "after" snapshot.
- **The one accepted exception, traced to its root**: <a name='id/BlockNode:00CE5EHVXR005' class='aperas-anchor aperas-id'></a> `issues/packaging.md`'s "## Pending Tasks" holds a 4-level-deep chain of `list` wrapper nodes that are entirely dead — every real listItem/paragraph inside was tombstoned individually over time as those tasks were resolved (and re-stated more clearly in "## Resolved"), but the empty wrapper shells were never cleaned up. The old renderer's `renderChildren` returns `''` for a genuinely empty list, but `.join('\n\n')`-ing two such `''`-rendering siblings manufactures a real blank line out of nothing, compounding through each level of nesting into 5 spurious blank lines before `## Resolved`. Confirmed via full-chain inspection (`BlockNode.jsonld` reads at every level) and reproduced by hand-tracing `renderChildren`'s recursion. The migration correctly tombstones the whole dead chain with nothing live left in it, so it renders as truly empty — a strict improvement, no visible content changed, approved by the user before letting the migration's diff-gate through for this one file.
- **Inserting a list item always spawns a fresh run-leader**: <a name='id/BlockNode:00CE5EHVXR008' class='aperas-anchor aperas-id'></a> see [Open Issues](../issues/list-consumption.md#id/BlockNode:00CE32GRZG002) — live-tested while writing this same Resolved section. A freshly `aperas insert`-ed bullet always parses as its own orphaned one-item list, so it gets its own explicit `orderedList`/`startIndex` per the normalization rule — marking it a run-leader relative to whatever precedes it, even an ordinary continuation of the identical list. Renders with a spurious blank line before it; not corruption (bullet type and numbering stay correct), but a real regression from the old anchor-owns-it model, where a freshly inserted item carried no prop of its own. Confirmed live twice more since: pushing a list's full corrected content instead of a bare `--after` insert avoids it, since the new item joins the same parsed run as a continuation rather than becoming its own orphaned list. **Resolved**: `kg:insert` (`kgInsert.ts`) now looks at the sibling landing immediately before the new item — for a bare `--after`, that sibling itself; for `--before`/append, whatever's already adjacent — and if it's a plain `listItem` carrying no `orderedList`/`startIndex` of its own (an ordinary continuation), strips the freshly-parsed item's own copy of those props before writing, so it silently joins that run instead of starting a spurious new one. Scoped deliberately to that one confirmed-live shape — landing right before an existing run's own leader is a different case (the new item would need to *take over* the leader role, not just avoid claiming one) and isn't handled.

- **GFM task-list round-trip bug, incidentally re-tested during this migration**: <a name='id/BlockNode:00CE8J339R001' class='aperas-anchor aperas-id'></a> does not reproduce — see [Open Issues](../issues/treeview.md#id/BlockNode:00CE1GW638007) for the finding itself; the bug belongs to treeview's own concern, not this design's, so it stays filed there rather than duplicated here.
