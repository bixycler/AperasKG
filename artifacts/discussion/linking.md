# Internal Linking & Addressing — Discussion

## Motivation: the syntax clash <a name='--internal-linking---addressing---discussion/---motivation--the-syntax-clash' class='aperas-anchor aperas-tree'></a>
Refactoring `documentation.md` surfaced a real bug: writing an internal cross-reference as a bare relative path with a heading segment appended (`../design/documentation.md/Context`) looks like a normal markdown link but isn't one — `documentation.md` is a file, not a folder, so no standard renderer can resolve it. The existing, already-implemented convention for this (`astParser.ts`) turned out to be `[title](<[[deep-path]]>)` — a `[[...]]`-wrapped, angle-bracket-escaped destination — which works, but is heavy: three layers of escaping stacked in one string, visible at scale in `Aperas-apeironngn-design.md`'s own self-references, which repeat full heading text as path segments.

## Considered: Obsidian and Logseq's answers <a name='--internal-linking---addressing---discussion/---considered--obsidian-and-logseq-s-answers' class='aperas-anchor aperas-tree'></a>
Both invent syntax that's never confused with a resolvable link: Obsidian's `[[Page]]`/`[[Page#^blockid]]`, Logseq's `((block-uuid))` (every block gets an id for free, since Logseq's document model is an outline). Both degrade gracefully in a plain renderer — inert bracketed text, not a link that looks clickable and 404s. Considered and set aside for now: a custom `apeiron://`-only bracket scheme would need new machinery Aperas didn't strictly need, since the trailing-address problem (not the bracket problem) turned out to be the real friction.

## The trade-off that doesn't go away <a name='--internal-linking---addressing---discussion/---the-trade-off-that-doesn-t-go-away' class='aperas-anchor aperas-tree'></a>
Two orthogonal axes were in play — syntax (does the bracket/escaping shape confuse a renderer?) and target (is the address a stable id, or a readable path?). Node-ID addressing and a custom `aperas://` URI scheme both already existed in the engine (`vocab.ts`'s `NODE_BASE`, `snowflake.ts`), so neither needed inventing. What was missing was a *target* form usable before ingestion at all: a snowflake only exists after a node is created, so hand-authoring or refactoring docs pre-ingestion has no id to reference. Slugified paths fill that gap, at the cost of breaking silently if the heading text they're derived from changes — a real trade-off, not one that picking "the right syntax" dissolves.

## Landing on standard links + injected anchors <a name='--internal-linking---addressing---discussion/---landing-on-standard-links---injected-anchors' class='aperas-anchor aperas-tree'></a>
The resolution that stuck: use plain `[title](target)` syntax throughout (no `[[...]]` wrapper needed, at least for now), splitting cross-file navigation (an ordinary relative path) from in-file addressing (a `#fragment` matched against an explicit `<a name="...">` anchor built from `slugify()`'s own output, joined by `/` per heading level). This was prototyped and validated live in `test-slugifed-path.md` before being written up as the design (see [Topology](../design/linking.md#--internal-linking---addressing/---topology)). It also produced a cleaner mental model than "two permanent addressing styles to pick between": slug-path addressing is inherently the *manual, pre-ingestion* form, and ingestion adds a node-ID anchor alongside it rather than replacing it — so an existing reference never breaks, and rename-fragility isn't something needing repair tooling at all, just an eventual cleanup once every referrer has moved off the compatibility form.

## Dropping anchor recognition entirely <a name='--internal-linking---addressing---discussion/---dropping-anchor-recognition-entirely' class='aperas-anchor aperas-tree'></a>
Planning the implementation started from assuming a hand-written tree anchor needed to be *recognized and absorbed*: detected during parsing, stashed as a prop, tied to whichever block followed it, so it could round-trip and projection could add the id-anchor alongside it without duplicating anything. That design ran into a real wall for list items specifically: raw HTML sitting between two list items as its own sibling block terminates the CommonMark list, splitting one list into two. The fix turned out to be dropping the whole absorption mechanism, not working around the split: `astParser.ts` already treats a raw `<a>` tag as an ordinary opaque leaf, and `project.ts` already re-emits any opaque leaf's text verbatim — a hand-written anchor left completely untouched round-trips today, for free, with zero new parsing code, which is exactly what these four docs' own anchors had already been proving through every prior edit in this conversation without anyone writing recognition logic for them. The only thing that's genuinely new is the id-anchor, and that's synthesized fresh at projection time regardless of what was in the source — so there was never a real reason to parse the old one at all.

## Verifying anchor placement against the real parser <a name='--internal-linking---addressing---discussion/---verifying-anchor-placement-against-the-real-parser' class='aperas-anchor aperas-tree'></a>
Dropping recognition didn't fully resolve where a *fresh* id-anchor should go, so this got checked directly against `astParser.ts`/`project.ts` rather than reasoned about in the abstract. First surprise: `<a>` isn't a CommonMark block-level HTML tag (only a fixed whitelist like `div`/`article`/`table` triggers block-level HTML — `a` isn't in it), so a standalone `<a name=...></a>` line doesn't parse as an opaque `html` node at all — it parses as an ordinary `paragraph` wrapping two inline `html` fragments. That's exactly the node type `astParser.ts`'s existing "a heading consumes its immediately-following paragraph as its own `text`" rule matches on, confirmed by actually ingesting one into a scratch artifact: it landed as the heading's `text`, which both projects *after* the title (reversing the intended order) and, when a heading already has real leading prose, would have displaced that prose into a separate child block instead of leaving it as the heading's `text`.

Appending the anchor to the *end of the heading's own line* instead — confirmed against a heading that also carries genuine leading prose — left `text` exactly as the real prose, completely unaffected; only `title` (which is the whole raw line for a heading) needed a trim of the trailing anchor markup before use. For a list item, the equivalent live check — anchor placed right after the lead-in colon, the placement from the author's own prior Logseq KG — confirmed it lands in `text` as inert literal content, doesn't confuse `collectLinkCodes` (which only matches real `link` mdast nodes, never inline HTML), and survives all the way through actual Oxigraph storage byte-for-byte, embedded quotes included, not just the pure parse/project tier.

## Distinguishing a wikilink from an ordinary anchor link <a name='--internal-linking---addressing---discussion/---distinguishing-a-wikilink-from-an-ordinary-anchor-link' class='aperas-anchor aperas-tree'></a>
Dropping the `[[...]]` wrapper for the compatible/pre-ingestion syntax raised a question the bracket form used to answer for free: given a plain relative link with a `#fragment`, how do you tell "this is meant as an internal reference" apart from an ordinary, unrelated same-page anchor link (`[jump to top](#top)`)? A scheme prefix (`aperas://...`) is never ambiguous — nothing external uses it — but a bare `#fragment` is syntactically identical either way.

The first instinct was a syntactic heuristic: a heading-derived slug always starts with at least two literal dashes (`slugify` runs on the raw `"## "` line, so the `#` markers survive as dashes), which an ordinary anchor essentially never does. But that signal doesn't exist for a list-item-derived lead-in term — `slugify("Term")` is just `"term"`, indistinguishable in shape from a plain anchor like `#installation`. Narrowing the pattern further (requiring a `/`, say) would have quietly dropped support for single-segment list-item slugs rather than actually resolving the ambiguity.

The better fix doesn't try to guess from the string's shape at all: after the existing name-token/id walk finds a *candidate* target, only accept it if that candidate actually carries a matching `class="aperas-anchor"` tag. This uses a fact already sitting in the corpus (was this block deliberately marked as an addressable target?) instead of a heuristic about what the fragment text looks like, and it matches what the anchor was for in the first place — a deliberate, hand-written marker of intent, not an incidental one. An untagged `#top` is now correctly never mistaken for a link target, regardless of whether some other block's slug happens to also read "top".

## Finding the real lead-in colon <a name='--internal-linking---addressing---discussion/---finding-the-real-lead-in-colon' class='aperas-anchor aperas-tree'></a>
The first implementation scanned raw characters for the first `:` outside a hand-tracked `**bold**` state — reasonable against a test string, wrong against the actual corpus. Live ingestion of `design/linking.md` itself surfaced two failures at once: a colon inside inline code (`` `Kind:snowflake` ``, `` `aperas://tree/...` ``) got treated as the delimiter, splicing a fresh id-anchor into the *middle* of the code span on projection; and a colon in ordinary flowing prose ("...not a second permanent form: it stays until...") produced a title that was nearly the whole paragraph, because nothing distinguished a deliberate lead-in from an incidental one deep in a real sentence.

The first fix was mechanical and uncontroversial: stop scanning raw characters and walk the block's actual parsed inline nodes instead, so `inlineCode` is structurally invisible (mirrors `collectLinkCodes`'s own inlineCode skip) and `strong`/`emphasis` are excluded by real node type rather than by counting `**` pairs.

The prose case took longer. The instinct was that a lead-in colon must be within the block's *first sentence* — real natural-language sentence-boundary detection, not more character-counting, since a period inside inline code (or an abbreviation) shouldn't end a sentence early. `mdast-util-to-nlcst` (feeding an mdast tree into an nlcst tree via a `parse-latin`/`parse-english` parser) does exactly this correctly — confirmed live, its `inlineCode` handling already treats code as an opaque `SourceNode`, never decomposed into words or punctuation. For Japanese, the equivalent parser (`parse-japanese`) turned out to be a single unmaintained 2015 release built on `kuromoji.js`, with an API that doesn't even match the `ParserConstructor` shape `mdast-util-to-nlcst` requires (that shape is `parse-latin`'s own; `parse-english`/`parse-dutch` are literal subclasses of it) — not worth building on, especially since Japanese doesn't need it: `。`/`！`/`？` are unambiguous sentence-enders there, without English's "Mr."/"e.g." ambiguity, so a direct terminator scan is correct for Japanese, not a corner cut.

Sentence-boundary detection was then tested directly against the actual failing paragraph — and failed to fix it. "The slug-path anchor is only ever a compatibility bridge, though, not a second permanent form: it stays until every referrer has itself been ingested..." parses as one single, entirely valid English sentence; the colon partway through it is a real, grammatical use of a colon *within* one sentence, and no sentence-boundary check can tell that apart from a genuine lead-in term. Every real lead-in term in the corpus (`Discussion`, `Slugified-path addressing`, `Node-ID addressing`) is short — one to a few words — which sentence structure has nothing to do with. Length turned out to be the actual discriminator, so the `mdast-util-to-nlcst`/`parse-latin`/`vfile` dependency was added and then removed again once this became clear: a length cap (word count for a space-delimited script, character count for Japanese) plus the existing code/bold exclusion, no sentence parser needed.

One more gap surfaced once ingestion was tested against real content again: an unwrapped technical string (a colon-bearing URL or `key:value` pair that just never got put in backticks) has no `inlineCode` node for the exclusion to catch, since it was never marked as code at all. Requiring a genuine lead-in colon to be followed by whitespace — true for essentially every real "Term: rest" lead-in, false for almost every such unwrapped technical string — catches most of what the structural exclusion can't, for space-delimited scripts (Japanese prose isn't space-delimited, so this check is skipped for `lang: ja`).

Best-effort throughout, not exact — see [Manual titles turned out to be the wrong fix](#--internal-linking---addressing---discussion/---manual-titles-turned-out-to-be-the-wrong-fix) for why a wrongly-detected title is corrected by editing the lead-in term itself, not by a separate override.

## Manual titles turned out to be the wrong fix <a name='--internal-linking---addressing---discussion/---manual-titles-turned-out-to-be-the-wrong-fix' class='aperas-anchor aperas-tree'></a>
Before lead-in-term extraction existed, a block with no real title had exactly one way to get one: `kg:title`, an interactive command that set `BlockNode.title` directly in the graph, decoupled from the block's own text. `reconcile.ts`'s `carryForwardFields` carried that title forward across re-ingestion, but only for a block matched by exact text equality — the moment the surrounding text changed at all, the block reconciled as removed-and-added rather than matched, and the manually-set title was silently lost, replaced by whatever the fresh parse guessed instead. This had always been true; it only became a visible problem once there was a real alternative to compare it against.

Once lead-in-term extraction existed as a deterministic, always-available function of a block's own text, `kg:title`'s fragility looked less like a feature with a rough edge and more like a whole mechanism worth dropping: an out-of-band override that only worked as long as you never touched the text around it wasn't actually more practical than editing the text itself. `kg:title` (and `carryForwardFields`'s title-carrying line) was removed outright — a title is now always a pure function of the current text, recomputed on every parse, for every block type. `kg:update` gained a compensating capability for the one block type that actually needed it: a heading's title is projected back to disk (no other block type's is), so `kg:update` now treats a piped leading heading line as the target's full new state, title included, instead of only ever touching `text`/`children` (see [History](../history/linking.md#--linking---history/---milestones)).

## Cross-artifact link staleness <a name='--internal-linking---addressing---discussion/---cross-artifact-link-staleness' class='aperas-anchor aperas-tree'></a>
Found live, not reasoned about in the abstract: `design/linking.md` gained a new heading mid-session, and `discussion/linking.md` linked to it in the same edit — but the *referring* artifact's link only resolves against whatever the *target* artifact's graph state already is at the moment the referrer itself gets ingested. Ingest them in the wrong order (or ingest only one, expecting the other to already reflect a change it doesn't yet), and the reference resolves against stale or absent content — not because anything about the reference itself was wrong, but because ingestion order and per-artifact hash-based skipping have nothing to do with each other. `kg:ingest`'s own `ingestedHash === fileHash` check exists specifically to make re-ingesting an unchanged file a no-op — exactly the case that also means "this artifact will never spontaneously notice a change somewhere else."

The first fix considered was the blunt one: always re-ingest everything, dropping the hash check entirely. Rejected immediately — it throws away the entire reason the check exists (a large corpus re-parsed on every single `kg:ingest` call, most of it for nothing) to fix a problem that only actually affects a small, identifiable set of artifacts: the ones with an unresolved reference in the first place. A targeted retry needs to know which artifacts those are without re-scanning everything — so a dangling code, instead of being logged and forgotten (the pre-existing behavior), is stashed on its own referring artifact as a `danglingRef` prop, reusing the existing generic props mechanism rather than inventing new storage. After every `kg:ingest` run's main work is done, every artifact with at least one stashed code gets that code retried against the *current* graph; a match forces exactly that one artifact through link resolution again.

Getting the "force" part right took a second pass. The obvious lever — clear `ingestedHash` so the unchanged-check no longer matches — turned out to be reaching into the wrong field: `ingestFromDisk` (`node.ts`) also reads `this.ingestedHash !== undefined` to decide `hadContent`, i.e. whether to reconcile against the artifact's existing tree or fresh-mint every block as if it had never been ingested before. Clearing the hash to dodge one check would have tripped the other, discarding every real block's identity — every existing `Link` pointing into that artifact would have gone dangling for real, the opposite of the fix. `ingestFromDisk` gained its own explicit `bypassUnchangedCheck` parameter instead, orthogonal to `hadContent`, so a forced retry still reconciles normally — the only thing that changes is that the "nothing to do" short-circuit doesn't fire.

One retry pass, not a loop to a fixed point: artifact A's own retry unblocking artifact B, whose retry then unblocks artifact C, is possible in principle but not a real pattern this corpus (or a documentation corpus in general) produces — a single sweep after the main ingestion work catches every case actually seen, and a longer chain can be revisited if one ever shows up in practice.
