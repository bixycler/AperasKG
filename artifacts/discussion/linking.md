# Internal Linking & Addressing — Discussion <a name='id/BlockNode:00CDBZ76T8001' class='aperas-anchor aperas-id'></a>

## Motivation: the syntax clash <a name='id/BlockNode:00CDBZ76T8002' class='aperas-anchor aperas-id'></a>

Refactoring [`documentation.md`](../design/documentation.md#id/BlockNode:00CDD68E80002) surfaced a real bug: writing an internal cross-reference as a bare relative path with a heading segment appended (`../design/documentation.md/Context`) looks like a normal markdown link but isn't one — `documentation.md` is a file, not a folder, so no standard renderer can resolve it. The existing, already-implemented convention for this (`astParser.ts`) turned out to be `[title](<[[deep-path]]>)` — a `[[...]]`-wrapped, angle-bracket-escaped destination — which works, but is heavy: three layers of escaping stacked in one string, visible at scale in `Aperas-apeironngn-design.md`'s own self-references, which repeat full heading text as path segments.

## Considered: Obsidian and Logseq's answers <a name='id/BlockNode:00CDBZ76TG000' class='aperas-anchor aperas-id'></a>

Both invent syntax that's never confused with a resolvable link: Obsidian's `[[Page]]`/`[[Page#^blockid]]`, Logseq's `((block-uuid))` (every block gets an id for free, since Logseq's document model is an outline). Both degrade gracefully in a plain renderer — inert bracketed text, not a link that looks clickable and 404s. Considered and set aside for now: a custom `apeiron://`-only bracket scheme would need new machinery Aperas didn't strictly need, since the trailing-address problem (not the bracket problem) turned out to be the real friction.

## The trade-off that doesn't go away <a name='id/BlockNode:00CDBZ76TG001' class='aperas-anchor aperas-id'></a>

Two orthogonal axes were in play — syntax (does the bracket/escaping shape confuse a renderer?) and target (is the address a stable id, or a readable path?). Node-ID addressing and a custom `aperas://` URI scheme both already existed in the engine (`vocab.ts`'s `NODE_BASE`, `snowflake.ts`), so neither needed inventing. What was missing was a *target* form usable before ingestion at all: a snowflake only exists after a node is created, so hand-authoring or refactoring docs pre-ingestion has no id to reference. Slugified paths fill that gap, at the cost of breaking silently if the heading text they're derived from changes — a real trade-off, not one that picking "the right syntax" dissolves.

## Landing on standard links + injected anchors <a name='id/BlockNode:00CDBZ76TG002' class='aperas-anchor aperas-id'></a>

The resolution that stuck: use plain `[title](target)` syntax throughout (no `[[...]]` wrapper needed, at least for now), splitting cross-file navigation (an ordinary relative path) from in-file addressing (a `#fragment` matched against an explicit `<a name="...">` anchor built from `slugify()`'s own output, joined by `/` per heading level). This was prototyped and validated live in `test-slugifed-path.md` before being written up as the design (see [Topology](../design/linking.md#id/BlockNode:00CDBYV4T8007)). It also produced a cleaner mental model than "two permanent addressing styles to pick between": slug-path addressing is inherently the *manual, pre-ingestion* form, and ingestion adds a node-ID anchor alongside it rather than replacing it — so an existing reference never breaks, and rename-fragility isn't something needing repair tooling at all, just an eventual cleanup once every referrer has moved off the compatibility form.

## Dropping anchor recognition entirely <a name='id/BlockNode:00CDBZ76TG003' class='aperas-anchor aperas-id'></a>

Planning the implementation started from assuming a hand-written tree anchor needed to be *recognized and absorbed*: detected during parsing, stashed as a prop, tied to whichever block followed it, so it could round-trip and projection could add the id-anchor alongside it without duplicating anything. That design ran into a real wall for list items specifically: raw HTML sitting between two list items as its own sibling block terminates the CommonMark list, splitting one list into two. The fix turned out to be dropping the whole absorption mechanism, not working around the split: `astParser.ts` already treats a raw `<a>` tag as an ordinary opaque leaf, and `project.ts` already re-emits any opaque leaf's text verbatim — a hand-written anchor left completely untouched round-trips today, for free, with zero new parsing code, which is exactly what these four docs' own anchors had already been proving through every prior edit in this conversation without anyone writing recognition logic for them. The only thing that's genuinely new is the id-anchor, and that's synthesized fresh at projection time regardless of what was in the source — so there was never a real reason to parse the old one at all.

## Verifying anchor placement against the real parser <a name='id/BlockNode:00CDBZ76TG004' class='aperas-anchor aperas-id'></a>

Dropping recognition didn't fully resolve where a *fresh* id-anchor should go, so this got checked directly against `astParser.ts`/`project.ts` rather than reasoned about in the abstract. First surprise: `<a>` isn't a CommonMark block-level HTML tag (only a fixed whitelist like `div`/`article`/`table` triggers block-level HTML — `a` isn't in it), so a standalone `<a name=...></a>` line doesn't parse as an opaque `html` node at all — it parses as an ordinary `paragraph` wrapping two inline `html` fragments. That's exactly the node type `astParser.ts`'s existing "a heading consumes its immediately-following paragraph as its own `text`" rule matches on, confirmed by actually ingesting one into a scratch artifact: it landed as the heading's `text`, which both projects *after* the title (reversing the intended order) and, when a heading already has real leading prose, would have displaced that prose into a separate child block instead of leaving it as the heading's `text`.

Appending the anchor to the *end of the heading's own line* instead — confirmed against a heading that also carries genuine leading prose — left `text` exactly as the real prose, completely unaffected; only `title` (which is the whole raw line for a heading) needed a trim of the trailing anchor markup before use. For a list item, the equivalent live check — anchor placed right after the lead-in colon, the placement from the author's own prior Logseq KG — confirmed it lands in `text` as inert literal content, doesn't confuse `collectLinkCodes` (which only matches real `link` mdast nodes, never inline HTML), and survives all the way through actual Oxigraph storage byte-for-byte, embedded quotes included, not just the pure parse/project tier.

## Distinguishing a wikilink from an ordinary anchor link <a name='id/BlockNode:00CDBZ76TG006' class='aperas-anchor aperas-id'></a>

Dropping the `[[...]]` wrapper for the compatible/pre-ingestion syntax raised a question the bracket form used to answer for free: given a plain relative link with a `#fragment`, how do you tell "this is meant as an internal reference" apart from an ordinary, unrelated same-page anchor link (`[jump to top](#top)`)? A scheme prefix (`aperas://...`) is never ambiguous — nothing external uses it — but a bare `#fragment` is syntactically identical either way.

The first instinct was a syntactic heuristic: <a name='id/BlockNode:00CDC0DA68009' class='aperas-anchor aperas-id'></a> <a name='id/BlockNode:00CDBZ76TG007' class='aperas-anchor aperas-id'></a> a heading-derived slug always starts with at least two literal dashes (`slugify` runs on the raw `"## "` line, so the `#` markers survive as dashes), which an ordinary anchor essentially never does. But that signal doesn't exist for a list-item-derived lead-in term — `slugify("Term")` is just `"term"`, indistinguishable in shape from a plain anchor like `#installation`. Narrowing the pattern further (requiring a `/`, say) would have quietly dropped support for single-segment list-item slugs rather than actually resolving the ambiguity.

The better fix doesn't try to guess from the string's shape at all: after the existing name-token/id walk finds a *candidate* target, only accept it if that candidate actually carries a matching `class="aperas-anchor"` tag. This uses a fact already sitting in the corpus (was this block deliberately marked as an addressable target?) instead of a heuristic about what the fragment text looks like, and it matches what the anchor was for in the first place — a deliberate, hand-written marker of intent, not an incidental one. An untagged `#top` is now correctly never mistaken for a link target, regardless of whether some other block's slug happens to also read "top".

## Finding the real lead-in colon <a name='id/BlockNode:00CDBZ76TR000' class='aperas-anchor aperas-id'></a>

The first implementation scanned raw characters for the first `:` outside a hand-tracked `**bold**` state — reasonable against a test string, wrong against the actual corpus. Live ingestion of `design/linking.md` itself surfaced two failures at once: a colon inside inline code (`` `Kind:snowflake` ``, `` `aperas://tree/...` ``) got treated as the delimiter, splicing a fresh id-anchor into the *middle* of the code span on projection; and a colon in ordinary flowing prose ("...not a second permanent form: it stays until...") produced a title that was nearly the whole paragraph, because nothing distinguished a deliberate lead-in from an incidental one deep in a real sentence.

The first fix was mechanical and uncontroversial: <a name='id/BlockNode:00CDC0DA6800C' class='aperas-anchor aperas-id'></a> <a name='id/BlockNode:00CDBZ76TR001' class='aperas-anchor aperas-id'></a> stop scanning raw characters and walk the block's actual parsed inline nodes instead, so `inlineCode` is structurally invisible (mirrors `collectLinkCodes`'s own inlineCode skip) and `strong`/`emphasis` are excluded by real node type rather than by counting `**` pairs.

The prose case took longer. The instinct was that a lead-in colon must be within the block's *first sentence* — real natural-language sentence-boundary detection, not more character-counting, since a period inside inline code (or an abbreviation) shouldn't end a sentence early. `mdast-util-to-nlcst` (feeding an mdast tree into an nlcst tree via a `parse-latin`/`parse-english` parser) does exactly this correctly — confirmed live, its `inlineCode` handling already treats code as an opaque `SourceNode`, never decomposed into words or punctuation. For Japanese, the equivalent parser (`parse-japanese`) turned out to be a single unmaintained 2015 release built on `kuromoji.js`, with an API that doesn't even match the `ParserConstructor` shape `mdast-util-to-nlcst` requires (that shape is `parse-latin`'s own; `parse-english`/`parse-dutch` are literal subclasses of it) — not worth building on, especially since Japanese doesn't need it: `。`/`！`/`？` are unambiguous sentence-enders there, without English's "Mr."/"e.g." ambiguity, so a direct terminator scan is correct for Japanese, not a corner cut.

Sentence-boundary detection was then tested directly against the actual failing paragraph — and failed to fix it. "The slug-path anchor is only ever a compatibility bridge, though, not a second permanent form: it stays until every referrer has itself been ingested..." parses as one single, entirely valid English sentence; the colon partway through it is a real, grammatical use of a colon *within* one sentence, and no sentence-boundary check can tell that apart from a genuine lead-in term. Every real lead-in term in the corpus (`Discussion`, `Slugified-path addressing`, `Node-ID addressing`) is short — one to a few words — which sentence structure has nothing to do with. Length turned out to be the actual discriminator, so the `mdast-util-to-nlcst`/`parse-latin`/`vfile` dependency was added and then removed again once this became clear: a length cap (word count for a space-delimited script, character count for Japanese) plus the existing code/bold exclusion, no sentence parser needed.

One more gap surfaced once ingestion was tested against real content again: an unwrapped technical string (a colon-bearing URL or `key:value` pair that just never got put in backticks) has no `inlineCode` node for the exclusion to catch, since it was never marked as code at all. Requiring a genuine lead-in colon to be followed by whitespace — true for essentially every real "Term: rest" lead-in, false for almost every such unwrapped technical string — catches most of what the structural exclusion can't, for space-delimited scripts (Japanese prose isn't space-delimited, so this check is skipped for `lang: ja`).

Best-effort throughout, not exact — see [Manual titles turned out to be the wrong fix](#id/BlockNode:00CDBZ76TR006) for why a wrongly-detected title is corrected by editing the lead-in term itself, not by a separate override.

## Manual titles turned out to be the wrong fix <a name='id/BlockNode:00CDBZ76TR006' class='aperas-anchor aperas-id'></a>

Before lead-in-term extraction existed, a block with no real title had exactly one way to get one: `kg:title`, an interactive command that set `BlockNode.title` directly in the graph, decoupled from the block's own text. `reconcile.ts`'s `carryForwardFields` carried that title forward across re-ingestion, but only for a block matched by exact text equality — the moment the surrounding text changed at all, the block reconciled as removed-and-added rather than matched, and the manually-set title was silently lost, replaced by whatever the fresh parse guessed instead. This had always been true; it only became a visible problem once there was a real alternative to compare it against.

Once lead-in-term extraction existed as a deterministic, always-available function of a block's own text, `kg:title`'s fragility looked less like a feature with a rough edge and more like a whole mechanism worth dropping: an out-of-band override that only worked as long as you never touched the text around it wasn't actually more practical than editing the text itself. `kg:title` (and `carryForwardFields`'s title-carrying line) was removed outright — a title is now always a pure function of the current text, recomputed on every parse, for every block type. `kg:update` gained a compensating capability for the one block type that actually needed it: a heading's title is projected back to disk (no other block type's is), so `kg:update` now treats a piped leading heading line as the target's full new state, title included, instead of only ever touching `text`/`children` (see [History](../history/linking.md#id/BlockNode:00CDBZ7698003)).

## Cross-artifact link staleness <a name='id/BlockNode:00CDBZ76TR008' class='aperas-anchor aperas-id'></a>

Found live, not reasoned about in the abstract: `design/linking.md` gained a new heading mid-session, and `discussion/linking.md` linked to it in the same edit — but the *referring* artifact's link only resolves against whatever the *target* artifact's graph state already is at the moment the referrer itself gets ingested. Ingest them in the wrong order (or ingest only one, expecting the other to already reflect a change it doesn't yet), and the reference resolves against stale or absent content — not because anything about the reference itself was wrong, but because ingestion order and per-artifact hash-based skipping have nothing to do with each other. `kg:ingest`'s own `ingestedHash === fileHash` check exists specifically to make re-ingesting an unchanged file a no-op — exactly the case that also means "this artifact will never spontaneously notice a change somewhere else."

The first fix considered was the blunt one: <a name='id/BlockNode:00CDC0DA80005' class='aperas-anchor aperas-id'></a> <a name='id/BlockNode:00CDBZ76TR009' class='aperas-anchor aperas-id'></a> always re-ingest everything, dropping the hash check entirely. Rejected immediately — it throws away the entire reason the check exists (a large corpus re-parsed on every single `kg:ingest` call, most of it for nothing) to fix a problem that only actually affects a small, identifiable set of artifacts: the ones with an unresolved reference in the first place. A targeted retry needs to know which artifacts those are without re-scanning everything — so a dangling code, instead of being logged and forgotten (the pre-existing behavior), is stashed on its own referring artifact as a `danglingRef` prop, reusing the existing generic props mechanism rather than inventing new storage. After every `kg:ingest` run's main work is done, every artifact with at least one stashed code gets that code retried against the *current* graph; a match forces exactly that one artifact through link resolution again.

Getting the "force" part right took a second pass. The obvious lever — clear `ingestedHash` so the unchanged-check no longer matches — turned out to be reaching into the wrong field: `ingestFromDisk` (`node.ts`) also reads `this.ingestedHash !== undefined` to decide `hadContent`, i.e. whether to reconcile against the artifact's existing tree or fresh-mint every block as if it had never been ingested before. Clearing the hash to dodge one check would have tripped the other, discarding every real block's identity — every existing `Link` pointing into that artifact would have gone dangling for real, the opposite of the fix. `ingestFromDisk` gained its own explicit `bypassUnchangedCheck` parameter instead, orthogonal to `hadContent`, so a forced retry still reconciles normally — the only thing that changes is that the "nothing to do" short-circuit doesn't fire.

One retry pass, not a loop to a fixed point: <a name='id/BlockNode:00CDC0DA80007' class='aperas-anchor aperas-id'></a> <a name='id/BlockNode:00CDBZ76TR00B' class='aperas-anchor aperas-id'></a> artifact A's own retry unblocking artifact B, whose retry then unblocks artifact C, is possible in principle but not a real pattern this corpus (or a documentation corpus in general) produces — a single sweep after the main ingestion work catches every case actually seen, and a longer chain can be revisited if one ever shows up in practice.

## A bare snowflake isn't a full node id <a name='id/BlockNode:00CDBZ76TR00C' class='aperas-anchor aperas-id'></a>

Landing the full-slug-path collision check (`apeironNgn/node.ts`'s `rejectSlugPathCollisions`) meant comparing a freshly-parsed block's own id against whatever a live scan of the store said already owned a given path — and every single reconciled (matched, unchanged) block came back as "colliding with itself." `ParsedBlockNode.blockId` (`generateNodeId()`'s own return) is a bare snowflake, e.g. `00CD9FZQP0001`; `allIdsOfKind`'s ids, and every live node's own `.id`, are always the full `Kind:snowflake` form, e.g. `BlockNode:00CD9FZQP0001`. The self-exclusion check (`liveOwner !== node.blockId`) was comparing these two different formats directly — never equal, even for the exact same node — so `reconcileTree`'s own carried-forward id (real, correct, unchanged) always failed the comparison. Fixed by prefixing `node.blockId` with `BlockNode:` before comparing (every node this check walks is a `BlockNode` by construction). Caught immediately by `verify.ts`'s own pre-existing steps 1-12 failing the moment this landed — a good sign the new check was wired into a real ingestion path, not a sign anything about steps 1-12 themselves was wrong.

A second, unrelated mistake surfaced writing the new `verify.ts` steps for this same landing: a bare `listItem` has no `serializeBlock` case of its own — `serializeListItem` (the function that actually applies the `- `/checkbox prefix and splices the id-anchor) is only ever invoked by the *parent*'s own `renderChildren`, when it detects a run of `listItem` children. Calling `.toMarkdown()` directly on a list item block hits `serializeBlock`'s generic container fallback instead, rendering only *its own* children (empty, for a leaf item) — silently returning `''`, not the list item's own line. The fix was in the test, not the production code: project the *parent* heading and check for the spliced anchor within that larger string.

## A colon at the very end of its own text node <a name='id/BlockNode:00CDBZ76TR00E' class='aperas-anchor aperas-id'></a>

Live re-ingestion of this very concern's own draft plan (`planning/linking.md`'s Slice 2 write-up) surfaced a second refinement to the same [lead-in colon detection](#id/BlockNode:00CDBZ76TR000): `- **Heading**:` immediately followed only by nested list items — no inline "rest of text" on the same line — got no title at all, falling back to the raw block id. The space-after-colon check (added to catch an unwrapped technical string like a bare URL or `key:value` pair) was reading the wrong string: it looked at the next character within the current mdast *text node's own* `.value`, not the real document. `**Heading**:` parses as a `strong` node followed by a separate, one-character `text` node holding just `":"` — that text node's own value simply ends there; the real file's next character (a newline, before the nested list begins) was never captured in it to begin with. The check saw "nothing left in this string" and treated it exactly like a genuinely ambiguous no-space case, when nothing suspicious was actually adjacent to the colon at all — there was just nothing left to look at.

The fix: <a name='id/BlockNode:00CDC0DA8000B' class='aperas-anchor aperas-id'></a> <a name='id/BlockNode:00CDBZ76TR00F' class='aperas-anchor aperas-id'></a> treat "nothing left in this text run" as satisfying the space-after-colon check, the same as an actual space. This doesn't touch the two guards that already run first and stay exactly as strict as before — a colon inside `inlineCode`/`code` is still never a candidate at all, and a colon inside `strong`/`emphasis` still never qualifies — only a colon that's already passed both of those is affected. Accepted as a known, deliberate side effect: a colon immediately followed by a *different* inline node with no space (`` note:**bold** ``) now also passes, since that colon's own text run ends the same way a genuinely-safe one does. Not treated as a real regression — matches the feature's existing best-effort, user-correctable philosophy ([Manual titles turned out to be the wrong fix](#id/BlockNode:00CDBZ76TR006)) rather than staying maximally strict at the cost of a real, common case — a lead-in immediately followed by nested children, the exact shape this concern's own docs use throughout — going untitled.

## A multi-artifact kg:ingest isn't transactional <a name='id/BlockNode:00CDCTB49R001' class='aperas-anchor aperas-id'></a>

Found live, not reasoned about in the abstract: ingesting `design/linking.md issues/linking.md history/linking.md discussion/linking.md planning/linking.md` in one `kg:ingest` call failed on the third path (`history/linking.md`'s duplicate-date collision), and the CLI reported the whole call as failed — but `design/linking.md` and `issues/linking.md`, processed earlier in the same loop, had already been fully ingested into the live in-memory `Store` by the time the failure surfaced. `ingestArtifacts`/`ingestAllArtifacts` (`apeironNgn/artifacts.ts`) loop over paths calling `ingestArtifact` per file with no `try`/`catch` around each iteration; nothing rolls back what an earlier iteration already committed when a later one throws. This is a lack of transaction semantics, not a one-off bug — the same shape of gap would apply to any batched multi-step write, `kg:insert`/`kg:update` sequences included, not just `kg:ingest`. Promoted to [issues/core.md's Open Issues](../issues/core.md#id/BlockNode:00CF1WZ4JG008).

The failure was only discovered indirectly: <a name='id/BlockNode:00CDCTB4A0000' class='aperas-anchor aperas-id'></a> a *later*, corrected re-run reported "Tracked 1, skipped 4 unchanged" instead of "Tracked 5" — the only sign that two of the five files had already been silently, partially processed by the earlier failed attempt. The pending `--flush` for that failed call never ran, so none of that partial progress reached disk that time — but it existed in the service's memory regardless, invisible until a later command exposed it.

The real risk, specifically for the graph-first editing direction (edit via `kg:insert`/`kg:update`, then `kg:project`): a scripted multi-step sequence that fails partway leaves the live graph ahead of disk in a way that's easy to miss, and a service restart before noticing would silently discard that in-memory-only progress with no error at all. Worth treating "the command reported failure" as "go check what state things are actually in," not "nothing happened."

**Status: identified, not yet implemented.** No fix landed this pass — recorded here first, per the deliberate policy going forward to document a gap like this before touching code. A real fix would need `ingestArtifacts`/`ingestAllArtifacts` to either stop after the first failure and report exactly which paths already committed (least invasive), or gain real transactional semantics across a whole batch (bigger, would need every mutation this session has relied on — `hydrateFromParsed`, `applyTombstone`, `resolveBlockLinks` — to be stageable and revocable, not just applied directly).

## `kg:update`/`kg:insert` never resolve wikilinks — a correctness bug in this concern's own mechanism, found and fixed elsewhere <a name='id/BlockNode:00CF1276D0001' class='aperas-anchor aperas-id'></a>

[Discussion — Packaging](../discussion/packaging.md#id/BlockNode:00CDG18FP0003) found and fixed a real defect in exactly this concern's [own resolution mechanism](../design/linking.md#id/BlockNode:00CDBYV4T8002): `resolveBlockLinks` only ever ran from `ingestArtifact` (the `kg:ingest`/disk-first path), so any block reconciled as "changed" or "added" via `kg:update`/`kg:insert` picked up no link resolution at all — silently, with no error. Neither this doc set's own issues nor history mention it; it was found while chasing a `packaging.md` retitle accident, not while working on linking directly. Worth knowing this concern's addressing/resolution design has a fix living in another concern's discussion doc, not its own.

## `aperas update` never re-derives a non-heading block's title <a name='id/BlockNode:00CGF83D4G001' class='aperas-anchor aperas-id'></a>

Found live [while rewriting Topology for the skill's v2](../discussion/aperas-skill.md#id/BlockNode:00CGF35FNG001): `aperas update` replaced a paragraph's `.text` correctly and left `.title` frozen at the value ingest had derived, so the node went on rendering under a title stating the very rule its new text had just retired. Re-running the update with a deliberately short lead-in term, well inside `extractLeadInTitle`'s heuristics, changed nothing; an `insert` of a sibling paragraph minutes later derived its title from the lead-in correctly, so the defect is in `update`'s path rather than in parsing. Promoted to [issues/linking.md's Open Issues](../issues/linking.md#id/BlockNode:00CGFE4SV0002).

[The `kg:title` removal](../history/linking.md#id/BlockNode:00CDBZ769800B) left the lead-in term as the one and only title mechanism for every block type, and gave `kg:update` a compensating path for heading targets only — a heading being the one block type whose title is projected back to disk. That reasoning holds for the projection: the paragraph's rendered markdown is correct and the stale title is invisible on disk. It does not hold for the graph, where `tree`, `unfold` and `backlinks --text` all display the title and nothing marks it stale, so the block reads as saying one thing in preview and another in full.

`reconcile.ts`'s `carryForwardFields` carries a title forward only when the block's text matches exactly, which should have left a changed paragraph with no title rather than the old one — so this is likely `update`'s own field handling, not the reconcile rule. The summary line reports `0 changed` and says nothing about the title either way, which is the usual silent shape. Not yet traced to the specific call, and there is no CLI route to repair an already-stale title short of tombstoning the block.

**Root cause confirmed, and it is worse than stale titles**: <a name='id/BlockNode:00CGGA9J68000' class='aperas-anchor aperas-id'></a> `runUpdate` (`kgUpdate.ts`) only ever assigns its local `title` variable inside the `target.type === 'heading' && firstChild?.type === 'heading'` branch — for any other target (a plain paragraph/listItem), `title` stays `undefined` for the whole function, so `newShape.title = title ?? target.title` carries the *old* title forward unconditionally. It is not that the freshly-parsed title is wrong or discarded after computation — it is never read at all for a non-heading target, regardless of this session's lead-in-cap fix or anything else in `astParser.ts`.

**Caught live, the expensive way**: <a name='id/BlockNode:00CGGA9J68001' class='aperas-anchor aperas-id'></a> verifying that fix by re-pushing `aperas update <id>` with the node's own `--text` output (assumed to be "the complete content," since `--text` is documented as the exact stored value) tombstoned 4 real nested children on `BlockNode:00CG9MDJF0001` — `--text` shows only a node's own leading text, never its children, and a non-`--text-only` `update` reconciles the piped input's (empty) overflow against the target's *real* existing children. `0 matched, 0 added, 4 removed`, not caught by the summary line alone, only by then noticing the title still hadn't updated and rechecking. Recovered via `git restore` on the staged `AperasKG/Apeiron/*.jsonld` mirror (pre-accident, from this session's own prior stage) plus `aperas reload -- --discard`; all 4 original ids verified live afterward, no data lost.

This is the same shape as *Preserve identity*'s already-documented parent-heading case — an `update` reconciling children as a side effect of an operation that reads as "just fixing the text" — except the operator here isn't even a heading, and the tell (children present at all) is invisible from `--text` output alone. `--children` needs checking before `update` on *any* target, not only a heading.

- **Two approved engine fixes, plus a graph-repair sweep, following the v2 skill review**: <a name='id/BlockNode:00CGG7BN40001' class='aperas-anchor aperas-id'></a> (1) `astParser.ts` never stripped an inline `aperas-anchor` tag before storing a paragraph/listItem's `text` — `stripInlineAnchors` only ran at *comparison* sites (`reconcile.ts`'s `leafKey`, rename matching), never at the one place `block.text = text` is actually set. Copying an already-projected file's content back through `update`/`insert` therefore baked the anchor into stored text permanently, even though `hasIdAnchor`'s idempotency check kept the *rendered* output looking unchanged.
