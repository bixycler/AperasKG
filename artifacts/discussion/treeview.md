- **Root-cause brainstorm: eliminating the opaque `list` container**: <a name='id/BlockNode:00CE1VPWWR002' class='aperas-anchor aperas-id'></a> surveyed the live graph before proposing anything. The container turns out to be both removable and already half-removed — but the deeper hazard is *where list-level metadata lives*, not the extra node.
  
  - Live survey: <a name='id/BlockNode:00CE1VPWWR003' class='aperas-anchor aperas-id'></a> 54 `list` nodes vs. 307 `listItem`s, and **159 items (52%) already have no `list` parent at all** — parented directly by a heading (53), another listItem (48), a paragraph (36), or an artifact (22). All of it projects correctly today.
  - Nothing depends on a list node's identity: <a name='id/BlockNode:00CE1VPWWR004' class='aperas-anchor aperas-id'></a> zero `Link`s target one, zero `TreeView.unfolds` entries name one. The only props a container carries are `orderedList` and `startIndex`.
  - **Three shapes coexist in the graph right now**: <a name='id/BlockNode:00CE1VPWWR005' class='aperas-anchor aperas-id'></a> (1) `heading -> list(props) -> items`, what the current parser emits; (2) `heading(props) -> items` — container consumed, its props absorbed by the heading (`design/documentation.md`'s Architecture section: the heading itself carries `orderedList: true`/`startIndex: 1`, its items carry none, and it still projects as a correct `1. 2. 3.` list); (3) `parent -> items(props)` — 9 items carrying the props themselves. The projector renders all three correctly, which is the strongest evidence the container is not load-bearing.
  - So heading-consumption of a list is **not a feature to build** — shape (2) proves some path already does it, including relocating the list's props onto the consumer. The real defect is that different paths disagree, leaving "where do I read ordered-ness from?" with three answers.
  - **Proposed model**: <a name='id/BlockNode:00CE1VPWX0000' class='aperas-anchor aperas-id'></a> drop `list` entirely; list-ness becomes a property of the *item*. Each `listItem` carries `ordered`; the first item of a run carries `startIndex`. Projection regroups adjacent sibling items sharing `ordered` into one markdown list — exactly how CommonMark itself recovers grouping from flat text. Nested lists become `listItem -> listItem` directly, already the live shape in 48 cases.
  - **Why props go on items, not on the consuming parent** (shape 2's approach): one parent can host two distinct lists separated by a paragraph — a bullet list, prose, then a numbered list. A single prop slot on the parent cannot describe both; per-item flags can, since each run carries its own. Shape (2) only looks adequate because the sections exercising it happen to contain exactly one list each.
  - **What this fixes at the root**: <a name='id/BlockNode:00CE1VPWX0002' class='aperas-anchor aperas-id'></a> the pending "let `List` be consumed by `Heading`" task dissolves into it; `insert`/`update` can no longer produce a nested-list wart, since there is no container to target and a piped `- item` unwraps on parse; `--after`/`--before` stops needing the "a heading's text and its list are two different levels" caveat; and deep items become directly insertable/movable **without re-sending a whole section**, which is the requirement that rules out the parent-heading workaround once the freeflow tree grows.
  - **Migration as a fixpoint**: <a name='id/BlockNode:00CE1VPWX0003' class='aperas-anchor aperas-id'></a> repeatedly splice every `list` node's children into its parent at the list's own position until none remain — this self-heals the 11 existing `list`-inside-`list` warts as a side effect, and preserves every item id (only the containers' own unreferenced ids are dropped). Shape (2)'s props-on-the-parent then normalize down onto the items.
  - **Verification gate**: <a name='id/BlockNode:00CE1VPWX0004' class='aperas-anchor aperas-id'></a> project every tracked artifact before and after, and diff. Expected byte-identical, since adjacency reproduces the grouping; a non-empty diff names exactly where the container was actually load-bearing. Cheap, and a genuine proof rather than a spot-check.
  - Not yet checked: <a name='id/BlockNode:00CE1VPWX0005' class='aperas-anchor aperas-id'></a> whether the serializer's existing regrouping covers every containerless case or only the ones live data happens to exercise. Marker char (`-`/`*`/`+`) is already not stored, so two adjacent same-orderedness lists distinguished only by marker already cannot round-trip — not a regression this introduces.
- **Superseded: promoted to a dedicated `list-consumption` concern**: <a name='id/BlockNode:00CE315NGG002' class='aperas-anchor aperas-id'></a> the brainstorm above (eliminating the opaque `list` container) turned out to be both narrower and deeper than first framed — narrower because most of it was already shipped (§8's adoption/dissolution), deeper because the real subject is a single unifying law ("a list attaches to whatever most immediately precedes it, textually — a separate node if one exists, or the container's own merged identity once its leading paragraph is consumed into it, per §2") that the code already implements correctly but nowhere states as one rule, plus one genuine remaining gap (an orphaned list — nothing precedes it at all, not even a merged self — should also dissolve, not stay wrapped, which in turn requires moving `orderedList`/`startIndex` from the enclosing node to each run's own first item, since one parent can host more than one orphaned run). This is core to how Apeiron maps markdown onto its unbounded tree, not specific to `treeview` — see `list-consumption`'s own doc set for the full analysis and the settled law.

- **`aperas unfold`'s raw preview omits the tombstone tag `aperas tree --view` shows**: <a name='id/BlockNode:00CE8T49MR001' class='aperas-anchor aperas-id'></a> found live while investigating a cross-linking question in `list-consumption` — `aperas unfold BlockNode:00CE1GW638002 --view <name>` printed two children (00CE5QD6W8001, 00CE1GW638003) with no marker distinguishing them from live siblings, read as stray/anomalous at first. Re-running `aperas tree BlockNode:00CE1GW638002 --view <name>` on the identical, already-unfolded subtree appended a plain `(tombstoned)` suffix to those same two lines — confirming both commands know the node is tombstoned, but only `tree` surfaces it. **Proposed fix — don't just add the tag to `unfold`; hide tombstoned nodes from default output entirely, in both commands**, revealed only via an explicit `--tombstoned` flag. A tombstoned node is dead data retained solely for id-stability; showing it unmarked in a raw exploratory listing invites exactly the misreading that happened here. See [Issues](../issues/treeview.md#id/BlockNode:00CE8T6W7G001) for the tracked gap.
