- **`flush --clobber` / `reload --discard` round-trip mechanics, startup GC, and shutdown logging design**: <a name='id/BlockNode:00CGR1F620001' class='aperas-anchor aperas-id'></a> investigated `reload --discard` and `flush --clobber` interaction, live, at the user's own request after a `flush --clobber` unexpectedly removed a real backlog. - **`aperas retype` — an identity-preserving block type-conversion channel, for refactoring/migration only**: <a name='id/BlockNode:00CJ4H44J8001' class='aperas-anchor aperas-id'></a> agreed, built and verified 2026-09-17; the entries below are this design's own working record, in the order it actually went. Today a block's `type` is pinned everywhere a write could touch it: `kgUpdate.ts` builds both its `--text-only` and reconcile shapes with `type: target.type`, so a piped input's own type is never adopted; `reconcileTree` could not pair the two sides anyway, since containers match partitioned `byType` (a `listItem` and a `heading` land in different buckets and never meet) and leaves match on `leafKey`, which keys a heading on `.title` and a paragraph on `.text` — unequal by construction, in the cross-parent salvage stage too. `kg:update` separately refuses a heading depth change outright (`oldDepth !== newDepth` throws). Each guard is correct on its own: an ordinary edit must never silently restructure. Together they leave no in-place route at all, so the only way to change a block's type today is `remove` + `insert`, which tombstones the id and every citation pointing at it — precisely what *Preserve identity* exists to prevent.
  
  - The data model has no objection: <a name='id/BlockNode:00CJ4H44J8002' class='aperas-anchor aperas-id'></a> `reconcile.ts`'s `carryForwardFields` carries `blockId` and `links` onto the **new** node and pointedly does *not* carry `type`, so "same identity, different type" is already expressible. Only the CLI pin and the matcher stand in the way, which is what makes this a narrow addition rather than an architectural one.
  - **Shape**: <a name='id/BlockNode:00CJ4H44J8003' class='aperas-anchor aperas-id'></a> `aperas retype <ref> --to <type>`, where `<type>` is `h1`..`h6` (heading, depth carried in the type itself) or any non-heading block type (`paragraph`, `listItem`, `code`, `blockquote`, …). Heading depth change is therefore the same operation as any other conversion (`h2` → `h3`), not a special case — one verb covers both pinned structural fields. Preserves id, `links`, children, parent and position; `.text` is never touched. Title is re-derived for the new type: an `h*` target rebuilds the heading line at the requested depth from the node's existing title words; a non-heading target re-derives via the ordinary lead-in-term rule.
  - **Deliberately type-only, not a content channel**: <a name='id/BlockNode:00CJ4H44J8004' class='aperas-anchor aperas-id'></a> changing a block's text stays `aperas update`'s job, run separately afterwards. The cost is a real one to design around — converting a heading away from `heading` re-derives its title from `.text`, which for a heading is its *body* (the consumed leading paragraph) and normally carries no lead-in term, so the title falls back to the raw block id and the heading's own words survive only in whatever the operator captured first. The verb must therefore report the outgoing title in its own result line, and warn when a conversion is about to leave a node titled by id fallback, so a migration can compose the follow-up `update --text-only` from it rather than recovering it from `git`.
  - **Automatic title migration across the heading boundary, built in rather than left to a manual follow-up**: <a name='id/BlockNode:00CJ4XG0RG001' class='aperas-anchor aperas-id'></a> reconsidered from the item above — a heading and a non-heading store their title in genuinely different places (a field vs. a lead-in folded into `.text`), so crossing that boundary now migrates the title *with* the type, in whichever direction applies. Heading → non-heading folds the heading's own words into `.text` as a canonical `**words**: <body>` lead-in — the always-uncapped shape, since the whole span before the colon sits inside one bold node — then derives the new title from that text via the real parser, not a hand-built guess. Non-heading → heading does the exact inverse: cuts the existing lead-in back out using `findLeadInSpliceOffset` (`astParser.ts`), the identical colon `project.ts`'s own anchor splice already relies on, so the cut lands exactly where the title was actually derived from. Verified live on the corpus's hardest real case (`kg:update`/`kg:insert` never resolve wikilinks — a title with embedded backtick colons and an em-dash): converts to a `listItem` with both links intact, and converting back reproduces the original title and text byte-for-byte. A depth-only heading change (`h2` → `h3`) and a non-heading → non-heading retype still never touch `.text` at all — only actually crossing the boundary does. The one remaining gap is a lead-in that isn't a single, fully-bold span, or missing entirely: that degrades to the old id-fallback behavior, `.text` left alone, `untitled` reported — the same graceful failure the parser already uses everywhere else.
  - **Props**: <a name='id/BlockNode:00CJ4H44J8005' class='aperas-anchor aperas-id'></a> a type-specific prop is meaningless on the new type (a heading's `treeAnchor`; a `listItem`'s `orderedList`/`startIndex`/`checked`), so a conversion drops the ones belonging to the old type rather than carrying stale state forward. Not a concern for the migration that motivated this — none of the 16 nodes involved carries an anchor prop — but it is the kind of leftover that turns into a rendering bug later.
  - **Motivating case**: <a name='id/BlockNode:00CJ4H44J8006' class='aperas-anchor aperas-id'></a> [discussion/linking.md's Freeflow](../discussion/linking.md#id/BlockNode:00CJ37GPRR009) holds 16 `##` headings that were moved under a `## Freeflow` heading, which markdown cannot nest — re-parsed from its own projection that section has zero children and all 16 read as siblings. Converting them to lead-in-term `listItem`s is what makes the grouping structural rather than only intended, since list items nest by indentation with no H6 ceiling — the same argument [issues/linking.md's "Heading-in-list"](../issues/linking.md#id/BlockNode:00CDBYV5A800C) already settled for titles. - **Frontmatter-backed `description` replaces the abstract dupe, 2026-09-20**: <a name='id/BlockNode:00CKE4FFF0001' class='aperas-anchor aperas-id'></a> found while chasing why a `../discussion/linking.md` link inside `linking.md`'s own `**Discussion**:` line still rendered `inline-link-inert` in a folder listing, even after the bare-relative-path resolver fix and the `bakeResolvedLinkIds` render-time fix ([history/linking.md](../history/linking.md#id/BlockNode:00CJAVGNJG001), [history/webapp.md](../history/webapp.md#id/BlockNode:00CJAVRF90001), both 2026-09-18) were verified working for the direct case. Root cause: a folder/artifact listing's abstract reads `ArtifactNode`/`FolderNode.text`, which is a *copy* of the first content-bearing descendant's text (`extractAbstract`), made once at hydration time — the descendant's own `Link` (confirmed already correctly resolved via `aperas show`) is never duplicated onto the container, so `bakeResolvedLinkIds(node.text, node.links)` finds `node.links` empty and has nothing to bake with. A narrower fix was considered first: a persisted `abstractSourceId` pointer riding alongside the existing `.text` copy, set at the same hydration moment, so render time could cheaply look up the real source's links. That fell apart on one question: how does the copy get refreshed when a descendant changes? Checked directly against `kgUpdate.ts` — it doesn't. `target.text = text` there never touches an ancestor's own `.text`; only a full re-hydration (`hydrateFromParsed`) or the one-time holder-promotion path (`kgProject.ts`) ever recomputes it. So the abstract is a stale-until-next-full-reingest snapshot *by design* — a reasonable feature when the main direction was ingestion (Phase 0: capture whatever's on disk), but a flaw now that the main direction is projection/live editing: once captured, it's stuck there forever, and a pointer riding on top of a frozen copy would only add a second thing that's frozen alongside it, not fix the freezing. Chosen direction instead: retire the copy-and-heuristic mechanism (`extractAbstract`/`deriveAbstractFromLiveChildren`) for `ArtifactNode`/`FolderNode` entirely. Give both a real, directly-authored `description` field living in the artifact/folder's own YAML frontmatter — already parsed out separately by `astParser.ts` via `remark-frontmatter`, but today kept fully opaque past one narrow `lang:` regex read. `description` may contain markdown links, extracted into real `Link`s owned by the container itself, so the original baking bug dissolves rather than needing a workaround: the container legitimately owns its own abstract's links now. Storage: stop treating the whole frontmatter block as one opaque `StringProp` — parse it into one `StringProp` per key found, known or not, so a hand-authored key the engine doesn't yet recognize still round-trips through projection instead of silently vanishing. Edit path settled without inventing anything new: this is the project's own long-standing "update as a scoped reconciliation" philosophy, making direct use of the ingestion mechanism — `aperas update <id>` already re-parses piped markdown and reconciles it exactly like a real re-ingest would. It just has two gaps to close: it rejects `FolderNode` targets outright today, and it never consumes the `frontmatter` that `parseMarkdownTree` already extracts from the piped input. Closing both means editing `description` is just piping a doc with a `description:` frontmatter line at the exact same call site every other edit already uses — no bespoke flag, no separate command. Migration still needed: every already-tracked artifact/folder holds the old opaque `frontmatter` prop and a stale `.text` copy; a one-time pass has to split existing frontmatter into per-key props and seed `description` from the current `.text` wherever `description` isn't already set. Filed as an Open Issue ([issues/core.md](../issues/core.md#id/BlockNode:00CKE4R93R001)) rather than a Design entry — `design/core.md` doesn't exist yet, and this corpus's own convention reserves Design for crystallized/built architecture, not a plan agreed in conversation but not yet implemented.
