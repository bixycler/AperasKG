## Settled <a name='id/BlockNode:00CF1WZE18000' class='aperas-anchor aperas-id'></a>

- **Scope**: <a name='id/BlockNode:00CF1WZE18001' class='aperas-anchor aperas-id'></a> `core` is the shared ApeironNgn engine — `treeview`, `linking`, `list-consumption`, and `crud` (once migrated) are its sub-parts. `cli` and a future `webapp` are thin wrappers over that same engine, each getting their own separate, much thinner concern rather than being folded in here. This concern was originally scoped and named `cli` before that distinction was drawn; see the rename note below.
- **The previous `cli.md` → `cli-packaging.md` → `packaging.md` rename is not evidence against this concern existing**: <a name='id/BlockNode:00CF1WZE18002' class='aperas-anchor aperas-id'></a> that doc was mis-scoped from the start — it was really packaging/distribution content wearing the "cli" name, not a case of "cli" being too broad a name to use. This time the scope is deliberate: the whole tool, not one facet of it. **Update**: this concern itself then turned out to be mis-scoped a second time — not because "cli" was too broad, but because the actual content (`reconcile.ts`, `node.ts`, `astParser.ts`, `apeironNgn/artifacts.ts`) is core engine code, not CLI-dispatcher code. Renamed to `core`; a genuinely thin `cli` was split back out separately. Two different failure modes wearing the same symptom (a rename), not the same mistake twice.
- **Sequencing**: <a name='id/BlockNode:00CF1WZE18003' class='aperas-anchor aperas-id'></a> `issues/core.md`, `discussion/core.md`, and `planning/core.md` (renamed from `cli.md`) hold the engine-level Open Issues and their fix plan; `design/core.md` and `history/core.md` stay deferred until the fixes actually settle the architecture and land. A separate, much thinner `cli` concern now holds only what's genuinely CLI-dispatcher-specific.

- **Every live Open Issue reviewed and ranked by how much it hinders graph *edit* specifically — a fix-order recommendation, not yet a decision**: <a name='id/BlockNode:00CGGNFG50001' class='aperas-anchor aperas-id'></a> covers `issues/{core,linking,treeview,list-consumption,archive-migration}.md` (`cli`/`packaging`/`documentation`/`aperas-skill` are all empty). The criterion: does it silently corrupt or lose content on an ordinary write, does it undermine trust in what the write-verification tooling reports, or does it block a legitimate write outright — ranked above anything read-side, cosmetic, or process-only, regardless of how it's currently ordered in its own doc.
  
  - **Tier 1 — silent corruption on ordinary writes, highest priority**: <a name='id/BlockNode:00CGGNFG50002' class='aperas-anchor aperas-id'></a> [`aperas update` never re-derives a non-heading title, and can tombstone real children as a side effect](../issues/linking.md#id/BlockNode:00CGFE4SV0002) — proven live this session, not hypothetical, and hits the single most common write (`update` on a leaf). [A parent-heading list-push reassigns live content onto the wrong id once a tombstoned sibling is interleaved](../issues/core.md#id/BlockNode:00CF1WZ4JG003) and [`update`'s reconciliation can silently match fresh content onto an already-tombstoned id without reviving it](../issues/core.md#id/BlockNode:00CF1WZ4JG004) — both live in the same matching machinery (`diffChildren`'s `matchKeyed`/`gestaltMatchingBlocks`), and the first item's own text already notes "one fix in `reconcile.ts` likely closes" both of these plus [item 3](../issues/core.md#id/BlockNode:00CF1WZ4JG005) — meaning a single fix here has 3x leverage, the highest of anything reviewed. **Misplaced on first pass, moved up here after direct diagnosis**: [the GFM task-list marker leak](../issues/treeview.md#id/BlockNode:00CE1GW638007) was filed in Tier 5 as "likely non-reproducible" — it reproduces every time a checkbox's content doesn't start with plain text (bold, italic, code, or a link lead-in all qualify), and it silently bakes the leftover marker into stored `.text` as literal prose on an ordinary `update`/`insert`, exactly the same failure shape as the rest of this tier: a write that looks clean and corrupts content nobody asked it to touch.   - **Tier 2 — hides Tier-1-style problems, or blocks legitimate writes outright**: <a name='id/BlockNode:00CGGNFG50003' class='aperas-anchor aperas-id'></a> [a props-only change reports as `0 changed`](../issues/core.md#id/BlockNode:00CFATMWY0001) — cheap to fix, and fixing it makes every other write's verification trustworthy, which every other item on this list depends on. - **`flush --clobber` / `reload --discard` round-trip mechanics, startup GC, and shutdown logging design**: <a name='id/BlockNode:00CGR1F620001' class='aperas-anchor aperas-id'></a> investigated `reload --discard` and `flush --clobber` interaction, live, at the user's own request after a `flush --clobber` unexpectedly removed a real backlog. Mismatches observed were traced to two *unrelated* mechanisms conflated at first: mark-and-sweep tombstone GC (`pruneUnreachableTombstones`, legitimate — the backlog really was dead) and a duplicate-`@id` collision in `Profile.jsonld` (a real, separate data bug, wrongly described here as "RDF deduplication" as if it were a working, intentional mechanism — corrected in [issues/core.md](../issues/core.md#id/BlockNode:00CHXSZ56R001), which now carries its own entry). Discovered that prior service restarts left GC garbage on disk because `shutdown()`'s guarded `flushIfDirty()` silently refused and dropped a computed GC result whenever disk had diverged externally, while service startup never ran the sweep at all. First design pass: (1) run the sweep at startup, (2) reword the shutdown warnings, (3) return GC metrics from `flush --clobber`. Reviewed afterward, on request, for correctness and completeness against the actual code rather than the summary of what was intended — found both (1) and (2) didn't actually work: (1) computed the sweep but never set `dirty`/`stateDirty` (declared *after* that block ran in the original patch), so nothing was ever flushed; (2) and every other service-side message, including (1)'s own new log line, went to `console.error`, which is unreachable in real operation since the service is always spawned with `stdio: 'ignore'` (`serviceClient.ts`). Actually fixed: reordered the startup sequence so the sweep can flush immediately when it finds something, and added a durable `logService()` helper (append to a `$XDG_RUNTIME_DIR`-based log file) used everywhere `console.error` alone used to be the only channel. Also closed a gap the first pass didn't touch at all: `kg:reload` never surfaced its own GC counts, only `kg:flush --clobber` did — `reloadStore()` now returns the same shape and `kg:reload` prints it the same way.

- **`aperas retype` — an identity-preserving block type-conversion channel, for refactoring/migration only**: <a name='id/BlockNode:00CJ4H44J8001' class='aperas-anchor aperas-id'></a> agreed, built and verified 2026-09-17; the entries below are this design's own working record, in the order it actually went. Today a block's `type` is pinned everywhere a write could touch it: `kgUpdate.ts` builds both its `--text-only` and reconcile shapes with `type: target.type`, so a piped input's own type is never adopted; `reconcileTree` could not pair the two sides anyway, since containers match partitioned `byType` (a `listItem` and a `heading` land in different buckets and never meet) and leaves match on `leafKey`, which keys a heading on `.title` and a paragraph on `.text` — unequal by construction, in the cross-parent salvage stage too. `kg:update` separately refuses a heading depth change outright (`oldDepth !== newDepth` throws). Each guard is correct on its own: an ordinary edit must never silently restructure. Together they leave no in-place route at all, so the only way to change a block's type today is `remove` + `insert`, which tombstones the id and every citation pointing at it — precisely what *Preserve identity* exists to prevent.
  
  - The data model has no objection: <a name='id/BlockNode:00CJ4H44J8002' class='aperas-anchor aperas-id'></a> `reconcile.ts`'s `carryForwardFields` carries `blockId` and `links` onto the **new** node and pointedly does *not* carry `type`, so "same identity, different type" is already expressible. Only the CLI pin and the matcher stand in the way, which is what makes this a narrow addition rather than an architectural one.
  - **Shape**: <a name='id/BlockNode:00CJ4H44J8003' class='aperas-anchor aperas-id'></a> `aperas retype <ref> --to <type>`, where `<type>` is `h1`..`h6` (heading, depth carried in the type itself) or any non-heading block type (`paragraph`, `listItem`, `code`, `blockquote`, …). Heading depth change is therefore the same operation as any other conversion (`h2` → `h3`), not a special case — one verb covers both pinned structural fields. Preserves id, `links`, children, parent and position; `.text` is never touched. Title is re-derived for the new type: an `h*` target rebuilds the heading line at the requested depth from the node's existing title words; a non-heading target re-derives via the ordinary lead-in-term rule.
  - **Deliberately type-only, not a content channel**: <a name='id/BlockNode:00CJ4H44J8004' class='aperas-anchor aperas-id'></a> changing a block's text stays `aperas update`'s job, run separately afterwards. The cost is a real one to design around — converting a heading away from `heading` re-derives its title from `.text`, which for a heading is its *body* (the consumed leading paragraph) and normally carries no lead-in term, so the title falls back to the raw block id and the heading's own words survive only in whatever the operator captured first. The verb must therefore report the outgoing title in its own result line, and warn when a conversion is about to leave a node titled by id fallback, so a migration can compose the follow-up `update --text-only` from it rather than recovering it from `git`.
  - **Automatic title migration across the heading boundary, built in rather than left to a manual follow-up**: <a name='id/BlockNode:00CJ4XG0RG001' class='aperas-anchor aperas-id'></a> reconsidered from the item above — a heading and a non-heading store their title in genuinely different places (a field vs. a lead-in folded into `.text`), so crossing that boundary now migrates the title *with* the type, in whichever direction applies. Heading → non-heading folds the heading's own words into `.text` as a canonical `**words**: <body>` lead-in — the always-uncapped shape, since the whole span before the colon sits inside one bold node — then derives the new title from that text via the real parser, not a hand-built guess. Non-heading → heading does the exact inverse: cuts the existing lead-in back out using `findLeadInSpliceOffset` (`astParser.ts`), the identical colon `project.ts`'s own anchor splice already relies on, so the cut lands exactly where the title was actually derived from. Verified live on the corpus's hardest real case (`kg:update`/`kg:insert` never resolve wikilinks — a title with embedded backtick colons and an em-dash): converts to a `listItem` with both links intact, and converting back reproduces the original title and text byte-for-byte. A depth-only heading change (`h2` → `h3`) and a non-heading → non-heading retype still never touch `.text` at all — only actually crossing the boundary does. The one remaining gap is a lead-in that isn't a single, fully-bold span, or missing entirely: that degrades to the old id-fallback behavior, `.text` left alone, `untitled` reported — the same graceful failure the parser already uses everywhere else.
  - **Props**: <a name='id/BlockNode:00CJ4H44J8005' class='aperas-anchor aperas-id'></a> a type-specific prop is meaningless on the new type (a heading's `treeAnchor`; a `listItem`'s `orderedList`/`startIndex`/`checked`), so a conversion drops the ones belonging to the old type rather than carrying stale state forward. Not a concern for the migration that motivated this — none of the 16 nodes involved carries an anchor prop — but it is the kind of leftover that turns into a rendering bug later.
  - **Motivating case**: <a name='id/BlockNode:00CJ4H44J8006' class='aperas-anchor aperas-id'></a> [discussion/linking.md's Freeflow](../discussion/linking.md#id/BlockNode:00CJ37GPRR009) holds 16 `##` headings that were moved under a `## Freeflow` heading, which markdown cannot nest — re-parsed from its own projection that section has zero children and all 16 read as siblings. Converting them to lead-in-term `listItem`s is what makes the grouping structural rather than only intended, since list items nest by indentation with no H6 ceiling — the same argument [issues/linking.md's "Heading-in-list"](../issues/linking.md#id/BlockNode:00CDBYV5A800C) already settled for titles. All 43 real citations into those 16 use `#id/BlockNode:` fragments, so they survive the conversion untouched.
