## Settled <a name='id/BlockNode:00CF1WZE18000' class='aperas-anchor aperas-id'></a>

- **Scope**: <a name='id/BlockNode:00CF1WZE18001' class='aperas-anchor aperas-id'></a> `core` is the shared ApeironNgn engine — `treeview`, `linking`, `list-consumption`, and `crud` (once migrated) are its sub-parts. `cli` and a future `webapp` are thin wrappers over that same engine, each getting their own separate, much thinner concern rather than being folded in here. This concern was originally scoped and named `cli` before that distinction was drawn; see the rename note below.
- **The previous `cli.md` → `cli-packaging.md` → `packaging.md` rename is not evidence against this concern existing**: that doc was mis-scoped from the start — it was really packaging/distribution content wearing the "cli" name, not a case of "cli" being too broad a name to use. This time the scope is deliberate: the whole tool, not one facet of it. **Update**: this concern itself then turned out to be mis-scoped a second time — not because "cli" was too broad, but because the actual content (`reconcile.ts`, `node.ts`, `astParser.ts`, `apeironNgn/artifacts.ts`) is core engine code, not CLI-dispatcher code. Renamed to `core`; a genuinely thin `cli` was split back out separately. Two different failure modes wearing the same symptom (a rename), not the same mistake twice.
- **Sequencing**: <a name='id/BlockNode:00CF1WZE18003' class='aperas-anchor aperas-id'></a> `issues/core.md`, `discussion/core.md`, and `planning/core.md` (renamed from `cli.md`) hold the engine-level Open Issues and their fix plan; `design/core.md` and `history/core.md` stay deferred until the fixes actually settle the architecture and land. A separate, much thinner `cli` concern now holds only what's genuinely CLI-dispatcher-specific.

## Freeflow <a name='id/BlockNode:00CF1WZE18004' class='aperas-anchor aperas-id'></a>

- **Where this concern's Open Issues came from**: <a name='id/BlockNode:00CF1WZE18005' class='aperas-anchor aperas-id'></a> a whole-graph dense-linking pass surfaced the same underlying `reconcile.ts` defect family described independently in three separate places — `aperas-skill`'s own eval findings, `list-consumption`'s Checkpoints, and `packaging`'s discussion — plus two separate insert/ingest transactionality gaps (`aperas-skill`'s single-`kg:insert` finding, `linking`'s multi-artifact `kg:ingest` finding). None of the four originating write-ups referenced each other; compiling them here is what made the shared root cause visible in the first place.
- **Live incident while creating this very doc set**: <a name='id/BlockNode:00CF1WZE18006' class='aperas-anchor aperas-id'></a> attempted the graph-first "sketch a structure" path (`aperas resolve --create-holder`) to scaffold `issues/cli.md` from nothing. Filled real content into the placeholder's Block children successfully, but `aperas project` then refused ("still has a placeholder (holder) node somewhere in its subtree"), and `kg:insert`'s promote path rejected the `ArtifactNode` outright ("kg:insert only positions Block-level nodes"). No verb exists to clear `.holder` on a Folder/Artifact once real content lands underneath it — confirmed by direct inspection, matches `Aperas-crud-design.md` §4.1/§6 exactly. Recovered by tombstoning the stuck holder chain (`aperas remove`) and redoing both `cli.md` docs disk-first instead — the same path `archive-migration`'s own established practice already uses for a genuinely new concern-doc-set. Filed as this concern's own Open Issues entry, since it's now a live-reproduced instance rather than just an archived design note.

- **Split planned: `cli` → `core` (rename) + a new, thin `cli`**: <a name='id/BlockNode:00CF282PR0001' class='aperas-anchor aperas-id'></a> realized while scoping this batch that `packages/` is `core`/`cli`/`web` — core is the shared ApeironNgn engine, cli is a thin dispatcher over it, and web will eventually be another thin wrapper over the same core. Almost everything filed under this concern so far (items 1-4, 6, 7; the `treeview`/`linking`/`list-consumption`/`crud` Sub-Parts) is core engine content, not CLI-dispatcher content — only item 5 (`kg:insert`'s own call-ordering) and `packaging` are genuinely cli-specific. Plan: retitle and reword this doc set's own content while still at the `cli.md` paths, `git mv` all three to `core.md`, `aperas ingest --track` scoped to confirm identity survives, then move (not copy) item 5 into a freshly-created thin `cli.md`/`discussion/cli.md`/`planning/cli.md` — `packaging` stays where it already lives, just re-indexed under the new thin `cli`'s own Sub-Parts. `documentation` and `archive-migration` are meta/process concerns about the graph itself, not part of the core/cli/webapp product split, and aren't reassigned to either. Executing next.

Same shape as [the dead-container gap](../issues/core.md#id/BlockNode:00CF1WZ4JG006) and the other tombstone-blind-spot findings in this batch — another site that treats a tombstoned node as if it still competes for a name. Not filed as its own Open Issue yet; parked here since it's minor and workaroundable (full-id lookup instead of bare-path resolve).
