## Settled <a name='id/BlockNode:00CF1WZE18000' class='aperas-anchor aperas-id'></a>

- **Scope**: <a name='id/BlockNode:00CF1WZE18001' class='aperas-anchor aperas-id'></a> `core` is the shared ApeironNgn engine — `treeview`, `linking`, `list-consumption`, and `crud` (once migrated) are its sub-parts. `cli` and a future `webapp` are thin wrappers over that same engine, each getting their own separate, much thinner concern rather than being folded in here. This concern was originally scoped and named `cli` before that distinction was drawn; see the rename note below.
- **The previous `cli.md` → `cli-packaging.md` → `packaging.md` rename is not evidence against this concern existing**: <a name='id/BlockNode:00CF1WZE18002' class='aperas-anchor aperas-id'></a> that doc was mis-scoped from the start — it was really packaging/distribution content wearing the "cli" name, not a case of "cli" being too broad a name to use. This time the scope is deliberate: the whole tool, not one facet of it. **Update**: this concern itself then turned out to be mis-scoped a second time — not because "cli" was too broad, but because the actual content (`reconcile.ts`, `node.ts`, `astParser.ts`, `apeironNgn/artifacts.ts`) is core engine code, not CLI-dispatcher code. Renamed to `core`; a genuinely thin `cli` was split back out separately. Two different failure modes wearing the same symptom (a rename), not the same mistake twice.
- **Sequencing**: <a name='id/BlockNode:00CF1WZE18003' class='aperas-anchor aperas-id'></a> `issues/core.md`, `discussion/core.md`, and `planning/core.md` (renamed from `cli.md`) hold the engine-level Open Issues and their fix plan; `design/core.md` and `history/core.md` stay deferred until the fixes actually settle the architecture and land. A separate, much thinner `cli` concern now holds only what's genuinely CLI-dispatcher-specific.

- **Every live Open Issue reviewed and ranked by how much it hinders graph *edit* specifically — a fix-order recommendation, not yet a decision**: <a name='id/BlockNode:00CGGNFG50001' class='aperas-anchor aperas-id'></a> covers `issues/{core,linking,treeview,list-consumption,archive-migration}.md` (`cli`/`packaging`/`documentation`/`aperas-skill` are all empty). - **`flush --clobber` / `reload --discard` round-trip mechanics, startup GC, and shutdown logging design**: <a name='id/BlockNode:00CGR1F620001' class='aperas-anchor aperas-id'></a> investigated `reload --discard` and `flush --clobber` interaction. Single-state round-trip holds for both disk state (disk -> memory -> disk) and memory quads (memory -> disk -> memory) in steady state. Mismatches observed on `flush --clobber` were traced to two automatic mechanisms: mark-and-sweep tombstone GC (`pruneUnreachableTombstones`) and RDF subject deduplication. Discovered that prior service restarts left garbage on disk because `shutdown()` used guarded `flushIfDirty()`, which silently refused and dropped GC/flushes whenever disk diverged externally (e.g. via git operations), while service startup did not run GC. Design decisions: (1) execute startup GC immediately upon rehydrating the store, (2) upgrade shutdown logging when guarded flushes are refused due to disk divergence, and (3) return GC metrics (`prunedTombstones`, `tombstonedContainers`, `prunedUnfolds`) in `flush` service responses to display explicit summary notifications in `aperas flush` — [promoted to issues/core.md](../issues/core.md#id/BlockNode:00CGR1BM9G001).
