## Resolved: anchor-drift strip, and a real trackFromDisk bug underneath it <a name='id/BlockNode:00CDEZ1A68001' class='aperas-anchor aperas-id'></a>

Added `stripInlineAnchors` (`astParser.ts`) and applied it everywhere a block's stored abstract/text gets compared against a fresh disk parse for exact equality: `extractAbstract` (before truncating, so a mid-window anchor can't survive as a mangled fragment either), `reconcile.ts`'s `leafKey` (block-level Gestalt matching), and the rename matchers' own key computation (`apeironNgn/artifacts.ts`). Verified against the two real cases that surfaced this (`design/cli.md`'s Discussion bullet, `discussion/cli.md`'s staging-practice paragraph): stripped text now round-trips exactly.

That got the batch rename to report "5 renamed" — but a direct check of the graph showed all 5 *still* duplicated. The real, deeper bug was in `ArtifactNode.trackFromDisk` (`node.ts`): its "skip if unchanged" guard compared `fileHash` alone, `this.path` never entered it. A pure rename is exactly the case where the hash *is* unchanged (nothing but the location moved) — so the guard's early return skipped the `this.path = artifactPath` write below it every time, on every rename, while still reporting `{ tracked: true }`-shaped success to its caller. `trackAllArtifacts`'s own rename path had carried this same bug the whole time; it just never surfaced because a real-world rename usually carries a content edit alongside it, which masked the hash match. Fixed: the guard now requires the path to match too, not just the hash — a rename (same hash, different path) now correctly falls through and updates `path`/`title`/`fileHash`/`lastTrackedAt`.

All three fixes together, re-verified: <a name='id/BlockNode:00CDEZ1A68003' class='aperas-anchor aperas-id'></a> batch-renaming the 5 `cli.md` docs to `cli-packaging.md` now reports "5 renamed" *and* the graph shows exactly 5 ArtifactNodes (no duplicates), each still carrying its original id and its original BlockNode children — confirmed via direct inspection, not just the summary line.

## Resolved: scoped rename detection, without a full-corpus sweep <a name='id/BlockNode:00CDEM7DVG001' class='aperas-anchor aperas-id'></a>

Added `trackArtifactsScoped` (`apeironNgn/artifacts.ts`), wired into `kg:track`/`kg:ingest`'s explicit-`<path>...` branch. It detects a rename by pairing only the paths the caller actually gave against already-tracked ArtifactNodes whose recorded path no longer exists on disk — never a directory listing, so `archive/` (or anything else not yet migrated) can't enter either side, no matter how large it gets.

First attempt reused `trackAllArtifacts`'s own `matchLeftoverByAbstract` (the Gestalt/Ratcliff-Obershelp recursion `reconcile.ts` uses everywhere else) and only matched 2 of 5 batch-renamed files — not from ambiguity, but because that algorithm is position-sensitive: it works for reconciling siblings that share a rough common order across an edit, not for an unordered bag of whole-artifact identities scattered across concern folders. A match's recursive split can discard a whole quadrant of otherwise-valid candidates just because the corresponding range on the other side is empty. Replaced with `matchByExactKey`: same "decline rather than guess" principle (a key occurring more than once on either side stays unmatched), but no positional requirement — confirmed via debug trace, then verified live (4 of 5 correctly renamed, identity preserved).

**Left open, a distinct bug:** the 5th case still doesn't match, and a separate block-level reconciliation surfaced the same shape of problem — an ArtifactNode's (or BlockNode's) cached abstract `.text` is snapshotted at ingestion time, before `kg:project` ever splices an inline `id/<ID>` anchor into a list-item/paragraph's rendered form. Once a block has been through even one project cycle, its stored text and its freshly-reparsed disk text differ by exactly that anchor — breaking any matcher that requires exact equality, ours included. Not attempted here; needs its own fix (re-deriving the stored abstract with anchors stripped, or comparing anchor-insensitively).

## Practice: stage checkpoints myself, leave commits to the user <a name='id/BlockNode:00CDEEJ8PR001' class='aperas-anchor aperas-id'></a>

The rename incident above recovered cleanly only because `Apeiron/*.jsonld` happened to already be staged from an earlier point — `git restore` could reset the working tree to that known-good index state in one step. That shouldn't be luck: after each verified-stable step (a clean round-trip, a successful reconciliation with no unexpected removals), stage the change (`git add`) immediately, so the git index is always a running checkpoint. If a later step goes wrong, `git restore`/`git diff` against the index recovers it without guesswork. Independently restated as a general practice in [aperas-skill's own edit loop](../design/aperas-skill.md#id/BlockNode:00CEB8N5EG001) — same rule, same reasoning, arrived at twice.

This is deliberately staging only, never committing: <a name='id/BlockNode:00CDEEJ8PR002' class='aperas-anchor aperas-id'></a> `git commit` stays a decision for the user to make explicitly, reviewing what accumulated. Staging is not that — it's a private safety net, the same role `git stash` or a snapshot would play, just reusing git's own index instead of a separate mechanism.

## Motivation: dogfooding vs. shipping <a name='id/BlockNode:00CDDVC33G006' class='aperas-anchor aperas-id'></a>

Every `kg:*` command today is its own `tsx`-run entrypoint (`web/src/lib/kgX.ts`) invoked as `npm run kg:X -- <args>` — that only works inside a source checkout of this repo, with `tsx` and every other devDependency installed. That's fine for us dogfooding the skills we write against this CLI, but the skills under `skills/` are meant for end users, who won't have this repo cloned. Before more skills lean on `kg:*` commands, the CLI itself needs to be something installable and runnable standalone.

## Considered: one bin per verb <a name='id/BlockNode:00CDDVC33G007' class='aperas-anchor aperas-id'></a>

Register each existing `kgX.ts` as its own `bin` entry (`aperas-ingest`, `aperas-tree`, ...). Minimal code change — every file already runs standalone. Rejected: pollutes the user's PATH with roughly twenty near-identically-named commands, and throws away the single `aperas <verb>` entrypoint every illustrative example in the corpus already assumes (e.g. [design/documentation.md's Crystallization step](../design/documentation.md#id/BlockNode:00CDD68E8800B): `echo "..." | aperas update design/crud.md/Architecture`).

## Landing on: one dispatcher binary <a name='id/BlockNode:00CDDVC33G008' class='aperas-anchor aperas-id'></a>

A single `aperas` executable that argv-dispatches to a subcommand (`aperas ingest ...`, `aperas tree ...`, ...). Low-risk refactor: every `kgX.ts` already separates a pure `run*` function (e.g. `runIngest`, `runProject`) from its own `main()`'s argv-parsing/help-printing glue — the dispatcher only needs to own argv routing and reuse the existing `run*`/`request()` calls and `kgHelp.ts` machinery, not rewrite any command's logic.

## Naming: `aperas`, not `kg` <a name='id/BlockNode:00CDF8B3TG00A' class='aperas-anchor aperas-id'></a>

`kg` is short and matches the existing `kg:*` script prefix, but it collides too easily with other tools people already have on their PATH (a common `kubectl` alias, among others) — a real risk once this is something end users install globally, not just an internal npm script name scoped to this repo. Settled on `aperas` instead: unambiguous, matches the project's own name, no realistic collision.

## Open question: the runtime <a name='id/BlockNode:00CDDVC33G009' class='aperas-anchor aperas-id'></a>

`tsx` (on-the-fly TypeScript execution) is a devDependency today, not something to ship a published CLI depending on. Needs a real build step (`esbuild`/`tsc`) compiling to plain JS, with `bin` pointing at the built entrypoint (a `#!/usr/bin/env node` shebang) — `npm run kg:X` during development can keep using `tsx` unchanged; only the published artifact needs to be compiled.

## Open question: where's the graph? <a name='id/BlockNode:00CDDVC33G00A' class='aperas-anchor aperas-id'></a>

`getArtifactsDir()` resolves `AperasKG/artifacts` as a hardcoded sibling of `web/` — true for us, not for an end user with no such sibling folder. Packaging needs some answer for where an installed `aperas` binary finds (or creates) its own graph — cwd-relative discovery, an env var, a config file — that's still open, and probably the biggest remaining unknown, separate from the dispatcher/bundling mechanics above.

## Resolved (partially): retitling a heading, and a deeper wikilink gap it exposed <a name='id/BlockNode:00CDG18FP0001' class='aperas-anchor aperas-id'></a>

Renaming this doc set (`cli-packaging.md` -> `packaging.md`) needed each doc's own H1 retitled too (`# CLI Packaging — X` -> `# Packaging — X`). Pushed the whole corrected document through `kg:update` targeting the *ArtifactNode* (`design/packaging.md`), the same way the `kg -> aperas` content fix worked earlier — and it blew up all 7 blocks into fresh "added" ones (0 matched), tombstoning every original BlockNode id in the process.

**Root cause:** `kg:update` *does* have a retitle-in-place feature (`kgUpdate.ts`: <a name='id/BlockNode:00CDG18FP0002' class='aperas-anchor aperas-id'></a> when the piped input's own first child is a heading of matching depth, it relabels `title`/`text` in place, no restructuring) — but it only fires when the *target itself* is that heading BlockNode. Targeting the ArtifactNode instead routes the whole document through the generic `reconcileTree`/Gestalt matcher, where a heading's match key is `title` alone (`reconcile.ts`'s `leafKey`) — no positional or depth-aware fallback. A title change is therefore an exact-key mismatch at the very top of the tree, and since nothing above it can anchor a match, the *entire* subtree reconciles as removed+added instead of "one heading changed, rest unchanged." Artifact-level renames get a real "same identity, new label" primitive (`trackFromDisk`, after this session's earlier fix); heading-level retitling only gets one when addressed directly, not through a whole-document push.

**A second, deeper gap this exposed:** neither `kg:update` nor `kg:insert` ever calls `resolveBlockLinks` — grepped every call site; it only ever runs from `ingestArtifact` (the `kg:ingest`/disk-first path). A block that's "matched" (untouched) keeps whatever links it already had, but anything reconciled as "changed" or "added" via `kg:update`/`kg:insert` gets *no* link resolution at all, silently. Confirmed directly: a fresh "added" list item's own BlockNode has no `links` field whatsoever. `documentation.md` and `linking.md` were unaffected (their wikilink-bearing blocks only ever went through "matched" `kg:update` passes, carrying forward resolution from an earlier real `kg:ingest`) — this doc set is the one place it actually broke, because the retitle accident forced every block through "added".

Recovered by restoring `Apeiron/*.jsonld` from the git index and reprojecting from the graph (the disk `.md` files needed a `kg:project` to come back after a restore mishap deleted them outright — recoverable because the graph itself, not the working tree, was the actual source of truth here). Not yet fixed: the rename to `packaging.md` (still `cli-packaging.md` on disk) and the wikilink-resolution gap in `kg:update`/`kg:insert` — tracked, not resolved.

## Resolved: `kg:update`/`kg:insert` now resolve wikilinks <a name='id/BlockNode:00CDGAFQQR001' class='aperas-anchor aperas-id'></a>

Both commands now call `resolveBlockLinks` (`apeironNgn/artifacts.ts`) themselves, the same wrapper `ingestArtifact` already used — closing the gap the retitle incident above exposed.

The pieces needed were already in `node.ts`, just private to `ingestFromDisk`: <a name='id/BlockNode:00CDGAFQR0000' class='aperas-anchor aperas-id'></a> `collectLinkTargetsByBlock`/`collectOldWikilinksByBlock` snapshot a block's pre-mutation resolved link state, and `extractLinkCodes` (`artifacts.ts`) reads the `linkCodes` a fresh parse already stashes per node. Both are now exported, plus a new `findEnclosingArtifactId` (mirroring `artifactPathOfBlock`'s walk, but returning an id) so a command that starts from an arbitrary Block/ArtifactNode target — not `ingestArtifact`'s own already-known artifact id — can still find the right node for `resolveBlockLinks`'s `danglingRef` bookkeeping.

`kg:update`: <a name='id/BlockNode:00CDGAFQR0001' class='aperas-anchor aperas-id'></a> the old-link snapshot is taken right after `oldShape` (before any mutation); whichever branch (`--text-only` or the default reconcile) builds the new tree also now extracts pending link codes from it *before* hydrating — same order `ingestFromDisk` uses, since `extractLinkCodes` strips the schema-unknown `linkCodes` field as it walks. `kg:insert`'s create mode does the same over its freshly-parsed `topLevel`, with empty old-state maps (nothing existed before).

Verified two ways: <a name='id/BlockNode:00CDGAFQR0002' class='aperas-anchor aperas-id'></a> a throwaway `kg:insert`'d block with a `#id/...` link resolved immediately (`kg:backlinks` showed the new block as a real backlink, not just a reported count); and a no-op `kg:update` reconcile of an existing two-link block reused both `Link` ids rather than minting duplicates (`kg:backlinks` afterward showed the same two entries, unchanged).

## Resolved: heading retitle-in-place, at the reconcile level too <a name='id/BlockNode:00CDGGTE6R001' class='aperas-anchor aperas-id'></a>

`kg:update`'s direct-heading-retitle feature only ever covered *targeting the heading itself*; a whole-document/whole-tree push (targeting the ArtifactNode, or a real `kg:ingest` re-parse of an edited file) still went through `reconcile.ts`'s generic `diffChildren`, where a heading's Stage A match key is `title` alone (`leafKey`) — an edited title was an exact-key miss with nothing to fall back on, so the entire subtree beneath a retitled heading reconciled as wholesale removed+added, exactly what happened above.

Added a Stage A2 to `diffChildren`: <a name='id/BlockNode:00CDGGTE6R002' class='aperas-anchor aperas-id'></a> headings still unmatched after Stage A's exact-title pass get a positional fallback — bucketed by depth (`astParser.ts`'s new `headingDepth`, reading the title's own leading `#` run, so a `##` can never fool-match a `#`), then paired in original relative order within each bucket. Same "position is the anchor" trade-off Stage B already accepts for `list`/`listItem` containers, just extended to headings once title itself is off the table as a key. A pair matched this way (or via Stage A's own text-only case) that differs in `title` and/or `text` is counted as `changed`, not folded into `matched` (`headingChanged`, generalized from the old `headingTextChanged`).

Verified on a throwaway test artifact: <a name='id/BlockNode:00CDGGTE6R003' class='aperas-anchor aperas-id'></a> retitling its H1 through a whole-document `kg:update` (the same shape of push that caused the original incident) now reports "2 matched, 1 changed, 0 added, 0 removed" — the two section headings matched cleanly, the retitled H1 counted as changed, and disk projection confirmed all three BlockNode ids were preserved (no tombstones).

## Freeflow: planning the `aperas` dispatcher itself <a name='id/BlockNode:00CDH8S908001' class='aperas-anchor aperas-id'></a>

The workspace split is done; the dispatcher it was meant to make room for ([Architecture](../design/packaging.md#id/BlockNode:00CDDVBXHG005)) still doesn't exist. Working out the concrete shape before writing any of it.

**Verb → module**: <a name='id/BlockNode:00CDH8S908002' class='aperas-anchor aperas-id'></a> a static table in the new `packages/cli/src/aperas.ts` (verb string -> the matching `kgX.ts` module), not filesystem auto-discovery — there are ~19 fixed commands, a static map is simpler and makes an unrecognized verb a clean, listable error rather than "whatever happens to be on disk."

**The real gap: every `kgX.ts`'s `main()` is private.** Each file already separates a pure `run*` function from its own `main()` (argv-parsing, stdin, printing) — but `main()` itself is never exported, only invoked at the bottom of the file behind `if (process.argv[1]?.endsWith('kgX.ts')) main()...`. A dispatcher importing the module and expecting to call its `main()` needs that export added, in every one of the ~19 files. The self-invocation guard stays exactly as-is underneath that export — direct `tsx kgX.ts` (what the existing `kg:*` npm scripts still do) keeps working unchanged; the dispatcher is a second caller of the same exported function, not a replacement for the first.

**argv re-slicing.** `main()` reads `process.argv.slice(2)` directly (not a parameter) expecting its own args to start there. Invoked as `aperas <verb> <rest...>`, `process.argv` is `[node, aperas.ts, <verb>, ...rest]` — one extra element ahead of what any `main()` expects. The dispatcher has to splice the verb back out of `process.argv` itself before calling the target's `main()`, since nothing here can change what `main()` reads from.

**No verb / unrecognized verb / `--help`.** The static verb table doubles as the source for a top-level listing (verb + one-line description, authored once in `aperas.ts`, not scraped from each command's own `kgHelp.ts` output — that's only reachable by actually invoking a specific command's `--help`, not introspectable ahead of time without doing so). `aperas <verb> --help` forwards straight into that verb's own existing `main()`, which already implements it via `wantsHelp`/`printHelp` — nothing new needed there.

**Entry point, deliberately punted on the bigger question.** A root `"aperas": "tsx packages/cli/src/aperas.ts"` script (`npm run aperas -- <verb> <args>`) is enough to make the dispatcher real and testable today, same mechanism every `kg:*` script already uses. This deliberately does *not* touch [the runtime question](#id/BlockNode:00CDDVC33G009) (a real compiled build + `bin` field + shebang, for an actual installable global command) or [the graph-location question](../issues/packaging.md#id/BlockNode:00CDDVC8N0002) — both stay open, tracked separately; the dispatcher mechanism itself doesn't depend on either being answered first ([Implementation Plan](../planning/packaging.md#id/BlockNode:00CDDVCDW8002) already says as much).

**Verification**: <a name='id/BlockNode:00CDH8S90G001' class='aperas-anchor aperas-id'></a> spot-check a handful of verbs through `aperas <verb>` against their `kg:<verb>` equivalent (same output), and re-run the full `npm run verify` harness — it calls `run*` functions directly, so the dispatcher layer shouldn't be able to affect it either way; a regression there would mean something broke in a shared file, not the dispatcher itself.

## Freeflow: why the runtime question isn't just "run tsc" <a name='id/BlockNode:00CDHFW4R8001' class='aperas-anchor aperas-id'></a>

Asked to explain why this stays open rather than being a trivial build step. Recorded here since it bundles a few real sub-decisions, not one.

**The immediate problem**: <a name='id/BlockNode:00CDHFW4RG000' class='aperas-anchor aperas-id'></a> every `kgX.ts`/`aperas.ts` is executed via `tsx` — an on-the-fly TypeScript-to-JS transpiler, listed as a `devDependency`. That's fine for dogfooding (`npm run aperas -- tree` inside this checkout, `tsx` already installed as part of `npm install`), but a published package's `bin` entry has to be something Node can execute directly on an end user's machine, with nothing but the shebang line to go on (`#!/usr/bin/env node`) — raw `.ts` isn't that, on the range of Node versions a published package would need to support.

**At least two genuinely different shapes this could take, not yet chosen between**:

- Compile to plain JS at publish time (`tsc`/`esbuild`), ship the output, `bin` points at a `#!/usr/bin/env node`-shebanged compiled entrypoint. No runtime TS dependency for the end user, but now there's a real build step and a decision about *how* to compile (see below).
- Ship the `.ts` source as-is and make `tsx` (or an equivalent) a real dependency rather than a dev one, with the `bin` shebang invoking it directly. No build step, but every invocation pays transpilation cost, and it's an unusual shape for a published CLI (most don't ship raw TS to end users).

**The concrete complication that makes "just bundle it" non-trivial**: <a name='id/BlockNode:00CDHFW4RG004' class='aperas-anchor aperas-id'></a> `oxigraph` — the graph store this whole engine is built on — ships as a WASM binary (`node_bg.wasm`) plus a thin JS wrapper, not plain JS. A single-file bundle (esbuild et al.) can't just inline that the way it would inline ordinary TS/JS; it either needs to be left external (`--external:oxigraph`, meaning the published package still needs real `node_modules` dependency resolution, not a single self-contained script) or the wasm asset needs to be copied alongside the bundle output and referenced correctly. Either way, "compile everything into one file" isn't the free win it would be for a pure-JS/TS codebase.

**One more thing a build step forces a decision on**: <a name='id/BlockNode:00CDHFW4RG005' class='aperas-anchor aperas-id'></a> `packages/core`'s (and `cli`'s) own `exports` map today points straight at `.ts` source (`"./*": "./src/*.ts"`) — correct for the dev workspace, where every package is a sibling symlink and `tsx` handles the extension. A published package needs its own answer for what those exports point at instead (compiled `dist/*.js`, most likely) — and whether that's a *second*, publish-only exports shape layered on top of the dev one (conditional exports keyed by `"import"`/`"development"` or similar), or a wholesale switch, is itself an open call.

None of this is decided yet — flagged as open specifically because answering it means picking a compiler, a bundling strategy that accounts for `oxigraph`'s WASM binary, and how the workspace's own `exports` maps adapt for a built artifact, not just running one command.

Settled: <a name='id/BlockNode:00CDHJGZV0001' class='aperas-anchor aperas-id'></a> `esbuild` (not `tsc`) bundling `packages/core`+`packages/cli` into one output file, `oxigraph` marked `--external` (it's WASM-backed, can't be inlined, and staying external is normal for a published package). The dev workspace's own `exports` maps (pointing at `.ts` source) stay exactly as they are — a separate build step produces its own `dist/`+minimal package.json for publishing, rather than one config trying to serve both dev and published via conditional exports. Trade-off accepted: a second thing to maintain (a build config), in exchange for the already-verified dev loop never having to change for a publish pipeline that doesn't exist yet.

## Settled: graph discovery via two separate config files, not env-var-only <a name='id/BlockNode:00CDHSCK8R001' class='aperas-anchor aperas-id'></a>

Started from a concrete pain point: `APERAS_MACHINE_NUMBER` (the snowflake id generator's machine-uniqueness input) is env-var-only today, left unset because there was nowhere better to put it, and warns on every single invocation as a result. That, plus a much bigger piece of context — the graph this all points at won't stay a single flat corpus. It's meant to grow into a tree: a corp graph, team graphs under it, member graphs under those, each mergeable up into its parent, the same shape a member's private notes eventually get merged into a team's, and a team's into the corp's. A bare "walk up from cwd looking for an `AperasKG/` directory" (the plain-search idea floated earlier) only ever finds *one* graph — it has no way to express "this graph's parent is that one," so it doesn't fit this shape at all. A real config file does.

**Two separate files, not one, because they're different *kinds* of setting with different lifecycles:**

- **`identity.json`** — machine-local, never committed (gitignored, or living outside the repo entirely, e.g. `~/.config/aperas/identity.json`). Holds `APERAS_MACHINE_NUMBER`'s replacement: a `machineNumber` that must differ across machines by construction. Putting it in a *shared* config would be actively wrong, not just untidy — every clone/checkout would inherit the same committed number and start colliding on generated ids, silently, which is the worst way for a uniqueness mechanism to fail. Solving this also directly kills the "complains every time" annoyance: set once per machine instead of once per shell session.
- **`aperas.config.json`** — shared, committed, describes a graph's own place in the corp/team/member tree. Kept deliberately minimal for now rather than designing the merge mechanics today (a separate, bigger question): just two pointers, `graph` (this level's own artifacts root) and `parent` (the graph above it to eventually merge into, absent for a root graph). Enough to express the hierarchy and be discoverable, without committing yet to *how* a merge actually walks it.

Both replace the current `getArtifactsDir()`'s `__dirname`-relative hop-counting, which only ever made sense for "the CLI's own source lives a fixed number of directories below the one graph it drives" — never true for an installed CLI, and now also not expressive enough for a tree of graphs regardless of install-vs-source-checkout.

Not yet decided (separate, later passes): <a name='id/BlockNode:00CDHSCK90004' class='aperas-anchor aperas-id'></a> the actual merge mechanics (what "member graph merges into team graph" does at the node/id level), and how upward discovery behaves when *no* `aperas.config.json` is found at all (this repo's own dev setup should probably keep working via some fallback, likely the existing hardcoded-relative-path behavior, so the split docs/graph work already done doesn't need its own migration just to keep functioning).

## Settled: no concurrency — one active graph at a time, explicit start/restart only <a name='id/BlockNode:00CDWPCC3G001' class='aperas-anchor aperas-id'></a>

Clarified a confusion in the write-up above: a service holding a graph that's stable for its whole lifetime *was* the intent all along — the actual bug was that any command could *silently* auto-spawn one, so whichever command happened to run first invisibly decided the binding for as long as that process lived. The fix isn't to thread cwd through every request (that would mean re-resolving, i.e. potentially re-binding, on every call — not stable, and not the intent); it's to make the one moment of binding explicit and human-driven instead of accidental.

- `aperas service start` (new — today's `kg:service` only has `restart`) is the *only* place that ever reads `process.cwd()` for this. It resolves the graph (`aperas.config.json` discovery, or the dev fallback) and binds the spawned service to it, permanently, for that process's life.
- Every other command never touches cwd for this at all. It looks for the currently running service at one fixed, well-known location — not derived from cwd, and not derived from where the code itself is installed (which also sidesteps the dev-vs-built hop-counting fragility fixed above entirely, as a side benefit: a fixed location doesn't care where the code physically sits). If nothing's there, it errors ("no service running — run `aperas service start`") instead of silently auto-spawning one bound to whatever cwd it happened to be called from.
- `aperas service restart` becomes "stop whatever's running, and re-resolve+rebind from wherever *this* invocation's cwd is" — still explicit, still a deliberate human action.

Deliberately no concurrency: <a name='id/BlockNode:00CDX5H5MG005' class='aperas-anchor aperas-id'></a> one active graph system-wide at a time, not one service per graph root. Working in two different graphs at once means explicitly restarting the service when switching, not two processes running side by side. Confirmed as the actual intent, not a limitation being settled for.

## Resolved: the explicit-start service redesign, shipped and verified <a name='id/BlockNode:00CDXFWK3R001' class='aperas-anchor aperas-id'></a>

`ensureServiceRunning()` no longer auto-spawns — it just pings, and throws `No ApeironNgn service running. Start one with: aperas service start` if nothing answers. `kgService.ts` gained `aperas service start` (binds a freshly-spawned service to the graph resolved from *this* invocation's own `process.cwd()`, or reports the existing binding if one's already running) alongside the existing `restart` (now also re-resolving and rebinding, not just restarting the process). `serviceLock.ts`'s `getRunDir()` dropped the dev-vs-built hop-counting entirely in favor of a fixed location: `$XDG_RUNTIME_DIR/aperas`, falling back to a uid-namespaced `tmpdir()` path when unset — exactly the kind of ephemeral, per-session state `XDG_RUNTIME_DIR` exists for, and the same pattern `identity.json` already established for `$XDG_CONFIG_HOME`.

- `graphConfig.ts` gained `resolveEffectiveGraphRoot(startDir?)` — `aperas.config.json` discovery if found, else the fixed dev fallback (now computed in one place, not duplicated across `artifacts.ts`/`store.ts`). `getArtifactsDir()`/`getApeironExportDir()` both take an optional explicit `graphRoot` now: a standalone dev tool (`verify.ts`, `apeironNgnSmokeTest.ts`) omits it and keeps the old cwd-or-fallback default; `apeironNgn/service.ts` passes the graph root it was actually bound to (via `APERAS_GRAPH_ROOT`, set in the spawned child's environment by `serviceClient.ts#spawnService` — not the child's own `process.cwd()`, which is set to a fixed directory for unrelated reasons and would otherwise silently disagree with what `start` resolved).
- The service's own `dehydrateToJsonLd`/`dehydrateStateToJsonLd` calls (all 4 call sites: <a name='id/BlockNode:00CDXFWK40000' class='aperas-anchor aperas-id'></a> `flushIfDirty`, `flushStateIfDirty`, `clobberFlush`) now pass their bound `contentDir`/`stateDir` explicitly too, instead of each defaulting to a fresh (and, before this fix, potentially divergent) resolution of its own — otherwise the "one binding for the whole process lifetime" guarantee would only have covered the *read* path (`rehydrateStore`), not the *write* path.
- Verified live, both ways: <a name='id/BlockNode:00CDXFWK40001' class='aperas-anchor aperas-id'></a> (1) dev mode — `aperas service start` binds and reports the graph root, a second `start` reports "already running", `restart` stops+rebinds, killing the service and running any ordinary command reports the new error instead of silently spawning one, the full `npm run verify` suite (18 checks) still passes clean; (2) built mode — a fresh `esbuild` bundle cold-started via `node packages/cli/dist/aperas.js service start` (no `tsx` anywhere) binds correctly and answers a real `tree` read.

## Resolved: two-path graph config + env-var default resolution closes the artifacts-dir gap <a name='id/BlockNode:00CDZM30JG001' class='aperas-anchor aperas-id'></a>

`aperas.config.json`'s `graph` field now accepts two shapes: <a name='id/BlockNode:00CDZM8GP8001' class='aperas-anchor aperas-id'></a> a plain string (shorthand — both `<root>/Apeiron` and `<root>/artifacts` co-located, exactly today's behavior, unchanged) or `{ "apeiron": "<path>", "artifacts": "<path>" }` (two independently-specifiable roots, for a graph whose data and markdown tree aren't co-located). `resolveGraphConfig()` resolves both forms into one `GraphConfig { apeironRoot, artifactsRoot, parent, configPath }`.

`graphConfig.ts` gained `resolveEffectiveApeironRoot(startDir?)`/`resolveEffectiveArtifactsRoot(startDir?)`, replacing the single `resolveEffectiveGraphRoot()`. Each checks its own env var first (`APERAS_APEIRON_ROOT`/`APERAS_ARTIFACTS_ROOT`), then `aperas.config.json` discovery, then the fixed dev fallback. `getApeironExportDir()`/`getArtifactsDir()`'s own default parameters call these — unchanged call sites everywhere else, since the env-var check now lives inside the shared default resolution itself rather than being each caller's job.

`aperas service start`/`restart` (`kgService.ts`) resolve both roots once, from that one invocation's own cwd — still the only place cwd is read — and `spawnService()` sets both env vars on the child. Every function that calls `getArtifactsDir()`/`getApeironExportDir()` with no argument (`runTrack`, `runIngest`, `runProject`, and the shared `apeironNgn/artifacts.ts`/`folders.ts`/`node.ts` helpers) now resolves correctly with **zero signature or call-site changes**, because they're all running inside the one process that already has both env vars set for its whole lifetime — the same guarantee the "no concurrency, one bound graph per process" design already committed to.

This replaces the parameter-threading approach the gap note above originally assumed was necessary: threading an explicit root through `runTrack`/`runIngest`/`runProject` and every function they call would have meant touching upwards of a dozen call sites across `apeironNgn/artifacts.ts`, `folders.ts`, `node.ts`, plus every one of `verify.ts`'s direct calls into them. The env-var default achieves the same correctness for free, because the architecture already guarantees a service process is bound to exactly one graph for its entire life — parameter-threading would only earn its keep if a single process needed to serve different graphs per call, which this design deliberately never does.
