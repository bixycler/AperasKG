# Webapp — Discussion <a name='id/BlockNode:00CJ2TCV40001' class='aperas-anchor aperas-id'></a>

## Dashboard <a name='id/BlockNode:00CJ2TCV40002' class='aperas-anchor aperas-id'></a>

- **Scope**: <a name='id/BlockNode:00CJ2TVGBR001' class='aperas-anchor aperas-id'></a> `webapp` is the third thin wrapper over the shared `core` engine, alongside `cli` — anticipated by name in [cli's Settled scope](../discussion/cli.md#id/BlockNode:00CF2AEMER007), and sitting over the engine described in [core's Dashboard](../discussion/core.md#id/BlockNode:00CF1WZE18001). Its subject is the **UI projection** tier only; the i-projection it consumes belongs to [treeview](../discussion/treeview.md#id/BlockNode:00CE1DDF4G001).
- **TreeView**: <a name='id/BlockNode:00CJ2TVGC0000' class='aperas-anchor aperas-id'></a> [Rendering](../design/treeview.md#id/BlockNode:00CE1GW4Y800G) and [Viewcone Zoom](../design/treeview.md#id/BlockNode:00CE1GW4YG008) are the semantics this UI renders — it re-derives none of them.
- **Linking**: <a name='id/BlockNode:00CJ2TVGC0001' class='aperas-anchor aperas-id'></a> [`name` vs `id`](../design/linking.md#id/BlockNode:00CDC0D590010) already reserves the `id` attribute for this concern's own HTML element management.
- Design, Issues, Planning and History are not written yet — nothing has been built.

## Open Questions <a name='id/BlockNode:00CJ2TESY0001' class='aperas-anchor aperas-id'></a>

- **Transport is undecided**: <a name='id/BlockNode:00CJ2V5K2G001' class='aperas-anchor aperas-id'></a> three options, laid out in Freeflow below. A separate HTTP-to-socket bridge leaves the service untouched but adds a third process; an HTTP listener inside the service is one hop and one lifecycle but widens a surface that today has no auth at all; a Node-hosted shell removes the wire entirely at the cost of a much larger delivery story and a two-writer hazard.
- **Does the UI need to see the Agent's deep writes as they land?** This is what actually decides the transport question. Live notification can only honestly originate in the service, which is the sole writer and the only thing that knows when the store changed — a bridge cannot push what the protocol never tells it. If manual refresh after a handoff is acceptable, the bridge wins; if not, the in-service listener earns its complexity immediately.
- **How is a deep write handed to the Agent?** Composing an intent and handing it off could be a copied prompt, an MCP endpoint, or an embedded chat pane. Unexamined.
- **One link cited twice in the same block**: <a name='id/BlockNode:00CJ2V5K2R002' class='aperas-anchor aperas-id'></a> Wikipedia answers this with `^ a b` back-references from a single endnote. Whether the render tree even distinguishes two marker positions for one `Link` is unchecked.
- **Projection anchors in stored text**: <a name='id/BlockNode:00CJ2V5K2R003' class='aperas-anchor aperas-id'></a> ingested block text carries `<a name='id/...' class='aperas-anchor aperas-id'>` spans. How the UI renders around them — and what an in-place text edit must preserve — is unexamined.

## Settled <a name='id/BlockNode:00CJ2TESY0002' class='aperas-anchor aperas-id'></a>

- **The webapp is the UI-projection tier, so it never owns fold state**: <a name='id/BlockNode:00CJ2V1YAR001' class='aperas-anchor aperas-id'></a> [three tiers of perata](../design/treeview.md#id/BlockNode:00CE1GW4Y8009) names a Human UI as a consumer of an i-projection, "rather than reading a raw fold-state flag off the graph directly". Every fold control is therefore a *controlled* component whose state is `TreeView.unfolds` membership, round-tripped through `unfold`/`fold` — there is no local expanded/collapsed state anywhere in the UI.
- **Deep read, shallow write**: <a name='id/BlockNode:00CJ2V1YAR002' class='aperas-anchor aperas-id'></a> the UI reads by traversal as freely as the CLI does, but writes only a block's own body text. Any block's body, not only leaves — headings' titles and every structural operation (insert, move, remove, relink) are delegated to the Agent.
- **Why that write boundary is principled, not just an MVP scope cut**: <a name='id/BlockNode:00CJ2V1YAR003' class='aperas-anchor aperas-id'></a> body-text replacement is the one edit class that cannot tombstone anything. A parent-heading `update` reconciles and remints its subtree as a side effect; a push that changes item depth defeats matching entirely; `remove` + `insert` destroys ids outright. Confining the UI to text keeps every id, backlink and history position safe by construction rather than by care.
- **`FolderDiv`'s three slots are already the three render tiers**: <a name='id/BlockNode:00CJ2V1YAR004' class='aperas-anchor aperas-id'></a> `heading` is tier 1 (title only), `unfoldable` is tier 2 (`{title, abstract}`), `foldable` is tier 3 (children and links). This is why the port is a natural fit rather than a coincidence, and it is why the component needs no new concepts to carry [a node's own-line detail tiers](../design/treeview.md#id/BlockNode:00CE1GW4YG000).
- **What the port drops**: <a name='id/BlockNode:00CJ2V1YAR005' class='aperas-anchor aperas-id'></a> the `slotchange` handler that sniffed for a leading `<h*>` element existed because HTML carried no type information; `BlockNode.type` already answers it, so the Solid component takes an explicit `variant` of `heading` / `item` / `leaf` instead. Shadow DOM goes; the CSS custom properties it exposed through `:host` (`--control-foreground`, `--stem-line-foreground`, `--contents-indent`, and the rest) are kept verbatim as the theming surface, as is the hover-highlighted stem line.
- **Links render at two sites sharing one identity**: <a name='id/BlockNode:00CJ2V1YAR006' class='aperas-anchor aperas-id'></a> a superscript marker at the link text inside the block's own prose, and an endnote entry in the link list after the children — the position [`aperas tree --view`](../design/treeview.md#id/BlockNode:00CE1GW4YG004) already puts it in. Wikipedia's scheme exactly: `cite-ref-<linkId>` and `cite-note-<linkId>`, with click-through from marker to endnote and a back-caret returning to the marker.
- **Hovering a marker previews, and can promote**: <a name='id/BlockNode:00CJ2V1YAR007' class='aperas-anchor aperas-id'></a> the popover shows the rule-a preview and offers an unfold control that adds the `Link` itself to `unfolds` — which is what makes the endnote below expand. One source of truth; the popover has no fold state of its own.
- **Both sites obey canonical position rather than re-deriving it**: <a name='id/BlockNode:00CJ2V1YAR008' class='aperas-anchor aperas-id'></a> a link whose target is canonical elsewhere shows the [`[*see <path>]` pointer](../design/treeview.md#id/BlockNode:00CE1GW4YG006) and a jump, never a duplicate preview; an upward link renders as `(outside view)` and offers a zoom instead.
- **Zoom in is a new apex, zoom out is the breadcrumb**: <a name='id/BlockNode:00CJ2V1YAR009' class='aperas-anchor aperas-id'></a> ctrl-clicking a fold arrow re-renders with that node as apex, which is [viewcone zoom](../design/treeview.md#id/BlockNode:00CE1GW4YG008) with no new mechanism; the breadcrumb bar is the apex's own ancestor chain, and clicking a segment re-apexes there. A nested cone gets its own inline breadcrumb strip, for the same reason the text render emits one.
- **The apex is UI-local, not view state**: <a name='id/BlockNode:00CJ2V1YAR00A' class='aperas-anchor aperas-id'></a> `TreeView` deliberately holds `unfolds` and not an apex, and this design does not add one. Zoom history is browser state; a reload returns to the root.

## Freeflow <a name='id/BlockNode:00CJ2TESY0003' class='aperas-anchor aperas-id'></a>

- **Code inventory, 2026-09-17.** `packages/web` is the unmodified Vite+Solid scaffold — `App.tsx`, `index.tsx`, two CSS files, nothing else. It declares `@aperas/core` as a dependency and imports it nowhere, which is just as well: 14 files under `packages/core/src` import `node:fs`, `node:path` or `oxigraph`, so core cannot be bundled for a browser at all. That dependency is a scaffold leftover and should move to whatever host actually runs the engine.
- **The renderer is already split where the UI needs it split.** `renderTreeWithView` in `packages/core/src/apeironNgn/node.ts` runs two passes: `discoverCone` builds a render *plan* (`ConeInfo` — which ids are unfolded in this cone, which links escape it, which nested cone each escaping link spawned, the shared canonical/attempt maps) and only then does `emitNode`/`emitLinkLine` flatten it to `string[]`. Pass 1 is exactly what a UI wants; pass 2 is the only part that assumes text.
- **Proposed shape of the structured render.** A `buildRenderTree(...)` returning a tree of render items — for a node: id, display label, title, abstract, tier, hidden count, and the starred / tombstoned / holder flags; for a link: link id, predicate, target id, title, abstract, a mode of `preview` / `expanded` / `pointer` / `outside-view`, the pointer target or zoom path where those apply, and its own children and links. Today's text output becomes `toText(buildRenderTree(...))`, which keeps the existing verification suite as the guarantee that the refactor changed nothing — the text render must stay byte-identical. A `format` discriminator on the existing `tree` service op carries it to a caller.
- **The transport comparison in full.** *A separate bridge*: <a name='id/BlockNode:00CJ2VBQR0004' class='aperas-anchor aperas-id'></a> the service changes not at all — NDJSON over a unix socket, single-writer discipline, lock file, code-fingerprint check and conflict reporting all untouched — and the bridge can reuse `serviceClient`'s own spawn helpers, keep the socket filesystem-scoped, and host web-only concerns that should never enter the engine protocol. Against it: a third process alongside the service and the dev server, one connection per request per hop given the protocol is one-request-per-connection, a duplicated slice of error handling, and no answer yet for who starts it in a packaged build. *An in-service listener*: one process, one lifecycle, one hop, conflict and fingerprint reports reaching the browser verbatim from where they are produced, and the only honest origin for change notification. Against it: the service today binds a unix socket with filesystem permissions and no auth whatsoever, so a TCP listener needs origin checking and probably a token before it is safe against any page in the browser — a design task, not a flag — and it further entrenches `packages/cli` owning the service. *A Node-hosted shell*: no wire at all, deep read as a function call, and `@aperas/core` in the UI's dependencies finally honest. Against it: much the largest delivery story, against a repo whose packaging concern is still open; it forecloses opening the UI in a browser; Tauri reintroduces a bridge under another name while Electron ships Chromium; and a shell embedding core in-process while a CLI service also runs gives two writers to one mirror, which is the single thing the service exists to prevent — unless the shell simply is the service, which is the in-service listener again.
- **Write-path footguns the UI must hide.** The input rules are per node type and unforgiving: an existing list item takes bare text with no bullet marker, or `update` replaces its children with a nested list; a heading needs `--text-only`, or reconciliation tombstones its subtree from an empty body. A single `updateText(id, text)` on the host side should pick the right form per type so the UI never encodes any of it. The per-artifact link sweep the service already runs after every write, and the known failure where a write reports links resolved but persists none, both have to surface in the UI rather than being swallowed.
