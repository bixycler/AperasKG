## Open Questions <a name='id/BlockNode:00CJ2TESY0001' class='aperas-anchor aperas-id'></a>

- **Whether the tree renderer surfaces every position of a multi-position `Link`**: <a name='id/BlockNode:00CJ69H0T0001' class='aperas-anchor aperas-id'></a> the graph carries one `position` per occurrence, but whether `aperas tree --view` renders such a link once or once per position is unchecked. A renderer question rather than a model one, and the webapp's endnote back-references need the same answer.

## Settled <a name='id/BlockNode:00CJ2TESY0002' class='aperas-anchor aperas-id'></a>

- **The webapp is the UI-projection tier, so it never owns fold state**: <a name='id/BlockNode:00CJ2V1YAR001' class='aperas-anchor aperas-id'></a> [three tiers of perata](../design/treeview.md#id/BlockNode:00CE1GW4Y8009) names a Human UI as a consumer of an i-projection, "rather than reading a raw fold-state flag off the graph directly". Every fold control is therefore a *controlled* component whose state is `TreeView.unfolds` membership, round-tripped through `unfold`/`fold` — there is no local expanded/collapsed state anywhere in the UI.
- **Deep read, shallow write**: <a name='id/BlockNode:00CJ2V1YAR002' class='aperas-anchor aperas-id'></a> the UI reads by traversal as freely as the CLI does, but writes only a block's own body text. Any block's body, not only leaves — headings' titles and every structural operation (insert, move, remove, relink) are delegated to the Agent.
- **Why that write boundary is principled, not just an MVP scope cut**: <a name='id/BlockNode:00CJ2V1YAR003' class='aperas-anchor aperas-id'></a> body-text replacement is the one edit class that cannot tombstone anything. A parent-heading `update` reconciles and remints its subtree as a side effect; a push that changes item depth defeats matching entirely; `remove` + `insert` destroys ids outright. Confining the UI to text keeps every id, backlink and history position safe by construction rather than by care.
- **`FolderDiv`'s three slots are already the three render tiers**: <a name='id/BlockNode:00CJ2V1YAR004' class='aperas-anchor aperas-id'></a> `heading` is tier 1 (title only), `unfoldable` is tier 2 (`{title, abstract}`), `foldable` is tier 3 (children and links). This is why the port is a natural fit rather than a coincidence, and it is why the component needs no new concepts to carry [a node's own-line detail tiers](../design/treeview.md#id/BlockNode:00CE1GW4YG000).
- **What the port drops**: <a name='id/BlockNode:00CJ2V1YAR005' class='aperas-anchor aperas-id'></a> the `slotchange` handler that sniffed for a leading `<h*>` element existed because HTML carried no type information; `BlockNode.type` already answers it, so the Solid component takes an explicit `variant` of `heading` / `item` / `leaf` instead. Shadow DOM goes; the CSS custom properties it exposed through `:host` (`--control-foreground`, `--stem-line-foreground`, `--contents-indent`, and the rest) are kept verbatim as the theming surface, as is the hover-highlighted stem line.
- **Links render at two sites sharing one identity**: <a name='id/BlockNode:00CJ2V1YAR006' class='aperas-anchor aperas-id'></a> the link's own text inside the block's prose, and an endnote entry in the link list after the children — the position [`aperas tree --view`](../design/treeview.md#id/BlockNode:00CE1GW4YG004) already puts it in. Wikipedia's `cite-ref`/`cite-note` scheme, minus the superscript marker: Wikipedia needs `[1]` because a citation has no visible text of its own, whereas a wikilink already carries the words the reader is looking at, so the link text *is* the marker — it holds `cite-ref-<linkId>-<n>`, jumps to the endnote on click, and is what the endnote's back-caret returns to. What a marker would otherwise have signalled — that an endnote exists below — is carried by styling instead: a wikilink that resolved to a graph node is styled as one, a dangling one is not, which is a distinction worth showing in its own right.
- **Hovering a link previews, and can promote**: <a name='id/BlockNode:00CJ2V1YAR007' class='aperas-anchor aperas-id'></a> the popover shows the rule-a preview and offers an unfold control that adds the `Link` itself to `unfolds` — which is what makes the endnote below expand. One source of truth; the popover has no fold state of its own. The hover target is the link text itself rather than a separate glyph, so the reader hovers the words already being read.
- **Both sites obey canonical position rather than re-deriving it**: <a name='id/BlockNode:00CJ2V1YAR008' class='aperas-anchor aperas-id'></a> how a link's target renders is not a property of the link — it is a property of where that target's structural home sits relative to the current render, which [canonical position](../design/treeview.md#id/BlockNode:00CE1GW4YG006) already decides. Three states. The home is nowhere in the render, and the link renders the target itself — a rule-a preview folded, rule-b one level unfolded. The home is in the render, even as a bare title-only breadcrumb, and the link collapses to the `[*see <path>]` pointer plus a jump, never a second copy of the body. The target sits above the apex, and it renders as `(outside view)` plus a zoom-out. Obeying rather than re-deriving is aimed at a specific temptation: the popover and the endnote are two code paths, and each will locally find it easy to just show the target, at which point the two can disagree with each other and with `aperas tree` while nothing looks broken. Both must read one shared verdict. It also makes link-following cycle-safe for free, so the UI needs no visited set of its own.
- **Zoom in is a new apex, zoom out is the breadcrumb**: <a name='id/BlockNode:00CJ2V1YAR009' class='aperas-anchor aperas-id'></a> ctrl-clicking a fold arrow re-renders with that node as apex, which is [viewcone zoom](../design/treeview.md#id/BlockNode:00CE1GW4YG008) with no new mechanism; the breadcrumb bar is the apex's own ancestor chain, and clicking a segment re-apexes there. A nested cone gets its own inline breadcrumb strip, for the same reason the text render emits one.
- **The apex is UI-local, not view state**: <a name='id/BlockNode:00CJ2V1YAR00A' class='aperas-anchor aperas-id'></a> `TreeView` deliberately holds `unfolds` and not an apex, and this design does not add one. Zoom history is browser state; a reload returns to the root.

- **Transport: an HTTP listener inside the ApeironNgn service**: <a name='id/BlockNode:00CJ2V5K2G001' class='aperas-anchor aperas-id'></a> the UI has to show the Agent's deep writes as they land, and live notification can only honestly originate in the service — it is the sole writer and the only thing that knows when the store changed, so a separate bridge cannot push what the protocol never tells it. That decides it against the bridge, and a Node-hosted shell is out on delivery cost and on the two-writer hazard besides. The unix socket stays exactly as it is for CLI callers; the listener is an addition beside it, not a replacement for it.
- **Change notification is a bare tick, not a delta**: <a name='id/BlockNode:00CJ2V5K2R000' class='aperas-anchor aperas-id'></a> the service pushes *the store changed* and the UI refetches its current apex. The UI renders a view's `unfolds` set rather than a document with cursor state, so there is nothing a per-node delta would preserve that a refetch loses, and no delta format has to be invented to find that out. Carried over SSE — one-directional, no framing library, trivially proxied — which is a second protocol shape alongside today's one-request-per-connection NDJSON rather than a reuse of it.
- **Deep-write handoff is Phase 2+**: <a name='id/BlockNode:00CJ2V5K2R001' class='aperas-anchor aperas-id'></a> composing an intent and handing it to the Agent — a copied prompt, an MCP endpoint, an embedded chat pane — is out of the first phase entirely, unexamined rather than decided against. That pins Phase 1's whole write surface to one thing: an in-place edit of the current node's own text, which is an ordinary `update --text-only` over the same channel.
- **One link cited twice in the same block is already the stored shape**: <a name='id/BlockNode:00CJ2V5K2R002' class='aperas-anchor aperas-id'></a> resolution groups a block's wikilinks by distinct *target* (`positionsByTarget`, in `apeironNgn/artifacts.ts`), so one `Link` carries one `position` prop per occurrence, and identity is the target alone — position is metadata on that identity, which is why two occurrences that merely swap order still count as a real change. Wikipedia's `^ a b` is therefore nothing to add: one endnote per `Link`, one back-reference per `position`, and those positions are exactly the link-text occurrences that serve as the markers.
- **The UI's text input is the ingestion input**: <a name='id/BlockNode:00CJ2V5K2R003' class='aperas-anchor aperas-id'></a> no projection anchor has to be preserved across an in-place edit, because none of them are stored. A heading's tree-anchors are scooped into the `treeAnchor` prop and stripped from its title at parse; the `aperas-id` anchor is generated fresh at projection time and never written back; and `stripInlineAnchors` runs at the point of storage itself, so an anchor cannot enter a block's stored text through ingestion or through `update`/`insert` either. The editor therefore round-trips plain authored markdown — the same text the `.md` file carried before projection spliced anything into it.
- **The canonical-position verdict moves into `@aperas/core`**: <a name='id/BlockNode:00CJ69EA7G001' class='aperas-anchor aperas-id'></a> that computation lives inside the CLI's tree renderer today, so obeying it from the webapp means extracting it as a pure function over a view's `unfolds` set, the current apex and a node, returning the render verdict — with the CLI renderer becoming its first consumer rather than its owner. Both of the webapp's two link sites then read the same function the CLI reads, which is what makes "obey rather than re-derive" enforceable instead of merely intended.

- **Auth for the in-service listener**: <a name='id/BlockNode:00CJ69GNM0001' class='aperas-anchor aperas-id'></a> the threat is the browser, not the network — once the service listens on TCP, any page the user has open can reach it, and CORS does not stop a simple cross-origin POST from being *sent*, only from being read. Five controls, all cheap. The listener serves an explicit op allowlist — deep read plus `update --text-only` on one node — rather than proxying the whole service protocol; this bounds the damage of every other failure and is the one decision that is hard to retrofit. Every request carries a custom `X-Aperas-Token` header, which forces a CORS preflight and so stops a cross-origin request from ever being sent, independent of the token's value. The listener binds `127.0.0.1` explicitly, never `0.0.0.0`. The token is a per-run `randomBytes(32)` written into the existing run directory beside the lock and socket at mode 0600 — already the trust anchor for the socket, so no new secret-storage story — read by the dev server, which runs as the same user, and compared with `timingSafeEqual`. `Host` is rejected unless it is the loopback address, which is the specific anti-DNS-rebinding control, and `Origin` is allowlisted as defence in depth, never reflected back. TLS on loopback, accounts and request signing buy nothing against this threat model.

- **The tick stream is consumed with `fetch()` + `ReadableStream`, not `EventSource`**: <a name='id/BlockNode:00CJ6SVHX8001' class='aperas-anchor aperas-id'></a> `EventSource` cannot set a request header at all — its constructor takes a URL and `withCredentials`, nothing else — so it could carry the token only as a cookie, which is ambient and reintroduces exactly the CSRF shape the custom header exists to prevent, or as a URL ticket, which adds an issuance endpoint and an expiry store. It also collapses every failure into one opaque `onerror`, so a 401 is indistinguishable from a restart; that is a real defect here rather than a nuisance, because the token is per-run and the service restarts constantly in development. What `EventSource` gives in exchange is reconnection, backoff and `Last-Event-ID` resumption — and resumption is worthless against [a bare tick](#id/BlockNode:00CJ2V5K2R000), since a missed tick is not a lost update: the next one refetches everything, and reconnecting refetches unconditionally. That leaves a reconnect loop of a few lines, which we would want to own anyway to refetch on reconnect and pause while the tab is hidden. With `EventSource` out, SSE's wire format stops earning its keep — it exists to be parsed by `EventSource` — so the stream carries NDJSON, already the service's framing on the unix socket, rather than adding a second wire format to the codebase.

- **Fold state is two axes, not one bit — whether a node is pinned, and how much of its children shows**: <a name='id/BlockNode:00CMWKJYR0001' class='aperas-anchor aperas-id'></a> the binary folded/unfolded can't name what the renderer actually produces, since a node whose text shows only because its parent previews it is neither. One shape, two fills, three angles: fill says pinned (`▶`, in `unfolds`) or not (`▷`), angle says how much is revealed — east nothing, southeast partially, south fully — so `▷` never reaches south, correctly, because an unpinned node never shows children as content. Revelation is a total order, `{▷0° ≡ ▶0°} < ▷45° < ▶45° < ▶90°`, and its one tie (1 and 1′, both title-only) is separated by fill alone, which is right: collapsing should look like folding. `●` is U+25CF, not U+2022, per `FolderDiv.js`'s own note that the standard bullet is too small; `▶`/`▷` are U+25B6/U+25B7, a designed solid/hollow pair with near-identical metrics, rotated through the `transform` transition `.fd-arrow` already carries.
  
  | State | Glyph | Own line | Children | Pinned |
  | --- | --- | --- | --- | --- |
  | 1 | `▷` 0° | title | none as content — may still pass a breadcrumb child through | no |
  | 2 | `▷` 45° | title + text | none | no |
  | 2′ | `●` | title + text | none exist — confirmed dead end | yes |
  | 1′ | `▶` 0° | title | hidden, their own pins kept | yes |
  | 3 | `▶` 45° | title + text | as bare titles | yes |
  | 4 | `▶` 90° | title + text | with their own text | yes |
  | cut-off | `…` | title + text | render stopped at `maxDepth` | n/a — a property of the render, not the node |

- **A solid stem means "fold me"; a sparse dotted guide means "this is path, not content"**: <a name='id/BlockNode:00CMWMMRGG001' class='aperas-anchor aperas-id'></a> the stem appears only in states 3 and 4 — pinned, children rendered as content — so its click action is always `fold`, never a lie. That restores the original sketch's own rule (`#stemLine { display: none }`, shown only when unfolded), which the Solid port lost by keying the stem on "has children" instead, leaving inert full-height stems on rows with no toggle at all — the [arrow and stem are one control](../design/webapp.md#id/BlockNode:00CJDHYES8001), so a stem with nothing behind it is a broken promise. A breadcrumb still showing a child below it gets a *passive* guide instead: no hover, no pointer, depth legibility only. That distinction is the point rather than a consolation — a non-recursive fold renders the path to pinned descendants as a stairway instead of `a/b/c`, and the passive guide is what says the child below is the next path segment, not this node's own content. UI: a `repeating-linear-gradient`, roughly 2px on / 5px off, since `dotted`/`dashed` at 1px read as a merely-lighter solid line. Console: `╎` — which needs more than a character swap, because `'│ '.repeat(depth)` cannot express per-column variation (the mark at column *k* belongs to the ancestor at depth *k*), so the prefix has to be built from a per-level stack in both `toText` and `renderTreeLines`.

- **`fold` stops cascading, and the gestures follow the state rather than a fixed verb**: <a name='id/BlockNode:00CMWMP6X8001' class='aperas-anchor aperas-id'></a> plain `fold` now removes only this node's own entry, leaving descendants pinned so it reduces to a breadcrumb; `fold --stash` keeps the entry and hides the children, remembering their pins — the outliner-standard collapse, and the everyday "put it away"; `fold --recursive` keeps today's cascade, demoted to deliberate cleanup. `unfold` gains the reciprocal `--recursive`, plus `--no-preview` for the titles level and `--unstash` to reopen. Recursive unfold is not reopening a settled call: the archive's own §5 records it as "corrected from an earlier draft" purely to match the then-current `setUnfolded` implementation, never rejected on merit — and its neighbouring principle, that `unfolds` records intent one entry per explicit act while visibility is derived, is exactly why `--recursive` stores a flag rather than materialising every descendant id. On the UI the bare click always does the obvious thing to whatever is in front of it, and ctrl applies on the arrow and stem as well as the row — which [this section already specified](#id/BlockNode:00CJ2V1YAR009) and the implementation never honoured.
  
  | Gesture | unpinned (1, 2) | 1′ stashed | 3 titles | 4 previews | 2′ leaf | cut-off |
  | --- | --- | --- | --- | --- | --- | --- |
  | click | `unfold` → 4 | `unfold --unstash` → the level it held | `fold --stash` → 1′ | `fold --stash` → 1′ | `fold` — unpin | zoom / re-root |
  | shift | `unfold --no-preview` → 3 | `unfold --unstash --no-preview` → 3 | → 4 | → 3 | — | — |
  | ctrl | zoom | zoom | zoom | zoom | zoom | zoom |
  | alt | — (already unpinned) | `fold` → unpinned | `fold` → unpinned | `fold` → unpinned | = click | — |
  | alt+shift | `unfold --recursive` | `unfold --recursive` | `fold --recursive` | `fold --recursive` | — | — |
  
  ```
                  unpinned       1′ stashed     3 titles       4 previews
                  1 ▷0°  2 ▷45°  ▶0°            ▶45°           ▶90°

   click                         ●──────────────▶╌╌╌╌╌╌╌╌╌╌╌╌╌╌▶    unfold --unstash → whichever level it held

   alt+shift      ◀─────────────────────────────●──────────────●    fold --recursive — clears descendants’ pins
   ────────────────────────────────────────────────────────────────────────────────────────────────────────

   cut-off (…)   click zooms; the cut belongs to the render, not to the node
  ```

- **The level is two orthogonal subset fields on `TreeView`, not a reified entry and not one ordered scalar**: <a name='id/BlockNode:00CMWMRX88001' class='aperas-anchor aperas-id'></a> `unfolds` is a bare `reference`-kind field — one triple per entry, with nowhere to hang a prop — so a per-node level means either reifying each entry the way `Link` already is (the right shape, but a schema change plus migrating every existing view) or adding hard-coded sibling fields. Two of them: `unfoldsCollapsed` and `unfoldsNoPreview`, both subsets of `unfolds`, with the default level costing no storage at all. Orthogonal rather than one ordered scalar, deliberately — the same two fields either way, but a scalar makes "collapsed" and "titles-only" mutually exclusive, an invariant that has to be enforced in code and can be violated by any writer, while independent flags make all four combinations legal and the fourth is precisely the memory that lets unstash return to the level it came from instead of guessing. `unfolds` itself keeps membership alone, so `removeDanglingUnfolds` and `pruneStaleUnfolds` keep working as they are — though each new field has to join both sweeps, and the former's doc comment stops being true where it claims `unfolds` is the only `reference` field whose target can be a `Link`.
  
  | `collapsed` | `noPreview` | renders as | unstash returns to |
  | --- | --- | --- | --- |
  | 0 | 0 | 4 — previews | — |
  | 0 | 1 | 3 — titles | — |
  | 1 | 0 | 1′ — stashed | 4, previews |
  | 1 | 1 | 1′ — stashed | 3, titles |

- **The webapp's depth limit is computed from available width, and stays a server-side render option**: <a name='id/BlockNode:00CMWMVMV0001' class='aperas-anchor aperas-id'></a> indentation is a fixed `1.2rem` gutter per level, so the point at which a render stops being legible is arithmetic — `floor((width − buffer) / gutter)` — rather than a guessed constant. It is a legibility backstop, not a performance cap: at a typical viewport that lands around thirty levels, far past anything this corpus nests to, so the `…` control is rare by construction. Kept as `maxDepth` on the server render, recomputed and refetched (debounced) on resize, rather than truncated client-side — that way `truncated` keeps a single meaning and the UI grows no parallel notion of depth, driving the same field the [link preview popover](#id/BlockNode:00CJ2V1YAR007) already uses with `depth: 0`.

## Freeflow <a name='id/BlockNode:00CJ2TESY0003' class='aperas-anchor aperas-id'></a>

- **`packages/web`'s code inventory, 2026-09-17**: <a name='id/BlockNode:00CJ2VBQR0001' class='aperas-anchor aperas-id'></a> the unmodified Vite+Solid scaffold — `App.tsx`, `index.tsx`, two CSS files, nothing else. It declares `@aperas/core` as a dependency and imports it nowhere, which is just as well: 14 files under `packages/core/src` import `node:fs`, `node:path` or `oxigraph`, so core cannot be bundled for a browser at all. That dependency is a scaffold leftover and should move to whatever host actually runs the engine.
- **The renderer already splits plan from text**: <a name='id/BlockNode:00CJ2VBQR0002' class='aperas-anchor aperas-id'></a> `renderTreeWithView` in `packages/core/src/apeironNgn/node.ts` runs two passes: `discoverCone` builds a render *plan* (`ConeInfo` — which ids are unfolded in this cone, which links escape it, which nested cone each escaping link spawned, the shared canonical/attempt maps) and only then does `emitNode`/`emitLinkLine` flatten it to `string[]`. Pass 1 is exactly what a UI wants; pass 2 is the only part that assumes text.
- **Proposed shape of the structured render**: <a name='id/BlockNode:00CJ2VBQR0003' class='aperas-anchor aperas-id'></a> A `buildRenderTree(...)` returning a tree of render items — for a node: id, display label, title, abstract, tier, hidden count, and the starred / tombstoned / holder flags; for a link: link id, predicate, target id, title, abstract, a mode of `preview` / `expanded` / `pointer` / `outside-view`, the pointer target or zoom path where those apply, and its own children and links. Today's text output becomes `toText(buildRenderTree(...))`, which keeps the existing verification suite as the guarantee that the refactor changed nothing — the text render must stay byte-identical. A `format` discriminator on the existing `tree` service op carries it to a caller.
- **The transport comparison in full**: <a name='id/BlockNode:00CJ2VBQR0004' class='aperas-anchor aperas-id'></a> *A separate bridge*: the service changes not at all — NDJSON over a unix socket, single-writer discipline, lock file, code-fingerprint check and conflict reporting all untouched — and the bridge can reuse `serviceClient`'s own spawn helpers, keep the socket filesystem-scoped, and host web-only concerns that should never enter the engine protocol. Against it: a third process alongside the service and the dev server, one connection per request per hop given the protocol is one-request-per-connection, a duplicated slice of error handling, and no answer yet for who starts it in a packaged build. *An in-service listener*: one process, one lifecycle, one hop, conflict and fingerprint reports reaching the browser verbatim from where they are produced, and the only honest origin for change notification. Against it: the service today binds a unix socket with filesystem permissions and no auth whatsoever, so a TCP listener needs origin checking and probably a token before it is safe against any page in the browser — a design task, not a flag — and it further entrenches `packages/cli` owning the service. *A Node-hosted shell*: no wire at all, deep read as a function call, and `@aperas/core` in the UI's dependencies finally honest. Against it: much the largest delivery story, against a repo whose packaging concern is still open; it forecloses opening the UI in a browser; Tauri reintroduces a bridge under another name while Electron ships Chromium; and a shell embedding core in-process while a CLI service also runs gives two writers to one mirror, which is the single thing the service exists to prevent — unless the shell simply is the service, which is the in-service listener again.
- **Write-path footguns the UI must hide**: <a name='id/BlockNode:00CJ2VBQR0005' class='aperas-anchor aperas-id'></a> The input rules are per node type and unforgiving: an existing list item takes bare text with no bullet marker, or `update` replaces its children with a nested list; a heading needs `--text-only`, or reconciliation tombstones its subtree from an empty body. A single `updateText(id, text)` on the host side should pick the right form per type so the UI never encodes any of it. The per-artifact link sweep the service already runs after every write, and the known failure where a write reports links resolved but persists none, both have to surface in the UI rather than being swallowed.
