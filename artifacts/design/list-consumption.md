## Architecture <a name='id/BlockNode:00CE32GQM8008' class='aperas-anchor aperas-id'></a>

A `list` block encountered while parsing markdown into the graph never survives as its own node when something can absorb it. What "absorb" means, precisely, is one law with two outcomes depending on what the nearest preceding text turns out to be:

1. **Consumption** — the list is immediately preceded, among its raw siblings, by a paragraph, listItem, or heading that gets emitted as a real node of its own. The list's items become that node's own `children`, nested one level inside it. This matches ordinary reading: a list right after "Given ...:" belongs to that sentence, not to whatever paragraph came before it.
2. **Dissolution via merged self** — the immediately preceding paragraph is the enclosing heading's or listItem's own *leading* paragraph, already consumed into the container's own `.text` (a separate, older rule: a heading/listItem's first paragraph child is text, not a child node). There is no separate node left for the list to nest into, so its items become the container's *own* children directly — flat, not nested one level deeper. This is the identical law to (1); it resolves to the container's own identity only because that's what "the nearest preceding text" turned out to be.
3. **Dissolution when orphaned** — nothing precedes the list at all: <a name='id/BlockNode:00CE32GQMG000' class='aperas-anchor aperas-id'></a> not a separate node, not even a mergeable leading paragraph (a code block or blockquote sits directly above it, or the list is the first content with nothing before it). The list still dissolves: its items become flat children of the true structural parent, at the position the list itself occupied among its siblings. There is no case under this law where a bare, unaddressable `list` node is the correct outcome, and none remain live in the corpus — fully implemented and migrated, see [History](../history/list-consumption.md#id/BlockNode:00CE32GW3G002).

`orderedList`/`startIndex` always live on the run's own first item, uniformly across all three cases above — never on the anchor, the merged container, or a synthetic wrapper. This is a deliberate normalization, not merely "wherever convenient": a structural parent can host more than one run (two authored lists separated by an intervening code block, say), and only a per-run location can describe two different runs at once — a shared slot on the anchor or container cannot, no matter which of the three cases produced that anchor. It also collapses what would otherwise be three different "where do these props go" decisions (one per case above) into one: whichever run of adjacent listItems this is, its own first member owns its metadata.

A run of adjacent `listItem`s doesn't always mean one list: <a name='id/BlockNode:00CE47F32G001' class='aperas-anchor aperas-id'></a> two lists can sit directly adjacent in the source with nothing between them (a bullet list immediately followed by an ordered list, no blank line — a real, common markdown shape, not a contrived edge case), and once both dissolve as orphans their items land back-to-back under the same parent, all typed `listItem` with no structural marker separating them. A run therefore ends not just where the type changes, but wherever the *next* item carries its own explicit `orderedList`/`startIndex` — a run-leader signal every dissolved run's first item already carries regardless of adjacency. This case is specific to orphan-dissolution: consumption and self-dissolution can never produce two runs under one parent, since only one thing can ever adopt into, or merge into, one given anchor.

Nested lists (`listItem -> listItem`, an item whose own content is only a sub-list) are unaffected by any of this — already, and still, an ordinary containment edge.

## Projection <a name='id/BlockNode:00CE32GQMG003' class='aperas-anchor aperas-id'></a>

A contiguous run of sibling `listItem`s renders as one markdown list, regrouped from adjacency the same way CommonMark itself recovers list structure from flat text — never from an explicit container. Regrouping keys on two things, not one: the type boundary (where `listItem`s stop), and — within a type-contiguous span — wherever the *next* item carries its own explicit `orderedList`/`startIndex`, marking the start of a new run even though the type hasn't changed (two orphan-dissolved lists landing back-to-back need this to stay distinguishable; see Architecture). The props sourced for each run always come from that run's own first item, uniformly — never from whichever anchor happens to sit above it (today's code still reads from the enclosing node instead, and only ever finds one run per node; see Issues/Planning). Projected markdown is identical regardless of whether a run's ownership is consumption or dissolution — the distinction is invisible on disk, and only matters for how the graph itself is addressed, folded, and traversed.
