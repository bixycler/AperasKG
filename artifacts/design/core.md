## Purpose and scope <a name='id/BlockNode:00D24N87SR006' class='aperas-anchor aperas-id'></a>

The engine is the graph the service holds in memory, between the mirror on disk and the commands that read and change the graph.

- **The boundary**: <a name='id/BlockNode:00D3CJFB7G001' class='aperas-anchor aperas-id'></a> the engine manages, in memory, the records of the nodes and the forward and reverse sides of their reference and embed fields, with their ports, the ordered and partitioning fields, the tombstones and several graphs, under the schema it is given (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)). The shell is the part that calls the engine ([the shell](#id/BlockNode:00D4M7YEZG001)). Dehydrating the records to disk and rehydrating them are the shell's: the mirror, its format, the load, the flush and the maps for lookups by a literal value make up the shell's persistence, which builds the engine's graphs and reads them out through the engine's [persistence API](#id/BlockNode:00D4MZ7DZG001). The code follows the boundary in its folders: `monorepo/packages/core/src/apeironNgn/` is the engine, in memory, `monorepo/packages/core/src/shell/` is the shell, on disk, and the engine's directory imports only files inside it: no `node:` module and no package at all, so nothing of the shell, no file system and no store library. This document follows the boundary: the engine, in memory, then the shell, on disk.

- **A reflection of the mirror**: <a name='id/BlockNode:00D24N87SR007' class='aperas-anchor aperas-id'></a> the JSON-LD files under `Apeiron/`, tracked in git, are the source of truth. The engine holds nothing that a fresh load of the mirror would not rebuild. It has no persistence of its own: the shell's persistence builds it from the mirror when the service starts or reloads, and reads it out to the mirror when it flushes, through the engine's [persistence API](#id/BlockNode:00D4MZ7DZG001) (see [The shell, on disk](#id/BlockNode:00D3CHMYQG001)).
- **One schema, handed in at construction**: <a name='id/BlockNode:00D24N87SR008' class='aperas-anchor aperas-id'></a> the fields a node can have are declared once for each kind, in the schema that the shell passes to the engine when it constructs it (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)), and that declaration is the only schema. There is no schema language beside it and no query surface that shapes the data differently from it; the accessors of a field, in the shell's classes, go through the schema, which knows the field's cardinality and storage kind. Whether the two paths that take keys from outside the schema (the load of a mirror document and the minting of an embedded node) are held to it as well is an Open point (see [Enforcement](#id/BlockNode:00D24N87T000M)).
- **Versioning is git**: <a name='id/BlockNode:00D24N87SR009' class='aperas-anchor aperas-id'></a> a write to the mirror followed by an ordinary commit is the version control. The engine has no commit layer, and merging work from another copy is git's merge on the mirror.
- **No concurrent access**: <a name='id/BlockNode:00D24N87SR00A' class='aperas-anchor aperas-id'></a> one process owns the engine and handles one request at a time. The engine has no locks, no transactions and no isolation of its own.
- **Search is not here**: <a name='id/BlockNode:00D24N87SR00B' class='aperas-anchor aperas-id'></a> free-text and pattern search have no index-servable shortcut in any engine and need a secondary index of their own, which this document does not describe (see [Open points](#id/BlockNode:00D24N87T000J)).
- **Why a node-based engine**: <a name='id/BlockNode:00D39EJSZ8001' class='aperas-anchor aperas-id'></a> the workload is node-heavy: commands read whole nodes, render trees of them, and write the mirror by a dump at each flush. So the properties of a node live on its record, and only the relations between nodes are pairs (see [The data model](#id/BlockNode:00D24N87SR00D)). An edge layout, which holds every property as a statement of its own, pays a lookup for each property read; it suits arbitrary pattern queries over an open vocabulary, and Aperas has neither: its vocabulary is closed and the shell asks no such query (see [Closed vocabulary](#id/BlockNode:00D24N87SR00E) and [Not offered](#id/BlockNode:00D24N87T000H)). The evidence is filed in [the full-store scans](../issues/core.md#id/BlockNode:00D0W02KPG001) and [the cost of a write](../issues/core.md#id/BlockNode:00D22Z1HJ8001), and the move away from the edge layout is recorded in [the history](../history/core.md#id/BlockNode:00D21FP4ZG009).
- **Outside this document**: <a name='id/BlockNode:00D24N87SR00C' class='aperas-anchor aperas-id'></a> the service lifecycle (start, stop, the timing and the guard of a flush, ownership of the process, recovery, the waits of the client), the mapping of markdown into blocks and back, the addressing grammar ([linking](../design/linking.md#id/BlockNode:00CDBYV4T0001)) and the views ([treeview](../design/treeview.md#id/BlockNode:00CE1GW4Y8001)). Each consumes the engine and none changes its rules; the mapping of markdown, the addressing and the views are parts of the shell ([the shell](#id/BlockNode:00D4M7YEZG001)).

## The engine, in memory <a name='id/BlockNode:00D3CHJXK0001' class='aperas-anchor aperas-id'></a>

### The data model <a name='id/BlockNode:00D24N87SR00D' class='aperas-anchor aperas-id'></a>

The engine stores pairs. Each field is a fixed relation, and a pair (s, v) is one link of that relation from a subject s to a value v; in RDF terms these are triples (subject, field, value) whose predicate, the field, never varies. The field is fixed first, and pairs are managed field by field. On a node n each field has two sides: the forward side holds the pairs n → v, where n is the subject, and the reverse side holds the pairs s → n, where n is the value. Each pair sits on two records, on its subject's forward side and on its value's reverse side. Only reference and embed fields hold pairs (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)).

- **The meta-model**: <a name='id/BlockNode:00D4MYZ6Q0000' class='aperas-anchor aperas-id'></a> the engine is generic and names no class or field of its own. The shell passes it a schema when it constructs it, and the schema is closed at construction, fixed for the engine's life. The schema is written in the engine's meta-model: kinds, each of which can extend another and inherit its fields; for each field of a kind, its [storage kind](#id/BlockNode:00D24N87SR00H) and its [cardinality](#id/BlockNode:00D24N87SR00G), a literal field declaring no type (its value is a string, a number or a boolean) and an embed field naming the kind it embeds, which the embedded node's id carries; the reference and embed fields, whose pairs the engine keeps, each with the name of its reverse side where the engine must expose that side as a field (the name is optional, and every other reverse side is read by the field and the value: see [A field is a relation](#id/BlockNode:00D24N87SR00F)), a reverse name taking a place in the field order of the kinds that have it as a derived entry, which the engine reads from the reverse side and for which it stores no pair; the [ordered](#id/BlockNode:00D255WVK0001) and [partitioning](#id/BlockNode:00D3CJDGH8001) fields; the field of [containment](#id/BlockNode:00D24N87SR00Z); the field that marks a [tombstone](#id/BlockNode:00D24N87SR01V); the reference fields whose value is dropped when its target is removed (see [Embedded nodes have ids and are removed outright](#id/BlockNode:00D24N87SR013)); and the root kinds of [the sweep](#id/BlockNode:00D3CHJXK8001) and the fields it follows. A rule of the engine that needs a particular field names the role that the schema assigns, and which field holds the role is the schema's choice. The Aperas schema, its classes and their fields, is the shell's (see [The Aperas schema](#id/BlockNode:00D4MZ15AR001)).

- **Closed vocabulary**: <a name='id/BlockNode:00D24N87SR00E' class='aperas-anchor aperas-id'></a> every field of a record is one that the schema declares for its subject's kind. Nothing else is stored. Containment is the field to which the schema assigns that role, and the parent is its reverse (see [Containment](#id/BlockNode:00D24N87SR00Z)). That the vocabulary is closed is a property of the data and of the shell; whether the engine enforces it is open (see [Open points](#id/BlockNode:00D24N87T000J)).
- **A field is a relation**: <a name='id/BlockNode:00D24N87SR00F' class='aperas-anchor aperas-id'></a> a reference or embed field relates subjects to the nodes that are their values, and has a forward side (the values of field F of subject S) and a reverse side (the subjects whose field F holds node V). The reverse side exists for every such field; which reverse sides the shell uses is the shell's choice, and the engine keeps no list of the fields that have one.
- **Literal fields are properties of the record**: <a name='id/BlockNode:00D39DRYB0001' class='aperas-anchor aperas-id'></a> a literal field is a plain property of its node's record, read and written there, with no pairs and no reverse side. The engine manages pairs for reference and embed fields only. A lookup by the value of a literal field (a profile by its `handle`, a view by its `name`, an artifact or a folder by its stored `path` as long as it is stored) is served by a map that the shell adds and keeps; the engine keeps no such map. Once the path is derived, the same map is keyed by the derived path, which no field holds (see [The path is derived from the parent chain](#id/BlockNode:00D24N87SR01S)).
- **Cardinalities**: <a name='id/BlockNode:00D24N87SR00G' class='aperas-anchor aperas-id'></a> `one` (exactly one value), `optional` (at most one), `set` (any number, unordered) and `ordered` (a set with an order, see [Ordered fields](#id/BlockNode:00D255WVK0001)). A cardinality is declared in the schema for each field of each kind and is never inferred from the data: a set field that holds one value must stay distinguishable from an optional field that happens to be set, which counting the values cannot tell.
- **Storage kinds**: <a name='id/BlockNode:00D24N87SR00H' class='aperas-anchor aperas-id'></a> `literal` (a plain value), `reference` (the id of another node, which the field does not own) and `embed` (a node the field owns: it has an id of its own, is written inside its owner's document in the mirror and is removed with its owner).
- **Literal types**: <a name='id/BlockNode:00D24N87SR00J' class='aperas-anchor aperas-id'></a> string, integer and boolean, kept as their JavaScript types, so the string "1" and the number 1 are different values. A string that looks like a date stays a plain string, because typing it as a date would let a store rewrite its text.
- **Ports, the two ends of a pair**: <a name='id/BlockNode:00D3CJCK10001' class='aperas-anchor aperas-id'></a> a port is a sub-address of a node that continues its deep path. A pair joins an outgoing port of its subject, such as an embedded node that holds a reference (a `Link` in the Aperas schema) or an item's place in an ordered list, to an incoming port of its object, the partition of its reverse side where the entry lands (see [Ports](#id/BlockNode:00D2T5VG08001)). "Port" is one notion with these two ends.
- **Ordered fields**: <a name='id/BlockNode:00D255WVK0001' class='aperas-anchor aperas-id'></a> a field can be declared ordered. Its forward side is then a list on its host: a set plus an order, so an item appears in it at most once. The port of an item is `host:item`, keyed by the item's own id, and the reverse of the item points at that port. The order is kept only in the live list: a reader that needs an item's place asks its port, which reads it from the host's list on demand. There is no sibling index and no order key, so an insertion or a move is one splice of the list and no reverse entry changes.
- **Partitioning fields**: <a name='id/BlockNode:00D3CJDGH8001' class='aperas-anchor aperas-id'></a> a field can be marked partitioning in the schema, closed at construction and never at run time, and the engine ensures the mark: each node has at most one value on the side that is climbed, and the relation has no cycle. The mark names no direction; the engine derives the climb from the field's cardinality. A single-valued field (`one` or `optional`) is climbed forward, from a node to its value, and its cardinality already bounds each node to at most one value on that side. A many-valued field is climbed on its reverse side, from a node to the subjects whose field holds it, and there the engine checks that a node has one subject at most (containment is such a field: a node is in one container's list). The cycle check follows the climb. The ports use a partitioning field as the hierarchy of a split (see [A partition hierarchy](#id/BlockNode:00D2T5XBH0001)).
- **Containment**: <a name='id/BlockNode:00D24N87SR00Z' class='aperas-anchor aperas-id'></a> containment is the field to which the schema assigns that role (`children` in the Aperas schema, declared on `TreeNode`, so that a block, an artifact and a folder all hold children), declared ordered and partitioning (see [Ordered fields](#id/BlockNode:00D255WVK0001) and [Partitioning fields](#id/BlockNode:00D3CJDGH8001)). The list of a container holds its children in order; a node is in at most one container's list, and containment has no cycle. The reverse of the containment field at a node is its port in its container's list, which gives the node's parent and its place; the parent is read from that reverse, under the name the schema gives the reverse side (`parent` in the Aperas schema), and the engine keeps it consistent with the lists on every write. A node has at most one parent. Containment is written through the containment field. Containment is not ownership: taking a node out of its container's list detaches it and does not delete it. A node is owned or contained, never both: an id of the embedded shape (`owner:field:Kind:snowflake`, see [Ids](#id/BlockNode:00D24N87SR01N)) cannot be listed in a containment field, so the node that an owner embeds has no place in any container's list and a node has one place in the tree. A tombstone is in no container's list (see [Tombstones](#id/BlockNode:00D3CHJXK8000)).
- **Where a node's parent comes from**: <a name='id/BlockNode:00D2562RC8001' class='aperas-anchor aperas-id'></a> the order of the children lives in the stored containment list of their container, whose positions are the order, so the list is not derived from the parent. Today's code extracts a sibling index for each child from the stored `children` at load, keeps it with the child's `parent`, and derives `children` from them afterwards; a file whose `parent` and `children` disagree loads as it stands ([the issue](../issues/core.md#id/BlockNode:00D2538VKR001)). The engine keeps the order in the list itself and reads an item's place from its port (see [Ordered fields](#id/BlockNode:00D255WVK0001)). The mirror states containment twice, in the container's `children` and in the child's `parent`, redundantly, for clarity; when the two disagree, the shell's load applies its rule (see [A file whose `parent` and `children` disagree](#id/BlockNode:00D2PV8GC0001)).
- **Records follow containment**: <a name='id/BlockNode:00D2T5P9Y8001' class='aperas-anchor aperas-id'></a> the records are arranged in the containment tree, a node's record under its container's, as the documents are in the mirror, and not in one flat table of all subjects. The forward hierarchy is authored (containment); the reverse hierarchy, the ports, is made by the engine (see [Ports](#id/BlockNode:00D2T5VG08001)). The engine aims to keep a node's record as close as possible to its document in the mirror, to reduce the shell's work: its literal fields as plain properties, the values of its reference fields, and its embedded nodes nested in the fields that own them. This is an aim and not a guarantee, and the shell always bridges the gap between a record and its document. A record also carries what the file does not hold: the reverse sides of its fields, with their ports, each built the first time the field is asked in reverse (see [Reverse, for each field, built on first use](#id/BlockNode:00D24N87SR017)). One master map from id to record sits beside the tree as an aid for direct access and does not replace the tree; it serves every graph, since an id is unique across all graphs (see [Ids](#id/BlockNode:00D24N87SR01N)).
- **Records by kind and by graph**: <a name='id/BlockNode:00D24N87SR018' class='aperas-anchor aperas-id'></a> the kind of a node is not a pair; it is read from the prefix of its id, and its graph is held in two folds. In memory the graph is a field: the record carries its `graph` and is filed in the collection of its graph and kind, with the master map from id to record across graphs beside the tree, so `graphOf` reads the field of the record that the master map finds. In the mirror the graph is file containment: a document has no `graph` field, the file for its graph and kind holds it, the load gives each record the graph of the file it reads, and the dump writes each record to the file of its graph and kind (see [Written by graph and kind](#id/BlockNode:00D24N87SR01Y)). The engine keeps one collection for each graph and each kind of the schema, a set of the records themselves, and no separate set of ids. Creating a node adds its record to its collection and deleting the node removes it; a dump or a sweep iterates the collection for all the nodes of a kind in a graph. The natural order of a collection is the order of insertion, which follows the increasing codes of the ids and so makes the shell's sort at a dump cheap (see [Orders in the mirror](#id/BlockNode:00D24N87SR01G)); it is promised to no reader.
- **No set of live ids**: <a name='id/BlockNode:00D24N87T000X' class='aperas-anchor aperas-id'></a> the engine keeps no set of live ids beside the collection of each kind (see [Records by kind and by graph](#id/BlockNode:00D24N87SR018)), because none of its operations needs one: the sweep walks reachability from the roots, the dump needs every id, and the lookups of live nodes are the shell's maps. The shell's `liveIdsOfKind` filters the tombstoned ids out of the collection of the kind, for the callers of "all ids of kind K" that need live nodes only.
- **Embedded nodes have ids and are removed outright**: <a name='id/BlockNode:00D24N87SR013' class='aperas-anchor aperas-id'></a> an embedded node (a `Link` or a `StringProp` in the Aperas schema) has an id of its own and can be addressed, but it has no tombstone. Removing a pair of an embed field (`removePair`) removes, recursively, the embedded node the pair names (the embedded nodes of a removed one go with it, as the props of a `Link` do), so no orphan stays in the store. A write of an embed field that keeps some of its embedded nodes is `removePair` for each value it drops and `addPair` for each value it adds, so the nodes it keeps keep their ids (see [Writes](#id/BlockNode:00D24N87T000C)). Removing any node also drops it from every reference field to which the schema assigns the role of a value dropped with its target (`unfolds` in the Aperas schema). Other incoming references (a link's target, a parent, a profile) are not removed by deleting the node; keeping none of them dangling is the work of the sweeps of the service, and the engine answers the ids that are referenced and never defined, which the shell asks once it has built a graph (see [Persistence](#id/BlockNode:00D4MZ7DZG001)); what is done with them belongs to the service lifecycle.

### The index <a name='id/BlockNode:00D24N87SR015' class='aperas-anchor aperas-id'></a>

Every lookup the shell makes binds either the subject or the field and the value, so the engine answers them from the forward and reverse sides of its records, iterates the collection of a kind when all the nodes of that kind are asked for, and traverses the whole store only for the check the shell asks at load, the ids that are referenced and never defined.

- **Forward, the record of each subject**: <a name='id/BlockNode:00D24N87SR016' class='aperas-anchor aperas-id'></a> the forward side of a node's fields is its record (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)). The values of field F of subject S are read from the record, and the whole record of S (what a flush or a wrapper needs) is read whole, with no lookup for each field.
- **Reverse, for each field, built on first use**: <a name='id/BlockNode:00D24N87SR017' class='aperas-anchor aperas-id'></a> the reverse of a field is built the first time the field is asked in reverse and kept up to date by every write afterwards, so the engine supports reversal for every reference and embed field without paying for the fields nobody reverses. It is held on the record of each object (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)), not in a table of its own: the bucket of an object for a field, the subjects whose field holds that object, is a leaf or a split record of ports (see [Ports](#id/BlockNode:00D2T5VG08001)). A leaf is a set, for the cost of removal and of membership: a bucket can hold thousands of subjects, and taking one out or asking whether one is present must not scan the rest.
- **Ports**: <a name='id/BlockNode:00D2T5VG08001' class='aperas-anchor aperas-id'></a> a bucket is split into incoming ports (see [Ports, the two ends of a pair](#id/BlockNode:00D3CJCK10001)) when it outgrows the cap set for its field. The shell sets the cap of each field and names the [partitioning field](#id/BlockNode:00D3CJDGH8001) of the sources that the split follows, such as containment for the tree of blocks; the engine chooses the levels: a bucket over the cap is split by the ancestors of its sources at the next level of that hierarchy, and a port still over the cap is split at the level below, so each branch goes only as deep as its own pairs need. A split merges back only when its count falls well below the cap, so the ports do not change back and forth around it. The cap is soft: pairs that the hierarchy cannot tell apart (sources with the same deepest ancestor, or with no place in the hierarchy) stay together in one port, the residue, even above the cap. Nothing about ports is stored: their shape follows from the current pairs and the caps.
- **A partition hierarchy**: <a name='id/BlockNode:00D2T5XBH0001' class='aperas-anchor aperas-id'></a> a field can serve as the hierarchy of a split only if it is marked partitioning (see [Partitioning fields](#id/BlockNode:00D3CJDGH8001)), so that every pair falls into exactly one port. The mark is set in the schema (see [Partitioning fields](#id/BlockNode:00D3CJDGH8001)), and the engine refuses every write that would give a node a second value on the climbed side or close a cycle; the climbed side follows from the field's cardinality, with no direction on the mark. For IS-A, where a tag may have several supertags, the data keeps the many-valued relation for its meaning and adds a single-valued primary-supertag field, which is the tree the partition follows, climbed forward from a tag to its primary supertag by its cardinality; a secondary supertag edge is marked as such when it is written, and the partition ignores it, so nothing is trimmed.
- **Captured port views**: <a name='id/BlockNode:00D2T5Z6J0001' class='aperas-anchor aperas-id'></a> the engine shows the port tree of a bucket as it currently is, and the shell can capture it as a view, which stays still while the engine's own ports go on changing. A captured port view keeps only the shape, the boundary node of each port; its contents are recomputed from the current pairs whenever it is used, and the engine answers through it by merging its own finer ports or sorting a coarser one on the fly. It is a kind of view of its own, distinct from the shell's views (`TreeView` in the Aperas schema); the shell keeps it on disk (see [Files](#id/BlockNode:00D24N87SR01X)), and it is removed only by hand, as it was captured by hand. What it is called is an Open point (see [The name of a captured port view](#id/BlockNode:00D2T6X3CG001)).
- **Writes**: <a name='id/BlockNode:00D24N87SR019' class='aperas-anchor aperas-id'></a> writing a field of a node updates that node's pairs of that field: its new values replace its old ones, and the reverse entries of the old values are updated; a write of an ordered field is one splice of its list (see [Ordered fields](#id/BlockNode:00D255WVK0001)). Adding a pair that is already present changes nothing; this is a property of the structure and not a promise the shell relies on. Removing a node removes all its pairs, its record from its kind's collection and its entries in every reverse side that was built.
- **The index is private**: <a name='id/BlockNode:00D24N87SR01A' class='aperas-anchor aperas-id'></a> the shell sees plain strings, numbers and booleans and never a pair (see [The engine's interface](#id/BlockNode:00D24N87T0003)).
- **Layout**: <a name='id/BlockNode:00D24N87SR01B' class='aperas-anchor aperas-id'></a> the forward side is a record for each subject and not a table for each field, for the reasons given in [Why a node-based engine](#id/BlockNode:00D39EJSZ8001); the engine aims to keep each record as close as possible to its document in the mirror, without guaranteeing it, the shell bridging the gap, and the records are arranged in the containment tree (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)). It is chosen for modularity, because the engine serves several graphs (see [Several graphs](#id/BlockNode:00D3CHJXK8002)). The reverse stays built on first use and is held on the records of the objects, and the layout does not change what the shell sees.

### Tombstones <a name='id/BlockNode:00D3CHJXK8000' class='aperas-anchor aperas-id'></a>

- **Tombstones**: <a name='id/BlockNode:00D24N87SR01V' class='aperas-anchor aperas-id'></a> the engine manages tombstones, since a tombstone is part of the meaning of a reference. Tombstoning is the engine's operation: a tombstoned node gets a timestamp, a string that the shell passes in so that the engine needs no clock, in the field to which the schema assigns the role of the tombstone marker (`tombstonedAt` in the Aperas schema), and a node is live when that field is unset. A tombstone loses all its references, its parent included, and keeps its literal properties, so that stale incoming links can check its content to update their reference. The engine tombstones one node, or a subtree over containment; the rule that a removed artifact tombstones its whole subtree is the shell's. A tombstone stays only to catch incoming links, so that they do not dangle. Which commands show a tombstoned node, and how they mark it, belongs to the commands and not to the engine; the shell's rules for a removed node are under [A removed node leaves its container](#id/BlockNode:00D24N87T000R). Two gaps remain open: [no operation revives a tombstoned node](../issues/core.md#id/BlockNode:00CN1PT1B0001) and [a block that is unreachable and was never tombstoned is never collected](../issues/core.md#id/BlockNode:00D1A2AY68001).
- **A removed node leaves its container**: <a name='id/BlockNode:00D24N87T000R' class='aperas-anchor aperas-id'></a> a tombstoned node loses its parent, so it is taken out of its container's list, and a container lists live nodes only. Once the path is derived, a tombstone is in no path, and the titles of live siblings alone decide which node a path names. In the shell this has three consequences. First, `tree --tombstoned` shows nothing for a removed child in its place, since its container no longer lists it; it keeps the `(tombstoned)` tag on a link whose target is tombstoned, and the commands keep a way to show a tombstone by its id. Second, a removal that empties a textless `listItem` or a `list` tombstones that container in the same write, a rule applied at the time of the removal; the boot sweep `tombstoneVacuousContainers` keeps the same rule over a container that has no live child. Third, `toPath()` of a tombstone is `null`, since it has no parent to derive a path from.

- **The sweep**: <a name='id/BlockNode:00D3CHJXK8001' class='aperas-anchor aperas-id'></a> a tombstone is deleted outright once no reference from a node reachable from the roots points at it: a mark from every live node of the root kinds that the schema marks, through the fields that the schema marks for the sweep to follow (in the Aperas schema, every live `ArtifactNode` and `FolderNode`, through `children` and the targets of links), and a sweep of every tombstone left unmarked. A dead island of nodes that point only at each other goes too, which a count of incoming references would keep alive. A sweep deals within one graph: the mark and the sweep read only the graph it names, so a live node of another graph does not keep a tombstone alive (see [Reads and rules across graphs](#id/BlockNode:00D5AYGHJ0001)). When the sweep runs belongs to the service lifecycle.

### Several graphs <a name='id/BlockNode:00D3CHJXK8002' class='aperas-anchor aperas-id'></a>

- **Graphs in memory**: <a name='id/BlockNode:00D3CHJXK8003' class='aperas-anchor aperas-id'></a> the engine holds several graphs in memory, in a map keyed by the graph's name, its `graph.domain`. The engine holds no settings of a graph: the persistence settings (where the mirror is, the flush interval) are the shell's, a table keyed by graph name, the `graphs` key of the shell's configuration (see [Addressing](#id/BlockNode:00D5AYBPWR001)). A graph has two folds: the engine's, in memory, and the shell's, on disk, which is its mirror (see [Files](#id/BlockNode:00D24N87SR01X)). The grammar of a `graph.domain` is that of the host of a URL authority, normally a (sub)domain name such as `my.graph.myhost`: lowercase DNS labels joined by dots, with letters, digits and hyphens inside a label, and no hyphen at either end of a label and no dot at either end of the name. The engine enforces the grammar and refuses a name that fails it, and it refuses the name `id`, the one reserved authority, since `aperas://id/` gives it a fixed meaning (see [Addressing](#id/BlockNode:00D5AYBPWR001)). It gives no other name a special case: the graph that exists at the start is a normal graph, with no default graph. The engine does not refuse the name `tree`. The shell warns, once, when its table of settings has an entry keyed `tree`, because the main graph has no identifier of its own in the configuration and is named `tree` today, and it uses the entry for the main graph. The rest of multi-graph modularity is a design of its own, outside this document.
- **Dropping a graph**: <a name='id/BlockNode:00D3CHJXK8004' class='aperas-anchor aperas-id'></a> a graph can be dropped only if no pair from the remaining graphs points into it, and on dropping it the engine removes its records from the master map and its outgoing pairs from the reverse records of the nodes that remain. The check reads across graphs (see [Reads and rules across graphs](#id/BlockNode:00D5AYGHJ0001)). The graph of the views, `treeviews`, is never refused, since nothing points into it (see [Addressing](#id/BlockNode:00D5AYBPWR001)).
- **Reads and rules across graphs**: <a name='id/BlockNode:00D5AYGHJ0001' class='aperas-anchor aperas-id'></a> an id is unique across all graphs, a pair may join a node of one graph to a node of another, and every read and write names the graph it acts on. The reads that give a node's relations are filtered to the graph they name: the subjects of a reverse side, their first one and their count, the derived entry of a node and the tree. The rules that guard an invariant of the whole store read across graphs: a node has one container and containment has no cycle (the same second-value and cycle rule of any partitioning field), and the check of dropping a graph. The drop of a value with its target (see [The roles it assigns](#id/BlockNode:00D4NB5FSR001)) reads across graphs too, so a node removed from one graph leaves the `unfolds` of the views of every graph. A sweep deals within one graph and never keeps another graph's tombstone alive (see [The sweep](#id/BlockNode:00D3CHJXK8001)): another graph that points at the tombstone may not be loaded, so it cannot be known, and a tombstone kept for it would stay for ever and could never be cleaned up. So a reference across graphs may dangle after the sweep of the graph it points into.
- **A reference across graphs**: <a name='id/BlockNode:00D4KD44M8001' class='aperas-anchor aperas-id'></a> the root folder's `children` in the tracked mirror names the `.threads` folder, whose document is in the threads graph (`threads.tree`, mirrored in the git-ignored `.state/`), so the main graph (`tree`) holds a reference into another graph. It exists today and is known ([the ghost folder](../issues/core.md#id/BlockNode:00D417WK80001)); the working engine works around it with a filter that leaves out documents without a `path`. The engine keeps a pair across graphs working, as [Reads and rules across graphs](#id/BlockNode:00D5AYGHJ0001) states, and for the same reason it refuses to drop the threads graph while this reference stands (see [Dropping a graph](#id/BlockNode:00D3CHJXK8004)); the reference may dangle after the sweep of the threads graph. It is the one pair that goes against the order of the graphs (see [Addressing](#id/BlockNode:00D5AYBPWR001)). Because an id defined in any graph counts as defined (see [Persistence](#id/BlockNode:00D4MZ7DZG001)), the main graph's entry for the `.threads` folder is not returned as an id referenced and never defined. The multi-graph design that would remove it is outside this document.

### Ordering <a name='id/BlockNode:00D24N87SR01C' class='aperas-anchor aperas-id'></a>

- **Sets are unordered**: <a name='id/BlockNode:00D24N87SR01D' class='aperas-anchor aperas-id'></a> the values of a set field and the subjects of a reverse lookup come back in no promised order. The order in which the engine happens to return them is incidental, may differ between implementations, and nothing may rely on it; a reader that needs an order sorts for itself.
- **Where an order shows**: <a name='id/BlockNode:00D24N87SR01E' class='aperas-anchor aperas-id'></a> the items of an ordered field come in the order of its list, as the children of a node do. Every other order is the reader's sort (see [Sets are unordered](#id/BlockNode:00D24N87SR01D)): in the Aperas schema, the `links` of a block are ordered by `position`, and anything else (props, unfolded ids, backlinks, the views of a profile, any other set) by id. Wherever equal keys occur (props with the same key) the tie is broken by id. The listing of the unfolded ids of a view is ordered by id.
- **The order of links without a position**: <a name='id/BlockNode:00D24N87T000P' class='aperas-anchor aperas-id'></a> the `links` of a block are listed by `position`, then by id, and a link that carries no `position` sorts after those that do (several without one by id), so the two kinds mix in a total order (see [Where an order shows](#id/BlockNode:00D24N87SR01E)). Whether a link can carry no `position` at all waits for the linking design that is to give the types of links (see [Links are outgoing ports](#id/BlockNode:00D24N87SR011)); every wikilink has one today.
- **Ids give a stable order**: <a name='id/BlockNode:00D24N87SR01F' class='aperas-anchor aperas-id'></a> ids compare as strings by plain code point, a total order that depends on no engine and no locale. In practice ids are issued in increasing order in time, but nothing relies on that.
- **A lookup does not depend on first match**: <a name='id/BlockNode:00D24N87SR01H' class='aperas-anchor aperas-id'></a> a lookup that names one node returns the live node (see [Lookups by a literal value](#id/BlockNode:00D3CHMYQG004)); for a path it is the one primitive that [How a path names one node](#id/BlockNode:00D25686RR001) states. The first or only value of a single-valued field is order-free as long as the cardinality is respected.
- **The canonical place in the render**: <a name='id/BlockNode:00D24N87T000Q' class='aperas-anchor aperas-id'></a> the render keeps one canonical place for a node reached through several unfolded links, and that place is the first in code-point order of the unfolded ids (see [Ids give a stable order](#id/BlockNode:00D24N87SR01F)), so the rendered tree depends on no order that is only listed by id.
- **A failing test**: <a name='id/BlockNode:00D24N87SR01K' class='aperas-anchor aperas-id'></a> when a test fails on an order, the rule is to check whether it caught a true bug or held a wrong assumption, and then to fix the code or the test.

### Identity and uniqueness <a name='id/BlockNode:00D24N87SR01M' class='aperas-anchor aperas-id'></a>

- **Ids**: <a name='id/BlockNode:00D24N87SR01N' class='aperas-anchor aperas-id'></a> a node id is the kind and a snowflake, `Kind:snowflake`, unique across all graphs; an embedded node's id carries its owner and field in front, `owner:field:Kind:snowflake`, and nests further for the props of a link. The kind of any id is read from its last `field:Kind:` segment, or from its prefix when it has none. The grammar is the engine's; the shell mints the ids and passes them in, and the engine checks the grammar and the uniqueness of each, and refuses an id that fails the grammar. The engine keeps the bare id, with no IRI or term encoding of its own, and the mirror stores the bare id as `@id`. The canonical address of a node is `aperas://id/` and the id, which belongs to the shell's addressing (see [Addressing](#id/BlockNode:00D5AYBPWR001) and [node-ID addressing](../design/linking.md#id/BlockNode:00CDBYV4T800B)). The resolvers of an address count a string as an id only if a valid snowflake follows `Kind:`, so a folder or an artifact named after a kind is never taken for an id; whether the load does the same is an Open point (see [An id-like string at load](#id/BlockNode:00D256098G001)). The address `aperas://graph.domain/` and a deep path (`aperas://tree/` for the main graph) is resolved at lookup time and never stored ([linking](../design/linking.md#id/BlockNode:00CDBYV4T0001)).

### The engine's interface <a name='id/BlockNode:00D24N87T0003' class='aperas-anchor aperas-id'></a>

The shell constructs the engine with its schema (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)) and then asks for the following and nothing else. Every read and write names the graph it acts on (see [Several graphs](#id/BlockNode:00D3CHJXK8002)), and every value the shell receives is a plain string, number, boolean or row, never a term.

- **Reads**: <a name='id/BlockNode:00D24N87T0004' class='aperas-anchor aperas-id'></a>
  
  - The values of field F of subject S, unordered.
  - The first or only value of a single-valued field, as a literal or as a reference.
  - The subjects whose reference or embed field F holds node V, with their first one and their count. The first one is the first in no promised order; the shell, when it must name one node, asks for the live one.
  - The items of an ordered field in order, such as the children of a node, and the place of an item in an ordered field, read from its port.
  - All ids of a kind, an iteration over the collection of the kind, and the existence of a node.
  - The size of the store.
  - The graph that holds a node, `graphOf(id)`: <a name='id/BlockNode:00D5AYTCJR001' class='aperas-anchor aperas-id'></a> it answers the graph whose record has the id, through the master map, or nothing when no graph holds one; it reads the `graph` field of the engine's record (`Rec.graph` in `records.ts`), which already exists. An id does not say its graph (`Kind:snowflake` carries none), so the read is from an id to its record's graph; it lets `aperas://id/<ID>` resolve through the engine without naming the graph first (see [Addressing](#id/BlockNode:00D5AYBPWR001)). Confirmed by the user on 2026-10-20.
- **Writes**: <a name='id/BlockNode:00D24N87T000C' class='aperas-anchor aperas-id'></a>
  
  - Create a node with the id that the shell mints, its kind and its graph; the engine checks the id's grammar and uniqueness (see [Ids](#id/BlockNode:00D24N87SR01N)).
  
  - Add a pair; adding a pair that is already present changes nothing, a property of the structure and not a promise the shell relies on (see [Writes](#id/BlockNode:00D24N87SR019)).
  - Clear a field of a subject, which a write of a `one` or `optional` field does before it adds the new value: those cardinalities refuse a second value, so changing the value means clearing the field first, and a clear is the plain operation for a caller that holds the new value and not the old. The reverse side is not the reason, since every pair the engine adds or removes keeps it in step.
  - Remove a pair, `removePair(graph, subject, field, value)`: <a name='id/BlockNode:00D4R9WX7R001' class='aperas-anchor aperas-id'></a> it removes the pair and, on an embed field, the embedded node the pair names, recursively (see [Embedded nodes have ids and are removed outright](#id/BlockNode:00D24N87SR013)). A write of an embed field that keeps some of its values is `removePair` for the values it drops and `addPair` for the new ones.
  - Remove a node, all of its pairs at once.
  - Insert, move or remove an item of an ordered field, as one splice of its list (see [Ordered fields](#id/BlockNode:00D255WVK0001)).
  - Tombstone a node, or a subtree over containment, with the timestamp the shell passes in; a tombstone loses all its references and keeps its literal properties (see [Tombstones](#id/BlockNode:00D3CHJXK8000)).
  - Sweep a graph, `sweep(graph)`: <a name='id/BlockNode:00D4T7VE70001' class='aperas-anchor aperas-id'></a> it deletes outright every tombstone that the mark from the live nodes of the schema's root kinds, through the schema's followed fields, does not reach, and gives the ids removed, sorted by code point; when it runs belongs to the service lifecycle (see [The sweep](#id/BlockNode:00D3CHJXK8001)).
  - Create a graph, and drop one, which the engine does only if no pair from the remaining graphs points into it (see [Dropping a graph](#id/BlockNode:00D3CHJXK8004)).
- **Persistence**: <a name='id/BlockNode:00D4MZ7DZG001' class='aperas-anchor aperas-id'></a> the API that the shell's persistence uses to build the engine's graphs from the mirror and to read them out at a flush; the engine does not care how the data is got or where it goes.
  
  - Build: <a name='id/BlockNode:00D4MZ7DZG002' class='aperas-anchor aperas-id'></a> one operation that creates a node with a given id, kind and graph and sets its fields; a reference to a node not yet built is accepted. A `parent` that a build supplies is an assertion by the shell and never a stored pair: the parent of a node is read from the `children` that hold it.
  - Read out: <a name='id/BlockNode:00D4MZ7DZR000' class='aperas-anchor aperas-id'></a> all ids of a kind in a graph, and the record of a node, its fields in the order the schema declares them, `parent` among them at its place, read from the reverse side of `children`.
  - The ids that are referenced and never defined, which the shell asks once it has built a graph: the ids that a pair of the graph references and that no graph defines, an id defined in any graph counting as defined (see [A reference across graphs](#id/BlockNode:00D4KD44M8001)). A `parent` that a build supplies is not a pair, so this read does not see an id that a `parent` names with no document: the load returns that id in a list of its own (see [A file whose `parent` and `children` disagree](#id/BlockNode:00D2PV8GC0001)).
- **Ports and captured port views**: <a name='id/BlockNode:00D2T6KMXR001' class='aperas-anchor aperas-id'></a> the shell sets the cap of a field and names the partitioning field its reverse is split along, asks for the current port tree of a bucket, captures it as a port view, reads a bucket through a captured port view and removes a captured port view (see [The index](#id/BlockNode:00D24N87SR015)).
- **Not offered**: <a name='id/BlockNode:00D24N87T000H' class='aperas-anchor aperas-id'></a> the engine has no pattern match over an unbound field beyond all the pairs of one subject (read together, or removed with the node) and the two traversals listed under Reads, no match on the object alone, no graph position and no query language. It has no load or dump of its own: the shell loads the mirror and builds the engine's graphs through the [persistence API](#id/BlockNode:00D4MZ7DZG001), and at a flush reads the records out and dumps them (see [The shell, on disk](#id/BlockNode:00D3CHMYQG001)).

## The shell, on disk <a name='id/BlockNode:00D3CHMYQG001' class='aperas-anchor aperas-id'></a>

- **The shell**: <a name='id/BlockNode:00D4M7YEZG001' class='aperas-anchor aperas-id'></a> the shell is the part that calls the engine. It holds `wrap`, the class hierarchy, the Aperas schema that it hands to the engine (see [The Aperas schema](#id/BlockNode:00D4MZ15AR001)), and all the code that calls the engine: persistence, ingest and project, resolve, render, link integrity, the sweeps of the service and the views. It lives in `monorepo/packages/core/src/shell/`, beside the engine's directory `monorepo/packages/core/src/apeironNgn/`; the shell calls the engine, and the engine's directory imports only files inside it: no `node:` module and no package at all, so nothing of the shell, no file system and no store library (see [The boundary](#id/BlockNode:00D3CJFB7G001)).
- **Addressing**: <a name='id/BlockNode:00D5AYBPWR001' class='aperas-anchor aperas-id'></a> the shell reads an `aperas://` string and resolves it; the engine does not. There are two forms. `aperas://id/<ID>` names a node by its id, and the shell resolves it through the engine, which finds the record by the master map and answers the graph that holds it (see [Reads](#id/BlockNode:00D24N87T0004)), so the reference need not name the graph. `aperas://graph.domain/<deep_path>` names a node by a deep path inside the graph that the domain names, and the shell resolves the path inside that graph. The first segment is the graph's name, so the name `id` is reserved for the first form and the engine refuses it as the name of a graph (see [Graphs in memory](#id/BlockNode:00D3CHJXK8003)). The shell has three graphs. The main graph, `tree`, has no identifier of its own yet and is called `tree` today, so its addresses begin `aperas://tree/`; the shell warns, once, when the table of settings has an entry keyed `tree`, because the main graph has no identifier of its own in the configuration and `tree` is its name today, and it uses the entry for the main graph; a fourth graph named `tree` is not a case, since the shell has three graphs. The threads graph is a subdomain of the main one, `threads.${main}`, that is `threads.tree` today. The graph of the views is `treeviews`, a name of one label at the top level and not under `tree`, because a view can index many graphs and not only `tree`. In the order of the linking topology (design, then issues, planning and history, then discussions, then threads, then views) the graphs are `tree`, `threads.tree` and `treeviews`: a graph points only at the graphs before it, and the one pair that goes the other way, the root folder's reference to the `.threads` folder, is kept (see [A reference across graphs](#id/BlockNode:00D4KD44M8001)). `treeviews` points at every other graph, through a view's profile, the nodes it unfolds and its root, and nothing points into it, so it can be dropped freely (see [Dropping a graph](#id/BlockNode:00D3CHJXK8004)). The shell keeps the settings of each graph (the mirror's location, the flush interval) in a table that is the `graphs` key of `aperas.config.json`, keyed by graph name; where the key is absent, or an entry lacks a setting, the existing `graph` keys give the main graph's location (and `APERAS_APEIRON_ROOT`, where it is set, gives the main graph's directory over any entry) and the shell's defaults give the rest: `tree` in the tracked directory every 10 s, and `threads.tree` and `treeviews` in its `.state/` directory every 3 s. At start the shell creates the three graphs in that order and drops the engine's first graph, `default` (see [Graphs in memory](#id/BlockNode:00D3CHJXK8003)).
- **Ids are stable**: <a name='id/BlockNode:00D24N87SR01Q' class='aperas-anchor aperas-id'></a> the shell mints the ids (see [Ids](#id/BlockNode:00D24N87SR01N)), and an operation that leaves content unchanged leaves them unchanged. Blocks keep their ids through reconciliation; a prop keeps its id only if its key and its value both stay; a wikilink `Link` keeps its id while its target stays in the block's text, and a change of positions rewrites its props and not the link.
- **A node exists when a document stands for it**: <a name='id/BlockNode:00D76AAE8G001' class='aperas-anchor aperas-id'></a> the shell asks the engine whether a node exists with one function, `nodeExists(id)`, which is `graphOf(id) !== undefined` (see [Reads](#id/BlockNode:00D24N87T0004)), so a change of the engine's answer changes one line. A node exists when a document stands for it, that is, when a graph holds a record with the id. An id that only a container's `children` names, with no document of its own, is a ghost and does not exist (the load returns such ids in the list of ids referenced and never defined, see [Persistence](#id/BlockNode:00D4MZ7DZG001)). The engine's `exists` and `size` stay undecided for a node that has incoming pairs and no record (see [Existence](#id/BlockNode:00D24N87T000K)), a case the shell never asks.

### The Aperas schema <a name='id/BlockNode:00D4MZ15AR001' class='aperas-anchor aperas-id'></a>

- **Handed to the engine**: <a name='id/BlockNode:00D4MZ15AR002' class='aperas-anchor aperas-id'></a> the shell holds the Aperas schema and passes it to the engine when it constructs it, closed for the engine's life (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)). The schema is written in the engine's meta-model, and the shell's classes (`wrap` and a class for each kind) read and write their fields through the engine.
- **Fields per class**: <a name='id/BlockNode:00D24N87SR00M' class='aperas-anchor aperas-id'></a>
  
  - `BaseNode`, shared by every tree node: <a name='id/BlockNode:00D24N87SR00N' class='aperas-anchor aperas-id'></a> `links` (set, embed, `Link`), `props` (set, embed, `StringProp`), `tombstonedAt` (optional literal), `holder` (optional boolean).
  - `TreeNode`, extending `BaseNode`: <a name='id/BlockNode:00D24N87SR00P' class='aperas-anchor aperas-id'></a> `title` (one), `text` (optional), `children` (ordered and partitioning reference, to blocks, folders and artifacts mixed: see [Containment](#id/BlockNode:00D24N87SR00Z)) and `parent` (optional reference, the reverse of `children`, kept consistent by the engine and never stored as a pair: it is a derived entry of the field order, read from the reverse side of `children`; see [Containment](#id/BlockNode:00D24N87SR00Z) and [Persistence](#id/BlockNode:00D4MZ7DZG001)).
  - `BlockNode`, extending `TreeNode`: <a name='id/BlockNode:00D24N87SR00Q' class='aperas-anchor aperas-id'></a> `type` (one: the kind of block, such as heading, paragraph or list item), the only field it adds; no other class has a `type`. Its `title` is the text of the heading or of the block.
  - `ArtifactNode`, extending `TreeNode`: <a name='id/BlockNode:00D24N87SR00R' class='aperas-anchor aperas-id'></a> it is its own root document and adds `path` (one) and five optional fields, `fileHash`, `lastTrackedAt`, `ingestedHash`, `lastIngestedAt` and `projectedHash`, which are set when the document is tracked, ingested or projected and are absent before. It has no `type`. Its `title` is the name of its file, extension included (the artifact `design/core.md` is titled `core.md`), the identity that the path is built from (see [The title of an artifact or a folder is its name](#id/BlockNode:00D4RSAZ3G001)). The stored `path` is transitional: the shell is to derive the path (see [The path is derived from the parent chain](#id/BlockNode:00D24N87SR01S)), and the field goes with the batch that removes it (see [Deriving the path](#id/BlockNode:00D25698B0001)).
  - `FolderNode`, extending `TreeNode`: <a name='id/BlockNode:00D24N87SR00S' class='aperas-anchor aperas-id'></a> `path` (one) and `projectedHash` (optional: set when the folder is projected, and absent before). In a document of a folder `path` stands before `children`, as in the real mirror (see [Format](#id/BlockNode:00D24N87SR01Z)). Its `path` is transitional, as an `ArtifactNode`'s is. Its `title` is the name of its directory (the folder of `design/core.md` is titled `design`), the identity that the path is built from (see [The title of an artifact or a folder is its name](#id/BlockNode:00D4RSAZ3G001)).
  - `Link`, embedded: <a name='id/BlockNode:00D24N87SR00T' class='aperas-anchor aperas-id'></a> `target` (one, reference) and `props` (set, embed, `StringProp`).
  - `StringProp`, embedded: <a name='id/BlockNode:00D24N87SR00V' class='aperas-anchor aperas-id'></a> `key` and `value`.
  - `Profile`: <a name='id/BlockNode:00D24N87SR00W' class='aperas-anchor aperas-id'></a> `handle`, `name` (optional), `kind` (optional: the `default` profile is the auto-generated fallback for everyone and cannot know its kind) and `preferences` (set, embed, `StringProp`).
  - `TreeView`: <a name='id/BlockNode:00D24N87SR00X' class='aperas-anchor aperas-id'></a> `profile` (reference), `name`, `unfolds` (set, reference) and `root` (optional reference).
  - A field the shapes declare as `one`, such as `title`, `path`, `handle`, `profile` and the `name` of a `TreeView`, is present on every document of its class.
- **The roles it assigns**: <a name='id/BlockNode:00D4NB5FSR001' class='aperas-anchor aperas-id'></a> containment to `children`, ordered and partitioning, whose reverse side is named `parent` (see [Containment](#id/BlockNode:00D24N87SR00Z)); the tombstone marker to `tombstonedAt` (see [Tombstones](#id/BlockNode:00D24N87SR01V)); the drop of a value with its target to `unfolds` (see [Embedded nodes have ids and are removed outright](#id/BlockNode:00D24N87SR013)); and, for [the sweep](#id/BlockNode:00D3CHJXK8001), the root kinds `ArtifactNode` and `FolderNode` and the fields `children`, `links` and the `target` of a `Link`.
- **The artifact is its own root document**: <a name='id/BlockNode:00D24N87SR010' class='aperas-anchor aperas-id'></a> no synthetic root block exists. The top-level blocks of a document (its top-level headings, and any block before the first heading) are ordinary children of its `ArtifactNode`; how the blocks below nest is the mapping of markdown, outside this document. The abstract of an artifact or a folder is its frontmatter `description`, which is also its `text`, the value the rename check compares; an artifact or a folder without a `description` has no basis for a rename, and no rename of it is detected.
- **Links are outgoing ports**: <a name='id/BlockNode:00D24N87SR011' class='aperas-anchor aperas-id'></a> an outgoing reference of a node is a `Link` in its `links`, which has a `target` and no predicate. A block has one wikilink `Link` for each distinct target, whose `props` hold one `position` for each occurrence of the target in the block's text, as a start offset relative to the block's own text. A block that cites one target through more than one `Link` has a `Link` subject for each, every one with its own `target` pair, so the multiplicity is of subjects and never of a repeated pair. The types of links are to be given by a linking design of their own, through containment and not through a predicate, and the metadata of a link sits in the content of the block that holds it. A claim that links two nodes is content, a block in prose holding a link, and there is no edge class with a justification field of its own. The backlinks of a node are the `Link`s whose `target` is the node, each reported with its owner.

### The mirror <a name='id/BlockNode:00D24N87SR01W' class='aperas-anchor aperas-id'></a>

- **Files**: <a name='id/BlockNode:00D24N87SR01X' class='aperas-anchor aperas-id'></a> the shell keeps a mirror for each graph, one JSON array for each kind, in the directory that the graph's entry in the table of settings names (see [Written by graph and kind](#id/BlockNode:00D24N87SR01Y)). The graph `tree` holds the tracked kinds, and its `ArtifactNode.jsonld`, `FolderNode.jsonld`, `BlockNode.jsonld` and `Profile.jsonld` are tracked in git under `Apeiron/`. Under `Apeiron/.state/`, which git ignores, are the mirror of the graph `threads.tree` (the `ArtifactNode.jsonld`, `FolderNode.jsonld` and `BlockNode.jsonld` of the thread-scoped nodes), the mirror of the graph `treeviews` (`TreeView.jsonld`) and the captured port views (see [Captured port views](#id/BlockNode:00D2T5Z6J0001)). `Link` and `StringProp` have no file: they are embedded in the document of their owner.
- **Written by graph and kind**: <a name='id/BlockNode:00D24N87SR01Y' class='aperas-anchor aperas-id'></a> the write-back is by graph and by kind. The shell has three graphs: `tree`, which holds the tracked kinds (`ArtifactNode`, `FolderNode`, `BlockNode` and `Profile`); `threads.tree`, which holds the thread-scoped nodes of the three tree kinds, since the threads are a graph of their own and the scope test of a node is the graph it belongs to; and `treeviews`, which holds the `TreeView` nodes (see [Addressing](#id/BlockNode:00D5AYBPWR001) for the names and their order). The file of a graph and a kind is a function of the graph alone, through the table of settings: the directory that the graph's entry names, with the name of the kind and the `.jsonld` ending. The shell reads out the records of each kind in each graph through the engine's [persistence API](#id/BlockNode:00D4MZ7DZG001). A document in the mirror has no `graph` field: the graph of a record is given by the file that holds it, the file for its graph and kind, so the load gives each record the graph of the file it reads and the dump writes each record to the file of its graph and kind; in memory the record carries its `graph` as a field (see [Records by kind and by graph](#id/BlockNode:00D24N87SR018), which states the two folds side by side).
- **Format**: <a name='id/BlockNode:00D24N87SR01Z' class='aperas-anchor aperas-id'></a> documents are sorted by `@id`, indented by two spaces and end with a newline. A document lists `@id` and `@type` and then its fields in the order the class shape declares. A field that is unset or an empty set is left out, except `children`, which is always written, as an empty array when empty. The field order is:
  
  - `BlockNode`: <a name='id/BlockNode:00D24N87SR020' class='aperas-anchor aperas-id'></a> `links`, `props`, `tombstonedAt`, `holder`, `title`, `text`, `parent`, `type`, `children`.
  - `ArtifactNode`: <a name='id/BlockNode:00D24N87SR021' class='aperas-anchor aperas-id'></a> `links`, `props`, `tombstonedAt`, `holder`, `title`, `text`, `parent`, `children`, `path`, `fileHash`, `lastTrackedAt`, `ingestedHash`, `lastIngestedAt`, `projectedHash`.
  - `FolderNode`: <a name='id/BlockNode:00D24N87SR022' class='aperas-anchor aperas-id'></a> `links`, `props`, `tombstonedAt`, `holder`, `title`, `text`, `parent`, `path`, `children`, `projectedHash`.
  - `Profile`: <a name='id/BlockNode:00D24N87SR023' class='aperas-anchor aperas-id'></a> `handle`, `name`, `kind`, `preferences`.
  - `TreeView`: <a name='id/BlockNode:00D24N87SR024' class='aperas-anchor aperas-id'></a> `profile`, `name`, `unfolds`, `root`.
  - An embedded `Link` lists `@id`, `@type`, `target`, `props`; an embedded `StringProp` lists `@id`, `@type`, `key`, `value`. The embedded entries of a field are sorted by `@id`.
- **Orders in the mirror**: <a name='id/BlockNode:00D24N87SR01G' class='aperas-anchor aperas-id'></a> the children of a container are in the order of its list, which the engine keeps as an ordered field (see [Ordered fields](#id/BlockNode:00D255WVK0001)); documents within a file, the embedded entries of a set field and the values of a reference set field, such as `unfolds`, are in id order, by plain code-point comparison, and the shell sorts them at a dump (see [A flush is a dump](#id/BlockNode:00D39EAKW0001)).
- **Containment in the file**: <a name='id/BlockNode:00D24N87T0000' class='aperas-anchor aperas-id'></a> the file states containment twice, redundantly, for clarity: the `children` array of a container, whose positions are the order, and the `parent` of each child. The load fills the engine's lists from them (see [A file whose `parent` and `children` disagree](#id/BlockNode:00D2PV8GC0001)), and the dump writes both from the engine's lists.
- **The round trip is exact**: <a name='id/BlockNode:00D24N87T0001' class='aperas-anchor aperas-id'></a> loading the mirror and writing it back returns the files byte for byte, so a flush with nothing changed leaves git clean. Every ordering above exists to keep this true, and a value must be written as it was read: strings unchanged, integers in their canonical text. The round trip is covered by [the tests](../design/testing.md#id/BlockNode:00D1D5F63R001).
- **Writers**: <a name='id/BlockNode:00D24N87T0002' class='aperas-anchor aperas-id'></a> only the service writes the mirror, and a flush rewrites a whole class file. The guard against overwriting a file that changed on disk belongs to the service lifecycle.

### The load and the flush <a name='id/BlockNode:00D3CHMYQG002' class='aperas-anchor aperas-id'></a>

- **An `@id` names one document**: <a name='id/BlockNode:00D24N87SR01P' class='aperas-anchor aperas-id'></a> no two documents may share one, and the load rejects a repeat (see [A repeated `@id` at load](#id/BlockNode:00D2PC3ZG8001); [the issue](../issues/core.md#id/BlockNode:00CHXSZ56R001)).
- **A repeated `@id` at load**: <a name='id/BlockNode:00D2PC3ZG8001' class='aperas-anchor aperas-id'></a> the load rejects every document that carries a repeated `@id`, keeps none of them, reports the id, and goes on with the other documents.
- **A file whose `parent` and `children` disagree**: <a name='id/BlockNode:00D2PV8GC0001' class='aperas-anchor aperas-id'></a> when the `parent` of a node and the `children` array of its container state different containments, `parent` wins: since it carries no place, the load appends the node at the end of the `children` of the container that its `parent` names, drops its entry from the `children` of the other container, and warns, naming both containers. A `parent` that names an id with no document leaves the node with no container, and the load warns. The load returns that id in a list of its own, together with the ids referenced and never defined that the engine gives (see [Persistence](#id/BlockNode:00D4MZ7DZG001)): the engine's `danglingRefs` does not see it, because the `parent` that a build supplies is an assertion of the shell and never a stored pair, and a derived entry is not read as a reference. A node that a container lists and that has no `parent` of its own stays in that container: the list is the source.
- **A flush is a dump**: <a name='id/BlockNode:00D39EAKW0001' class='aperas-anchor aperas-id'></a> the engine aims to keep a node's record close to its document (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)), so a flush serializes the engine's records of each file and rebuilds nothing from pairs. The aim is not a guarantee, and the dump bridges whatever differs between a record and its document, the orders of the file among it: the shell sorts the documents of a file and the embedded entries of each set field by id, and writes the children of each container in the order of its list (see [Orders in the mirror](#id/BlockNode:00D24N87SR01G)). Each graph is flushed at an interval of its own. A flush still writes each class file whole; partitioning the files, so that a flush writes only what changed, comes later, and it changes the mirror's format.

### Lookups by a literal value <a name='id/BlockNode:00D3CHMYQG004' class='aperas-anchor aperas-id'></a>

- **Handles and names**: <a name='id/BlockNode:00D24N87SR01T' class='aperas-anchor aperas-id'></a> a profile's `handle` is unique and a view's `name` is unique among views. The `name` field is shared by profiles and views, so a lookup by name filters the kind. A lookup by `handle` or by `name` is served by a map that the shell adds and keeps, not by the engine (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)).
- **The shell's map goes to an id**: <a name='id/BlockNode:00D6HT5PP8001' class='aperas-anchor aperas-id'></a> the engine has no map from a literal to a record, and its reads answer for an id (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)). The shell's map goes from the literal value to an id, and the shell then reads the record from the engine by that id.
- **The path is derived from the parent chain**: <a name='id/BlockNode:00D24N87SR01S' class='aperas-anchor aperas-id'></a> the path of an artifact or a folder is, in the end, derived and stored nowhere; the stored `path` that the Aperas schema keeps for now is transitional, and it goes with the batch that removes it (see [Deriving the path](#id/BlockNode:00D25698B0001)). The path is the chain of the node's `title`s (an artifact's or a folder's is its name, see [The title of an artifact or a folder is its name](#id/BlockNode:00D4RSAZ3G001)) along its parent chain, from the root folder down to the node, and the shell derives it over the engine's reads of `parent` and `title` (the root folder is `.`: its place is the directory that `graph.artifacts` in the configuration names). A block's path is built from its nearest artifact's path and the slugs of the titles above it. The derived path serves the lookup of a node for a path (ingest, track, project, link integrity, the anchor of reference resolution), the deep path of a block and the tie to the file on disk; the scope test of a node does not need it, since it is the graph the node belongs to (see [Written by graph and kind](#id/BlockNode:00D24N87SR01Y)). A lookup by path is served by a map that the shell keeps, holding only the live nodes' ids (see [How a path names one node](#id/BlockNode:00D25686RR001)), keyed by the stored `path` while it is stored and by the derived path once it is not (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)). A path names one node as long as live siblings under one parent have distinct titles.
- **How a path names one node**: <a name='id/BlockNode:00D25686RR001' class='aperas-anchor aperas-id'></a> the path map holds only live nodes' ids, and every lookup by path goes through one primitive, "the live node at this path", with an optional kind and an optional graph, so that the answer does not depend on the order of the store (see [A lookup does not depend on first match](#id/BlockNode:00D24N87SR01H)). While the path is stored, a removed node keeps it, as a tombstone keeps its literal properties (see [Tombstones](#id/BlockNode:00D3CHJXK8000)), so two nodes may hold one path and only one of them is live; the tombstone is never in the map. Once the path is derived, a tombstone, which has no parent, is in no path.

- **A key held by two live nodes**: <a name='id/BlockNode:00D6J3N65R001' class='aperas-anchor aperas-id'></a> a handle and a view name are unique by design, and a path names one node while live siblings have distinct titles (see [How a path names one node](#id/BlockNode:00D25686RR001)), but a mirror edited by hand or a failed ingest can hold a key twice among live nodes; the real mirror has no such repeat today. The map keeps every live holder of a key in `compareIds` order and answers the first, so the answer never depends on the order of the store, and it lists the keys that have more than one holder, for the load to warn about; the load does not refuse the mirror and a later write does not win. A view created with the name of a live view is refused, as the code refuses it today.

- **The title of an artifact or a folder is its name**: <a name='id/BlockNode:00D4RSAZ3G001' class='aperas-anchor aperas-id'></a> the `title` of an `ArtifactNode` is the name of its file, extension included, and the `title` of a `FolderNode` is the name of its directory (the artifact `design/core.md` is titled `core.md`, and its folder `design`), as [Fields per class](#id/BlockNode:00D24N87SR00M) states. It is the identity that [the path derived from the parent chain](#id/BlockNode:00D24N87SR01S) is built from, since that path is the chain of these titles. The shell sets the `title` of an artifact or a folder only from that name, never from pushed text: a rename of the file or of the directory is the only change of it. The engine knows nothing of the rule, since it is the shell's: to the engine `title` is a literal field like another.

- **A path that cannot be derived**: <a name='id/BlockNode:00D4R9VPGR001' class='aperas-anchor aperas-id'></a> the shell refuses to give the path of a node whose parent chain does not reach the root folder. Ingest and project throw "path undeterminable: no parent" when they are asked for it, and the load warns once, listing every such node. `concepts.md`, the one artifact at the root with no parent, is such a case, and it is kept as a test of the refusal (see [Deriving the path](#id/BlockNode:00D25698B0001)).

## Open points <a name='id/BlockNode:00D24N87T000J' class='aperas-anchor aperas-id'></a>

- **Existence**: <a name='id/BlockNode:00D24N87T000K' class='aperas-anchor aperas-id'></a> whether a node exists by being in a registry or by having at least one pair. One case is undecided under either answer and stays so: a node that has incoming pairs and no record of its own, which arises when a build accepts a reference to a node not yet built ([Build](#id/BlockNode:00D4MZ7DZG002)) and when a removal leaves the references to the node removed ([Embedded nodes have ids and are removed outright](#id/BlockNode:00D24N87SR013)); whether such a node exists is not decided, and the reverse side it has ([Reverse, for each field, built on first use](#id/BlockNode:00D24N87SR017)) is not to be read as its existence until it is. The shell never asks that case: its `nodeExists` is `graphOf(id) !== undefined` (see [A node exists when a document stands for it](#id/BlockNode:00D76AAE8G001)), and the engine's answer for it stays open.
- **Enforcement**: <a name='id/BlockNode:00D24N87T000M' class='aperas-anchor aperas-id'></a> whether the engine enforces the cardinalities and the closed vocabulary from the schema, or the shell does. Enforcement in the engine changes the behaviour of the two paths that take keys from outside the schema and of the tests that write made-up predicates on scratch stores ([the issue](../issues/core.md#id/BlockNode:00D22ZWZMR001), [the stale smoke test](../issues/core.md#id/BlockNode:00D22ZV0FG001)). For a field marked partitioning it is decided: the engine ensures the mark and refuses the writes that would break it (see [Partitioning fields](#id/BlockNode:00D3CJDGH8001)); the question stands for every other field.
- **An invalid id and a non-canonical integer**: <a name='id/BlockNode:00D24N87T000S' class='aperas-anchor aperas-id'></a> the engine refuses an id that fails the grammar (see [Ids](#id/BlockNode:00D24N87SR01N)), which settles the first half; whether it rewrites a non-canonical integer into its canonical form is not decided.
- **Size**: <a name='id/BlockNode:00D24N87T000T' class='aperas-anchor aperas-id'></a> what happens when the mirror outgrows memory, since the engine holds it all and loads it all at start. The answer is deferred until the size is a problem.
- **Secondary index for search**: <a name='id/BlockNode:00D24N87T000V' class='aperas-anchor aperas-id'></a> what pairs with the engine for free-text and pattern search, a hand-built index over the pairs or an embeddable engine.
- **The service lifecycle**: <a name='id/BlockNode:00D24N87T000W' class='aperas-anchor aperas-id'></a> outside this document. What the design of the repository states of the service is kept in [Packaging — Design](../design/packaging.md#id/BlockNode:00CDY7PGG0001), where the rule for a load that rejects a document is stated: the service refuses to start, a reload refuses to replace the graph, and an explicit start-anyway option lets the user work on the unaffected parts, with a side copy of the raw rejected documents before the first flush overwrites their file ([the rule](../design/packaging.md#id/BlockNode:00D76B1ZTR001)).
- **An id-like string at load**: <a name='id/BlockNode:00D256098G001' class='aperas-anchor aperas-id'></a> what the load does with a string value that begins like an id, `Kind:` and more, but is not one, in a title, a text or any other field. The options are (a) the load applies the test of the resolvers, a valid snowflake after `Kind:`, so such a string stays a string and a reference is always a real id; (b) the load refuses the string and names the document and the field (see [An invalid id and a non-canonical integer](#id/BlockNode:00D24N87T000S)); (c) the mirror marks a reference in the file, so that a reference and a string differ by their format and not by their content, which changes the format of the mirror.
- **Deriving the path**: <a name='id/BlockNode:00D25698B0001' class='aperas-anchor aperas-id'></a> not settled. The target is decided (2026-10-16): the shell derives the path of an artifact or a folder from the parent chain, as [The path is derived from the parent chain](#id/BlockNode:00D24N87SR01S) states, a path that cannot be derived is refused ([A path that cannot be derived](#id/BlockNode:00D4R9VPGR001)), the root folder needs no parent (its place is the directory that `graph.artifacts` in the configuration names), and the `README.md` files are not artifacts (the content of a README is the sub-blocks of its folder, and the migration deletes the stray README artifacts). The stored `path` stays for now, for the technical reasons below, and is transitional ([Fields per class](#id/BlockNode:00D24N87SR00M)); its removal is a later batch of the plan, after the engine is in place. What is open is how that removal handles five holes, which the count of the readers of the stored `path` found, undecided: (1) a tracked artifact has a path and no parent until the next folder ingest (`trackArtifact` creates the node, and the folder ingest finds it by a map by path to give it a parent), so with a derived path a second `aperas track` of the same file mints a duplicate and a match by title alone is ambiguous (`a/x.md` and `b/x.md` are both titled `x.md`); the ways out are that track attaches the node at once, creating the folder chain as the creation of a holder does, that something stored keeps the identity of an unattached node (a second field, which defeats removing `path`), or that track always runs the folder ingest next and the artifact ingest takes the node and not the path; (2) the tombstoned nodes keep their `path` today, and `staleOnDisk` and the reuse of a path after a removal rely on it, while a tombstone loses its `parent` and so has no derived path; (3) the thread scope reads the path in a module of raw quads that cannot import the node classes, so it needs its own walk over `parent` and `title`, and the answer for an undeterminable chain (a throw, or a quiet default) decides whether a thread artifact that lost its parent leaks into the tracked mirror instead of `.state/`; (4) the mirror holds 7 live artifacts with no parent (`concepts.md` and the six `README.md` artifacts, which the migration deletes), whose derived path fails, and `concepts.md` stays as the test of the refusal; (5) the root folder is the one folder with no parent in this mirror, but a folder holder or a ghost could lack one too, so whether "the live folder with no parent" is the definition of the root, or a marker is, is open.
- **The name of a captured port view**: <a name='id/BlockNode:00D2T6X3CG001' class='aperas-anchor aperas-id'></a> what the kind of view that captures a port tree (see [Captured port views](#id/BlockNode:00D2T5Z6J0001)) is called.
