## Purpose and scope <a name='id/BlockNode:00D24N87SR006' class='aperas-anchor aperas-id'></a>

The engine is the graph the service holds in memory, between the mirror on disk and the commands that read and change the graph.

- **The boundary**: <a name='id/BlockNode:00D3CJFB7G001' class='aperas-anchor aperas-id'></a> the engine manages, in memory, the records of the nodes and the forward and reverse sides of their reference and embed fields, with their ports, the ordered and partitioning fields, the tombstones and several graphs, under the schema it is given (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)). The shell is the part that calls the engine ([the shell](#id/BlockNode:00D4M7YEZG001)). Dehydrating the records to disk and rehydrating them are the shell's: the mirror, its format, the load, the flush and the maps for lookups by a literal value make up the shell's persistence, which builds the engine's graphs and reads them out through the engine's [persistence API](#id/BlockNode:00D4MZ7DZG001). The code follows the boundary in its folders: `monorepo/packages/core/src/apeironNgn/` is the engine, in memory, `monorepo/packages/core/src/shell/` is the shell, on disk, and the engine's directory imports nothing of the shell, no file system and no store library. This document follows the boundary: the engine, in memory, then the shell, on disk.

- **A reflection of the mirror**: <a name='id/BlockNode:00D24N87SR007' class='aperas-anchor aperas-id'></a> the JSON-LD files under `Apeiron/`, tracked in git, are the source of truth. The engine holds nothing that a fresh load of the mirror would not rebuild. It has no persistence of its own: the shell's persistence builds it from the mirror when the service starts or reloads, and reads it out to the mirror when it flushes, through the engine's [persistence API](#id/BlockNode:00D4MZ7DZG001) (see [The shell, on disk](#id/BlockNode:00D3CHMYQG001)).
- **One schema, handed in at construction**: <a name='id/BlockNode:00D24N87SR008' class='aperas-anchor aperas-id'></a> the fields a node can have are declared once for each kind, in the schema that the shell passes to the engine when it constructs it (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)), and that declaration is the only schema. There is no schema language beside it and no query surface that shapes the data differently from it; the accessors of a field, in the shell's classes, go through the schema, which knows the field's cardinality and storage kind. Whether the two paths that take keys from outside the schema (the load of a mirror document and the minting of an embedded node) are held to it as well is an Open point (see [Enforcement](#id/BlockNode:00D24N87T000M)).
- **Versioning is git**: <a name='id/BlockNode:00D24N87SR009' class='aperas-anchor aperas-id'></a> a write to the mirror followed by an ordinary commit is the version control. The engine has no commit layer, and merging work from another copy is git's merge on the mirror.
- **No concurrent access**: <a name='id/BlockNode:00D24N87SR00A' class='aperas-anchor aperas-id'></a> one process owns the engine and handles one request at a time. The engine has no locks, no transactions and no isolation of its own.
- **Search is not here**: <a name='id/BlockNode:00D24N87SR00B' class='aperas-anchor aperas-id'></a> free-text and pattern search have no index-servable shortcut in any engine and need a secondary index of their own, which this document does not describe (see [Open points](#id/BlockNode:00D24N87T000J)).
- **Why a node-based engine**: <a name='id/BlockNode:00D39EJSZ8001' class='aperas-anchor aperas-id'></a> the workload is node-heavy: commands read whole nodes, render trees of them, and write the mirror by a dump at each flush. So the properties of a node live on its record, and only the relations between nodes are pairs (see [The data model](#id/BlockNode:00D24N87SR00D)). An edge layout, which holds every property as a statement of its own, pays a lookup for each property read; it suits arbitrary pattern queries over an open vocabulary, and Aperas has neither: its vocabulary is closed and the shell asks no such query (see [Closed vocabulary](#id/BlockNode:00D24N87SR00E) and [Not offered](#id/BlockNode:00D24N87T000H)). The evidence is filed in [the full-store scans](../issues/core.md#id/BlockNode:00D0W02KPG001) and [the cost of a write](../issues/core.md#id/BlockNode:00D22Z1HJ8001), and the move away from the edge layout is recorded in [the history](../history/core.md#id/BlockNode:00D21FP4ZG009).
- **Outside this document**: <a name='id/BlockNode:00D24N87SR00C' class='aperas-anchor aperas-id'></a> the service lifecycle (start, stop, the timing and the guard of a flush, ownership of the process, recovery, the waits of the client), the mapping of markdown into blocks and back, the addressing grammar ([linking](../design/linking.md#id/BlockNode:00CDBYV4T0001)) and the views ([treeview](../design/treeview.md#id/BlockNode:00CE1GW4Y8001)). Each consumes the engine and none changes its rules; the mapping of markdown, the addressing and the views are parts of the shell ([the shell](#id/BlockNode:00D4M7YEZG001)).

## The engine, in memory <a name='id/BlockNode:00D3CHJXK0001' class='aperas-anchor aperas-id'></a>

### The data model <a name='id/BlockNode:00D24N87SR00D' class='aperas-anchor aperas-id'></a>

The engine stores pairs. Each field is a fixed relation, and a pair (s, v) is one link of that relation from a subject s to a value v; in RDF terms these are triples (subject, field, value) whose predicate, the field, never varies. The field is fixed first, and pairs are managed field by field. On a node n each field has two sides: the forward side holds the pairs n → v, where n is the subject, and the reverse side holds the pairs s → n, where n is the value. Each pair sits on two records, on its subject's forward side and on its value's reverse side. Only reference and embed fields hold pairs (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)).

- **The meta-model**: <a name='id/BlockNode:00D4MYZ6Q0000' class='aperas-anchor aperas-id'></a> the engine is generic and names no class or field of its own. The shell passes it a schema when it constructs it, and the schema is closed at construction, fixed for the engine's life. The schema is written in the engine's meta-model: kinds, each of which can extend another and inherit its fields; for each field of a kind, its [storage kind](#id/BlockNode:00D24N87SR00H) and its [cardinality](#id/BlockNode:00D24N87SR00G); the reference and embed fields, whose pairs the engine keeps, each with the name of its reverse side; the [ordered](#id/BlockNode:00D255WVK0001) and [partitioning](#id/BlockNode:00D3CJDGH8001) fields; the field of [containment](#id/BlockNode:00D24N87SR00Z); the field that marks a [tombstone](#id/BlockNode:00D24N87SR01V); the reference fields whose value is dropped when its target is removed (see [Embedded nodes have ids and are removed outright](#id/BlockNode:00D24N87SR013)); and the root kinds of [the sweep](#id/BlockNode:00D3CHJXK8001) and the fields it follows. A rule of the engine that needs a particular field names the role that the schema assigns, and which field holds the role is the schema's choice. The Aperas schema, its classes and their fields, is the shell's (see [The Aperas schema](#id/BlockNode:00D4MZ15AR001)).

- **Closed vocabulary**: <a name='id/BlockNode:00D24N87SR00E' class='aperas-anchor aperas-id'></a> every field of a record is one that the schema declares for its subject's kind. Nothing else is stored. Containment is the field to which the schema assigns that role, and the parent is its reverse (see [Containment](#id/BlockNode:00D24N87SR00Z)). That the vocabulary is closed is a property of the data and of the shell; whether the engine enforces it is open (see [Open points](#id/BlockNode:00D24N87T000J)).
- **A field is a relation**: <a name='id/BlockNode:00D24N87SR00F' class='aperas-anchor aperas-id'></a> a reference or embed field relates subjects to the nodes that are their values, and has a forward side (the values of field F of subject S) and a reverse side (the subjects whose field F holds node V). The reverse side exists for every such field; which reverse sides the shell uses is the shell's choice, and the engine keeps no list of the fields that have one.
- **Literal fields are properties of the record**: <a name='id/BlockNode:00D39DRYB0001' class='aperas-anchor aperas-id'></a> a literal field is a plain property of its node's record, read and written there, with no pairs and no reverse side. The engine manages pairs for reference and embed fields only. A lookup by the value of a literal field (a profile by its `handle`, a view by its `name`, an artifact or a folder by its stored `path`) is served by a map that the shell adds and keeps; the engine keeps no such map.
- **Cardinalities**: <a name='id/BlockNode:00D24N87SR00G' class='aperas-anchor aperas-id'></a> `one` (exactly one value), `optional` (at most one), `set` (any number, unordered) and `ordered` (a set with an order, see [Ordered fields](#id/BlockNode:00D255WVK0001)). A cardinality is declared in the schema for each field of each kind and is never inferred from the data: a set field that holds one value must stay distinguishable from an optional field that happens to be set, which counting the values cannot tell.
- **Storage kinds**: <a name='id/BlockNode:00D24N87SR00H' class='aperas-anchor aperas-id'></a> `literal` (a plain value), `reference` (the id of another node, which the field does not own) and `embed` (a node the field owns: it has an id of its own, is written inside its owner's document in the mirror and is removed with its owner).
- **Literal types**: <a name='id/BlockNode:00D24N87SR00J' class='aperas-anchor aperas-id'></a> string, integer and boolean, kept as their JavaScript types, so the string "1" and the number 1 are different values. A string that looks like a date stays a plain string, because typing it as a date would let a store rewrite its text.
- **Ports, the two ends of a pair**: <a name='id/BlockNode:00D3CJCK10001' class='aperas-anchor aperas-id'></a> a port is a sub-address of a node that continues its deep path. A pair joins an outgoing port of its subject, such as an embedded node that holds a reference (a `Link` in the Aperas schema) or an item's place in an ordered list, to an incoming port of its object, the partition of its reverse side where the entry lands (see [Ports](#id/BlockNode:00D2T5VG08001)). "Port" is one notion with these two ends.
- **Ordered fields**: <a name='id/BlockNode:00D255WVK0001' class='aperas-anchor aperas-id'></a> a field can be declared ordered. Its forward side is then a list on its host: a set plus an order, so an item appears in it at most once. The port of an item is `host:item`, keyed by the item's own id, and the reverse of the item points at that port. The order is kept only in the live list: a reader that needs an item's place asks its port, which reads it from the host's list on demand. There is no sibling index and no order key, so an insertion or a move is one splice of the list and no reverse entry changes.
- **Partitioning fields**: <a name='id/BlockNode:00D3CJDGH8001' class='aperas-anchor aperas-id'></a> a field can be marked partitioning in the schema, closed at construction and never at run time, and the engine ensures the mark: each node has at most one value on the side that is climbed, and the relation has no cycle. The ports use a partitioning field as the hierarchy of a split (see [A partition hierarchy](#id/BlockNode:00D2T5XBH0001)).
- **Containment**: <a name='id/BlockNode:00D24N87SR00Z' class='aperas-anchor aperas-id'></a> containment is the field to which the schema assigns that role (`children` in the Aperas schema), declared ordered and partitioning (see [Ordered fields](#id/BlockNode:00D255WVK0001) and [Partitioning fields](#id/BlockNode:00D3CJDGH8001)). The list of a container holds its children in order; a node is in at most one container's list, and containment has no cycle. The reverse of the containment field at a node is its port in its container's list, which gives the node's parent and its place; the parent is read from that reverse, under the name the schema gives the reverse side (`parent` in the Aperas schema), and the engine keeps it consistent with the lists on every write. A node has at most one parent. Containment is written through the containment field. Containment is not ownership: taking a node out of its container's list detaches it and does not delete it. A tombstone is in no container's list (see [Tombstones](#id/BlockNode:00D3CHJXK8000)).
- **Where a node's parent comes from**: <a name='id/BlockNode:00D2562RC8001' class='aperas-anchor aperas-id'></a> the order of the children lives in the stored containment list of their container, whose positions are the order, so the list is not derived from the parent. Today's code extracts a sibling index for each child from the stored `children` at load, keeps it with the child's `parent`, and derives `children` from them afterwards; a file whose `parent` and `children` disagree loads as it stands ([the issue](../issues/core.md#id/BlockNode:00D2538VKR001)). The engine keeps the order in the list itself and reads an item's place from its port (see [Ordered fields](#id/BlockNode:00D255WVK0001)). The mirror states containment twice, in the container's `children` and in the child's `parent`, redundantly, for clarity; when the two disagree, the shell's load applies its rule (see [A file whose `parent` and `children` disagree](#id/BlockNode:00D2PV8GC0001)).
- **Records follow containment**: <a name='id/BlockNode:00D2T5P9Y8001' class='aperas-anchor aperas-id'></a> the records are arranged in the containment tree, a node's record under its container's, as the documents are in the mirror, and not in one flat table of all subjects. The forward hierarchy is authored (containment); the reverse hierarchy, the ports, is made by the engine (see [Ports](#id/BlockNode:00D2T5VG08001)). The engine aims to keep a node's record as close as possible to its document in the mirror, to reduce the shell's work: its literal fields as plain properties, the values of its reference fields, and its embedded nodes nested in the fields that own them. This is an aim and not a guarantee, and the shell always bridges the gap between a record and its document. A record also carries what the file does not hold: the reverse sides of its fields, with their ports, each built the first time the field is asked in reverse (see [Reverse, for each field, built on first use](#id/BlockNode:00D24N87SR017)). One master map from id to record sits beside the tree as an aid for direct access and does not replace the tree; it serves every graph, since an id is unique across all graphs (see [Ids](#id/BlockNode:00D24N87SR01N)).
- **Records by kind and by graph**: <a name='id/BlockNode:00D24N87SR018' class='aperas-anchor aperas-id'></a> the kind of a node is not a pair; it is read from the prefix of its id. Beside the tree and the master map, the engine keeps one collection for each graph and each kind of the schema, a set of the records themselves, and no separate set of ids. Creating a node adds its record to its collection and deleting the node removes it; a dump or a sweep iterates the collection for all the nodes of a kind in a graph. The natural order of a collection is the order of insertion, which follows the increasing codes of the ids and so makes the shell's sort at a dump cheap (see [Orders in the mirror](#id/BlockNode:00D24N87SR01G)); it is promised to no reader.
- **Embedded nodes have ids and are removed outright**: <a name='id/BlockNode:00D24N87SR013' class='aperas-anchor aperas-id'></a> an embedded node (a `Link` or a `StringProp` in the Aperas schema) has an id of its own and can be addressed, but it has no tombstone. Assigning an embed field removes, recursively, every embedded node that the new value does not keep (the embedded nodes of a removed one go with it, as the props of a `Link` do), so no orphan stays in the store. Removing any node also drops it from every reference field to which the schema assigns the role of a value dropped with its target (`unfolds` in the Aperas schema). Other incoming references (a link's target, a parent, a profile) are not removed by deleting the node; keeping none of them dangling is the work of the sweeps of the service, and the engine answers the ids that are referenced and never defined, which the shell asks once it has built a graph (see [Persistence](#id/BlockNode:00D4MZ7DZG001)); what is done with them belongs to the service lifecycle.

### The index <a name='id/BlockNode:00D24N87SR015' class='aperas-anchor aperas-id'></a>

Every lookup the shell makes binds either the subject or the field and the value, so the engine answers them from the forward and reverse sides of its records, iterates the collection of a kind when all the nodes of that kind are asked for, and traverses the whole store only for the check the shell asks at load, the ids that are referenced and never defined.

- **Forward, the record of each subject**: <a name='id/BlockNode:00D24N87SR016' class='aperas-anchor aperas-id'></a> the forward side of a node's fields is its record (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)). The values of field F of subject S are read from the record, and the whole record of S (what a flush or a wrapper needs) is read whole, with no lookup for each field.
- **Reverse, for each field, built on first use**: <a name='id/BlockNode:00D24N87SR017' class='aperas-anchor aperas-id'></a> the reverse of a field is built the first time the field is asked in reverse and kept up to date by every write afterwards, so the engine supports reversal for every reference and embed field without paying for the fields nobody reverses. It is held on the record of each object (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)), not in a table of its own: the bucket of an object for a field, the subjects whose field holds that object, is a leaf or a split record of ports (see [Ports](#id/BlockNode:00D2T5VG08001)). A leaf is a set, for the cost of removal and of membership: a bucket can hold thousands of subjects, and taking one out or asking whether one is present must not scan the rest.
- **Ports**: <a name='id/BlockNode:00D2T5VG08001' class='aperas-anchor aperas-id'></a> a bucket is split into incoming ports (see [Ports, the two ends of a pair](#id/BlockNode:00D3CJCK10001)) when it outgrows the cap set for its field. The shell sets the cap of each field and names the [partitioning field](#id/BlockNode:00D3CJDGH8001) of the sources that the split follows, such as containment for the tree of blocks; the engine chooses the levels: a bucket over the cap is split by the ancestors of its sources at the next level of that hierarchy, and a port still over the cap is split at the level below, so each branch goes only as deep as its own pairs need. A split merges back only when its count falls well below the cap, so the ports do not change back and forth around it. The cap is soft: pairs that the hierarchy cannot tell apart (sources with the same deepest ancestor, or with no place in the hierarchy) stay together in one port, the residue, even above the cap. Nothing about ports is stored: their shape follows from the current pairs and the caps.
- **A partition hierarchy**: <a name='id/BlockNode:00D2T5XBH0001' class='aperas-anchor aperas-id'></a> a field can serve as the hierarchy of a split only if it is marked partitioning (see [Partitioning fields](#id/BlockNode:00D3CJDGH8001)), so that every pair falls into exactly one port. The mark is set in the schema (see [Partitioning fields](#id/BlockNode:00D3CJDGH8001)), and the engine refuses every write that would give a node a second value on the climbed side or close a cycle. For IS-A, where a tag may have several supertags, the data keeps the many-valued relation for its meaning and adds a single-valued primary-supertag field, which is the tree the partition follows; a secondary supertag edge is marked as such when it is written, and the partition ignores it, so nothing is trimmed.
- **Captured port views**: <a name='id/BlockNode:00D2T5Z6J0001' class='aperas-anchor aperas-id'></a> the engine shows the port tree of a bucket as it currently is, and the shell can capture it as a view, which stays still while the engine's own ports go on changing. A captured port view keeps only the shape, the boundary node of each port; its contents are recomputed from the current pairs whenever it is used, and the engine answers through it by merging its own finer ports or sorting a coarser one on the fly. It is a kind of view of its own, distinct from the shell's views (`TreeView` in the Aperas schema); the shell keeps it on disk (see [Files](#id/BlockNode:00D24N87SR01X)), and it is removed only by hand, as it was captured by hand. What it is called is an Open point (see [The name of a captured port view](#id/BlockNode:00D2T6X3CG001)).
- **Writes**: <a name='id/BlockNode:00D24N87SR019' class='aperas-anchor aperas-id'></a> writing a field of a node updates that node's pairs of that field: its new values replace its old ones, and the reverse entries of the old values are updated; a write of an ordered field is one splice of its list (see [Ordered fields](#id/BlockNode:00D255WVK0001)). Adding a pair that is already present changes nothing; this is a property of the structure and not a promise the shell relies on. Removing a node removes all its pairs, its record from its kind's collection and its entries in every reverse side that was built.
- **The index is private**: <a name='id/BlockNode:00D24N87SR01A' class='aperas-anchor aperas-id'></a> the shell sees plain strings, numbers and booleans and never a pair (see [The engine's interface](#id/BlockNode:00D24N87T0003)).
- **Layout**: <a name='id/BlockNode:00D24N87SR01B' class='aperas-anchor aperas-id'></a> the forward side is a record for each subject and not a table for each field, for the reasons given in [Why a node-based engine](#id/BlockNode:00D39EJSZ8001); the engine aims to keep each record as close as possible to its document in the mirror, without guaranteeing it, the shell bridging the gap, and the records are arranged in the containment tree (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)). It is chosen for modularity, because the engine serves several graphs (see [Several graphs](#id/BlockNode:00D3CHJXK8002)). The reverse stays built on first use and is held on the records of the objects, and the layout does not change what the shell sees.

### Tombstones <a name='id/BlockNode:00D3CHJXK8000' class='aperas-anchor aperas-id'></a>

- **Tombstones**: <a name='id/BlockNode:00D24N87SR01V' class='aperas-anchor aperas-id'></a> the engine manages tombstones, since a tombstone is part of the meaning of a reference. Tombstoning is the engine's operation: a tombstoned node gets a timestamp, a string that the shell passes in so that the engine needs no clock, in the field to which the schema assigns the role of the tombstone marker (`tombstonedAt` in the Aperas schema), and a node is live when that field is unset. A tombstone loses all its references, its parent included, and keeps its literal properties, so that stale incoming links can check its content to update their reference. The engine tombstones one node, or a subtree over containment; the rule that a removed artifact tombstones its whole subtree is the shell's. A tombstone stays only to catch incoming links, so that they do not dangle. Which commands show a tombstoned node, and how they mark it, belongs to the commands and not to the engine. Two gaps remain open: [no operation revives a tombstoned node](../issues/core.md#id/BlockNode:00CN1PT1B0001) and [a block that is unreachable and was never tombstoned is never collected](../issues/core.md#id/BlockNode:00D1A2AY68001).
- **A removed node leaves its container**: <a name='id/BlockNode:00D24N87T000R' class='aperas-anchor aperas-id'></a> a tombstoned node loses its parent, so it is taken out of its container's list, and a container lists live nodes only. Once the path is derived, a tombstone is in no path, and the titles of live siblings alone decide which node a path names.

- **The sweep**: <a name='id/BlockNode:00D3CHJXK8001' class='aperas-anchor aperas-id'></a> a tombstone is deleted outright once no reference from a node reachable from the roots points at it: a mark from every live node of the root kinds that the schema marks, through the fields that the schema marks for the sweep to follow (in the Aperas schema, every live `ArtifactNode` and `FolderNode`, through `children` and the targets of links), and a sweep of every tombstone left unmarked. A dead island of nodes that point only at each other goes too, which a count of incoming references would keep alive. When the sweep runs belongs to the service lifecycle.

### Several graphs <a name='id/BlockNode:00D3CHJXK8002' class='aperas-anchor aperas-id'></a>

- **Graphs in memory**: <a name='id/BlockNode:00D3CHJXK8003' class='aperas-anchor aperas-id'></a> the engine holds several graphs in memory, each with its own settings. A graph has two folds: the engine's, in memory, and the shell's, on disk, which is its mirror (see [Files](#id/BlockNode:00D24N87SR01X)). The rest of multi-graph modularity is a design of its own, outside this document.
- **Dropping a graph**: <a name='id/BlockNode:00D3CHJXK8004' class='aperas-anchor aperas-id'></a> a graph can be dropped only if no pair from the remaining graphs points into it, and on dropping it the engine removes its records from the master map and its outgoing pairs from the reverse records of the nodes that remain.
- **A reference across graphs**: <a name='id/BlockNode:00D4KD44M8001' class='aperas-anchor aperas-id'></a> the root folder's `children` in the tracked mirror names the `.threads` folder, whose document is in the threads graph (the git-ignored `.state/`), so the main graph holds a reference into another graph. It exists today and is known ([the ghost folder](../issues/core.md#id/BlockNode:00D417WK80001)); the working engine works around it with a filter that leaves out documents without a `path`. The multi-graph design that would remove it is outside this document.

### Ordering <a name='id/BlockNode:00D24N87SR01C' class='aperas-anchor aperas-id'></a>

- **Sets are unordered**: <a name='id/BlockNode:00D24N87SR01D' class='aperas-anchor aperas-id'></a> the values of a set field and the subjects of a reverse lookup come back in no promised order. The order in which the engine happens to return them is incidental, may differ between implementations, and nothing may rely on it; a reader that needs an order sorts for itself.
- **Where an order shows**: <a name='id/BlockNode:00D24N87SR01E' class='aperas-anchor aperas-id'></a> the items of an ordered field come in the order of its list, as the children of a node do. Every other order is the reader's sort (see [Sets are unordered](#id/BlockNode:00D24N87SR01D)): in the Aperas schema, the `links` of a block are ordered by `position`, and anything else (props, unfolded ids, backlinks, the views of a profile, any other set) by id. Wherever equal keys occur (props with the same key) the tie is broken by id. The listing of the unfolded ids of a view is ordered by id.
- **Ids give a stable order**: <a name='id/BlockNode:00D24N87SR01F' class='aperas-anchor aperas-id'></a> ids compare as strings by plain code point, a total order that depends on no engine and no locale. In practice ids are issued in increasing order in time, but nothing relies on that.
- **A lookup does not depend on first match**: <a name='id/BlockNode:00D24N87SR01H' class='aperas-anchor aperas-id'></a> a lookup that names one node returns the live node (see [Lookups by a literal value](#id/BlockNode:00D3CHMYQG004)). The first or only value of a single-valued field is order-free as long as the cardinality is respected.
- **A failing test**: <a name='id/BlockNode:00D24N87SR01K' class='aperas-anchor aperas-id'></a> when a test fails on an order, the rule is to check whether it caught a true bug or held a wrong assumption, and then to fix the code or the test.

### Identity and uniqueness <a name='id/BlockNode:00D24N87SR01M' class='aperas-anchor aperas-id'></a>

- **Ids**: <a name='id/BlockNode:00D24N87SR01N' class='aperas-anchor aperas-id'></a> a node id is the kind and a snowflake, `Kind:snowflake`, unique across all graphs; an embedded node's id carries its owner and field in front, `owner:field:Kind:snowflake`, and nests further for the props of a link. The kind of any id is read from its last `field:Kind:` segment, or from its prefix when it has none. The grammar is the engine's; the shell mints the ids and passes them in, and the engine checks the grammar and the uniqueness of each, and refuses an id that fails the grammar. The engine keeps the bare id, with no IRI or term encoding of its own, and the mirror stores the bare id as `@id`. The canonical address of a node is `aperas://id/` and the id, which belongs to the shell's addressing ([node-ID addressing](../design/linking.md#id/BlockNode:00CDBYV4T800B)). The resolvers of an address count a string as an id only if a valid snowflake follows `Kind:`, so a folder or an artifact named after a kind is never taken for an id; whether the load does the same is an Open point (see [An id-like string at load](#id/BlockNode:00D256098G001)). The address `aperas://tree/` and a path is resolved at lookup time and never stored ([linking](../design/linking.md#id/BlockNode:00CDBYV4T0001)).

### The engine's interface <a name='id/BlockNode:00D24N87T0003' class='aperas-anchor aperas-id'></a>

The shell constructs the engine with its schema (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)) and then asks for the following and nothing else. Every read and write names the graph it acts on (see [Several graphs](#id/BlockNode:00D3CHJXK8002)), and every value the shell receives is a plain string, number, boolean or row, never a term.

- **Reads**: <a name='id/BlockNode:00D24N87T0004' class='aperas-anchor aperas-id'></a>
  
  - The values of field F of subject S, unordered.
  - The first or only value of a single-valued field, as a literal or as a reference.
  - The subjects whose reference or embed field F holds node V, with their first one and their count. The first one is the first in no promised order; the shell, when it must name one node, asks for the live one.
  - The items of an ordered field in order, such as the children of a node, and the place of an item in an ordered field, read from its port.
  - All ids of a kind, an iteration over the collection of the kind, and the existence of a node.
  - The size of the store.
- **Writes**: <a name='id/BlockNode:00D24N87T000C' class='aperas-anchor aperas-id'></a>
  
  - Create a node with the id that the shell mints, its kind and its graph; the engine checks the id's grammar and uniqueness (see [Ids](#id/BlockNode:00D24N87SR01N)).
  
  - Add a pair; adding a pair that is already present changes nothing, a property of the structure and not a promise the shell relies on (see [Writes](#id/BlockNode:00D24N87SR019)).
  - Clear a field of a subject, which a write of the field does before it adds the new values.
  - Remove a node, all of its pairs at once.
  - Insert, move or remove an item of an ordered field, as one splice of its list (see [Ordered fields](#id/BlockNode:00D255WVK0001)).
  - Tombstone a node, or a subtree over containment, with the timestamp the shell passes in; a tombstone loses all its references and keeps its literal properties (see [Tombstones](#id/BlockNode:00D3CHJXK8000)).
  - Create a graph, and drop one, which the engine does only if no pair from the remaining graphs points into it (see [Dropping a graph](#id/BlockNode:00D3CHJXK8004)).
- **Persistence**: <a name='id/BlockNode:00D4MZ7DZG001' class='aperas-anchor aperas-id'></a> the API that the shell's persistence uses to build the engine's graphs from the mirror and to read them out at a flush; the engine does not care how the data is got or where it goes.
  
  - Build: <a name='id/BlockNode:00D4MZ7DZG002' class='aperas-anchor aperas-id'></a> create a node with a given id, kind and graph, and set its fields; a reference to a node not yet built is accepted.
  - Read out: <a name='id/BlockNode:00D4MZ7DZR000' class='aperas-anchor aperas-id'></a> all ids of a kind in a graph, and the record of a node, its fields in the order the schema declares them.
  - The ids that are referenced and never defined, which the shell asks once it has built a graph.
- **Ports and captured port views**: <a name='id/BlockNode:00D2T6KMXR001' class='aperas-anchor aperas-id'></a> the shell sets the cap of a field and names the partitioning field its reverse is split along, asks for the current port tree of a bucket, captures it as a port view, reads a bucket through a captured port view and removes a captured port view (see [The index](#id/BlockNode:00D24N87SR015)).
- **Not offered**: <a name='id/BlockNode:00D24N87T000H' class='aperas-anchor aperas-id'></a> the engine has no pattern match over an unbound field beyond all the pairs of one subject (read together, or removed with the node) and the two traversals listed under Reads, no match on the object alone, no graph position and no query language. It has no load or dump of its own: the shell loads the mirror and builds the engine's graphs through the [persistence API](#id/BlockNode:00D4MZ7DZG001), and at a flush reads the records out and dumps them (see [The shell, on disk](#id/BlockNode:00D3CHMYQG001)).

## The shell, on disk <a name='id/BlockNode:00D3CHMYQG001' class='aperas-anchor aperas-id'></a>

- **The shell**: <a name='id/BlockNode:00D4M7YEZG001' class='aperas-anchor aperas-id'></a> the shell is the part that calls the engine. It holds `wrap`, the class hierarchy, the Aperas schema that it hands to the engine (see [The Aperas schema](#id/BlockNode:00D4MZ15AR001)), and all the code that calls the engine: persistence, ingest and project, resolve, render, link integrity, the sweeps of the service and the views. It lives in `monorepo/packages/core/src/shell/`, beside the engine's directory `monorepo/packages/core/src/apeironNgn/`; the shell calls the engine, and the engine's directory imports nothing of the shell, no file system and no store library (see [The boundary](#id/BlockNode:00D3CJFB7G001)).
- **Ids are stable**: <a name='id/BlockNode:00D24N87SR01Q' class='aperas-anchor aperas-id'></a> the shell mints the ids (see [Ids](#id/BlockNode:00D24N87SR01N)), and an operation that leaves content unchanged leaves them unchanged. Blocks keep their ids through reconciliation; a prop keeps its id only if its key and its value both stay; a wikilink `Link` keeps its id while its target stays in the block's text, and a change of positions rewrites its props and not the link.

### The Aperas schema <a name='id/BlockNode:00D4MZ15AR001' class='aperas-anchor aperas-id'></a>

- **Handed to the engine**: <a name='id/BlockNode:00D4MZ15AR002' class='aperas-anchor aperas-id'></a> the shell holds the Aperas schema and passes it to the engine when it constructs it, closed for the engine's life (see [The meta-model](#id/BlockNode:00D4MYZ6Q0000)). The schema is written in the engine's meta-model, and the shell's classes (`wrap` and a class for each kind) read and write their fields through the engine.
- **Fields per class**: <a name='id/BlockNode:00D24N87SR00M' class='aperas-anchor aperas-id'></a>
  
  - `BaseNode`, shared by every tree node: <a name='id/BlockNode:00D24N87SR00N' class='aperas-anchor aperas-id'></a> `links` (set, embed, `Link`), `props` (set, embed, `StringProp`), `tombstonedAt` (optional literal), `holder` (optional boolean).
  - `TreeNode`, extending `BaseNode`: <a name='id/BlockNode:00D24N87SR00P' class='aperas-anchor aperas-id'></a> `title` (one), `text` (optional), `parent` (optional reference, the reverse of `children`, kept consistent by the engine: see [Containment](#id/BlockNode:00D24N87SR00Z)).
  - `BlockNode`, extending `TreeNode`: <a name='id/BlockNode:00D24N87SR00Q' class='aperas-anchor aperas-id'></a> `type` (one: the kind of block, such as heading, paragraph or list item) and `children` (ordered and partitioning reference: see [Containment](#id/BlockNode:00D24N87SR00Z)).
  - `ArtifactNode`, extending `BlockNode`: <a name='id/BlockNode:00D24N87SR00R' class='aperas-anchor aperas-id'></a> it is its own root document and gains `path` and five optional fields, `fileHash`, `lastTrackedAt`, `ingestedHash`, `lastIngestedAt` and `projectedHash`, which are set when the document is tracked, ingested or projected and are absent before; its `type` is optional.
  - `FolderNode`, extending `TreeNode` and not `BlockNode`: <a name='id/BlockNode:00D24N87SR00S' class='aperas-anchor aperas-id'></a> `path`, `children` (ordered and partitioning reference, to blocks, folders and artifacts mixed: see [Containment](#id/BlockNode:00D24N87SR00Z)) and `projectedHash` (optional: set when the folder is projected, and absent before).
  - `Link`, embedded: <a name='id/BlockNode:00D24N87SR00T' class='aperas-anchor aperas-id'></a> `target` (one, reference) and `props` (set, embed).
  - `StringProp`, embedded: <a name='id/BlockNode:00D24N87SR00V' class='aperas-anchor aperas-id'></a> `key` and `value`.
  - `Profile`: <a name='id/BlockNode:00D24N87SR00W' class='aperas-anchor aperas-id'></a> `handle`, `name`, `kind` (optional: the `default` profile is the auto-generated fallback for everyone and cannot know its kind) and `preferences` (set, embed).
  - `TreeView`: <a name='id/BlockNode:00D24N87SR00X' class='aperas-anchor aperas-id'></a> `profile` (reference), `name`, `unfolds` (set, reference) and `root` (optional reference).
  - A field the shapes declare as `one`, such as `path`, `handle`, `name` and `profile`, is present on every document of its class.
- **The roles it assigns**: <a name='id/BlockNode:00D4NB5FSR001' class='aperas-anchor aperas-id'></a> containment to `children`, ordered and partitioning, whose reverse side is named `parent` (see [Containment](#id/BlockNode:00D24N87SR00Z)); the tombstone marker to `tombstonedAt` (see [Tombstones](#id/BlockNode:00D24N87SR01V)); the drop of a value with its target to `unfolds` (see [Embedded nodes have ids and are removed outright](#id/BlockNode:00D24N87SR013)); and, for [the sweep](#id/BlockNode:00D3CHJXK8001), the root kinds `ArtifactNode` and `FolderNode` and the fields `children`, `links` and the `target` of a `Link`.
- **The artifact is its own root document**: <a name='id/BlockNode:00D24N87SR010' class='aperas-anchor aperas-id'></a> no synthetic root block exists. The top-level blocks of a document (its top-level headings, and any block before the first heading) are ordinary children of its `ArtifactNode`; how the blocks below nest is the mapping of markdown, outside this document. The abstract of an artifact or a folder is its frontmatter `description`, which is also its `text`, the value the rename check compares; an artifact or a folder without a `description` has no basis for a rename, and no rename of it is detected.
- **Links are outgoing ports**: <a name='id/BlockNode:00D24N87SR011' class='aperas-anchor aperas-id'></a> an outgoing reference of a node is a `Link` in its `links`, which has a `target` and no predicate. A block has one wikilink `Link` for each distinct target, whose `props` hold one `position` for each occurrence of the target in the block's text, as a start offset relative to the block's own text. A block that cites one target through more than one `Link` has a `Link` subject for each, every one with its own `target` pair, so the multiplicity is of subjects and never of a repeated pair. The types of links are to be given by a linking design of their own, through containment and not through a predicate, and the metadata of a link sits in the content of the block that holds it. A claim that links two nodes is content, a block in prose holding a link, and there is no edge class with a justification field of its own. The backlinks of a node are the `Link`s whose `target` is the node, each reported with its owner.

### The mirror <a name='id/BlockNode:00D24N87SR01W' class='aperas-anchor aperas-id'></a>

- **Files**: <a name='id/BlockNode:00D24N87SR01X' class='aperas-anchor aperas-id'></a> the shell keeps a mirror for each graph, one JSON array for each kind. The main graph's `ArtifactNode.jsonld`, `FolderNode.jsonld`, `BlockNode.jsonld` and `Profile.jsonld` are tracked in git under `Apeiron/`; under `Apeiron/.state/`, which git ignores, are `TreeView.jsonld`, the captured port views (see [Captured port views](#id/BlockNode:00D2T5Z6J0001)) and the mirror of the threads, which are a graph of their own (see [Written by graph and kind](#id/BlockNode:00D24N87SR01Y)). `Link` and `StringProp` have no file: they are embedded in the document of their owner.
- **Written by graph and kind**: <a name='id/BlockNode:00D24N87SR01Y' class='aperas-anchor aperas-id'></a> the write-back is by graph and by kind. The threads are a graph of their own, whose mirror is `.state/`, so the scope test of a node is the graph it belongs to; the shell reads out the records of each kind in each graph through the engine's [persistence API](#id/BlockNode:00D4MZ7DZG001).
- **Format**: <a name='id/BlockNode:00D24N87SR01Z' class='aperas-anchor aperas-id'></a> documents are sorted by `@id`, indented by two spaces and end with a newline. A document lists `@id` and `@type` and then its fields in the order the class shape declares. A field that is unset or an empty set is left out, except `children`, which is always written, as an empty array when empty. The field order is:
  
  - `BlockNode`: <a name='id/BlockNode:00D24N87SR020' class='aperas-anchor aperas-id'></a> `links`, `props`, `tombstonedAt`, `holder`, `title`, `text`, `parent`, `type`, `children`.
  - `ArtifactNode`: <a name='id/BlockNode:00D24N87SR021' class='aperas-anchor aperas-id'></a> the same, then `path`, `fileHash`, `lastTrackedAt`, `ingestedHash`, `lastIngestedAt`, `projectedHash`.
  - `FolderNode`: <a name='id/BlockNode:00D24N87SR022' class='aperas-anchor aperas-id'></a> `links`, `props`, `tombstonedAt`, `holder`, `title`, `text`, `parent`, `path`, `children`, `projectedHash`.
  - `Profile`: <a name='id/BlockNode:00D24N87SR023' class='aperas-anchor aperas-id'></a> `handle`, `name`, `kind`, `preferences`.
  - `TreeView`: <a name='id/BlockNode:00D24N87SR024' class='aperas-anchor aperas-id'></a> `profile`, `name`, `unfolds`, `root`.
  - An embedded `Link` lists `@id`, `@type`, `target`, `props`; an embedded `StringProp` lists `@id`, `@type`, `key`, `value`. The embedded entries of a field are sorted by `@id`.
- **Orders in the mirror**: <a name='id/BlockNode:00D24N87SR01G' class='aperas-anchor aperas-id'></a> the children of a container are in the order of its list, which the engine keeps as an ordered field (see [Ordered fields](#id/BlockNode:00D255WVK0001)); documents within a file, the embedded entries of a set field and the values of a reference set field, such as `unfolds`, are in id order, by plain code-point comparison, and the shell sorts them at a dump (see [A flush is a dump](#id/BlockNode:00D39EAKW0001)).
- **Containment in the file**: <a name='id/BlockNode:00D24N87T0000' class='aperas-anchor aperas-id'></a> the file states containment twice, redundantly, for clarity: the `children` array of a container, whose positions are the order, and the `parent` of each child. The load fills the engine's lists from them (see [A file whose `parent` and `children` disagree](#id/BlockNode:00D2PV8GC0001)), and the dump writes both from the engine's lists.
- **The round trip is exact**: <a name='id/BlockNode:00D24N87T0001' class='aperas-anchor aperas-id'></a> loading the mirror and writing it back returns the files byte for byte, so a flush with nothing changed leaves git clean. Every ordering above exists to keep this true, and a value must be written as it was read: strings unchanged, integers in their canonical text. The round trip is covered by [the tests](../design/testing.md#id/BlockNode:00D1D5F63R001).
- **Writers**: <a name='id/BlockNode:00D24N87T0002' class='aperas-anchor aperas-id'></a> only the service writes the mirror, and a flush rewrites a whole class file. The guard against overwriting a file that changed on disk belongs to the service lifecycle.

### The load and the flush <a name='id/BlockNode:00D3CHMYQG002' class='aperas-anchor aperas-id'></a>

- **An `@id` names one document**: <a name='id/BlockNode:00D24N87SR01P' class='aperas-anchor aperas-id'></a> no two documents may share one, and the load rejects a repeat (see [A repeated `@id` at load](#id/BlockNode:00D2PC3ZG8001); [the issue](../issues/core.md#id/BlockNode:00CHXSZ56R001)).
- **A repeated `@id` at load**: <a name='id/BlockNode:00D2PC3ZG8001' class='aperas-anchor aperas-id'></a> the load rejects every document that carries a repeated `@id`, keeps none of them, reports the id, and goes on with the other documents.
- **A file whose `parent` and `children` disagree**: <a name='id/BlockNode:00D2PV8GC0001' class='aperas-anchor aperas-id'></a> when the `parent` of a node and the `children` array of its container state different containments, `parent` wins; since it carries no place, the load appends the node at the end of its parent's `children` and warns.
- **A flush is a dump**: <a name='id/BlockNode:00D39EAKW0001' class='aperas-anchor aperas-id'></a> the engine aims to keep a node's record close to its document (see [Records follow containment](#id/BlockNode:00D2T5P9Y8001)), so a flush serializes the engine's records of each file and rebuilds nothing from pairs. The aim is not a guarantee, and the dump bridges whatever differs between a record and its document, the orders of the file among it: the shell sorts the documents of a file and the embedded entries of each set field by id, and writes the children of each container in the order of its list (see [Orders in the mirror](#id/BlockNode:00D24N87SR01G)). Each graph is flushed at an interval of its own. A flush still writes each class file whole; partitioning the files, so that a flush writes only what changed, comes later, and it changes the mirror's format.

### Lookups by a literal value <a name='id/BlockNode:00D3CHMYQG004' class='aperas-anchor aperas-id'></a>

- **Handles and names**: <a name='id/BlockNode:00D24N87SR01T' class='aperas-anchor aperas-id'></a> a profile's `handle` is unique and a view's `name` is unique among views. The `name` field is shared by profiles and views, so a lookup by name filters the kind. A lookup by `handle` or by `name` is served by a map that the shell adds and keeps, not by the engine (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)).
- **The path is derived from the parent chain**: <a name='id/BlockNode:00D24N87SR01S' class='aperas-anchor aperas-id'></a> the stored `path` of an artifact or a folder is a redundant copy of the titles along its parent chain (the root folder is `.`). A block stores no path: its path is built from its nearest artifact's path and the slugs of the titles above it. The first engine keeps the stored copy; deriving it from the parent chain is a later refactor, which needs every artifact and folder but the root folder to have a parent (see [Deriving the path](#id/BlockNode:00D25698B0001) in Open points). The copy serves the lookup of a node for a path (ingest, track, project, link integrity, the anchor of reference resolution), the deep path of a block and the tie to the file on disk, and the parent chain with the titles can answer each of these; the scope test of a node does not need it, since it is the graph the node belongs to (see [Written by graph and kind](#id/BlockNode:00D24N87SR01Y)). While the copy is stored, a lookup by it is a lookup by the value of a literal field, served by a map the shell keeps (see [Literal fields are properties of the record](#id/BlockNode:00D39DRYB0001)). Once it is derived, a path names one node as long as live siblings under one parent have distinct titles.

## Open points <a name='id/BlockNode:00D24N87T000J' class='aperas-anchor aperas-id'></a>

- **Existence**: <a name='id/BlockNode:00D24N87T000K' class='aperas-anchor aperas-id'></a> whether a node exists by being in a registry or by having at least one pair.
- **Enforcement**: <a name='id/BlockNode:00D24N87T000M' class='aperas-anchor aperas-id'></a> whether the engine enforces the cardinalities and the closed vocabulary from the schema, or the shell does. Enforcement in the engine changes the behaviour of the two paths that take keys from outside the schema and of the tests that write made-up predicates on scratch stores ([the issue](../issues/core.md#id/BlockNode:00D22ZWZMR001), [the stale smoke test](../issues/core.md#id/BlockNode:00D22ZV0FG001)). For a field marked partitioning it is decided: the engine ensures the mark and refuses the writes that would break it (see [Partitioning fields](#id/BlockNode:00D3CJDGH8001)); the question stands for every other field.
- **The order of links without a position**: <a name='id/BlockNode:00D24N87T000P' class='aperas-anchor aperas-id'></a> whether a link can carry no `position`, and if it can, how it sorts against the links that do, waits for the linking design that is to give the types of links (see [Links are outgoing ports](#id/BlockNode:00D24N87SR011)); the rule orders links by position and anything else by id, and does not say how the two mix.
- **The canonical-render order check**: <a name='id/BlockNode:00D24N87T000Q' class='aperas-anchor aperas-id'></a> the render keeps one canonical place for a node reached through several unfolded links. If the choice of that place follows the order of the unfolded ids, the rendered tree depends on an order that is only listed by id.
- **An invalid id and a non-canonical integer**: <a name='id/BlockNode:00D24N87T000S' class='aperas-anchor aperas-id'></a> the engine refuses an id that fails the grammar (see [Ids](#id/BlockNode:00D24N87SR01N)), which settles the first half; whether it rewrites a non-canonical integer into its canonical form is not decided.
- **Size**: <a name='id/BlockNode:00D24N87T000T' class='aperas-anchor aperas-id'></a> what happens when the mirror outgrows memory, since the engine holds it all and loads it all at start. The answer is deferred until the size is a problem.
- **Secondary index for search**: <a name='id/BlockNode:00D24N87T000V' class='aperas-anchor aperas-id'></a> what pairs with the engine for free-text and pattern search, a hand-built index over the pairs or an embeddable engine.
- **The service lifecycle**: <a name='id/BlockNode:00D24N87T000W' class='aperas-anchor aperas-id'></a> outside this document.

- **An id-like string at load**: <a name='id/BlockNode:00D256098G001' class='aperas-anchor aperas-id'></a> what the load does with a string value that begins like an id, `Kind:` and more, but is not one, in a title, a text or any other field. The options are (a) the load applies the test of the resolvers, a valid snowflake after `Kind:`, so such a string stays a string and a reference is always a real id; (b) the load refuses the string and names the document and the field (see [An invalid id and a non-canonical integer](#id/BlockNode:00D24N87T000S)); (c) the mirror marks a reference in the file, so that a reference and a string differ by their format and not by their content, which changes the format of the mirror.
- **How a path names one node**: <a name='id/BlockNode:00D25686RR001' class='aperas-anchor aperas-id'></a> while the path is stored, a removed node keeps it, as a tombstone keeps its literal properties (see [Tombstones](#id/BlockNode:00D3CHJXK8000)), so two nodes may hold one path and only one of them is live. Once the path is derived, a tombstone, which has no parent, is in no path. Until then, whether every lookup by path asks for the live node through one primitive, "the live node at this path", is not decided.
- **Deriving the path**: <a name='id/BlockNode:00D25698B0001' class='aperas-anchor aperas-id'></a> deriving the path of an artifact or a folder from the parent chain needs every one of them but the root folder to have a parent. The root folder needs none: its place is the directory that `graph.artifacts` in the configuration names. The `README.md` files are not artifacts: the content of a README is the sub-blocks of its folder, and the migration deletes the stray README artifacts. The one artifact without a parent is `concepts.md`, at the root. The options for it are (a) give it the folder that holds it as its parent, before the path is derived; (b) keep the stored path for it as an exception, so that the derivation covers only the artifacts and folders that have a parent.
