## Architecture <a name='id/BlockNode:00CJ6TGSYG005' class='aperas-anchor aperas-id'></a>

- **The webapp is a third thin wrapper over `@aperas/core`**: <a name='id/BlockNode:00CJ6TGSYG006' class='aperas-anchor aperas-id'></a> the UI-projection tier, alongside `cli` and anticipated by name in [cli's settled scope](../discussion/cli.md#id/BlockNode:00CF2AEMER007). It owns presentation and interaction, not graph semantics — every rule it renders (fold tiers, canonical position, zoom) is computed in core and consumed here.
- **The ApeironNgn service remains the sole writer**: <a name='id/BlockNode:00CJ6TGSYG007' class='aperas-anchor aperas-id'></a> the webapp never opens the store, reaching the graph only through the service, which keeps single-writer discipline, the lock file, the code-fingerprint check and conflict reporting exactly as they are for CLI callers.
- **Transport is an HTTP listener inside the service**: <a name='id/BlockNode:00CJ6TGSYG008' class='aperas-anchor aperas-id'></a> not a separate bridge process and not a Node-hosted shell. Live notification can only honestly originate in the service, because it is the sole writer and the only thing that knows when the store changed. The unix socket is untouched and remains the CLI's path; the listener is an addition beside it.
- **The listener exposes an explicit op allowlist**: <a name='id/BlockNode:00CJ6TGSYG009' class='aperas-anchor aperas-id'></a> not a proxy onto the service protocol — deep read, plus a single-node text update. This bounds the blast radius of any auth failure and is the part that cannot be retrofitted cheaply.
- **Auth rests on five controls**: <a name='id/BlockNode:00CJ6TGSYG00A' class='aperas-anchor aperas-id'></a> a custom `X-Aperas-Token` header on every request, which forces a CORS preflight and so prevents a cross-origin request being sent at all, independent of the token's value; a `127.0.0.1` bind; a per-run `randomBytes(32)` token stored in the existing run directory beside the lock and socket at mode 0600, compared with `timingSafeEqual`; a `Host` check against the loopback address, which is the specific anti-DNS-rebinding control; and an `Origin` allowlist as defence in depth, never reflected back.
- **Change notification is a bare tick**: <a name='id/BlockNode:00CJ6TGSYG00B' class='aperas-anchor aperas-id'></a> the service pushes *the store changed*, and the UI refetches its current apex. The tick is idempotent and stateless, so no delta format exists and none is needed.
- **Until the tick channel ships, a client-side poll stands in**: <a name='id/BlockNode:00CJDHHVA8000' class='aperas-anchor aperas-id'></a> the dev tab bumps its own refetch every 1s regardless of whether anything actually changed, through the same refetch path an in-page fold/edit action already uses — so an external `aperas fold`/`unfold`/CLI write is picked up without a manual reload. User-toggleable (a `sync` checkbox in the header), since a poll racing a session that's deliberately mid-edit via the CLI is more noise than help. Deliberately not the design above: it's a poll, not a push, and it lives entirely client-side rather than in the service.
- **The tick stream is NDJSON over a streaming `fetch()` response**: <a name='id/BlockNode:00CJ6TGSYG00C' class='aperas-anchor aperas-id'></a> read with `ReadableStream` rather than `EventSource`, which cannot set a request header and so cannot carry the token without falling back to a cookie or a URL ticket. NDJSON is already the service's framing on the unix socket, so no second wire format is introduced.
- **`buildRenderTree` is core's structured render**: <a name='id/BlockNode:00CJ6TGSYG00D' class='aperas-anchor aperas-id'></a> the CLI's text output becomes a projection of it. `renderTreeWithView` already runs two passes — `discoverCone` builds the render plan, and only then does `emitNode`/`emitLinkLine` flatten it to strings; pass 1 is what a UI wants, pass 2 is the only part that assumes text. Extracting the plan as a tree of render items, and redefining the text render as `toText(buildRenderTree(...))`, keeps the existing verification suite as the guarantee that nothing changed — the text output must stay byte-identical.
- **A single `updateText(id, text)` hides the write-path's rules**: <a name='id/BlockNode:00CJ6TGSYG00E' class='aperas-anchor aperas-id'></a> on the host side, per node type — an existing list item takes bare text with no bullet marker, a heading needs `--text-only` — so the UI encodes none of it.
- **`TreeView` carries the child-display level as two orthogonal subset fields**: <a name='id/BlockNode:00CMX5GNB0001' class='aperas-anchor aperas-id'></a> `unfolds` keeps membership alone, so every existing sweep over it is untouched; `unfoldsCollapsed` and `unfoldsNoPreview` are subsets of it, and the default level (previews) is the absence of both, costing no storage. Orthogonal rather than one ordered scalar so that no mutual-exclusion invariant has to be enforced in code, and so that stashing remembers the level to return to. Both new fields have to join `removeDanglingUnfolds` and `pruneStaleUnfolds`. [The four sub-states, and why not a reified entry](../discussion/webapp.md#id/BlockNode:00CMWMRX88001).

## Topology <a name='id/BlockNode:00CJ6TGSYR000' class='aperas-anchor aperas-id'></a>

- **`FolderDiv`'s three slots are the three render tiers**: <a name='id/BlockNode:00CJ6TGSYR001' class='aperas-anchor aperas-id'></a> which is why the port is a port and not a rewrite.

- **The node-kind tag is a glyph, not a bracketed type name**: <a name='id/BlockNode:00CJDHWT9G001' class='aperas-anchor aperas-id'></a> `📂`/`📄`/`§`/`¶`/`🔗` for `FolderNode`/`ArtifactNode`/heading/paragraph/link — the handful of kinds a reader actually orients by — and no tag at all for anything else (`listItem`, `code`, `table`, ...), rather than falling back to the old `[type]` text. A silent per-kind opt-in, not a universal re-skin: unmapped kinds stay exactly as bare as a plain list item always read.

- **The arrow and its stem are one control, not two**: <a name='id/BlockNode:00CJDHYES8001' class='aperas-anchor aperas-id'></a> hovering or clicking either the fold arrow or the guide line below it is the same action, ported from the original vanilla `FolderDiv.js` sketch's single `<label>` wrapping both (`UniinfoNotes/assets/HTML/FolderDiv.js`, outside this repo). The stem's own position falls out of sharing the arrow's fixed-width column rather than from a separately-guessed margin — the earlier `.fd-children` border-left had no actual relationship to the arrow's position, which is what made it misaligned. Hovering recolors the arrow and the line together; it never washes the row with a background highlight, which read as an unrelated hover box rather than part of the control.

- **Body text renders at full brightness, not dimmed by default**: <a name='id/BlockNode:00CJE11FRR000' class='aperas-anchor aperas-id'></a> `.fd-abstract` and the link-preview popover's own abstract used to sit at reduced opacity or a muted color (`0.75`, `var(--fg-muted)`) for no reason tied to actual state. Dimming is reserved for things that are genuinely secondary — a tombstoned tag, a truncation ellipsis, the poll status line — not for a node's own stored text. A link's title is the one exception in the other direction: it's link-highlighted (the same blue as an inline wikilink) precisely because it's the part that's clickable, while its abstract stays at that same full brightness rather than sharing the highlight.

- **The palette is explicit and dual: screen dark, print light**: <a name='id/BlockNode:00CMNJY31G001' class='aperas-anchor aperas-id'></a> every theme color is a `--bg`/`--fg`/`--fg-muted`/`--border`/`--surface`/`--surface-hover`/`--accent` custom property on `:root` (`index.css`), never left to an inherited `color-scheme` default — the same discipline behind [full-brightness body text](#id/BlockNode:00CJE11FRR000): an implicit color is one half of a pairing that can silently disagree with its other half. Screen values (`--bg #26292b`, `--surface #313538`, `--fg #9ea4aa`, `--fg-muted #6b7278`, `--border #3a3d40`, `--accent #5aa7ff`) were sampled directly from the pixels of the Logseq UI this app is read alongside day to day (`UniinfoNotes/logseq/custom.css`), not eyeballed — the first pass matched a numerically-close but wrong pixel cluster (Logseq's page-title heading rather than its ordinary body text) and had to be corrected once compared by role, not just by value. `--accent` was never checked against Logseq this way; its hue happens to land within ~10° of Logseq's own `--accent` (`#0090ff`) regardless, apparently by common convergence on "the obvious blue" rather than by design. An `@media print` block on the same `:root` re-declares every variable for light-on-white (`--bg #fff`, `--fg #1b1e21`, `--accent #1a63c4`, ...) plus `color-scheme: light` and `print-color-adjust: exact`, so print never depends on the browser's own "Background graphics" toggle — that option only decides whether an authored background survives, and a page with no light palette of its own had nothing to fall back to once one was stripped. This only holds where a rule actually reads the variable: a literal hex bypasses both the Logseq match and the print fallback silently, which is how `.fd-link-title`, `.inline-link`, and the gutter's hover state each carried their own hardcoded blue until found by inspection.
- **A link renders at two sites sharing one identity**: <a name='id/BlockNode:00CJ6TGSYR002' class='aperas-anchor aperas-id'></a> its own text inside the block's prose, and an endnote in the link list after the children. Wikipedia's `cite-ref`/`cite-note` scheme without the superscript marker — a wikilink already carries the words the reader is looking at, so the link text *is* the marker. That an endnote exists below is carried by styling: a link that resolved to a graph node is styled as one, a dangling link is not.
- **A link row shows the target's own kind glyph next to the link glyph, and its title/abstract split like a normal node's**: <a name='id/BlockNode:00CJE14W0R001' class='aperas-anchor aperas-id'></a> `RenderLinkItem.targetDisplayLabel` (added alongside `targetTitle`, populated in every mode but `no-target`) is what makes the first half possible — no second lookup, same reasoning as `RenderNodeItemFound.displayLabel`. The two used to run together as one `"title — abstract"` string inside a single highlighted span; now only the title carries the link highlight, and the abstract renders as an ordinary `.fd-abstract` line beneath it, so a link preview reads as "a title, then its actual body text" the same way an unfolded node does, rather than one long highlighted run.
- **Both sites obey canonical position**: <a name='id/BlockNode:00CJ6TGSYR003' class='aperas-anchor aperas-id'></a> rather than re-deriving it — how a link's target renders is a property of where that target's [structural home](treeview.md#id/BlockNode:00CE1GW4YG006) sits relative to the current render, not a property of the link. Three states: the home is nowhere in the render, and the link renders the target itself ([rule a folded, rule b unfolded](treeview.md#id/BlockNode:00CE1GW4YG004)); the home is in the render, even as a title-only breadcrumb, and the link collapses to the `[*see <path>]` pointer plus a jump; the target sits above the apex, and it renders as `(outside view)` plus a zoom-out. Both sites read one shared verdict, so they cannot disagree with each other or with `aperas tree`. This also makes link-following cycle-safe without a visited set.
- **One target cited twice is one `Link`**: <a name='id/BlockNode:00CJ6TGSYR004' class='aperas-anchor aperas-id'></a> with two positions. Resolution groups by distinct target, so identity is the target alone and each occurrence contributes a `position` — the endnote is therefore per-`Link`, with one back-reference per position, Wikipedia's `^ a b`, already the stored shape.
- **The apex is UI-local**: <a name='id/BlockNode:00CJ6TGSYR005' class='aperas-anchor aperas-id'></a> zooming in sets a new apex, zooming out is a click on a breadcrumb above it — neither is view state, and neither is persisted.
- **A node's title line carries its own backlink count, and a click reveals them**: <a name='id/BlockNode:00CJEDTR40001' class='aperas-anchor aperas-id'></a> `RenderNodeItemFound.backlinkCount` (`backlinks(store, id, 'target').length` in `buildNodeItem`, an indexed store match, not a corpus scan — `0` while `hidden`, like this item's sibling found-node fields) drives a small badge floating right on the title line, shown only once there's something to show. Clicking it fetches the actual list lazily (the dev bridge's `/api/backlinks`, a thin wrapper over the CLI's own `backlinks` service op) and opens a popover above the line (or below, clamped into the viewport, when there isn't room above), each entry rendered like a folded node's own preview — kind glyph, title, abstract — since that's what a backlink is: another node's title-and-text, citing this one. A plain click on an entry unfolds both the citing `Link` and its owning node *without changing the apex*, then scrolls to wherever the owner actually renders — the same canonical-position machinery [both sites already obey](#id/BlockNode:00CJ6TGSYR003) decides whether that's inline content, a pointer elsewhere in the current render, or nowhere at all if the owner isn't reachable from the current apex (in which case the scroll silently finds nothing, same as any anchor to an absent id). Ctrl-click is the stronger action — it also zooms the apex to the owner — matching ctrl-click's meaning everywhere else in this app rather than introducing a third gesture. Revealing the link needs both unfolds, not just the link's own: a node's own links only render at all once the node itself is in the view's `unfolds` set (`buildNodeItem`'s `linksToShow`) — the link's own unfold alone leaves it invisible until its owner is unfolded too.
- **A link row's click toggles its own fold state; ctrl-click zooms**: <a name='id/BlockNode:00CJFDGBVR001' class='aperas-anchor aperas-id'></a> `preview` and `expanded` share one row-level `onClick` — plain click unfolds (`preview`) or folds (`expanded`) that link, ctrl/meta-click zooms to its target instead, mirroring the same modifier-key convention this UX pass gave the [backlinks popover](#id/BlockNode:00CJEDTR40001). The `Gutter`'s own arrow/stem click still works too (`e.stopPropagation()` keeps the two from double-toggling on the same click) — this just extends the same fold/unfold gesture to the rest of the row instead of leaving it as the arrow's own private affordance. `pointer`/`outside-view` rows are unchanged: they have no fold state of their own to toggle, so their plain click still jumps directly, same as before.
- **The hover popover's open is delayed too, not just its close**: <a name='id/BlockNode:00CMPNNP90001' class='aperas-anchor aperas-id'></a> a quick pass over a link — reading down the list, not actually pausing on it — used to trigger the popover on every link the pointer crossed. `NavigableLink`'s `onEnter` (`Inline.tsx`) now schedules the same way `scheduleClose` already did, cancelled by a matching `cancelOpen` if the pointer leaves before it fires — 600ms, tuned to match this OS's own tooltip delay.
- **Every row gets its own id-copy button, next to the edit pencil**: <a name='id/BlockNode:00CMPNQAVR001' class='aperas-anchor aperas-id'></a> `CopyIdButton` (`FolderDiv.tsx`) copies that row's exact id — a node's own `n.id`, or a `Link`'s own `l().linkId` on every `LinkRow` mode, which had no pencil to sit next to at all — to the clipboard, swapping to `✅` for about a second first: unlike the pencil's own click (a visible edit box opens) or an unfold (a visible expansion), a clipboard write has no effect of its own to see, so leaving it silent would read as broken. Same hover-reveal styling as the pencil. The pencil itself was quietly illegible before this same pass too — `✎` (U+270E) renders as a thin, low-contrast outline glyph in most fonts — swapped for the two-tone `✏️` (U+270F+FE0F) emoji presentation, matching every other icon already in the row.
- **A node's fold state is two axes: whether it is pinned, and how much of its children shows**: <a name='id/BlockNode:00CMX5F2H8001' class='aperas-anchor aperas-id'></a> `unfolds` membership is the first axis; a per-node *level* — stashed, titles, previews — is the second, and applies only to a pinned node. The two together produce six states, plus a seventh (cut off by `maxDepth`) that belongs to the render rather than to the node and so carries no arrow at all — there the `…` marker is itself the control. One shape, two fills, three angles: `▶` (U+25B6) pinned, `▷` (U+25B7) not, rotated 0°/45°/90° through the `transform` transition `.fd-arrow` already carries. Angle reads east-nothing, southeast-partially, south-fully, so `▷` never reaches south: an unpinned node never shows children as content. `●` (U+25CF, not the too-small U+2022) marks a pinned leaf, a confirmed dead end. [Every state tabulated, and why two axes rather than one bit](../discussion/webapp.md#id/BlockNode:00CMWKJYR0001).
- **The gesture is chosen by the state it lands on, not fixed per key**: <a name='id/BlockNode:00CMX5FF3G001' class='aperas-anchor aperas-id'></a> bare click always does the obvious thing to whatever is in front of it — unfold when folded, stash when open, unstash when stashed, unpin at a leaf, zoom at a depth cut-off — so one click reads as "close this" wherever the row looks closed and "open this" wherever it looks open, and never needs a second gesture to mean the same intent. Modifiers rank by how often they are wanted: shift steps the level, ctrl zooms, alt is the plain non-recursive `fold`, alt+shift the recursive pair. Bare click therefore never removes a node from `unfolds` except at a leaf — click is "remember", alt is "forget". Ctrl applies on the arrow and the stem as well as the row, which the [arrow has never actually honoured](../issues/webapp.md#id/BlockNode:00CMWN0XDG001). [The full gesture matrix and its transition diagram](../discussion/webapp.md#id/BlockNode:00CMWMP6X8001).
- **The stem is the fold control; a passive guide marks path**: <a name='id/BlockNode:00CMX5FXA0001' class='aperas-anchor aperas-id'></a> a solid, hoverable stem appears only where a node is pinned *and* its children render as content, so clicking it always folds and never promises an action that isn't there. A row showing a child only because something deeper is pinned — a breadcrumb — gets a non-interactive sparse dotted guide instead (`repeating-linear-gradient`, roughly 2px on / 5px off; `╎` on the console), which is what tells a path stairway apart from real content. This restores the rule the [arrow and its stem are one control](#id/BlockNode:00CJDHYES8001) already implied and the Solid port lost by keying the stem on "has children". On the console the prefix has to be built from a per-level stack rather than `'│ '.repeat(depth)`, which cannot vary per column. [Rationale](../discussion/webapp.md#id/BlockNode:00CMWMMRGG001).
- **The webapp's depth limit is derived from available width**: <a name='id/BlockNode:00CMX5G968001' class='aperas-anchor aperas-id'></a> `floor((width − buffer) / gutter)` against a fixed `1.2rem` gutter, recomputed and refetched (debounced) on resize, and kept as `maxDepth` on the server render rather than truncated client-side so that `truncated` keeps a single meaning. A legibility backstop rather than a performance cap — at a typical viewport it lands far past anything this corpus nests to, so the `…` control is rare by construction. [Rationale](../discussion/webapp.md#id/BlockNode:00CMWMVMV0001).

## Workflows <a name='id/BlockNode:00CJ6TGSYR006' class='aperas-anchor aperas-id'></a>

- **Reading renders from the apex down**: <a name='id/BlockNode:00CJ6TGSYR007' class='aperas-anchor aperas-id'></a> at whatever tier each node earns, following a link by its endnote or its hover popover — both of which obey canonical position.
- **Fold and unfold share one arrow handle**: <a name='id/BlockNode:00CJ6TGSYR008' class='aperas-anchor aperas-id'></a> it toggles children and the endnote list alike. Hovering a link offers an unfold control that adds the `Link` itself to `unfolds`, which is what expands its endnote — one source of truth, no fold state in the popover.
- **Zooming uses the arrow handle and the breadcrumb**: <a name='id/BlockNode:00CJ6TGSYR009' class='aperas-anchor aperas-id'></a> ctrl-click the arrow handle to make that node the apex, click a breadcrumb to zoom back out to it.
- **Live sync follows the tick**: <a name='id/BlockNode:00CJ6TGSYR00A' class='aperas-anchor aperas-id'></a> the service pushes one on every store change, the UI refetches its apex, and refetches unconditionally on reconnect. A 401 is surfaced as a distinct state, because the per-run token dies whenever the service restarts.
- **Shallow write is an in-place text edit**: <a name='id/BlockNode:00CJ6TGSYR00B' class='aperas-anchor aperas-id'></a> of the current node's own text, sent as a single-node update. The editor round-trips plain authored markdown — no projection anchor is stored, so there is nothing for an edit to preserve.
