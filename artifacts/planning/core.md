# Core — Planning <a name='id/BlockNode:00CF23FB1G001' class='aperas-anchor aperas-id'></a>

## Implementation Plan <a name='id/BlockNode:00CF23FB1G002' class='aperas-anchor aperas-id'></a>

The plan builds the engine of [Core — Design](../design/core.md#id/BlockNode:00D24N87SR001) in plain JavaScript, in the checkout `Aperas.dev/` on branch `js-apeironngn`. The code repo `Aperas/` stays on branch `oxigraph` as the working engine the workflow uses while the new one is built. The Oxigraph-based code is kept as a frozen reference copy in `Aperas.dev/monorepo/.archive/oxigraph/` (the TerminusDB-era code is in `.archive/tdb/`), and the live code in `monorepo/packages/` is rewritten for the new engine. The plan follows the design's own boundary: first the current code moved out of the engine's directory into the shell's ([Batch 15](#id/BlockNode:00D4NBFKAG001), done), then the engine in memory (Batches 3 to 8), then the shell on disk (Batches 9 and 10), then the layers above the engine moved onto it (Batches 11 and 12), then the comparison with the Oxigraph engine (Batch 13), and last the ports (Batch 14), which no other batch needs.

- **Numbering**: <a name='id/BlockNode:00D3XQM4X0001' class='aperas-anchor aperas-id'></a> the batches continue the numbering of [Batch 1](#id/BlockNode:00CGK2C16G001) and [Batch 2](#id/BlockNode:00CGK3AH60001). [Batch 15](#id/BlockNode:00D4NBFKAG001) took the next number and came first in the order, before [Batch 3](#id/BlockNode:00D3XQQ2VG001). The eleven are done and kept in the [Archive](#id/BlockNode:00D3XP4XK0001). [Batch 16](#id/BlockNode:00D4RNDQVG001) took the number after Batch 15 and comes last in the order, after [Batch 14](#id/BlockNode:00D3XQQ2W0019).
- **Order**: <a name='id/BlockNode:00D3XQM4X0002' class='aperas-anchor aperas-id'></a> work that no open point blocks comes first. A batch that an open point gates builds all it can and names the gated step under **Gated by**; that step waits for the decision, and the batch is done when its other steps are and the gated step is recorded as waiting. [Batch 16](#id/BlockNode:00D4RNDQVG001) comes last: it removes the stored `path`, which every batch before it keeps, and its open points wait for the user. The plan decides none of the [Open points](../design/core.md#id/BlockNode:00D24N87T000J).
- **The design is the contract, the Oxigraph code is the reference**: <a name='id/BlockNode:00D3XQM4X0003' class='aperas-anchor aperas-id'></a> [Core — Design](../design/core.md#id/BlockNode:00D24N87SR001) states rules the engine must satisfy, not a description of the old code ([Status](../design/core.md#id/BlockNode:00D24N87SR005)). Where the old code differs from a rule, the rule wins and the difference is one of the filed issues, closed by the batch that names it under **Closes**. Where the design is silent, the reference copy's behaviour is kept and the batch says so.
- **Scratch mirrors only**: <a name='id/BlockNode:00D3XQM4X8000' class='aperas-anchor aperas-id'></a> no test and no run of the new engine reads or writes the live `AperasKG/Apeiron/`; they use a fixture or a copy of the mirror under `/tmp`.
- **The code map the plan stands on**: <a name='id/BlockNode:00D3XQM4X8001' class='aperas-anchor aperas-id'></a> the graph holds the map of the store reads of the Oxigraph code, by file and line ([the map](../issues/core.md#id/BlockNode:00D1GCR1XR001)), the census of its predicates and the fact-check of the design. The structure of the callers above the store (which of `node.ts`'s 2,241 lines are the engine's, which are ingest, reconcile, render or sweeps, and which exports the commands and the service use) is in [the map of the callers above the store](../issues/core.md#id/BlockNode:00D3YFA80R001). Batch 11 stands on that map; Batches 3 to 10 do not.
- **Not in this plan**: <a name='id/BlockNode:00D3XQM4X8002' class='aperas-anchor aperas-id'></a> [Size](../design/core.md#id/BlockNode:00D24N87T000T) (what happens when the mirror outgrows memory), [Secondary index for search](../design/core.md#id/BlockNode:00D24N87T000V), the service lifecycle, which the design leaves outside itself, and the design of several graphs beyond what [Several graphs](../design/core.md#id/BlockNode:00D3CHJXK8002) states.

### Batch 14 — ports and captured port views <a name='id/BlockNode:00D3XQQ2W0019' class='aperas-anchor aperas-id'></a>

The ports are the design's answer to a reverse bucket of thousands of subjects. No other batch needs them, since a flat set is the case of an unbounded cap, so they follow the comparison and a second run of its measurements shows what they add.

- [ ] **1. Splitting a bucket**: <a name='id/BlockNode:00D3XQQ2W001A' class='aperas-anchor aperas-id'></a> a reverse bucket over the cap set for its field is split into incoming ports along the partitioning field the shell names, by the ancestors of its sources at the next level, and a port still over the cap is split at the level below; pairs the hierarchy cannot tell apart stay together as the residue, even above the cap ([Ports](../design/core.md#id/BlockNode:00D2T5VG08001)).
- [ ] **2. Merging back**: <a name='id/BlockNode:00D3XQQ2W8000' class='aperas-anchor aperas-id'></a> a split merges back only when its count falls well below the cap, so ports do not change back and forth around it. Nothing about ports is stored.
- [ ] **3. A partition hierarchy**: <a name='id/BlockNode:00D3XQQ2W8001' class='aperas-anchor aperas-id'></a> the check of the mark applies (Batch 6), and the mark names no direction: the climbed side follows from the field's cardinality, forward for a single-valued field (the primary-supertag field of an IS-A use) and on the reverse side for a many-valued one, which is the only side Batch 6 built (`partition` in `engine.ts`); a secondary edge of a many-valued relation is marked as such when written and the partition ignores it ([A partition hierarchy](../design/core.md#id/BlockNode:00D2T5XBH0001), [Partitioning fields](../design/core.md#id/BlockNode:00D3CJDGH8001)).
- [ ] **4. Captured port views**: <a name='id/BlockNode:00D3XQQ2W8002' class='aperas-anchor aperas-id'></a> the engine shows the port tree of a bucket, the shell captures it as a view that keeps only the shape, the boundary node of each port, and the engine answers through it by merging its finer ports or sorting a coarser one ([Captured port views](../design/core.md#id/BlockNode:00D2T5Z6J0001), [the interface](../design/core.md#id/BlockNode:00D2T6KMXR001)).
- **Gated by**: <a name='id/BlockNode:00D3XQQ2W8003' class='aperas-anchor aperas-id'></a> [The name of a captured port view](../design/core.md#id/BlockNode:00D2T6X3CG001) gates step 4's kind and file name; the capture and the read through it do not wait.
- **Done when**: <a name='id/BlockNode:00D3XQQ2W8004' class='aperas-anchor aperas-id'></a> the model-based test holds the ports, flattened, equal to the flat bucket for random pairs and hierarchies; every pair falls into exactly one port; a single-valued partitioning field is checked forward and a many-valued one on its reverse side; a split happens only over the cap and a merge only well below it; removal and membership in a bucket of thousands do not scan the rest; Batch 13's measurements are run again and recorded.

### Batch 16 — the path derived <a name='id/BlockNode:00D4RNDQVG001' class='aperas-anchor aperas-id'></a>

The engine's batches keep the stored `path` of an artifact and a folder, and this batch removes it, last in the order, after the engine is in place. The design keeps the derived path as the target and states the stored `path` as transitional ([Deriving the path](../design/core.md#id/BlockNode:00D25698B0001)). The batch is recorded here with the count of the readers of the stored `path`; the five holes of the removal are its open points, undecided, and the batch is not built until the user decides on them.

- **1. The path derived**: <a name='id/BlockNode:00D4RATA00001' class='aperas-anchor aperas-id'></a> the shell derives the path of an artifact or a folder from its parent chain ([The path is derived from the parent chain](../design/core.md#id/BlockNode:00D24N87SR01S)) and every read of the stored `.path` is replaced by the derivation: ingest, track, project, link integrity, the anchor of reference resolution, the deep path of a block and the tie to the file on disk, with the lookup by path over the maps of [Batch 10](#id/BlockNode:00D3XQQ2W0004). Ingest and project throw "path undeterminable: no parent" for a node whose chain does not reach the root folder, and the load warns once, listing them; `concepts.md` is such a node and is kept as the test of the refusal ([A path that cannot be derived](../design/core.md#id/BlockNode:00D4R9VPGR001)). The stored `path` then leaves the Aperas schema, the Format and the mirror; how the mirror loses it is not planned yet. The count of the readers, made by the Coder on 2026-10-16: 47 lines read or write the stored field of `ArtifactNode` and `FolderNode` outside the schema (38 in 8 files of `core`, 9 in 4 files of `cli`, none in `web`), plus 4 declaration lines and 4 test lines. Of the 47, 27 can take the derived path as it is, 8 can but throw for a node with no chain, 9 need something else, and 3 are writes that go away. By role: ingest and track 11, rename detection and the removal sweep 13, project 1, resolve and lookup by path 10, render and the CLI commands 7 (and 14 calls through `toPath`), link integrity 2, thread scope 1, the service 0, the web package 0, tests and tools 6 (and their call sites). The stored path is the title chain for every attached node today; it is not for the 7 live artifacts with no parent, and the largest hole is a tracked artifact that has no parent until the next folder ingest (see the open points below).

- **Open points of the batch**: <a name='id/BlockNode:00D4RNDQVG002' class='aperas-anchor aperas-id'></a> five holes, found by the count of the readers of the stored `path`, undecided; the design states them in [Deriving the path](../design/core.md#id/BlockNode:00D25698B0001).
  
  - **A tracked artifact with no parent**: <a name='id/BlockNode:00D4RNDQVG003' class='aperas-anchor aperas-id'></a> `trackArtifact` creates a node that has a path and no parent until the next folder ingest, which finds it by a map by path to give it one; with a derived path a second `aperas track` of the same file mints a duplicate, a match by title alone is ambiguous (`a/x.md` and `b/x.md` are both titled `x.md`) and 12 track-then-ingest sites of the tests break. The ways out: track attaches the node at once, creating the folder chain as the creation of a holder does; something stored keeps the identity of an unattached node (a second field, which defeats removing `path`); or track always runs the folder ingest next and the artifact ingest takes the node and not the path.
  - **The tombstoned nodes**: <a name='id/BlockNode:00D4RNDQVG004' class='aperas-anchor aperas-id'></a> a tombstone keeps its `path` today, and `staleOnDisk` (a tombstoned artifact whose path still names a file on disk) and the reuse of a path after a removal rely on it, while a tombstone loses its `parent` and so has no derived path. Whether the migration keeps the last path somewhere is open.
  - **The thread scope**: <a name='id/BlockNode:00D4RNDQVG005' class='aperas-anchor aperas-id'></a> the scope of a node is read through its path in a module of raw quads that cannot import the node classes, so it needs its own walk over `parent` and `title`, and the answer for a chain that cannot be walked, a throw or a quiet default, decides whether a thread artifact that lost its parent leaks into the tracked mirror instead of `.state/`. The same question stands for the flush and the reverse track.
  - **The seven parentless live artifacts**: <a name='id/BlockNode:00D4RNDQVG006' class='aperas-anchor aperas-id'></a> the mirror holds 7 live artifacts with no parent, `concepts.md` and the six `README.md` artifacts, which [the migration deletes](#id/BlockNode:00D3Y3DMTR001); the derived path of each fails until then, and `concepts.md` alone stays, as the test of the refusal.
  - **The root folder**: <a name='id/BlockNode:00D4RNDQVG007' class='aperas-anchor aperas-id'></a> the root is the one folder with no parent in this mirror, with path `.` and title `Artifacts`, so it is the one node whose path is not its own title; whether "the live folder with no parent" is the definition of the root, or a marker is, is open, since a folder holder or a ghost could lack a parent too.
- **Design**: <a name='id/BlockNode:00D4RNDQVG008' class='aperas-anchor aperas-id'></a> [Deriving the path](../design/core.md#id/BlockNode:00D25698B0001), [The path is derived from the parent chain](../design/core.md#id/BlockNode:00D24N87SR01S), [A path that cannot be derived](../design/core.md#id/BlockNode:00D4R9VPGR001).
- **Gated by**: <a name='id/BlockNode:00D4RNDQVG009' class='aperas-anchor aperas-id'></a> [Deriving the path](../design/core.md#id/BlockNode:00D25698B0001) gates the whole batch: the five holes are for the user to decide. The batch also waits for the engine, that is [Batch 9](#id/BlockNode:00D3XQQ2VR01M), [Batch 10](#id/BlockNode:00D3XQQ2W0004) and [Batch 11](#id/BlockNode:00D3XQQ2W000C).
- **Done when**: <a name='id/BlockNode:00D4RNDQVG00A' class='aperas-anchor aperas-id'></a> not written yet; it is written when the five holes are decided.

## Verification Plan <a name='id/BlockNode:00CF23FB1G009' class='aperas-anchor aperas-id'></a>

A batch is done when its tests pass at the tier it names, the entries under its **Closes** can honestly move to Resolved with the actual mechanism named, and no gated step is passed off as done. Evidence is gathered in layers, the cheapest first, and each batch names the layers it uses.

- **Layer 1, group tests**: <a name='id/BlockNode:00D3XQW6AG001' class='aperas-anchor aperas-id'></a> each batch adds its tests to a group `engine/` (or to the group of the code it moved) as standalone `<name>.test.ts` files named in a suite, per [the tiers](../design/testing.md#id/BlockNode:00D1D5F64000N). After an edit, `npm run verify -- --group <area>` and `npm run verify -- --suite essential` (5 s); before handing a batch back, and at the orchestrator's check, `npm run verify` (the `commit` suite, 60 s). If `commit` passes its budget, the work stops and is reported, for the suite needs a split. The legacy suite is never run, and `demand` ([the demand tier](../design/testing.md#id/BlockNode:00D1D5F648001)) only when the user asks for it. The tests that [step 10 of Batch 11](#id/BlockNode:00D3Z01YER001) adds for the commands and the service that no test group covers today (`runTree`, `runShow`, `runPath`, `runResolve`, `runUnfold`, `runFold`, `runZoom`, `runProfile*`, `runRemove`, `runProject`, `runTrack`, `runReverseTrack`, `service.ts` and `serviceClient.ts`) are group tests of this layer, one test group for each group of the batch whose commands lack one, and each is written at the batch that requires it, Batch 11, before its group moves and not before the batch; only `runLinkCandidates` is waived, because it goes with its verb ([which of them can be waived](#id/BlockNode:00D3Z01YER006)); the other commands are tested, the differential run being Batch 13.
  
  - **The suites**: <a name='id/BlockNode:00D76D2W00000' class='aperas-anchor aperas-id'></a> Batch 11's tests would push `commit` toward its budget (904 of 904 in 34.2 s of 60 s on an idle machine before the cut, 40.9 s under load, and about 10 s more with the roughly 20 files and 8 s in-file that Batch 11 adds; the cost of a file is about 0.58 s of start whatever it holds, and two files run at a time), so the suite is cut in three, as [the tiers](../design/testing.md#id/BlockNode:00D1D5F64000K) list, and the cut is built. (a) `models` (budget 30 s) holds the seven seeded model files, `engine/graphs.model`, `engine/tombstone.model`, `engine/containment.model`, `engine/relations.model`, `engine/literals.model`, `mirror/roundtrip.model` and `lookups/lookups.model`, plus `shell/writeLayer.model` from piece 5: 145 cases in 12.0 s; a model file over about 1 s in-file goes there, a smaller one stays in `commit`. (b) `tools` (budget 30 s) holds `runner/runner.test.ts`, one file of 14 cases that start the runner as a process, 14.0 s; it is run when `run.mjs`, `support/suite.mjs`, `support/reporter.mjs` or a suite file changes. (c) `commit` keeps everything else, including the fast engine files and `engine/boundary`: 53 files, 888 cases, 15.4 s of its 60 s at a load average of 0.9 to 2.5, before the files of pieces 4 to 10, so most of the budget is free for them and for Batches 12 to 14. (d) `demand` lists `commit`, `models`, `tools` and the six corpus files. (e) `essential` takes at most two of the new files, one of `commands/` and one of `shell/`, only if each runs in 300 ms or less; it has 74 cases in 3.6 s of 5. A new test file is named in exactly one of `commit`, `models` and `tools` (or in `corpus/` for `demand` only); `runner/suites.test.ts`, in `commit`, fails if a test file is in none or in two. `models` is run by whoever edits `core/src/apeironNgn/`, `lookups.ts`, `mirror*.ts` or the write layer, and by the orchestrator at Step 7 of such a batch and before Batch 13's baseline; `tools` is run by whoever edits the runner, the suite helper, the reporter or a suite file. The figures for the files of pieces 4 to 10 are estimates until the pieces are built.
- **Layer 2, model-based tests**: <a name='id/BlockNode:00D3XQW6AR000' class='aperas-anchor aperas-id'></a> seeded random sequences of operations on the engine and on the oracle of Batch 3, compared after every operation, with the seed printed when one fails. The operations grow with the batches: writes of literal, reference and embed fields, ordered insertions, moves and removals, tombstones, sweeps, creating and dropping a graph. The invariants held after every operation: the reverse side is the inverse of the forward side; a node is in at most one container's list and containment has no cycle; `parent` is the reverse of `children` and the place of an item is its index; a tombstone is in no list and keeps its literals; ids come back in code-point order wherever the design promises an order; no operation leaves an orphan embedded node. From Batch 14, the ports flattened equal the flat bucket.
- **Layer 3, the round trip**: <a name='id/BlockNode:00D3XQW6AR001' class='aperas-anchor aperas-id'></a> a load followed by a dump returns the files byte for byte ([The round trip is exact](../design/core.md#id/BlockNode:00D24N87T0001)), on a tiny fixture in `essential`, and on a copy of the mirror in `demand`. The mirror in the repository holds data that the design no longer states (a `predicate` on every `Link`, tombstones that still hold `children`, `links` or `props` and keep their `parent` and their place in the `children` of their container, six artifacts for `README.md` files that stand outside any folder, a `type` on every artifact, a view's `unfolds` entry whose target is not defined, and `dinhlx` with no `kind`), so the real mirror is migrated once before this layer is run on it, and the baseline of this layer on the real mirror is the migrated mirror ([the migration, Batch 9 step 6](#id/BlockNode:00D3Y3DMTR001)). In that migration the `predicate` leaves every `Link`, the tombstones are stripped from the tree, the six `README.md` artifacts are deleted, `dinhlx` is given `kind: human`, the `unfolds` entries whose target is not defined are stripped and the `type` of every artifact is stripped (all settled); the live blocks and the artifact that have no parent are left as they stand ([settled](#id/BlockNode:00D3YSA5T8002)).
- **Layer 4, the differential run**: <a name='id/BlockNode:00D3XQW6AR002' class='aperas-anchor aperas-id'></a> the same script of commands on the reference engine and on the new one, and the dumps compared. The two designs have no mirror in common ([which mirror the differential run starts from](#id/BlockNode:00D3YG50B0002)): the reference runs on an unmigrated copy of the mirror and the new engine on the migrated copy of it, and the dumps are compared after the differences that the migration and the design make on purpose are normalised. The deliberate differences are listed and few: the migration's own changes ([Batch 9, step 6](#id/BlockNode:00D3Y3DMTR001): no `predicate` on a `Link`, the tombstones stripped from the tree, the six `README.md` artifacts and their paragraphs deleted, `dinhlx` given `kind: human`, the `unfolds` entries whose target is not defined stripped, the `type` of every artifact stripped), the order of ids by code point where `localeCompare` ordered them, the `children` order and `parent` rule of the load, the rejection of a repeated `@id`, the empty tombstone, the text of a link in `tree` and `unfold` without its predicate, the removal of `aperas link` and `aperas unlink` ([manual links are dropped](../issues/core.md#id/BlockNode:00D3WNBPPG001)), and whatever the settled open points change. Any other difference is a finding and not a pass. The harness copies both mirrors from one snapshot that includes `Apeiron/.state/`, runs every command with `</dev/null` under a timeout, and has a fixture for a `children` entry that names an id with no document ([the ghost folder](../issues/core.md#id/BlockNode:00D417WK80001)): the new engine returns it in the list of ids referenced and never defined, and what the shell does with the list is the service lifecycle.
- **Layer 5, the reproductions**: <a name='id/BlockNode:00D3XQW6AR003' class='aperas-anchor aperas-id'></a> each filed issue a batch closes has a test written from its own reproduction first, failing on the reference copy and passing on the engine, as the archived Batches were held to: a sibling gap after a move to another parent and an append, a second `parent` after a write of `children`, a repeated `@id`, a `parent` and `children` that disagree, a live and a tombstoned node at one path, a tombstone that keeps `children`.
- **Layer 6, the tools**: <a name='id/BlockNode:00D3XQW6AR004' class='aperas-anchor aperas-id'></a> `aperas check-links` and the other commands run on a copy of the mirror and agree with the reference engine's output, and `npm run build:aperas` builds a bundle that starts.
- **Layer 7, the measurements**: <a name='id/BlockNode:00D3XQW6AR005' class='aperas-anchor aperas-id'></a> Batch 13's protocol. A figure is recorded with its sample size and what it does not show, and a comparison is made only between runs on the same machine and the same copy of the mirror.
  
  - **Every timing carries its calibration**: <a name='id/BlockNode:00D457HDWG001' class='aperas-anchor aperas-id'></a> a timing is taken with a calibration beside it, the clock of the cores (`scaling_cur_freq`, read under the load) and the time of a fixed 10M-iteration Python loop (about 0.6 s at normal speed). A timing taken when the calibration is off is discarded, not corrected. A clamped CPU, held at its 400 MHz minimum, made the timings of one evening 12.7 times too slow and passed for a defect of the service ([the cost of a write](../issues/core.md#id/BlockNode:00D22Z1HJ8001)).
- **What no run does**: <a name='id/BlockNode:00D3XQW6AR006' class='aperas-anchor aperas-id'></a> read or write the live `AperasKG/Apeiron/`, restart or kill the service of `Aperas/`, or run the legacy suite.

### Batch 4 — done: records, literal fields, ids, collections and orders <a name='id/BlockNode:00D3XQQ2VR006' class='aperas-anchor aperas-id'></a>

The data model of the engine for literal and single-valued fields, before any relation exists.

- [ ] **1. Records and literal fields**: <a name='id/BlockNode:00D3XQQ2VR007' class='aperas-anchor aperas-id'></a> a record for each subject; a literal field is a plain property of the record, with no pair and no reverse side ([Literal fields are properties of the record](../design/core.md#id/BlockNode:00D39DRYB0001)); the engine reads and writes a field as the schema declares it for the node's kind ([One schema, handed in at construction](../design/core.md#id/BlockNode:00D24N87SR008)). Literals are kept as JavaScript strings, integers and booleans, so the string "1" and the number 1 differ, and a string that looks like a date stays a string ([Literal types](../design/core.md#id/BlockNode:00D24N87SR00J)).
- [ ] **2. Cardinalities**: <a name='id/BlockNode:00D3XQQ2VR008' class='aperas-anchor aperas-id'></a> `one`, `optional` and `set`, declared and never inferred from the data; the values of a set come back in no promised order; the first or only value of a single-valued field is read without a scan.
- [ ] **3. Ids**: <a name='id/BlockNode:00D3XQQ2VR009' class='aperas-anchor aperas-id'></a> [Ids](../design/core.md#id/BlockNode:00D24N87SR01N) are `Kind:snowflake`, an embedded node's id `owner:field:Kind:snowflake`, nested further for the props of a link. The kind of an id is read from its last `field:Kind:` segment, or from its prefix when it has none, and a string counts as an id only if a valid snowflake follows `Kind:`. Ids are unique across all graphs. The shell mints the ids and passes them in; the engine checks the grammar and the uniqueness of each, and refuses an id that fails the grammar.
- [ ] **4. The master map and the collections**: <a name='id/BlockNode:00D3XQQ2VR00A' class='aperas-anchor aperas-id'></a> one map from id to record, and one collection for each graph and kind holding the records themselves, in order of insertion; creating a node adds its record, and deleting it removes it, which waits for `removeNode` in [Batch 5](#id/BlockNode:00D3XQQ2VR00H) step 3 ([Records by kind and by graph](../design/core.md#id/BlockNode:00D24N87SR018)). - [ ] **5. A test shuffles the order of insertion and sees the same sorted output.
- [ ] **6. Existence and size**: <a name='id/BlockNode:00D3XQQ2VR00C' class='aperas-anchor aperas-id'></a> the reads "does a node exist" and "the size of the store".

### Batch 9 — done: the mirror, the format, the dump and the load <a name='id/BlockNode:00D3XQQ2VR01M' class='aperas-anchor aperas-id'></a>

The shell's persistence, on disk, in `src/shell/`: it builds the engine's graphs from the mirror and reads them out through the engine's [persistence API](../design/core.md#id/BlockNode:00D4MZ7DZG001).

- [ ] **1. The dump**: <a name='id/BlockNode:00D3XQQ2VR01N' class='aperas-anchor aperas-id'></a> the files of [The mirror](../design/core.md#id/BlockNode:00D24N87SR01W) and their [format](../design/core.md#id/BlockNode:00D24N87SR01Z): documents sorted by `@id` by code point, indented by two spaces, ending with a newline, fields in the order the schema declares, an unset field or an empty set left out except `children`, embedded entries and the values of a reference set sorted by id, integers in their canonical text. A dump reads the records out through the persistence API, serializes them and rebuilds nothing from pairs ([A flush is a dump](../design/core.md#id/BlockNode:00D39EAKW0001)).
- [ ] **2. Written by graph and kind**: <a name='id/BlockNode:00D3XQQ2VR01P' class='aperas-anchor aperas-id'></a> one file for each kind and graph, and a document holds no `graph` field: the file for its graph and kind holds it, so the dump writes each record to the file of its graph and kind ([Records by kind and by graph](../design/core.md#id/BlockNode:00D24N87SR018)). The shell has three graphs: `tree`, the tracked kinds, in `Apeiron/` (tracked in git); `threads.tree` (a subdomain of the main one), the thread-scoped nodes of the three tree kinds, in `Apeiron/.state/`; and `treeviews`, the `TreeView` nodes, in `Apeiron/.state/` ([Files](../design/core.md#id/BlockNode:00D24N87SR01X), [Written by graph and kind](../design/core.md#id/BlockNode:00D24N87SR01Y), [Addressing](../design/core.md#id/BlockNode:00D5AYBPWR001)). The file of a graph and a kind is a function of the graph alone, through the table of settings. The table is the `graphs` key of `aperas.config.json`, keyed by graph name, each entry with the mirror's location (`mirror`) and the flush interval (`flushIntervalMs`), and the existing `graph` keys give the main graph's defaults when the key is absent, the other two following from them (`tree` every 10 s, `threads.tree` and `treeviews` every 3 s). The table's reader is in `graphConfig.ts`, and the mapping from a graph and a kind to a file, made from the table, is in `mirrorFiles.ts`, where the dump and the load take it as an argument. At start the shell creates the graphs `tree`, `threads.tree` and `treeviews`, in that order, and drops the engine's `default`; the engine is unchanged. `createMirrorGraphs` does this for a start with no load and for tests, and `loadMirror` creates the same three graphs itself from its mapping. The shell warns once when the table has an entry keyed `tree`, and uses the entry (`APERAS_APEIRON_ROOT` still wins for the main graph's directory), and relies on the engine's refusal of `id`. The test of whether a node belongs to the threads graph (`threadScope.ts`, in `src/shell/` since Batch 15) is replaced by `graphOfPath.ts`, a rule that decides the graph of a new node (an artifact or a folder by its file-system path, `.threads` or under `.threads/`; a block, a `Link` or a `StringProp` by the graph of its container; a `Profile` in `tree`; a `TreeView` in `treeviews`); it is built and tested, and wired at Batch 11, since the shell has no creation path before it, and `threadScope.ts` stays until then; the engine holds none of the settings.
- [ ] **3. The load**: <a name='id/BlockNode:00D3XQQ2VR01Q' class='aperas-anchor aperas-id'></a> the shell's load builds the engine's graphs from the files through the persistence API: it creates each node with its id and kind in the graph of the file it reads (a document holds no `graph` field) and sets its fields, a reference to a node not yet built being accepted ([Persistence](../design/core.md#id/BlockNode:00D4MZ7DZG001)). No two documents share an `@id`: the load rejects every document that carries a repeated one, keeps none of them, reports the id, and goes on ([An `@id` names one document](../design/core.md#id/BlockNode:00D24N87SR01P), [A repeated `@id` at load](../design/core.md#id/BlockNode:00D2PC3ZG8001)). When the `parent` of a node and the `children` array of its container disagree, `parent` wins: the load appends the node at the end of its parent's `children`, drops its entry from the `children` of the other container and warns, naming both; a `parent` that names an id with no document leaves the node with no container, returns the id in a list of its own and warns; a node that a container lists and that has no `parent` stays in that container ([A file whose `parent` and `children` disagree](../design/core.md#id/BlockNode:00D2PV8GC0001)). Once a graph is built, the load asks the engine for the ids that are referenced and never defined, and returns them together with the ids that a `parent` names with no document: the engine's list does not see those, since a `parent` that a build supplies is never a stored pair.
- [ ] **4. The round trip is exact**: <a name='id/BlockNode:00D3XQQ2VR01R' class='aperas-anchor aperas-id'></a> a load followed by a dump returns the files byte for byte, so a flush with nothing changed leaves git clean ([The round trip is exact](../design/core.md#id/BlockNode:00D24N87T0001)).
- [ ] **5. Writers**: <a name='id/BlockNode:00D3XQQ2VR01S' class='aperas-anchor aperas-id'></a> only the service writes the mirror, and a flush rewrites a whole class file. The guard against overwriting a file that changed on disk stays the service's.
