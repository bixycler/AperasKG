### Batch 1 — done: reconcile identity/reporting family, plus two out-of-scope finds fixed alongside <a name='id/BlockNode:00CGK2C16G001' class='aperas-anchor aperas-id'></a>

Executed directly, not as originally sketched below — that plan predates the actual investigation and was never followed as written. `diffChildren`'s real mechanism (Stage B's positional container zip, not Stage A's `matchKeyed`) only came out once `reconcile.ts` was actually read, which is also what showed items 3 and 4 don't share this fix at all and belong in the next batch instead. Two items outside this doc's original scope (the props-only-`0-changed` report, and a `FolderNode` holder-promotion gap that turned out to need no design work) surfaced during the same pass and were fixed alongside rather than filed and deferred.

- [x] **1. `aperas update` never re-derives a non-heading title, and can tombstone children** ([issues/linking.md](../issues/linking.md#id/BlockNode:00CGFE4SV0002)): `runUpdate`'s local `title` only gets assigned in the heading-target/heading-input branch. Fix: in the `firstChild?.type === 'paragraph'` branch, also read `title = firstChild.title` (already computed by the parser for every paragraph via `extractLeadInTitle` — nothing new to compute, just wire it through) and thread it into `newShape.title`/`--text-only`'s title assignment the same way the heading branch already does.
- [x] **2. Stage B's container alignment is positional, not content-keyed — the real cause of [core.md #1](../issues/core.md#id/BlockNode:00CF1WZ4JG003) and [#2](../issues/core.md#id/BlockNode:00CF1WZ4JG004)**: <a name='id/BlockNode:00CGGTQ620003' class='aperas-anchor aperas-id'></a> fix by keying `listItem`-typed buckets through the same `matchKeyed`+`leafKey` machinery Stage A already uses for leaves, instead of a plain `Math.min(old.length, new.length)` zip — reproduced above, a real diff not a hypothetical. Alongside it: exclude every tombstoned old candidate from every matching pool (Stage A's `oldLeafIdx`/heading buckets *and* Stage B's container buckets) — today nothing stops live new content being matched onto an already-dead id without reviving it (core.md #2's exact complaint), and it turns out Stage A has the identical exposure for headings/paragraphs, not only Stage B for list items. A dead slot should never be reused; new content lands on a fresh id instead. Corrects the wrong root-cause note above once landed.
- [x] **3. A props-only change reports as `0 changed`** ([issues/core.md](../issues/core.md#id/BlockNode:00CFATMWY0001)): <a name='id/BlockNode:00CGGTQ620004' class='aperas-anchor aperas-id'></a> `headingChanged` only compares heading `text`/`title`, never `props`, and never runs for non-heading matched pairs at all (their key *is* their text, so a changed leaf can't reach "matched"). Fix: generalize into a `pairChanged` check — `headingChanged`'s existing test, plus a props comparison (key/value map, order-independent) — applied at both call sites, for every matched pair regardless of type. Makes the summary line trustworthy for exactly the case (`checked`, `orderedList`/`startIndex`) this session already had to work around by verifying through traversal instead.
- [x] **4. `extractAnchorNames` treats a quoted example anchor as a real claimed name** ([issues/linking.md](../issues/linking.md#id/BlockNode:00CGGHVBF8001)): fix by stripping backtick-delimited inline-code spans before running `ANCHOR_NAME_RE`, mirroring `findLeadInColonOffset`'s existing `inlineCode` exclusion (regex-based here, not AST, since every call site only ever has raw stored text). **Found while designing this fix, not yet filed as its own issue**: `stripInlineAnchors` — this session's own new storage-time call included — has the identical gap in the opposite direction: it would *strip* a legitimately backtick-quoted anchor example as if it were real projection markup, corrupting genuine prose the moment such a node is next touched (confirmed live on [`BlockNode:00CE95MVP8008`](../discussion/aperas-skill.md#id/BlockNode:00CE95MVP8008), which quotes exactly this pattern today). Both functions share `ANCHOR_NAME_RE`; fixing both from one shared "matches outside code spans" helper closes this before it bites, rather than after.
- [x] **5. Multi-artifact `kg:ingest` isn't transactional** ([issues/core.md](../issues/core.md#id/BlockNode:00CF1WZ4JG008)): <a name='id/BlockNode:00CGGTQ628001' class='aperas-anchor aperas-id'></a> `ingestArtifacts`/`ingestAllArtifacts` loop per file with no try/catch, so one file's failure mid-batch leaves earlier files' writes already committed with no rollback, and later files never attempted. True all-or-nothing would need a store-wide snapshot/rollback primitive that doesn't exist here — a bigger undertaking than this item's scope. Chosen design instead: isolate per file, matching the pattern `ingestAllArtifacts` already uses for `untracked` — wrap each `ingestArtifact` call in try/catch, collect `{path, error}` for failures, keep going, return successes *and* failures both, so a bad file no longer silently aborts every file after it in the same batch, and the caller gets an accurate report instead of a mid-loop throw. Flagging this design choice explicitly since a true-rollback alternative existed and wasn't picked.
- [x] **6. Folder-tier holders have no promotion channel** ([issues/core.md](../issues/core.md#id/BlockNode:00CF1WZ4JG009), narrowed): <a name='id/BlockNode:00CGGTQ628002' class='aperas-anchor aperas-id'></a> the issue names "Folder/Artifact" together, but `ArtifactNode extends BlockNode` and already passes `kg:update`'s own type check — piping any content through `kg:update` on a holder `ArtifactNode` already clears `.holder` today, confirmed by reading `kgUpdate.ts` directly. The real, narrower gap is `FolderNode` alone: `kg:insert`'s move/promote mode is hard-restricted to `BlockNode`, and `kg:update` explicitly excludes `FolderNode` from its own target-kind check, so nothing graph-first ever reaches `FolderNode.hydrateFromParsed`'s existing (and already-correct) `this.holder = undefined`. Fix: extend `kg:insert`'s anchor-*less* bare-promote branch to also accept a `FolderNode` target (reject a `FolderNode` + `--after`/`--before` combination outright, with a clear message — a folder's position comes from its path, not list order, so repositioning was never the missing piece).

- [x] **7. GFM task-list items leak their marker into stored text — found investigating this plan's own doubled checkboxes** ([issues/treeview.md](../issues/treeview.md#id/BlockNode:00CE1GW638007), moved up from a misdiagnosed Tier 5): `mdast-util-gfm-task-list-item` only trims the checkbox's leftover space (and re-bases the paragraph's position past it) when the item's content starts with a plain `text` node — bold, italic, inline code, and link lead-ins all leave the marker in, since CommonMark's inline tokenizer never materializes that lone leading space as its own text node. Fix: `astParser.ts` defensively strips a leading `[ ]`/`[x]` from both `.text` and `.title` for any listItem already known to be a checkbox. Verified end-to-end, then applied to fix this very plan's own six checkboxes, which had rendered doubled (`[ ] [x]`) before it.

Order: <a name='id/BlockNode:00CGGTQ628003' class='aperas-anchor aperas-id'></a> 2 first (highest leverage, 3-for-1 plus corrects the standing wrong note), then 1 (proven danger), then 3 (cheap, and every fix after it becomes easier to verify), then 4 (contained, same shape as this session's `findLeadInColonOffset` fix), then 5 and 6 (larger, independent). Each verified by an isolated script against the live source before any live-graph write, given this session's own near-miss on item 1's very bug class.
